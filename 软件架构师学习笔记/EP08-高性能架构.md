## 0. 课程地图：三高的最后一高，和一个 8 秒的秒杀夜

### 0.1 开场：三高拼图的最后一块

作者第一句就把位置点清楚：前面讲过**高并发**和**高可用**，今天进入三高里的最后一高——**高性能**。

| 维度 | 回答的问题 | 失败时的表现 | 对应 |
|---|---|---|---|
| 高并发 | 一次来很多人，接不接得住 | 拒服务、排队、限流 | 第 6 集 |
| 高可用 | 有人挂了，还活不活 | 白屏、宕机、502 | 第 7 集 |
| **高性能** | **每个人等多久** | **没挂，但慢得让人退出** | **本集** |

本课的定义式判断，后面反复回扣：

> **系统没宕机，只是慢——但对用户来说，慢就是另一种形式的宕机。**

这也是第四章「治理」存在的理由：可用性有监控、有 SLO、有人负责；而「慢」往往是**没人报警、没人负责、慢慢烂掉**的那种坏。复现门槛很低：**一台至少 8G 的机器 + Docker + SpringBoot / MySQL / Redis / RabbitMQ**，「我相信就能进行一个很好的复现」。

### 0.2 事故主角：果小满，每晚 8 点整点秒杀

为了让内容真实，作者虚构了一个生鲜电商叫**果小满**。这业务有个致命特征：

> 它的流量**不是慢慢涨的**，而是在 **19:59:59 到 20:00:00** 之间**瞬间砸过来**的。

日常大促是**斜坡**，可以靠弹性扩容慢慢追；秒杀是**断崖**，只能靠提前设计好的缓冲。

```
19:59:59              20:00:00              20:03            20:30
   │                     │                    │                │
 42 万人预约          RT 80ms → 8000ms     紧急扩容 +10 台    重启数据库
 QPS 200 → 12000      用户开始转圈          RT → 12000ms      才恢复
 监控一片绿           灾难开始              雪上加霜           粗暴止血
```

**风平浪静**：预约 **42 万**人，QPS 从 **200** 涨到 **12000**，但 CPU 不高、内存正常、**监控大盘一切正常**。作者插了一句最像老运维的话：

> 很多事故都是这样的——**在真正爆发的前一秒，它看起来还是风平浪静的。**

**开抢**：下单接口 RT 从 **80ms** 拉到 **8000ms**。作者用具体数字解释 8 秒多致命：

> 移动端**超过 5 秒的白屏，大约 60% 的用户会直接退出**。而且很有可能——**转圈最久、等得最久的那批用户，反而是最想买东西的用户。**

这句话是「平均值会骗人」的伏笔：最有意愿的人，恰好被伤得最深。

**扩容**：值班运维做了教科书式操作，**加 10 台应用服务器**，结果「所有人都傻脸了」——RT **不降反升，冲到 12 秒**。

**重启**：重启数据库才恢复，代价是 App Store 多了**三四百条一星**。

### 0.3 损失账单

| 项目 | 数值 |
|---|---|
| 转圈超 5 秒直接流失的用户 | **60%** |
| 折算订单损失 | **几十万** |
| 一星评价 | **三四百条** |
| 品牌损失 | 「没办法用钱衡量」——后续用户可能因为这些评价不下载 APP |
| **加 10 台机器之后** | **响应时间反而变慢了** |

最后一行最刺眼，因为它打破了一个默认假设：**机器多了，应该更快**。

### 0.4 四个悬念与四章路线

作者故意不给答案，把问题挂起来当路标：① 快慢怎么衡量？② 为什么加机器更慢？③ 时间漏在哪儿？④ 一刀刀怎么砍、砍完怎么不退化？

| 章 | 名称 | 讲什么 | 学完得到什么 |
|---|---|---|---|
| 一 | **认知篇** | 不讲组件，只答三个问题：快慢怎么衡量、为什么加机器更慢、时间漏在哪 | 一把**尺子** + 两条**定律** |
| 二 | **原理篇** | 几百个组件，底层只有四类动作：**缓存、异步、池化、批量** | 看见新组件能一句话归类 |
| 三 | **实战篇** | 把慢接口**一刀刀砍下去**，每刀都压测 | 可复现的实验 + 一张对账表 |
| 四 | **治理篇** | 个人英雄救不了团队，要把打法变**制度** | RT 预算表、定位三板斧、三阶段 |

## 1. 第一章 认知篇：性能是算出来的

### 1.1 三条规矩

作者发尺子之前先立三条规矩，「不仅是针对课程，希望大家日后接触架构时也这么干」：

| 规矩 | 原话大意 | 落地动作 |
|---|---|---|
| **① 性能必须带数字** | 不能说「快了」「慢了一点」，在真正的软件评审会上**这不算数** | 说「P99 从 8200ms 降到 90ms」 |
| **② 动手之前先算账** | 算瓶颈在哪一层、占总时间多少比例 | 按占比排序，先砍最大的 |
| **③ 承认优化有代价** | 天底下没有免费的加速 | 每上一招，先把账单摆出来 |

意思很硬：**性能讨论一旦失去数字，就退化成信仰之争**——谁嗓门大听谁的，最后拍脑袋加机器，就是开场那 10 台。

### 1.2 四把尺子

#### 第一把：RT 响应时间

> 一个请求从发出去到收到响应，一共花了多久。

食堂类比：**你从站在窗口前，到端着菜走开，一共用了几秒。** 但作者马上提醒：**单独看 RT 是非常容易被骗的**——因为大家看的是**平均值**。果小满下单接口平均 RT **120ms**，看着很健康，但 P99 是 **8 秒**。

#### 第二把：P99（平均值会骗人）

> 把同一时间段内所有请求的耗时**从快到慢排序**，取排在第 **99%** 位置上的那个值。

```
耗时
 8s │                                      █ ← P99
    │                                      █
120ms│ ████████████████████████████████████  ← 99% 的请求都在这儿
    └──────────────────────────────────────▶ 请求（按耗时排序）
      0%                                99%  100%
```

| 项目 | 数值 |
|---|---|
| 平均 RT | 120ms（看着健康） |
| P99 | **8 秒** |
| 一晚总请求 | **1200 万** |
| 1% 是多少人 | **12 万人次** |
| 这 12 万人的体验 | 转圈 8 秒 |

作者顺着往下推：这 12 万人里有一部分去发帖、去吐槽，**你是不是就多了一条黑热搜**？他还点了这个时代特有的现象——「我们现在是不是经常在热搜上看到『什么什么 APP 崩了』？」

**本课最重要的一句结论**：

> **定性能目标要用 P99，不要写平均值。平均值会骗人，因为慢请求永远是少数，而少数恰恰很多时候是能决定你口碑的。**

> 📌 **补充**：分位数选错会误导方向。P50 看中位体验、P95 做日常告警、**P99 定对外 SLO（本课口径）**、P999 定位长尾。经验法则：**P99 与 P50 相差超过 10 倍，说明系统里存在排队或锁竞争**——不是「有几个慢请求」，而是「有一批请求在等同一把锁」，正是后面第三宗罪。

#### 第三把：QPS

> 系统每秒能处理多少个请求，也就是吞吐量。

> 它量的是**接待能力**，不是**速度**。就像食堂 1 秒钟能打出多少份饭，取决于**窗口数量**和**每个窗口的效率**。

| 指标 | 量的是 | 提高它靠 |
|---|---|---|
| RT | 单个请求的**速度** | 减少单次耗时（缓存、索引） |
| QPS | 系统的**接待能力** | 增加并行度 / **降低单次耗时** |

后半句很重要——**RT 降了，QPS 自然升**，这是后面「6.2 → 820」的依据。

#### 第四把：并发数

> 同一时刻系统里正在处理中的请求数。相当于**站在打饭窗口前的人数**（正在被服务 + 正在排队），不是「今天来了多少人」。

### 1.3 利特尔法则：把四把尺子串起来

```
QPS = 并发数 / RT        并发数 = QPS × RT
```

作者说这就是鼎鼎大名的**利特尔法则（Little's Law）**，翻译成食堂语言：

> **窗口前同时站着多少人 = 每秒钟来多少人 × 每个人在窗口站几秒。**

假设每秒来 **10 个人**不变：

| 场景 | 每人站窗口 | 窗口前同时站多少人 |
|---|---|---|
| 正常 | 5 秒 | **50 人** |
| 变慢 | 8 秒 | **80 人** |

> 你要注意——**没有任何一个人是多来的**，只是每个人磨蹭得久了，队伍就自然变长了。

用事故数字验一遍：基线 **50 并发 / P99 8.2s** → `50 / 8.2 ≈ 6.1`，正是压测出的 **QPS 6.2**，公式自洽。优化后 **820 QPS / 90ms** → `820 × 0.09 ≈ 74` 并发：同样入口、同样的人，占用却完全不同，因为「站窗口的时间」从 8 秒变成 0.09 秒。

### 1.4 死亡螺旋：为什么加了 10 台机器反而更慢

```
RT 变长（8s）
    │
    ▼
并发数暴涨（QPS 不变，每人占更久）→ 同时占着线程、占着数据库连接
    │
    ▼
线程池满 + 连接池满 → 后来的请求只能排队
    │
    ▼
RT 更长 ──────────┐
    │             │
    └─────────────┘   ← 恶性循环
```

那晚瓶颈在**数据库**（CPU **100%**），8 秒的 RT 就是它拖出来的。但运维加的是 **10 台应用服务器**，每台带自己的连接池，**默认 20 个连接**：

| 状态 | 打到数据库的连接 |
|---|---|
| 扩容前（5 台 × 20） | **100** |
| 扩容后（15 台 × 20） | **300** |

> 数据库前面排队的连接从 100 瞬间变成 300，数据库更堵，RT 更长，并发更高，**客户端超时重试也更多了**——这是不是一个**死亡螺旋**？

作者给出的判词，也是本课金句：

> **扩容只对瓶颈所在的那一层有效。** 你瓶颈在数据库，去扩应用层，就相当于**在一个本来就堵车的路段，还多放了一批车进去**。

他还很公道地补了一句：那 10 台机器**本身没有做错什么**，它们只是把更多的连接和重试，砸向了本来就已经瘫痪的数据库。

> 📌 **补充**：这现象叫「**扩容放大故障**」。判据很简单——**扩完容后瓶颈层利用率上升、整体 RT 变差，说明你扩错了层**。还有个隐蔽帮凶：**客户端重试**，超时 → 重试 → 数据库多收一份 → 更慢 → 更多超时，这是第 7 集的「重试风暴」，在这里是加速死亡的第二脚油门。

### 1.5 木桶定律：总耗时由最慢那一段决定

> **木桶能装多少水，看最短的那块板。** 放到性能上：一个请求的总耗时，由链路里最慢的那一段决定。

```
网关          ▏2ms
应用计算      ███ 15ms
渲染返回      ▏3ms
SQL 查询      ████████████████████████████████████████████ 7800ms
              └──────────────────────────────────────────┘
               最慢这一段把整根桶壁拉到了 7.8 秒
```

**思想实验**：把网关、渲染、应用计算全优化到 **0ms**，总耗时是多少？`2+15+3+7800 → 0+0+0+7800 = 7800ms 出头`。从 7820ms 变成 7800ms，**用户那边毫无感觉**。

> 这就是为什么很多优化「做了等于没做」——**你砍的全是长板，短板一根手指也没碰到。**

### 1.6 阿姆达尔定律：砍一块板到底能快多少

木桶回答「砍哪块」，**阿姆达尔定律**回答「砍了能快多少」：

```
               1
加速比 = ─────────────────        P = 要优化的部分占总时间比例
          (1 − P) + P / S        S = 把它提速的倍数
                                 (1−P) = 怎么都碰不到的天花板
```

作者说公式不用背，理解就行。用事故数字算三遍：

| 优化对象 | 占比 P | 提速 S | 计算 | 整体加速比 | 8s 变成 |
|---|---|---|---|---|---|
| **SQL** | 0.96 | 100× | `1/(0.04+0.0096)` | **20×** | **400ms** |
| SQL | 0.96 | 10000× | `1/(0.04+0.000096)` | **25×（封顶）** | 320ms |
| 应用计算 | 0.04 | 100× | `1/(0.96+0.0004)` | **1.04×** | 7.7s（省 300ms） |

三条读法：优化 SQL 能把它**从秒级变成毫秒级**；但**就算提速 1 万倍，整体加速比也就 25 倍封顶**，剩下 4% 无法触碰；而砍应用计算，你忙活一圈**换来 300ms**。

**两条定律合起来**：

> **先测量出最短的板和它的时间占比，再决定往哪里投入。占比大的才值得砍，占比小的你就算砍出花儿来，也没有人感觉得到。**

> 📌 **补充**：阿姆达尔有个双胞胎叫「**古斯塔夫森定律**」——如果问题规模可以变大，加速比就没有上限。放到业务上：**优化省下的算力，不该只让接口变快，而应该拿去扛更多流量**。这也解释了为什么对账表里 QPS 涨幅比 RT 降幅更夸张。

### 1.7 慢的四宗罪

> 漏时间的地方有千千万，但归归类，大概只有 4 种。

| # | 罪名 | 具体形态 | 量级 | 方向 |
|---|---|---|---|---|
| 1 | **网络往返** | 每跨一次网络；串行调多个下游 | 同机房 **1~5ms**／次，跨机房 **30ms** 起 | 少走网络 |
| 2 | **计算与序列化** | 大 JSON 反复序列化、循环内可外提的计算、写得差的正则 | CPU 占用高 | 少做计算 |
| 3 | **锁与排队** | 线程池排队、数据库行锁、同步块串行化 | 「代码一行没跑，时间却在流逝」 | 少排队 |
| 4 | **IO** | 慢 SQL、缺索引、N+1 循环查库 | 内存**纳秒**／磁盘**毫秒**／跨网络查库**几十毫秒** | 少碰磁盘 |

两个原文细节：**串行**调 8 个下游，光路上就 **40ms 起步**（时间全部累加）；**IO 是最大头**，三种访问差了**五六个数量级**，慢 SQL、缺索引、N+1 全在这一类。

> 📌 **补充**：为什么排队最坑？因为它**不消耗 CPU**。监控上 CPU 只有 20%，看起来「机器很闲」，但用户已经等了 3 秒。这就是「**CPU 不高但很慢**」的经典误诊场景，也是本课事故里「监控一片绿」却在崩的原因之一。

### 1.8 给那 8 秒做一次归因

| 归因 | 罪名 | 耗时 | 占比 |
|---|---|---|---|
| SQL 查询 | 第四宗罪 IO | **7800ms** | **97%** |
| 下游串行调用 | 第一宗罪 网络 | 120ms | 1.5% |
| 排队与锁 | 第三宗罪 排队 | 70ms | 0.9% |
| 序列化 | 第二宗罪 计算 | 10ms | 0.1% |
| **合计** | | **8000ms** | 100% |

> 是不是很明白地就能看出来，SQL 占了 **97%**？

这个 97% 直接决定了**优化顺序**：先用**缓存**卸掉数据库查询压力，再**异步**、再**池化**。四宗罪也就变成了四个方向——**少走网络、少做计算、少排队、少碰磁盘**，正是四板斧的来源。

### 1.9 四笔账：每一刀都有代价

作者坚持「先把账单摆出来，再去学招式」：

> 每一个让系统更快的组件，都是我们要克服的一道坎，也都是代码评审时你要多讲 10 分钟的东西。

| # | 账 | 内容 | 表现 |
|---|---|---|---|
| 1 | **复杂度** | 加了缓存要管失效；上了异步要管补偿与幂等；动了并发要防超卖 | **快，是用复杂度买来的** |
| 2 | **一致性让步** | 缓存里永远是「上一刻」的数据库；异步结果永远是「几秒之前」的请求 | **绝对正确 → 最终正确** |
| 3 | **钱** | 缓存集群、MQ 集群、更大内存、更多机器 | 采购 / 扩容 / 备份 |
| 4 | **运维负担** | Redis 会挂、MQ 会堆积、连接池会配错 | 多一类故障模式、多一组指标、多一本手册 |

关于一致性（作者说它「隐蔽且致命」）：「你把系统变快的同时，就把**绝对正确**变成了**最终正确**。**这不是缺陷，这是一种交易。** 很多团队是**出了事故之后**才意识到自己做了这样的交易。」

关于钱（要算性价比）：缓存命中率为了从 **92% 提到 97%** 就把整个内存预算**翻倍**，你先看一下到底值不值。

> 📌 **补充**：这账能算。92% → 97%，落库流量 8% → 3%，**数据库压力降 62.5%**；92% → 99%，8% → 1%，**降 87.5%**。命中率的边际价值在**高位区间更陡**——但前提是数据库真的扛不住那 8%，**若余量充足，这 62.5% 一点价值都没有**。

关于运维（作者下了重话）：「每多一个组件，就**多一类故障模式、多一组监控指标、多一本运维手册**。**没有监控和预案的优化，都不是优化，是一种埋雷。**」

### 1.10 隐性代价：迁移成本

> 今天你为了性能引入的组件，明天想换掉可就不一定好换了。

因为**缓存的数据结构、MQ 的消息格式，会变成系统的骨骼，和业务长在一起**。所以选型时要自问：**假如我几年后要换掉它，要花多少工时、多大代价？** 留后路两招：**用标准协议**、**加抽象层**（别让业务代码直接依赖组件特有 API）。

> 📌 **补充**：这就是「**防腐层**」。反面案例是业务代码里到处 `redisTemplate.opsForHash().xxx`——将来换存储要改几百处；正面做法是定义 `CacheService.get(key)`，只有实现层碰 Redis 的 API。

### 1.11 第一章收口

| 产物 | 内容 | 用途 |
|---|---|---|
| **一把尺子** | RT / P99 / QPS / 并发数 + 利特尔法则 | 衡量任何系统 |
| **两条定律** | 木桶定律、阿姆达尔定律 | 决定砍哪块、砍了值不值 |
| **一份归因表** | 四宗罪 + 四笔账 | 知道时间漏在哪，也知道要付什么 |

> 学完这一章，你应该能：**定性目标、定位瓶颈、给慢做归因**。

## 2. 第二章 原理篇：招式有千百个，底层只有四板斧

### 2.1 先把组件归位

作者先破一个迷思：

> 市面上能叫上名字的高性能组件少说有几十个。很多新人觉得性能优化就是一门「**背组件的学问**」——**但其实并不是的**。

按「本质动作」重排一遍，这是本课最提气的一张表：

| 组件 / 手段 | 本质动作 | 斧头 |
|---|---|---|
| Redis、Caffeine、CDN、读写分离里的「读库」 | 把答案**提前放在更近的地方** | **缓存** |
| Kafka、RabbitMQ、线程池任务队列、前端的一些队列 | 把**不着急的事往后放** | **异步** |
| 连接池、线程池、对象池 | **复用贵重的资源** | **池化** |
| 批量插入、IN 查询、云服务合并下发 | **减少往返次数** | **批量** |

> **招式有千千万，但底层就这四类。**

看穿这一层的好处有二：① 学**新组件**只需问「它是哪把斧头」，原理瞬间就懂；② 遇到**新场景**先想「该用哪把斧」，而不是先想「该装哪个软件」。第二点把「选型」从**软件目录**拉回到了**问题本身**。

### 2.2 第一板斧 缓存：把答案放到更近的地方

> **一句话定义：把答案放在离请求更近的地方，用空间换时间。**

```
┌────────────────────────────────────────────┐
│ L1 本地缓存（Caffeine）                    │
│   进程内存 · 纳秒级 · 零网络开销           │
│   缺点：多实例各存一份，改了这个那个不知道 │
├────────────────────────────────────────────┤
│ L2 分布式缓存（Redis 集群）                │
│   独立进程 · 毫秒以内 · 所有实例共享       │
├────────────────────────────────────────────┤
│ L3 数据库（MySQL）                         │
│   几十毫秒起 · 最后的防线                  │
└────────────────────────────────────────────┘
   读取顺序：永远从近到远（本地 → Redis → 数据库）
```

**最重要的数字是命中率**：

| 命中率 | 落到数据库的请求 | 数据库压力 |
|---|---|---|
| 90% | 100 个里 **10 个** | 降为 **1/10** |
| **99%** | 100 个里 **1 个** | 降为 **1%** |

> **缓存的价值就在于此处。**

> 📌 **补充**：命中率是**乘数型**收益，对数据库的意义远大于「让接口快一点」。它也是**水位线**——第 4 章「命中率跌破 95% 立刻告警」就是硬规则，因为「掉一个点，数据库压力就上一个台阶」。

**为什么成立：局部性原理**。**时间局部性**：刚用过的数据很快会被再次使用；**空间局部性**：存储上挨着的数据常被一块儿使用。电商**商品详情页**是标准案例——「一个爆款商品一秒内可能被读**几万次**，而它**几秒内都不会变**」。

**能不能用：一条判断标准**——**读多写少，且业务能容忍几毫秒到几秒的「旧值」**。反过来，作者给了个血淋淋的反例：**库存余量**这种强一致数据进缓存，就会变成「用户看到有货（读缓存）→ 下单 → 数据库真正扣减 → 没货」，体验崩了还可能超卖。

> 📌 **补充**：工程上很好用的「缓存三问」：① **读:写比**是否 > 10:1（否则维护成本高于收益）？② **能容忍多久旧值**（决定 TTL）？③ **一致性要求是「最终」还是「绝对」**？一个常见折中：库存**可以缓存**，但只缓存「有/无」这种粗粒度标记用于页面展示，真正扣减永远走数据库 + 原子操作。

### 2.3 第二板斧 异步：把不着急的事挪出主链路

> **一句话定义：把不着急的事情，从用户等待的主链路上挪出去。**

**同步下单：6 步串行，480ms**

```
用户点击下单
   ├─ ① 校验库存  ┐
   ├─ ② 扣减库存  │
   ├─ ③ 创建订单  ├── 用户真正关心的
   ├─ ④ 发优惠券  │
   ├─ ⑤ 加积分    │
   └─ ⑥ 发短信    ┘        合计 480ms
```

> 这 480ms 里，用户真正关心的**只有前三步**——他要的就是「下单成功」这个确认。至于积分什么时候到账、短信什么时候发出来，**用户根本不在乎**。

但同步代码不管这些：短信网关抖一下，下单**慢几十毫秒**；积分/营销服务挂了，**下单直接失败**。

> **每一个下游的抖动，都会 100% 贡献到用户 RT 的增长上。**

**异步下单：主链路 210ms + 投递 2ms**

```
① 校验库存 ┐
② 扣减库存 ├─ 事务内·强一致（210ms）
③ 创建订单 ┘
      ├─ ④ 投 MQ（2ms）──▶ 立即返回「下单成功」
      └──────────────▶ ┌──────────────┐
                       │ MQ 削峰缓冲  │
                       └───────┬──────┘
                               ▼
                       消费者：发券 / 积分 / 短信 · 失败重试
```

**为什么前三步必须留下**：扣库存不扣干净就会**超卖**；订单不落库就**没有这笔交易的数据**。结果 `480ms → 210ms + 2ms = 212ms`。

**附赠的两个红利**：**削峰填谷**（洪峰先进 MQ，消费者按自己能力匀速消费，数据库不再被瞬时 QPS 打爆）、**解耦**（营销服务挂掉只是积分晚到，下单主链路纹丝不动）。

> 📌 **补充**：「削峰填谷」要拆开看——**削的是峰（瞬时 12000），填的是谷（消费者 2000/s 匀速消化）**。它不是让系统变快，而是**把尖峰摊平到更长的时间窗**。代价是消息可能在队列里待几十秒，这正是判断依据的来源。

**代价与唯一判断标准**：天底下没有免费的加速，异步的代价是**一致性从「实时」变成「最终」**。

> **这件事晚几秒完成，业务到底会不会出事？** 会 → 留在主链路；不会 → 扔给 MQ。

### 2.4 第三板斧 池化：把贵的资源反复用

作者说这把斧头「很不起眼，但性价比很高」。先算账：

| 环节 | 耗时 |
|---|---|
| TCP 三次握手 + MySQL 认证握手 | **几毫秒 ~ 几十毫秒** |
| 真正的查询 | **约 2ms** |

> **建连接的成本，是干活成本的几倍甚至几十倍。而且用完就断了，下次还要再来一遍。**

食堂比喻（本课最好笑的一个）：

> 就好像食堂每来一个客人，你就**现制作一个餐盘**，用完**立刻砸掉**。池化的做法是：**餐厅常备 20 个餐盘循环使用。**

```
启动时：一次性建好一批放进池子
   ┌──────────────────────────────────────┐
   │ ● ● ● ● ● ● ● ● ● ●  (20)            │
   └──────────────────────────────────────┘
运行时：借一个（微秒级）→ 用完还回去
   ┌──────────────────────────────────────┐
   │ ○ ● ● ● ● ● ● ● ● ●                  │  ○ = 正在被用
   └──────────────────────────────────────┘
```

> 本质上就是**把「创建贵、使用短」的成本一次性预付**，之后每次使用都几乎免费。

**三类池**：**数据库连接池**（HikariCP，SpringBoot 默认自带，复用 TCP 连接 + 认证会话）、**HTTP 客户端池**（keep-alive 连接复用）、**线程池**（栈约 **1MB**，更贵的是**上下文切换**）。

**三个共同要素**：**核心数量**（平时保持多少）、**上限**（最多扩到多少）、**借完必须还**（这是纪律不是建议）。「你借了连接不还，池子里很快就被借空，**系统就要出问题**。」

**代价**：「**基本为零**，它是少数你配对了就是纯赚的优化」，风险**不在于要不要用，而在于你配多大**：

```
池子太小 → 请求在池子前排队     ← 第三宗罪
池子太大 → 把下游压垮           ← 变成攻击
```

### 2.5 第四板斧 批量：成本单位是「趟」

> **往返次数，才是成本的单位。**

**写：1000 条插入**

| 做法 | 耗时 | 倍数 |
|---|---|---|
| 一条一个 INSERT，一条一个事务 | **8.2 秒** | 1× |
| 一条 INSERT 带 1000 组 VALUES，一个事务提交 | **0.2 秒** | **快 40 倍** |

> 数据一模一样，表一模一样，**差的只是跑了几趟**。每一趟都有**网络往返**、都有**事务提交**。那 1000 趟的 **fsync 固定开销**，远大于干活的成本。

> 📌 **补充**：`fsync` 是关键词——MySQL 每次事务提交默认要保证 redo log 落盘（`innodb_flush_log_at_trx_commit=1`），这是一次**真实的磁盘刷写**。1000 次提交 = 1000 次刷盘，而刷盘是毫秒级的。所以合并事务省下的不是 CPU，是**磁盘同步次数**。

**读：N+1 问题**

| 做法 | 耗时 | 倍数 |
|---|---|---|
| 查 100 个商品详情，循环里调 100 次 | **3000ms** | 1× |
| 先收集 100 个 ID，一条 `WHERE id IN (...)` | **30ms** | **快 100 倍** |

**批量的原则**：**先收集齐这一轮要什么，再一次性拿全。** 不只用于数据库，作者特意延伸到接口设计——**对外提供批量接口**，别让前端循环调上百次。

**高级形态：预计算**——「实时算不动的**报表、榜单、库存快照**，提前在**凌晨低峰期**算好，存成结果表，请求来了直接读」。本质是**把缓存思想用在「计算结果」上，用凌晨便宜的 CPU 换晚高峰的响应时间**。

> 📌 **补充**：这就是**物化视图**的手写版。三个变体按实时性排序：凌晨跑批写结果表（T+1，成本最低）→ 定时任务每 5 分钟刷新（分钟级）→ 流式计算 Flink（秒级，成本最高）。选哪个只看一件事：**业务能容忍多旧的数据**。榜单容忍 5 分钟，库存快照容忍 0 秒。

**代价：攒批是在等**。「攒太小 → 退化成一条一条，等于没做；攒太大 → 内存爆了，延迟也爆了」。两种折中触发：**按条数**（攒满 **500** 条就发）、**按时间窗口**（**200ms** 先到先发），实际工程通常**两者取先到**。

### 2.6 四板斧总表

| 斧头 | 一句话 | 换掉了什么 | 主要代价 | 治哪一宗罪 |
|---|---|---|---|---|
| **缓存** | 把答案放近处 | **空间**换时间 | 失效管理、一致性 | 第四宗罪 IO |
| **异步** | 不着急的往后放 | **实时性**换时间 | 最终一致、补偿幂等 | 第一宗罪 网络 |
| **池化** | 贵的资源反复用 | 无（纯赚） | 配大了压垮下游 | 第三宗罪 排队 |
| **批量** | 少跑几趟 | **延迟**换吞吐 | 攒批等待 | 第一/四宗罪 |

作者给的口诀：**缓存换读、异步换实时、池化换建连接、批量换往返。**

## 3. 第三章 实战篇：把 8 秒一刀一刀砍到 90ms

### 3.1 实验路线与三条守则

```
① 搭环境 → ② 写 8 秒慢接口 → ③ 压基线 → ④ 四板斧逐一上场 → ⑤ 补刀 → ⑥ 对账
```

| # | 守则 | 为什么 |
|---|---|---|
| 1 | **一次只动一个变量** | 压基线 → 改一处 → 重新压 → 对比数字 |
| 2 | **顺序有讲究**：先缓存，再异步，最后池化 | 阿姆达尔定律的实战应用（先砍占比最大的） |
| 3 | **每一步都要留数字** | 优化前后 QPS、P99 全记录，否则没法对账 |

> 你三个优化一起上，最后效果好了，**你说不清是谁的功劳**；效果差了，**也查不出是谁拖的后腿**。

作者先「吊了个胃口」：全做完之后，8 秒的慢接口能降到**几十毫秒**级别，数据库峰值 **12000 → 约 900**。

**两个实验细节**：① **环境要干净**——关 IDE 自动构建、别开会、给容器限好资源，「**本机压测最大的敌人就是噪声**」；② **预热 JVM**——先空跑 **1 分钟**再正式压，因为刚启动时 **JIT 还没编译热点代码**，头 **30 秒**的数据偏低。

> 📌 **补充**：所以压测报告必须写「预热时长」。严谨做法：预热 60s → 正式压 30s → 重复 3 轮取中位数。预热还会掩盖「**去优化（deoptimization）**」——有些代码 C2 编译后反而变慢，只压 30 秒看不出来。

### 3.2 环境准备：一份 docker-compose

> 📌 以下 compose 是按视频口述的「三个服务 + 两个 MySQL 参数」还原的可运行版本（视频只念了关键行）。

```yaml
services:
  mysql:
    image: mysql:8.0
    ports: ["3306:3306"]
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: fruit
    command: >
      --slow_query_log=1
      --long_query_time=0.05
      --innodb-buffer-pool-size=512M
  redis:
    image: redis:7
    ports: ["6379:6379"]
  rabbitmq:
    image: rabbitmq:3-management
    ports: ["5672:5672", "15672:15672"]
```

**两个 MySQL 参数是重点**：`slow_query_log=1` 打开慢查询日志；`long_query_time=0.05` 表示**凡是超过 50ms 的 SQL 全部记录在案**。

> 之后定位慢 SQL 就靠这份日志，**它是需要提前打开的**。

> 📌 **补充**：这是全课最容易被忽略的一句。慢查询日志**不是出事之后才开的**——出事时你既不敢重启数据库改参数，也来不及补历史数据。**上线前就开，阈值设在你 SLO 的 1/2 左右**。

**三只容器各司其职**，作者强调「不是随便选的」：**Redis → 第一板斧缓存**，**RabbitMQ → 第二板斧异步**，**MySQL → 我们要拯救的对象**。而本机与生产的差别**只有规模**：「生产是多机器 + 内网域名，本机是三个容器；但从复制机制、消息确认这些逻辑上，是**一模一样**的。」

### 3.3 慢接口解剖：语法挑不出毛病，为什么 8 秒

作者先给了一个重要前提：

> 它没有任何故意写错的语法，**Code Review 也挑不出毛病**。但为什么要这么长时间？

```
① 三个 SELECT：查商品、查库存、查最新价格           → 5.8 秒
   病根：单表 500 万行，全部没有索引 → 每次都是全表扫描
② 循环检查优惠券：购物车有几张券就调几次下游，全部串行
   病根：每张券一次网络往返（第一宗罪）
③ INSERT 订单，一条一条插入，没有批量
   病根：每趟一次网络往返 + 一次事务提交
④ 同步发短信、同步加积分，各自几十到上百毫秒
   病根：本该异步的活全挤进主链路
                    合计：5.8s + 2.2s = 8.0s
```

**关于「为什么开发环境跑得挺快」**，作者预判了所有人的疑问：「开发环境表里就几百几千行模拟数据，跑到生产上全表扫描，数据量可就大了。」于是给出本课核心判词之一：

> **性能的问题，从来不在语法里，而在数据量和并发量上。**

> 📌 **补充**：这句解释了「本地跑得好好的，上线就炸」。工程含义是**压测数据量必须接近生产**——用 1000 行压出来的 QPS，和 500 万行差着数量级，因为**执行计划可能都不一样**（`type=ALL` vs `type=ref`）。

四宗罪在这里集齐：三个 SELECT = 第四宗罪；循环查券 = 第一宗罪；逐条 INSERT = 往返 + 事务提交；同步短信/积分 = 串行等待。

### 3.4 压出基线：先证明它慢

> 有了代码，**你先别急着改**。我们要先证明它慢，**要压出来基线**。

```bash
wrk -t8 -c50 -d30s --latency \
    -s post.lua \
    http://localhost:8080/api/seckill/order
```

| 参数 | 含义 | 参数 | 含义 |
|---|---|---|---|
| `-t8` | 8 个压测线程 | `-d30s` | 压 30 秒 |
| `-c50` | **50 个并发连接** | `--latency` | 输出延迟分布 |
| `-s post.lua` | 发 POST，**每次随机生成商品 ID** | | |

> 真实流量不是打同一个商品。**随机化才能够暴露缓存和锁的问题。**

> 📌 **补充**：这是压测方法论的关键。固定 ID 会让**单条缓存命中率虚高到接近 100%**，你测不出缓存未命中的代价，也测不出热点 key 的锁竞争。**至少准备 1000+ 个 ID 做随机分布**，并额外准备一个「热点 ID」场景单独压。

**基线结果（四个数字，后面每步都回来对照）**：

| 指标 | 数值 | 说明 |
|---|---|---|
| QPS | **6.2** | 这套系统**一秒只能完成 6 个下单** |
| 错误数 | **4121** | 大量请求被拒——**线程池满了** |
| **P99** | **8.2 秒** | |
| 数据库 CPU | **100%** | |

注意那个 **4121**——不是「有点慢」，是**直接失败**：**慢到一定程度，系统会退化成「拒绝服务」**。

### 3.5 复现悬念：加一台机器，P99 涨到 11 秒

这是全课设计最妙的一段——**把开场的事故亲手复现一遍**：「什么都不改，再启动一个应用实例，把并发数从 **50 提到 150**，模拟扩容 + 流量增长。」

| 指标 | 单实例 | 扩容后 |
|---|---|---|
| QPS | 6.2 | **不升反降** |
| P99 | 8.2s | **11 秒** |

> 原因和前面讲的事故**一模一样**：瓶颈在数据库，多加应用机器只是**多一份连接池**，让数据库前面排队的人更多了。

**30 秒就能做的验证**：

```sql
SHOW PROCESSLIST;
-- 看到几百行 State = 'Sending data' / 'Locked'，就是「排队」的确凿证据
```

> 📌 **补充**：生产上更常用按耗时倒序查：
> ```sql
> SELECT id, user, time, state, LEFT(info, 80) AS sql_text
> FROM information_schema.processlist
> WHERE command <> 'Sleep' ORDER BY time DESC LIMIT 20;
> ```
> 若看到大量**相同 SQL** 在排队，那不是「数据库慢」，是「**同一条 SQL 被打了 N 遍**」——解法是缓存或限流，不是加索引。

### 3.6 第一刀 缓存：Caffeine 三步

> 这 4 个数字里最刺眼的，就是那 3 个 1.8 秒的 SELECT（合计 5.8 秒）。所以**第一板斧先砍它**。

**为什么选 Caffeine**：**Spring 官方推荐的本地缓存库，SpringBoot 的底层缓存就是它。**

```java
// 第一步：建缓存（两个参数是重点）
Cache<String, Item> itemCache = Caffeine.newBuilder()
    .maximumSize(50_000)                      // ① 容量上限 5 万条，防止撑爆进程内存
    .expireAfterWrite(Duration.ofSeconds(5))  // ② 写完 5 秒后过期
    .build();

// 第二步：读（核心）
Item item = itemCache.get(itemId, id -> itemMapper.selectById(id));

// 第三步：失效
itemCache.invalidate(itemId);   // 运营改价/改描述，主动删掉
```

| 步骤 | 关键点 |
|---|---|
| 建缓存 | `maximumSize` **5 万**防内存爆；`expireAfterWrite` **5s** 定陈旧度 |
| 读 | `get(key, 加载函数)`：**命中直接返回；未命中自动查库并回填** |
| 失效 | 光等 5 秒过期**不够保险**，运营改价要主动 `invalidate` |

> `key` 是商品 ID，`value` 是一个**加载函数**。这样就把「查缓存、查数据库、回填」**三件事全包了**。

> 📌 **补充**：`get(key, mappingFunction)` 是**原子**的——同一 key 并发未命中时只有一个线程执行加载函数，其余阻塞等待（按 key 分段加锁）。这顺带缓解了「缓存击穿」，但**只在单机内有效**，多实例下每个实例仍会各查一次库。

**效果**：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 命中率 | —— | **92%** |
| 数据库 QPS | 12000 | **960** |
| **P99** | **8.2s** | **2.9s** |

对账关系很清楚：命中率 92% → 落库流量 8% ≈ 1/12.5，而 QPS 从 12000 降到 960 **正好是 1/12.5**，**数字是自洽的**。

### 3.7 为什么先本地缓存，不是 Redis

| 理由 | 说明 |
|---|---|
| **① 更快** | 本地缓存**纳秒级、零网络开销**。读多写少、单机装得下的数据，本地这层就够 |
| **② 时机** | 多实例要共享、或数据量大到单机装不下，**才需要 Redis** |

> **别一听性能问题就上 Redis 集群，那其实就是拿大炮打蚊子。**

关于那个 5 秒：「**5 秒过期是什么意思？就是业务声明「我能容忍 5 秒的旧值」。** 商品详情肯定可以，但**秒杀或者库存这种就绝对不行**。」

> 📌 **补充**：这句话把「TTL 是技术参数」翻成了「**TTL 是一份业务合同**」。工程上最好写进接口文档：`本接口数据最大陈旧度：5s`。将来业务方要「实时价格」，你就有依据说这是换方案，不是改个数字。

### 3.8 缓存三异常：穿透 / 击穿 / 雪崩

作者说缓存「快是真的快，但翻起车来非但不能帮忙，反而会把数据库打死」。

| 异常 | 触发条件 | 后果 | 解法 |
|---|---|---|---|
| **穿透** | key **在数据库里也不存在** | 每次都未命中直落库，缓存形同虚设 | ① 空值缓存 ② 参数校验 ③ 布隆过滤器 |
| **击穿** | **某一个热点 key 过期的那一瞬间** | 成千请求同时未命中、同时查库回填 | ① 互斥重建 ② 逻辑过期 |
| **雪崩** | **一大片缓存同时失效**／Redis 宕机 | 全量流量瞬间砸向数据库 | ① 过期抖动 ② 多级缓存 ③ 限流兜底 |

**穿透**：用户拿**负数 ID** 疯狂请求，缓存怎么查都未命中。解法按成本递增：**空值缓存**（数据库也没查到时把空结果缓存 **30 秒**）→ **参数校验**（负数直接拒绝）→ **布隆过滤器**（在缓存前挡一道，判断 key 到底存不存在）。

**击穿**：某个热点 key 过期的那**毫秒级瞬间**，成千请求同时未命中、同时查库、同时回填——数据库被**同一个查询**打了几千遍。作者点出场景：「这在**秒杀商品**场景里最容易中招。」

| 解法 | 机制 | 代价 |
|---|---|---|
| **互斥重建** | 用锁保证同一时刻**只有一个**请求查库，其他等它回填 | 一个请求变慢，其余短暂阻塞 |
| **逻辑过期** | 缓存**不真删**，value 里带逻辑过期时间；过期就用**异步线程**刷新 | 返回旧值，但请求**照常返回**、不阻塞 |

**雪崩**：作者说它「最凶险」——「比如你之前偷懒给所有 key 设了统一的 5 秒过期，是不是有可能在某个整点**准时失效**？或者 Redis 干脆宕机了。」解法：**过期时间加随机抖动**（5 秒 → **5.0~6.0** 之间随机，比如 5.1、5.2、4.8、4.9，把失效点**分散开**）、**多级缓存兜底**、**集群**、**数据库侧限流**。

**三种异常的共同点**：

> 它们其实都在问**同一个问题**——**缓存里边没有的时候，这个流量该去哪儿？**

```
空值缓存            → 防穿透
互斥重建            → 防击穿
过期抖动 + 多级缓存 → 防雪崩
数据库限流          → 兜底
```

> **以后任何缓存上线前，先问一句：这 4 件套配齐了没有。**

> 📌 **补充**：还有常被漏掉的第 5 件——**缓存预热**。大促前缓存是空的，第一批流量会全打到数据库（等于人为制造一次雪崩）。标准做法：**提前 30 分钟把热点数据刷进缓存**，小流量灰度验证命中率达标后再放量。

### 3.9 缓存一致性：先删缓存的那个空窗

读的问题防住了，写的问题来了。作者用「运营改价 99 → 79」把时序漏洞一步步演出来。

**错误做法：先删缓存，再更新数据库**

```
T1  运营：删除缓存        → 缓存 = 空
T2  读请求进来：未命中 → 查数据库
T3  读到 99（事务还没提交！）→ 回填缓存 = 99
T4  运营事务提交          → 数据库 = 79
    ─────────────────────────────────────
    最终：数据库 79，缓存 99      ← 不一致！
```

> 第一步他先删除缓存，此刻缓存是空的。**就在这毫秒之间**，一个读请求进来，缓存未命中，去查数据库。你要注意——**运营的事务还没有提交**，所以查到的还是旧值 99。第三步把这个 99 回填进缓存。第四步事务提交，数据库变 79，但缓存里是 99。

后果：**后续所有读请求都可能命中这个旧值，一直到过期为止**，用户看到错误的价格。

> 这就是**先删缓存的一个时序漏洞**——**在删除和更新之间有一个空窗，正好被读请求钻了空子**。

**正确做法：先更新数据库，再删缓存**

```
T1  运营：事务提交   → 数据库 = 79
T2  删除缓存         → 缓存 = 空
T3  读请求未命中 → 查库读到 79 → 回填 79   ✔ 一致
```

> 就算有读请求进来未命中，查数据库查到的也是 79，回填的也是 79。**脏值的生成窗口被压到了最小。**

**两道保险**：**延迟双删**——删完缓存 **500ms 后**再删一次，管**并发**（极端窗口仍可能回填旧值，再删一次扫掉尾巴）；**兜底过期**——TTL 一定要有，管**故障**（删除失败时旧值自然死亡）。「一道管并发，一道管故障。」

**为什么是「删缓存」而不是「更新缓存」**：

```
如果「更新缓存」：B 先到→200；A 后到→100      ← 旧值覆盖新值
如果「删除缓存」：B 先删→空；A 后删→还是空     ← 幂等，下次读自然回填最新
```

> 因为**并发写**时，两个更新操作可能**乱序到达**，互相覆盖，把旧值写回去。而**删除是幂等的**。

**适用边界**：**Cache Aside 能做到秒级以内的最终一致**；若业务要求**极致强一致**（如**账户余额扣减**），那就别用缓存，用「读数据库 + 加锁」。

> **一致性，是用响应时间买来的。**

> 📌 **补充**：「先更新库再删缓存」也不是 100% 安全（读请求可能「删缓存前读到旧值、删缓存后完成回填」）。更严格的方案：**延迟双删**（简单，但有 500ms 污染窗口）、**订阅 binlog 删缓存**（Canal，用 CDC 拿到数据库真实提交事件再删，更准但多一个组件）。缓存一致性没有免费的完美解，只有「你能接受多长的脏窗口」。

### 3.10 第二刀 慢 SQL：抓罪犯、验明正身、建索引、复查

缓存砍完，刀转向**数据库本体**：「现在我们要去抓这个罪犯——导致数据库慢的罪犯。」

**第一步·抓罪犯**（慢查询日志按耗时排序）：

```sql
-- 头号通缉犯：按商品 ID 查价格，按创建时间倒序取最新一条
SELECT * FROM item_price
WHERE item_id = ? ORDER BY created_at DESC LIMIT 1;
```

耗时 **1.8 秒**，占剩余耗时**约八成**。

**第二步·验明正身**（EXPLAIN 三看）：

| 关键输出 | 值 | 说明 |
|---|---|---|
| `type` | **ALL** | **全表扫描**，一行一行翻过去 |
| `rows` | **4998211** | 接近 **500 万行**全部要过一遍 |
| `Extra` | **Using filesort** | 还要**额外排序** |

**第三步·建索引（这里有个坑）**：「假如你**只给 item_id 加索引**，行不行？**能快一点，但排序还要额外做。**」

```sql
ALTER TABLE item_price ADD INDEX idx_item_created (item_id, created_at);
```

> **item_id 在前，created_at 在后**——「**等值条件的列在前，排序的列在后**」。这样 MySQL **沿着索引一路扫过去，天然就是排好序的**，直接取第一条就行。

> 📌 **补充**：这就是「**最左前缀 + 索引有序性**」。B+ 树在 `(item_id, created_at)` 上，同一 item_id 下记录**按 created_at 有序**，所以 `ORDER BY created_at DESC` 可沿索引反向扫，`filesort` 消失。反过来建成 `(created_at, item_id)` 就差很多。另外 `SELECT *` 仍是**回表**；若只需要价格和时间，改成**覆盖索引**可完全不回表。

**第四步·复查**：

| 输出 | 优化前 | 优化后 |
|---|---|---|
| `type` | ALL | **ref**（走索引精确定位） |
| `rows` | 4998211 | **8** |
| `Extra` | Using filesort | **消失** |
| **耗时** | **1.8s** | **12ms** |

> 快了 **150 倍**，慢日志里**从此就安静了**。

作者用了个很贴的比喻：「**索引就像书的目录。** 没有索引就是**翻遍整本书找一句话**；有索引就是**先查目录，直接翻到那一页**。」

**索引也要算账**：「每建一个索引，写入时就要多维护一份有序结构——写入变慢，磁盘多占。」所以「**不能拍脑袋把所有列都建上索引。先抓慢日志，谁的查询多就给谁建，宁缺毋滥。**」

**本阶段的账**：P99 **2.9s → 1.1s**，数据库 CPU **100% → 35%**。但流量洪峰一来，数据库仍是第一个受害者。

### 3.11 第三刀 异步削峰：主链路瘦身

作者提醒：**这一刀动的是架构**，不是代码细节。

```java
@Transactional
public OrderResult createOrder(Long userId, Long itemId) {
    int affected = stockMapper.deduct(itemId, 1);       // ① 扣库存，否则超卖
    if (affected == 0) throw new BizException("库存不足");

    Order order = orderMapper.insert(buildOrder(userId, itemId));  // ② 建订单

    rabbitTemplate.convertAndSend("order.exchange", "order.created",
        new OrderCreatedEvent(order.getId(), userId, itemId));     // ③ 投递即返回
    return OrderResult.success(order.getId());
}

@RabbitListener(queues = "order.created.queue")
public void onOrderCreated(OrderCreatedEvent e) {
    couponService.issue(e.getUserId());   // 发券
    pointService.add(e.getUserId());      // 加积分
    smsService.send(e.getUserId());       // 发短信（失败自动重试）
}
```

> 主链路瘦成两步，包在一个**事务**里。这两步必须强一致——库存扣错就超卖，订单落不了库就没有这笔生意。然后往 MQ 投一条消息，**投完立刻返回**，P99 只剩 **210ms**。发券/短信/积分由消费者**慢慢办**，失败还能**自动重试**。用户等待的链路里，**是不是已经没有它们了**？

**削峰的机制**：

```
12000 QPS ──▶ ┌────────────────┐ ──▶ 2000/s ──▶ 下游服务
   洪峰       │  MQ 队列       │
              │ 12000 QPS 进   │      峰值被「摊平」到 6 秒
              │ 2000/s 匀速出  │
              └────────────────┘
```

> 如果直接压到数据库，数据库**必然挂掉**。现在数据库只剩「下单那两步」的量，其他全部进队列，消费者按**每秒 2000** 的能力**匀速消化**。

**效果**：P99 **1.1s → 240ms**；解耦红利也到手——「当晚营销服务真的抖动了 **10 分钟**，下单成功率还是**纹丝不动**」。判断依据仍是那句：看**有没有人 care 它**。

**三条隐藏账单**（「很多团队上了 MQ 之后才了解到」）：

| # | 账单 | 后果 | 对策 |
|---|---|---|---|
| 1 | **积压监控** | 消费者挂了/消费慢，消息堆在队列里，**堆到几百万条才发现就晚了** | **积压数必须进告警** |
| 2 | **消息幂等** | 重试机制意味着同一条消息**可能被投递多次** | 消费端要能认出「处理过」，否则**重复发券** |
| 3 | **队列容量告警** | 堆满之后的**丢弃策略** | 要**事先想好**（拒绝？死信？降级？） |

> 📌 **补充**：还有一条常被忽略——**消息丢失**。生产端开 **publisher confirm**、消费端**手动 ack**（别用 autoAck）、队列与消息都 **durable**，三个都开了才算「不丢」，但都开了吞吐会降。「不丢」和「高吞吐」在 MQ 里本身就是一对取舍。

### 3.12 第四刀 池化调参：两个公式

这一刀的特殊性：「**它不写在业务代码里，改的是配置。但你配错一个数，前面所有的功夫可能就白费了。**」

**公式一：数据库连接池** `连接数 = CPU 核数 × 2 + 有效磁盘数`——「一台**四核 + 一块 SSD** 的机器，配 **9~10 个连接**是最优的。」

为什么这么小？这是本课最反直觉的一段论证：

> 数据库的**并发能力天生是有限的**。连接数超过它能并行处理的事务数，**多出来的连接就只能在数据库里排队，还挤占资源**。

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10        # 按公式，别贪大
      minimum-idle: 10             # 与 max 相等 → 不伸缩，避免抖动
      connection-timeout: 3000     # 3s 借不到就快速失败，绝不让请求干等
      max-lifetime: 1800000        # 30min 强制换血，清掉数据库侧悄悄断掉的死连接
```

回到那个事故：

| 配置 | 连接总数 | 结果 |
|---|---|---|
| 默认 20 × 10 台 | **200** | 砸向只能有效处理 **50** 个连接的数据库 → **变成一种攻击** |
| 公式 10 × 10 台 | **100** | 而且**大部分时间闲置** → 能比较好地应对 |

> 📌 **补充**：这公式来自 HikariCP 官方 wiki（引用 PostgreSQL benchmark），**前提是「SSD + 数据库不是瓶颈」**。若数据库本身已 CPU 100%，调连接数毫无意义——先解决慢 SQL。所以顺序永远是：**先砍慢查询，再调池子**；调反了就是「给一个已经堵死的路口多开几条车道」。

**公式二：线程池** `线程数 = CPU 核数 × (1 + 等待时间 / 计算时间)`。代入下单接口：核数 **4**、等待 **200ms**、计算 **20ms** → `4 × (1 + 200/20) =` **44 个线程**。

> 它比 CPU 密集型要大，因为**线程大部分时间是在等 IO 的**。

**两个必写项：有界队列 + CallerRuns**

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    44, 44, 0L, TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<>(500),                 // ① 有界队列，500
    new ThreadPoolExecutor.CallerRunsPolicy()      // ② 满了让提交者自己干
);
```

> `newFixedThreadPool` 用的是**无界队列**，请求堆积没有上限，**内存早晚会爆掉（OOM）**。队列满了就让**提交请求的线程自己干活**——**我们宁可慢一点，也不丢请求、不崩服务**。

| 策略 | 行为 | 后果 |
|---|---|---|
| `AbortPolicy`（默认） | 抛异常 | 用户直接看到失败 |
| `DiscardPolicy` | 静默丢弃 | **最危险，请求凭空消失** |
| `DiscardOldestPolicy` | 丢最老的 | 老请求的用户白等了 |
| **`CallerRunsPolicy`** | **提交者自己执行** | **自动限流 + 不丢请求** |

**本阶段的账**：P99 **240ms → 90ms**，**全程零报错**。四板斧砍完，**8 秒 → 90ms**。

### 3.13 补刀：深分页与大事务

这两个「不属于哪一板斧能解决，但几乎大家都碰到过」，通常**在管理后台和运营操作里炸开**。

**深分页**：

```sql
-- 问题：订单表翻到第 5 万页，耗时 4.2 秒，越往后越慢
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;

-- 解法：游标分页（Keyset Pagination）
SELECT * FROM orders
WHERE id > #{lastId}      -- 上一页最后一行的 ID，就像书签
ORDER BY id LIMIT 20;
```

作者纠正了一个普遍误解：

> 很多人以为数据库会**跳过**前面这 100 万行。**但其实并不是**——它是**老老实实把 100 万行都读出来，然后扔掉**，再给你 20 行。你翻得越深，扔掉的越多，时间**线性暴涨**。

> 上一页最后一行的 ID 就像**书签**，下次从书签继续往后读 20 行。配合主键索引，**不管你翻到第几页，都是同样的 20 行范围扫描**。

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 耗时 | 4.2s | **80ms** |
| 随页数衰减 | 线性暴涨 | **不衰减** |

**代价**：只能**顺序翻页，不能跳页**。作者的现实判断很毒：「但放到真实情况里你想一下——**用户真的会跳到第 5 万页吗？** 这种跳跃需求，可能都是**产品拍脑袋想出来的**。」

**大事务**：一个事务里包了 **1 万条 UPDATE**，锁从第一条持有到最后一条要花**几十秒**，期间所有相关查询都在**排队**。

```java
for (int i = 0; i < list.size(); i += 500) {          // 500 条一批
    batchUpdate(list.subList(i, Math.min(i + 500, list.size())));
}                                                      // 批间提交
```

锁持有时间从**几十秒**变为**毫秒级**。

**剩下几个小补刀位**：**大 JSON → 精简 DTO**（序列化时间和带宽一起省）、**循环查库 → IN 批量**（3000ms → 30ms）、**JVM / GC 调优**（「本课不讲，要讲也是一个大块内容，之后找机会」）。

### 3.14 对账：8 秒 → 90ms

这是全课最该截图保存的一张表。

| 指标 | 事故当天 | 优化后 | 谁干的 |
|---|---|---|---|
| **下单 P99** | **8.2s** | **90ms** | 四板斧合力 |
| **QPS** | **6.2** | **820** | 「RT 降了，吞吐自然就升了」 |
| **数据库峰值 QPS** | **12000** | **900** | 缓存挡住大半 + MQ 削峰 |
| **数据库 CPU** | **100%** | **30%** | 索引消灭了全表扫描 |
| **加 10 台机器的效果** | RT **反而慢 4 秒**（8s→12s） | RT **再降 30%** | 先砍瓶颈，扩容才有意义 |

对最后一行，作者给了一句极重的判词：

> **同样的扩容动作，先砍瓶颈再去做它才有意义。顺序弄错了，扩容就相当于一个「攻击放大器」。**

> **每一行收益，都对应一个实验、一页原理。快不是玄学，是可以解释、可复现、可审计的工程结果。**

### 3.15 打法闭环：三步流程 + 映射表 + 口诀

```
① 压测拿基线 → QPS / P99 / 错误率 / DB CPU 全记录
                「没有基线就不许动手」——没有对照组，优化就是玄学
② 按 P99 找短板 → 链路追踪看时间花在哪一跳，用四宗罪归类：IO / 网络 / 排队 / 计算
                  「归因不清，斧头就只能乱挥」
③ 按占比选斧头 → 算占比 → 砍最大的 → 重新压测 → 对账 → 再砍下一块
                  一次只动一个变量
```

| 罪名 | 对应的斧头 / 手段 |
|---|---|
| **IO 查询慢**（第四宗罪） | **缓存 + 索引** |
| **串行往返多**（第一宗罪） | **异步 + 批量** |
| **锁与排队**（第三宗罪） | **池化调参 + 分批事务** |
| **CPU 白干**（第二宗罪） | **精简序列化 + 预计算** |

口诀（作者原话的顺序）：

> **读的问题，先想缓存；写的问题，再想异步；资源问题，去调池化参数。** 大多数场景按这个顺序走，都是**收益很大、风险很小**的。

## 4. 第四章 治理篇：把一次优化变成一套制度

### 4.1 三个月后它还会是 90ms 吗

> 几个月之后，这个生鲜电商的系统**还会是 90ms 吗？大概率不一定。**

原因有三种极常见的退化：新人加了一段循环查库的代码（Code Review 没人拦）、某个下游悄悄变慢（没人对比历史基线）、缓存命中率缓慢下滑（没人看这个指标）。

> **性能是有惯性的，会退化——除非你用制度去拦住它。**

这就是第四章存在的理由：**个人英雄式的优化救不了一个团队**。

### 4.2 第一件工具：RT 预算表

先给一个洞察，值得单独抄下来：

> **性能问题从来不是在上线那天爆发的，而是在需求评审的时候埋下的。**

因为产品随便说一句「加一个实时榜单」，**没有人会去问「这句查询要多少毫秒、落在哪一层」**。所以要把性能变成**像工程预算一样的东西**：

> **每一层花多少毫秒，要事先约定，写进文档，超标了就报警。**

| 层 | 预算 | 具体约束 |
|---|---|---|
| **网关 + 鉴权** | **10ms** | 规则数据放**本地缓存**，**禁止实时调数据库**；此层命中率必须 **> 99%**（被调用次数最多） |
| **应用计算 + 序列化** | **30ms** | 超了就查：DTO 是不是太肥？循环里是不是有可外提的计算？ |
| **缓存读取** | **5ms** | **命中率跌破 95% 立刻告警** |
| **下游 RPC（合计）** | **50ms** | **超过 3 个串行调用就上评审会**；能异步的异步，能批量的批量 |
| **数据库 / 余量** | 剩余额度 | 📌 补充：200 − 95 = **105ms**，视频未逐项念这一行，按总额反推 |

**为什么命中率卡在 95%**：「因为**命中率就是数据库的水位线**。命中率**掉一个点**，数据库压力就**上一个台阶**。」

> 📌 **补充**：这句能量化。95% 附近掉一个点，未命中率 5% → 6%，**数据库压力涨 20%**；99% 附近掉一个点，1% → 2%，**压力直接翻倍**。所以**命中率越高越要盯得紧**——反直觉但极重要。

**两个使用场合**：**需求评审（事前）**——新接口立项**先分预算再写代码**，产品要加功能就打开表看它占哪层预算，**性能在源头就有约束**；**线上运行（事后）**——每层**实际耗时**通过监控实时对比，**预算超限自动告警**，**退化在用户感知之前被抓出来**。

**预算数字从哪儿来**：「**从你自己的对账表来。** 每次压测、优化之后，**每层的实测值都是下一版预算的起点**。**这个预算是活的**，要随架构演进去修订——**但它是必须存在的**。」

> 📌 **补充**：这把预算表和 3.14 的对账表连成闭环：**实测 → 定预算 → 监控对比 → 超限告警 → 再实测**。没有第一步的实测，预算是拍脑袋；没有最后一步的告警，预算是墙上的一张纸。

### 4.3 第二件工具：定位三板斧

预算超了怎么找原因？作者给了固定顺序的三件工具，强调「**不能靠老师傅的直觉**」。

| 顺序 | 工具 | 干什么 | 产出 |
|---|---|---|---|
| **①** | **链路追踪（SkyWalking）** | 把请求链路展开成**瀑布图**，接入成本低 | **嫌疑人**：数据库？下游？还是应用自身？ |
| **②** | **火焰图（async-profiler）** | 采样看**哪段代码在烧 CPU** | **嫌疑代码行** |
| **③** | **慢日志 + EXPLAIN** | 拿到**确切的 SQL 和执行计划** | **可执行的修复动作** |

```
请求总耗时 1200ms
├─ 网关            8ms   ▏
├─ 应用自身       32ms   █
├─ RPC 调营销服务 1050ms ██████████████████████████████  ← 嫌疑人
└─ SQL            110ms  ███
```

> 它把网关多少毫秒、应用多少毫秒、**哪次 SQL 调用占了多少毫秒**展开得**一目了然**。这一步的产出是**嫌疑人**，下一步再找根因。

**火焰图**：「**横条越宽，代表占用的 CPU 越多**。要找到**最宽的那个平顶**——平顶就意味着这个函数是热点。」三个「无处遁形」的元凶：**序列化**（宽条堆在 `ObjectMapper`）、**正则回溯**（单条极宽的 `Pattern.match`）、**锁自旋**（宽条出现在 `Unsafe.park`）。

> 📌 **补充**：视频口述「采样 **30ms**」应是口误。async-profiler 通常按**时长**采样：`./profiler.sh -d 30 -e cpu -f flame.html <pid>`（采 30 秒）。默认采样频率约 100Hz，采 30ms 只有 3 个样本，没有统计意义。

**慢日志**：「加上 `EXPLAIN` 就能拿到**确切的 SQL 和执行计划**，可以**建索引**或**改写 SQL**，**当场就能见效**。它的产出是**一个可执行的修复动作**——**定位到此结束**。」

> 📌 **补充**：三板斧的顺序不能乱，因为它遵循「**成本递增**」：链路追踪只加探针不改代码；火焰图要 attach 或重启；慢日志改完还要回归。**先用最便宜的手段把范围缩小，再上贵的。**

### 4.4 第三件工具：三阶段路线

| 阶段 | 周期 | 做什么 | 目标 / 标志 |
|---|---|---|---|
| **① 止血** | **1~2 周** | **别谈架构，先去救命**：压测拿基线、砍最粗的短板、最痛的查询加索引、热点数据上缓存、连接池按公式调参 | **P99 砍一半**（成本低、见效快） |
| **② 提速** | **1~2 个月** | **可以动架构**：核心链路异步化、多级缓存体系、批量接口改造 | **RT 预算化**——每层有预算和告警，性能从「救火项目」变成「常态监控」 |
| **③ 体系** | **长期** | 预算进需求模板、评审会问性能、容量规划常态化、**大促前全链路压测** | **性能退化在上线前就被拦住** |

> 📌 **补充**：顺序有隐含逻辑——**止血阶段的动作全是「配置级」**，不改代码、不跨团队，所以 2 周能落地；**提速阶段必然改代码、协调上下游**，所以要 1~2 个月；**体系阶段改流程和模板**，只有前两阶段拿到数字，流程才有依据。反过来做（先上流程）就是「没有数据的制度」，没人会遵守。

### 4.5 五个坑

| # | 坑 | 后果 |
|---|---|---|
| 1 | **没基线就优化** | 改完**说不清有没有效果**，性能工作沦为**玄学** |
| 2 | **一次动多个变量** | 出了问题**查不清是谁的锅**，效果好了**也查不清是谁的功劳** |
| 3 | **只测单接口** | 单接口 90ms 很漂亮，**全链路一压，缓存击穿把数据库打穿** → **单接口的快 ≠ 系统的快** |
| 4 | **缓存当万能药** | 连**强一致的库存**也塞缓存 → **超卖事故，损失比慢查询贵数十倍** |
| 5 | **只优化不设防** | 没预算没告警 → **3 个月后悄悄退化，所有功劳全没了** |

第 4 坑的量化对比最扎心：慢查询只是转化率下降，**超卖却是要赔付、要公关、要修数据**。

## 6. 速查卡：公式 / 数字 / 决策树

### 6.1 五个公式

| 公式 | 用途 | 注意 |
|---|---|---|
| `并发数 = QPS × RT` | 利特尔法则 | RT 一涨，并发必暴涨 |
| `加速比 = 1 / ((1−P) + P/S)` | 阿姆达尔定律 | `(1−P)` 是天花板 |
| `连接数 = CPU核数 × 2 + 磁盘数` | HikariCP | 4 核 1 SSD ≈ 9~10 |
| `线程数 = CPU核数 × (1 + 等待/计算)` | 线程池 | 下单：4×(1+200/20)=44 |
| `数据库压力 = 1 − 命中率` | 缓存价值 | 92% → 8%；99% → 1% |

### 6.2 关键数字

| 分类 | 数字 |
|---|---|
| **量级** | 内存 100ns / SSD 100µs / 磁盘 10ms；跨机房 30ms |
| **网络** | 同机房一次 1~5ms；串行 8 个下游 ≈ 40ms 起 |
| **用户耐心** | 白屏 **5 秒** → **60%** 退出 |
| **事故现场** | QPS 200→12000；RT 80ms→8s；扩容后 12s；42 万预约 |
| **基线** | QPS 6.2；P99 8.2s；错误 4121；DB CPU 100% |
| **缓存后** | 命中率 92%；DB QPS 12000→960；P99 →2.9s |
| **索引后** | 1.8s→12ms（150×）；rows 4998211→8；P99 →1.1s；CPU →35% |
| **异步后** | P99 →240ms；消费者 2000/s |
| **池化后** | P99 →90ms；线程 44；队列 500 |
| **深分页 / 批量** | 4.2s→80ms；1000 条 8.2s→0.2s（40×）；N+1 3000ms→30ms（100×） |
| **终局** | P99 90ms；QPS 820；DB 峰值 900；DB CPU 30% |

### 6.3 📌 决策树：接口慢了先做什么

```
接口 P99 超标
  ├─ ① 有基线吗？── 没有 ──▶ 先压测，别再往下走
  ├─ ② 链路追踪：时间花在哪一跳？
  │     ├─ 数据库/SQL ─▶ 第四宗罪 IO
  │     │    ├─ 慢日志 + EXPLAIN 三看（type / rows / Extra）
  │     │    ├─ type=ALL → 建索引（等值在前、排序在后）
  │     │    └─ 仍是热点读 → 上缓存
  │     ├─ 下游 RPC ───▶ 第一宗罪 网络：能异步→MQ / 能并行→并发调 / 能批量→IN
  │     ├─ 应用自身 ───▶ 第二/三宗罪：火焰图见平顶→精简序列化；宽条在 park→缩锁
  │     └─ 都正常但 CPU 不高 ─▶ 第三宗罪 排队
  │          ├─ 连接池太小？按公式调
  │          ├─ 队列无界？改有界 + CallerRuns
  │          └─ 大事务/长事务？拆批 500
  ▼
③ 改一处 → 重新压测 → 对账 → 再砍下一块
```

## 7. 动手路线

| 步 | 动作 | 验收标准 |
|---|---|---|
| 1 | `docker compose up -d` 起三件套 | 三个端口都通 |
| 2 | 建一张 **500 万行**的表，**故意不建索引** | `EXPLAIN` 出现 `type=ALL` |
| 3 | 写那个 8 秒慢接口（3 SELECT + 循环查券 + 逐条 INSERT + 同步短信） | 耗时 ≈ 8s |
| 4 | `wrk -t8 -c50 -d30s --latency` 压基线，**记录 4 个数字** | QPS < 10，P99 > 8s |

## 8. 面试自测题（含答案）

**Q1：为什么加机器反而更慢了？**
**扩容只对瓶颈所在的那一层有效**。瓶颈在数据库，扩应用层只是让每台机器带一份连接池（20 × 10 = 200 连接），砸向一个只能有效处理 50 连接的数据库 → 排队更长 → RT 更长 → 并发更高（利特尔法则）→ 超时重试更多 → **死亡螺旋**。

**Q2：为什么性能目标要用 P99 而不是平均值？**
**慢请求永远是少数，而少数恰恰能决定口碑**。平均 120ms 看着健康，但 P99 是 8 秒；一晚 1200 万请求，1% 就是 **12 万人次**转圈 8 秒，而最有意愿的用户往往等得最久。

**Q3：木桶定律和阿姆达尔定律分别解决什么？**
木桶解决「**砍哪块**」——总耗时由最慢那段决定（把其他都优化到 0，7820ms 只变 7800ms）；阿姆达尔解决「**砍了值不值**」——`1/((1−P)+P/S)`，P=0.96、S=100 → 20 倍，S=10000 → 25 倍封顶，P=0.04、S=100 → 只有 1.04 倍。

**Q4：四宗罪是什么？怎么归类？**
**网络往返 / 计算与序列化 / 锁与排队 / IO**。归类看三条线索：CPU 高 → 第二宗罪；CPU 不高但很慢 → 第三宗罪；`SHOW PROCESSLIST` 大量 SQL 排队 → 第四宗罪；链路追踪耗时在跨服务调用上 → 第一宗罪。

**Q5：为什么先上本地缓存而不是 Redis？**
① 本地缓存**纳秒级、零网络开销**，比 Redis 快一个数量级；② 读多写少、单机装得下的数据，本地这层就够。**「别一听性能问题就上 Redis 集群，那是拿大炮打蚊子。」**

**Q6：穿透 / 击穿 / 雪崩的区别？**
穿透是 key **在数据库里也不存在**，每次都落库；击穿是**单个热点 key 过期瞬间**，成千请求同时查同一条；雪崩是**一大片 key 同时失效或 Redis 宕机**。共同点都在问「**缓存里没有时流量该去哪儿**」。组合拳：空值缓存 + 互斥重建 + 过期抖动 + 多级缓存 + 数据库限流。

**Q7：为什么「先更新数据库再删缓存」？**
先删缓存有**空窗**：删完到事务提交之间，读请求未命中会读到**旧值**并回填，之后数据库变新值、缓存却是旧值，直到过期。先更新库再删缓存把窗口压到最小，再加两道保险：**延迟双删（500ms）管并发**、**TTL 兜底管故障**。

**Q8：为什么是「删缓存」而不是「更新缓存」？**
并发写时两个更新可能**乱序到达**互相覆盖，把旧值写回去。**删除是幂等的**——谁先谁后结果一样，下次读自然回填最新值。

**Q9：联合索引为什么「item_id 在前、created_at 在后」？**
**等值条件在前、排序在后**。B+ 树在 `(item_id, created_at)` 上，同一 item_id 下记录按 created_at **天然有序**，`ORDER BY created_at DESC` 可沿索引反向扫，`filesort` 消失；反过来建效果差很多。

**Q10：连接池为什么不是越大越好？**
数据库**并发处理能力天生有限**。连接数超过它能并行处理的事务数，多出来的**只能在数据库里排队，还挤占资源**。公式 `CPU×2 + 磁盘数`（4 核 1 SSD ≈ 9~10）。视频里的反例：10 台 × 20 默认 = 200 连接，砸向只能处理 50 个连接的库，**变成一种攻击**。

**Q11：线程池为什么必须用有界队列？**
`newFixedThreadPool` 用近乎无界的 `LinkedBlockingQueue`，请求堆积没有上限，**内存早晚 OOM**。要用 `ArrayBlockingQueue(500)` + `CallerRunsPolicy`——满了让提交线程自己干，**宁可慢一点，也不丢请求、不崩服务**。

**Q12：深分页为什么越翻越慢？**
`LIMIT 1000000, 20` 不是「跳过」前 100 万行，而是**老老实实读出来再扔掉**，翻得越深扔得越多，时间线性暴涨（第 5 万页 4.2s）。解法是**游标分页** `WHERE id > lastId ORDER BY id LIMIT 20`，任何页都是 20 行范围扫描（80ms，不衰减），代价是**不能跳页**。

**Q13：异步的代价与判断依据？**
代价是**一致性从实时变为最终**，并带来三条隐藏账单：**积压监控、消息幂等、队列容量告警**。判断依据只有一条：**这件事晚几秒完成，业务会不会出事？**

## 9. 📌 补充：视频没细讲但一定会踩的坑

**9.1 热点 key：缓存异常的「第四种」。** 穿透/击穿/雪崩之外还有个纯性能问题——**单个 key 的 QPS 打爆单个 Redis 分片**，表现是「集群整体 CPU 不高，但某个节点 100%」。解法：**本地缓存挡在前面**（本课其实已经这么做），或把热点 key 拆成 `key:0..N` 分散到多分片。

**9.2 TTL 抖动别抖太小。** 视频说 5 秒加 0~1 秒抖动。若 key 数量少（比如只有 100 个），抖 1 秒仍可能撞在一起。经验值：**抖动幅度 ≈ TTL × 10%~20%**；更稳的是**分批预热 + 分批过期**。

**9.3 本地缓存的「多实例不一致」。** Caffeine 是**每台机器一份**。10 台实例，运营改价后 `invalidate` 只删掉**本机**那份，其余 9 台仍是旧值，最长等 TTL。解法：**广播失效**（Redis pub/sub 或 MQ 广播），或接受这个窗口——这也是 TTL 必须写进接口文档的原因。

**9.4 `EXPLAIN` 的 `rows` 是估算值。** `rows=4998211` 是优化器的**统计估算**。要定期 `ANALYZE TABLE`，否则统计信息过期会导致优化器**选错索引**（明明有索引却走全表）。

**9.5 加索引会让「写」变慢多少。** 视频只说「写入变慢、磁盘多占」，没给量级。经验值：**每多一个二级索引，INSERT 约多 5%~15% 耗时**，且写放大（WAL/binlog 也变大）。**高频写入表（如订单流水）索引最好控制在 3 个以内。**

**9.6 `CallerRunsPolicy` 的副作用。** 它把压力**回传到调用者线程**。若调用者是 Tomcat 工作线程，会导致 Tomcat 线程池占满、**新连接直接被拒**。从「保护后端」看是好事（背压），但**用户看到的是连接失败而不是变慢**，所以入口层还要**限流**配合。

**9.7 削峰填谷的隐藏前提：队列容量要够。** 「12000 进、2000/s 出」意味着每秒净增 10000 条，洪峰持续 60 秒就要堆 **60 万条**。必须算：**容量 ≥ (峰值QPS − 消费QPS) × 洪峰持续秒数**，否则「队列写满 → 生产端阻塞或丢消息」。

**9.8 RT 预算表最容易死的地方：没人维护。** 最大风险不是「定错」，而是「**定完没人更新**」。半年后架构变了、预算还是老的，于是要么天天误报（被无视），要么永远不报（形同虚设）。对策：**把预算表和压测报告绑定**，每次大版本发布必须更新对账表。

**9.9 别忘了「慢」也可能是客户端的问题。** 本课是服务端视角，但 P99 差也可能来自 **DNS 解析慢、TLS 握手、客户端弱网、CDN 未命中**。排查顺序：先对比「**服务端 RT**」和「**端到端 RT**」，差值大就说明问题在网络或客户端。

## 10. 一句话总结

作者最后给了三句话，从事故一路收到方法论。

> **第一句：瓶颈在数据库，我们扩错了层。** 8 秒的 RT 是数据库拖出来的，加 10 台应用机只是把更多连接和重试砸向一个已经瘫痪的数据库——**扩容变成了攻击放大器**。

> **第二句：时间漏在四宗罪上，解法是四板斧。** 网络、计算、排队、IO；缓存换读、异步换实时、池化换建连接、批量换往返。**8.2 秒到 90 毫秒，每一刀都能对上账。**

> **第三句：防退化要靠预算和制度。** 高性能不是一次性的大扫除，而是**一套让退化无处藏身的制度**。

最后那句是全课的方法论收口：

> **快不是玄学，是算术。先测量，再定位，后优化。性能是设计出来的，不是碰运气碰出来的。**

作者还留了一句特别有这门课风格的祝福：

> 希望在下一次你碰到秒杀场景的时候，你的接口能够**稳如老狗**，用户能够**毫无感知**。
