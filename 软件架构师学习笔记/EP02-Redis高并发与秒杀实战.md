## 1. 第一章 真题：100 件库存卖出 130 件

### 1.1 题干

> 某电商公司在商品秒杀场景中，大量用户同时访问购买同一件商品。如果系统缺少并发控制，就会导致**超卖**或者**数据不一致**。

### 1.2 什么叫超卖

假设库存只有 **100 件**，最后卖出去 **130 件**。

多出来的 30 个用户，**钱付了，货拿不到**。接下来发生的事是可预期的：

```
库存 100 件
   ↓ 并发扣减没有控制
卖出 130 单（超卖 30 单）
   ↓
30 个用户付款成功但发不出货
   ↓
客服电话被打爆 → 平台赔钱 / 补偿 / 口碑受损
```

这是电商最经典的事故之一，也是很多公司**真踩过**的坑。

> 作者特意提醒：可以去搜一搜历史上真实发生过的超卖案例，看完会更有感觉。

### 1.3 三问（这三问要背下来，后面每一章都在为它们服务）

| 题号 | 题干 | 分值提示 |
|---|---|---|
| **问题 1** | 按**锁的行为**分类，列举**至少两种**不同类别的**悲观锁**，并分析差别 | 基础分 |
| **问题 2** | 从**应用层**和 **DBMS 层**给出**乐观锁**的实现方案，比较悲观锁与乐观锁的优缺点 | **全场分值最高**，且问了两层（实现 + 对比） |
| **问题 3** | 结合 **Redis 缓存**，列举**至少 3 个**高并发控制场景的**优化策略** | 综合分 |

### 1.4 三问其实指向同一个东西

```
问题1 问「锁」        ┐
问题2 问「乐观锁悲观锁」├──→ 都指向：并发控制到底怎么保证正确
问题3 问「Redis 缓存」 ┘        而 Redis 在里面到底干了什么
```

所以作者的建议是：**先把这三个问题记在脑子里，别急着找答案**，等把 Redis 摸清楚了，最后再回来一问一问填。

> 📌 **补充**：这道题的出题逻辑值得注意——它不考你背名词，而是给一个业务事故，然后**从数据库层（锁）→ 应用层（乐观锁）→ 缓存层（Redis）**三层依次追问。这正是架构师考试喜欢的「分层递进」结构。答题时也按这三层组织，阅卷老师一眼就能找到分。

## 2. 第二章 认识 Redis：一台跑得飞快的小仓库

> 这一章是给「从来没碰过 Redis」的人准备的。碰过的可以只读 2.5 之后的对比表和算账部分。

### 2.1 名字就是说明书：REmote DIctionary Server

Redis 全称 **Remote Dictionary Server**，中文叫**远程字典服务**。三个词，三件事，全都要记清楚：

| 词 | 中文 | 它到底在说什么 | 对你的实际影响 |
|---|---|---|---|
| **Remote** | 远程 | 它**不是你程序里的一个库**（不是一个 jar 包），而是**跑在另一台机器上的独立软件**，你的程序通过网络连它 | 要装、要连、**会挂**、要运维 |
| **DIctionary** | 字典 | 存东西的方式就是查字典：**给一个词，还你一段解释** | 心智模型极简：**key → value**，没有表结构，不用建库建表 |
| **Server** | 服务 | 它是一个**独立进程**，要启动、要占内存、也可能挂机 | 会满 → 要考虑淘汰策略；会崩 → 要考虑高可用 |

### 2.2 装上 Redis 之后，架构多了什么

```
【原来】
用户 → 你的程序 → MySQL

【加上 Redis 之后】
用户 → 你的程序 → Redis → MySQL
                      ↑
            多出来的一层"闸门"
```

作者的说法很形象：**相当于在你程序旁边多了一台跑得飞快、但容量不大的小仓库。**

程序会先去小仓库问一句「有没有能直接用的」，有就直接拿走；没有才去 MySQL 拿。

> **所以 Redis 不是把 MySQL 换掉，而是在它前面加了一道闸门。**

这句话是全课的地基，第 10 章还会再回到它。

### 2.3 Redis 是什么：一个超快的内存字典

一句话定义：**跑在内存里的键值数据库。**

什么叫键值？一本字典：你给它一个词（**key**），它立刻还你解释（**value**）。

你其实早就用过这个模型：

| 语言 | 长得像 Redis 的东西 |
|---|---|
| Java | `HashMap` |
| Python | `dict`（dictionary） |
| JavaScript | 对象 `{}` |

**本质上都是 map：给一个 key，立刻还一个 value。就这么简单。**

### 2.4 三条命令，先认得就行

```bash
SET  key value     # 存
GET  key           # 取
INCR key           # 自增 1
```

作者在这一页特别强调四个字：

> **INCR 是「天然原子」的。**

为什么强调？因为后面所有「防超卖」的方案，本质都是**把「读—判断—写」压缩成一个天然原子的动作**。而这四个字，就是 Redis 能承担这个角色的根本原因。（第 5 章的 Lua 脚本，是把「原子」从一条命令扩展到一段脚本。）

### 2.5 一个真实场景：手机验证码

这是最容易理解的例子：

```bash
# 用户点「获取验证码」，后端存一条，5 分钟后自动消失
SET code:13800008888 482913 EX 300

# 用户提交验证码，后端取出来比对
GET code:13800008888
```

**为什么这种数据不存 MySQL？**

| 原因 | 说明 |
|---|---|
| 生命周期极短 | 验证码一般只活 5 分钟 |
| 量极大 | 一天可能几百万条 |
| 写入慢 | 全写进数据库，既慢，又要定期集中清理 |

放到 Redis：**过期自动消失，一行 `EX 300` 就搞定。**

> 📌 **补充**：这类「短命、量大、只按 key 查」的数据，是缓存型存储的经典适用面。反过来，需要长期留存、需要范围查询、需要事务保证的数据，一步都不要往 Redis 里放（理由见 2.7）。

### 2.6 内存 vs 磁盘：图书馆的桌子与书柜

作者用图书馆打比方，这一段值得逐字记住，因为它解释了「为什么快」和「为什么不能替代数据库」两件事。

| | 内存（Redis） | 磁盘（MySQL） |
|---|---|---|
| 比喻 | **图书馆里你那张桌子** | **一排排书柜** |
| 速度 | 东西摊在桌上，伸手就拿到，快得不得了 | 站起来走过去、找到柜子、拉开柜门、翻半天 |
| 容量 | 桌子小，放不下全部 | 能放很久，容量大 |
| 断电 | **闭馆人一走，桌上东西全被清掉** | **闭馆了它也不会丢** |

**正确做法（也就是缓存的全部思想）：**

> 今天要用的、最常用的东西，先摊到桌子上；全部资料仍然放书柜。

```
用户请求 → Redis（桌面）
             ├─ 命中 → 直接返回，压根不碰数据库
             └─ 未命中 → MySQL 捞一次（书柜）→ 顺手写回 Redis → 下次就快了
```

### 2.7 Redis 天生的三个优势

作者列出三个「打勾」项，每一个后面都能对上一个具体的机制：

| 优势 | 通俗解释 | 它撑起了后面的什么 |
|---|---|---|
| **① 所有命令串行执行，天生不会相互打架** | 像**只有一个收银员的便利店**，所有顾客必须一个一个结账，永远不会出现两个人同时改同一个数字 | **这是所有并发方案的基础**（Lua、INCR、分布式锁都建立在它上面） |
| **② 数据全在内存** | 读写是**微秒级**的；一微秒什么概念？**一秒钟可以做 100 万次** | 挡住 10 万 QPS 的底气 |
| **③ 每个 key 都能设过期时间** | 到点自动清理 | 验证码、token、缓存自动失效 |

### 2.8 但它不是 MySQL 的替代品（三个硬理由）

| 理由 | 具体说明 |
|---|---|
| **只能按 key 查** | 你没法跟它说「把所有价格大于 100 的商品查出来」。这种**条件查询、join、排序**，只有 SQL 能做 |
| **容量小** | 内存比磁盘贵太多。一般几个 G 到几十个 G，**放不下几亿条业务数据** |
| **断电会丢** | 虽然也能持久化，但**那是兜底，不是它的本行** |

> **一句话记住：Redis 管热数据，数据库管真数据。**

### 2.9 正式对比表（考试/面试可直接用）

| 维度 | MySQL | Redis |
|---|---|---|
| **数据放哪儿** | 磁盘，**断电不丢** | 内存，**断电会丢** |
| **单机速度** | 毫秒级，约 **4000 QPS** | 微秒级，约 **10 万+ QPS** |
| **怎么查** | SQL，**任意条件**，支持 join、排序 | **只能按 key 取**，没有复杂查询 |
| **容量量级** | **TB 级** | **GB 级** |
| **秒杀中的角色** | **最终的真数据，兜底** | **热数据，阻挡流量的第一道闸门** |

📌 补充：4000 和 10 万都是**单机、简单查询**的量级参考值，不是标准答案。真实数字跟机器、索引、数据量、网络都有关系。但**「差一个数量级以上」这个结论是稳的**，考试写这个结论比写具体数字安全。

### 2.10 算一笔账：为什么必须加 Redis

作者用一个具体场景把数字变得有感觉：

> 双十一零点，一款手机 **10 万人同时点「立即抢购」**——在爆款秒杀里这是正常量级。

```
【直打 MySQL】
100,000 ÷ 4,000 = 25 秒排队

而且这还是"理想情况"：
数据库连接数一旦打满 → 响应越来越慢 → 最后直接拒绝服务
用户看到的是：页面一直转圈 → 报错

【先过 Redis】
100,000 ÷ 100,000 = 1 秒
而且绝大多数请求在 Redis 这层就被挡住了，压根没碰到数据库
```

**但作者说：重点不是数字，是这句话——**

> **秒杀开场那一瞬间，流量是平时的百倍以上。这些请求如果直接打到数据库，数据库不是「可能会挂」，是「必挂」。**

### 2.11 更可怕的不是秒杀挂了，是全站挂了

很多人以为「秒杀挂了就挂了，反正份额也抢完了」。完全不是。

**数据库是全站公用的。它一趴下：**

```
MySQL 被打挂
 ├── 商品列表打不开
 ├── 订单查不了
 ├── 个人中心转圈
 └── 连登录都登不进去
```

这就是 2015 年前后，很多电商在双十一凌晨真实发生过的场景——**一个秒杀活动，把整个 APP 拖垮。**

> **所以目标不是「让秒杀更快」，而是「让秒杀不要把你整个系统拖下水」。**
> 这才是 Redis 这道闸门存在的意义。加它不是因为时髦，是因为**没有它很多业务根本跑不起来**。

### 2.12 五种基础结构：五个形状不一样的箱子

作者说：**命令不用背，用时查文档。真正要记住的是「每种结构适合放什么数据」，也就是它们像什么。**

> 五个箱子：有的只能放一个东西，有的能放一张表，有的能排队，有的能自动去重，有的还会自动排序。**什么数据配什么箱子，这就是今天要带走的东西。**

#### ① string —— 一个标签配一个东西（超市储物柜）

- **像什么**：超市储物柜，一个号码一个格子，里面放一样东西。也是最像 map 的结构。
- **秒杀里的角色**：**缓存库存、做计数器**。用得最多，**八成以上的场景都是它**。

| 现实场景 | 怎么用 |
|---|---|
| 手机验证码 | `SET code:xxx 482913 EX 300` |
| 文章阅读量 / 视频播放数 | `INCR views:1001` —— 每点一次加一，**天然不会数错** |
| 登录令牌 | 两个小时不操作自动退出（靠过期时间） |
| **库存** | **秒杀场景的主角** |

#### ② hash —— 一个标签配一张表（一张名片）

- **像什么**：一张名片。上面有姓名、电话、公司、职位，**全都归在这一个人名下**。
- **结构**：1 个 key → 一组 field:value，像一个对象。
- **秒杀里的角色**：**存商品详情。**

```
key   = item:1001
field = title    → "XX 手机"
        price    → "4999"
        stock    → "100"
        image    → "https://..."
        status   → "on_sale"
```

一张 hash 就是一条完整的商品记录。用户点开详情页，**像一次取出整张名片**，不用查数据库。

**购物车也是 hash：**

```
key   = cart:user_9527
field = 商品ID   → value = 数量
```

加购只改一个字段，不用查库。

**❓ 那为什么不用 string 存商品？**

| 方案 | 改一个价格要做什么 |
|---|---|
| string（存整个 JSON） | 整个对象**取出来 → 改 → 整个存回去** |
| hash | **只改一个字段**，更省流量，也更安全 |

#### ③ list —— 一列队伍（两头都能进出）

- **像什么**：排队。左边能进人，右边能出人，反过来也行；**天然有序**。
- **秒杀里的角色**：**订单排队、简单的消息队列**。

| 场景 | 做法 |
|---|---|
| 最新 10 条评论 | 新评论从左边进，显示时从左边取 10 条，**永远保留最新的** |
| 任务队列 | 一边往队尾塞任务，另一边工作进程从队头取任务执行 |
| 操作日志 | 只留最近 1000 条，超了自动踢掉最老的 |

#### ④ set —— 一个不重复的名单（无序、自动去重）

- **像什么**：数学里的集合。往里面塞 10 个「张三」，里面也只有 **1 个**张三。
- **秒杀里的角色**：**记录「谁已经抢过了」。这是防止一个人抢 10 次的那道锁。**

| 场景 | 做法 |
|---|---|
| **秒杀已购名单** | 写多少遍都只有一条 → **天然幂等** |
| 文章点赞 | 同一个人点 100 次也只算一个赞 |
| 共同好友 | 两个 set 求**交集**，一行命令搞定 |

#### ⑤ zset —— 会自动排序的名单（带分数）

- **像什么**：一个随时都在重新排队的排行榜。每个人身上贴一个分数，**谁分高谁排前面，你不用管，它自己就排好了**。
- **秒杀里的角色**：排行榜、**延迟队列**、**限流窗口**。

| 场景 | 做法 |
|---|---|
| 微博热搜 / 游戏积分榜 | 分数 = 热度，直接按分数取前 N |
| **延迟队列** | **把「什么时候该执行」的时间戳当分数存进去**，到点取出来执行 → 订单 15 分钟未支付自动取消 |
| **限流窗口** | 记住「最近 60 秒内这个 IP 请求了几次」，超了就拒绝 |

#### 五种结构一页对照

| 类型 | 比喻 | 结构 | 秒杀中的用途 | 现实场景 |
|---|---|---|---|---|
| **string** | 储物柜 | 1 key → 1 value | **库存、计数器** | 验证码、播放量、token |
| **hash** | 名片 | 1 key → 多 field | **商品详情** | 商品页、购物车 |
| **list** | 队伍 | 有序、两头进出 | 订单排队、简单队列 | 最新评论、任务队列、日志 |
| **set** | 不重复名单 | 无序、去重 | **已购名单（防重复抢）** | 点赞、共同好友 |
| **zset** | 排行榜 | 带分数自动排序 | 排行榜、延迟队列、限流 | 热搜、超时取消、IP 限流 |

> 口诀（沿用上一集的记法）：**单个值用 string，对象用 hash，排队用 list，去重用 set，排名用 zset。**

### 2.13 三个扩展结构（有个印象就行）

| 结构 | 干什么 | 一句话记忆 |
|---|---|---|
| **bitmap** | 签到打卡 | 一个人一天一个 bit，一年 365 个 bit |
| **stream** | 消息队列 | 比 list 更"专业"的队列，支持消费组和 ACK |
| **HyperLogLog** | 统计 UV（今天有多少不同的人来过） | **12 KB 就能估算上亿的去重人数**，代价是**有一点误差** |

## 3. 第三章 八个技术点：每个技术背后都是一个具体的疼

作者给了一张「技术地图」，明确说：**今天只讲这 8 个，别的先不碰。我不希望大家去背命令。**

表格三列，**最右边一列才是重点**：

|---|---|---|---|
| 1 | **原子计数** | `DECR` / `INCR` | 库存预扣减，**一步到位不超卖** |

## 4. 第四章 分布式锁：上厕所要先锁门

### 4.1 超卖的最小复现：就两行代码

最朴素的写法：

```
① GET  stock:1001   → 读到 1
② SET  stock:1001 0 → 扣减
```

**问题在哪？这两步之间有空隙。**

```
t=0  ┌─ 请求 A：GET stock → 1
t=1  │  ┌─ 请求 B：GET stock → 1        ← B 在 A 还没写回时就读了
t=2  └─ │  A: SET stock = 0
t=3     └─ B: SET stock = 0              ← 卖了 2 件，库存只减 1

结果：库存 1，卖出 2 单 → 超卖
```

如果两个请求都读到 1，都去扣，最后库存变成 **-1**。**这就是超卖的最小复现。**

### 4.2 所有并发问题的根源，是同一句话

> **读和写之间，被别人插了一脚。**

这句话要背下来。后面所有方案（锁、Lua、CAS、条件更新），**瞄准的都是这一个空隙**。

本能的反应是：**加锁。**

### 4.3 厕所锁门：锁这件事本身也得是原子的

作者用的比喻（原文保留）：

> 就像**上厕所要锁门**：我进去先锁上，别人只能在外面等。

**但真正的问题是——加锁这件事本身，怎么保证是原子的？**

如果加锁也要两步（先写 key，再设过期），那**加锁本身也会出问题**。

**Redis 给出的答案是一条命令：**

```bash
SET lock:stock:1001 <requestId> NX EX 10
```

| 参数 | 含义 | 保证了什么 |
|---|---|---|
| **NX** | Not eXists，**键不存在才设置** | **互斥**：只有第一个人能设置成功；第二个人来的时候键已存在，直接失败 → **相当于锁门** |
| **EX** | EXpire，**自动过期** | **防死锁**：持有锁的进程崩了、或忘了释放，锁会自动到期，不会把整条业务线卡死 |

关于 EX，作者又补了一个比喻：

> 就像这扇厕所门上装了一个**自动弹开的装置**，防止里面有人晕倒、把门锁死，外面的人进不去。
> （当然现实中的厕所没有这个装置，只是举个例子。）

### 4.4 Java 代码：加锁就一行

```java
String requestId = UUID.randomUUID().toString();   // 每个请求一个唯一 ID

Boolean ok = redis.opsForValue()
        .setIfAbsent("lock:stock:1001", requestId, 10, TimeUnit.SECONDS);

if (Boolean.FALSE.equals(ok)) {
    return Result.fail("手慢了，请稍后再试");   // 没抢到锁
}
try {
    doSeckillBusiness();                        // 真正的扣库存、建订单
} finally {
    unlock("lock:stock:1001", requestId);       // ⚠️ 一定写在 finally 里
}
```

**注意：`value` 不是随便填的，一般填一个「请求唯一 ID」。** 原因在下一节。

### 4.5 解锁的坑：直接 DEL 会删掉别人的锁

**为什么解锁必须用 Lua？** 因为解锁真正要做的不是「删掉」，而是「**先判断这把锁是不是我的，是才删**」。

**如果直接 `DEL`：**

```
t=0s   A 拿到锁，过期时间 10s
       A 的业务卡住了（GC / 慢查询 / 网络抖动）
t=10s  锁自动过期，B 拿到新锁
t=12s  A 的业务终于跑完，执行 DEL lock:stock:1001
       ↑ A 删掉的是 B 的锁！       ← 这就是「误删」
t=12s+ B 以为自己还持有锁，实际上锁已经没了
       → C 也能拿到锁 → 互斥彻底失效
```

作者的原话版比喻：

> 你**超时出厕所**了，另一个人进去锁上了门，结果你现在回头又把门给打开了——是不是就尴尬了？

✅ **正确写法（Lua）**：

```lua
-- KEYS[1] = 锁的 key，ARGV[1] = 我自己的 requestId
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```

### 4.6 生产上别手写：用 Redisson

作者的注释很直接：**生产环境更推荐使用 Redisson。**

| Redisson 帮你解决的问题 | 说明 |
|---|---|
| **可重入** | 同一线程可以重复加同一把锁，不会自己把自己锁死 |
| **看门狗（Watchdog）自动续期** | 手写锁最容易错的就是「业务还没跑完，锁就过期了」。看门狗专门治这个 |

> 📌 **补充**：手写 `SET NX EX` 的死结是——**你没法预知业务要跑多久**。设 10 秒，业务跑 12 秒锁就提前释放；设 60 秒，程序崩了别人要干等 60 秒。看门狗的做法是：不指定过期时间时默认 30 秒，后台每 10 秒续一次，**只要进程活着锁就一直有效，进程死了续期停止，锁 30 秒后自然释放。**

### 4.7 分布式锁在真实系统里的其他四个岗位

| 用途 | 为什么需要锁 |
|---|---|
| **定时任务防重复执行** | 多台机器都配了同一个 cron，只允许一台真跑 |
| **券码 / 红包发放** | 防止同一张券被发给两个人 |
| **缓存重建** | 热点 key 失效时，**只放一个请求**回源数据库重建，其他请求等结果 |
| **同一商品的库存修改** | 本课主线 |

## 5. 第五章 Lua 脚本：一个脚本，三件事，一次原子完成

### 5.1 为什么 Lua 是防超卖的「终极答案」

左边三个大字（作者原文）：**一个脚本，三件事，一次原子完成。**

**为什么能原子？**

> 这个脚本在 Redis 里是**整体执行**的，中间**不会插入任何其他命令**。
> 你可以把它理解成：Redis 把这段脚本当成「一件事」，**这件事做完之前，谁来都不理会**。

所以在脚本内部，「查库存 → 扣库存 → 记录用户」这三步**永远不会被打断**。

```
普通写法（3 条命令）：
GET ──空隙── DECR ──空隙── SADD        ← 每一步之间都可能被插一脚

Lua 脚本（1 次执行）：
┌────────────────────────────────┐
│ GET → 判断 → DECR → SADD → 返回 │   ← 中间谁也别想进来
└────────────────────────────────┘
```

上一章说的「读和写之间被别人插一脚」的漏洞，在这里**被彻底堵死**。

### 5.2 脚本本体：有效代码就四五行

```lua
-- KEYS[1] = 库存 key      （例：stock:sku:1001）
-- KEYS[2] = 已购集合 key  （例：bought:sku:1001）
-- ARGV[1] = 用户 ID

-- ① 幂等拦截：这个用户是不是已经抢过了？
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -1                      -- 重复下单
end

-- ② 判断库存
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock <= 0 then
    return 0                       -- 售罄
end

-- ③ 扣库存 + 记录已购
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1                           -- 抢购成功
```

**干了三件事：**

| 步骤 | 命令 | 作用 |
|---|---|---|
| ① | `SISMEMBER` | 检查用户是否已在已购集合 → **幂等拦截，防重复下单**（这就是第 2 章讲的 **set** 结构在实战里的用法） |
| ② | `GET` + 判断 `<= 0` | 库存不足 → 返回 0，代表售罄 |
| ③ | `DECR` + `SADD` | 扣库存、把用户加进已购集合 → 返回 1 |

### 5.3 三个返回码 = 三种业务结果 = 三句前端提示

| 返回码 | 含义 | 业务动作 | 前端提示 |
|---|---|---|---|
| **1** | 抢购成功 | **进入下单流程** | 「抢到了，请尽快支付」 |
| **0** | 库存不足 | **直接拒绝** | 「已售罄」 |
| **-1** | 重复下单 | **幂等拦截** | 「您已参与过本次抢购」 |

> 作者特意强调：**三个返回码对应三种前端提示语，一一对应，这样比较干净。**
> 📌 **补充**：这种「用返回值表达业务结果」的设计，比抛异常干净得多——异常只应该表示"系统出错"，业务上的「没抢到」是**正常结果**，不是错误。

### 5.4 一个脚本解决三个问题

```
超卖     → 判断和扣减在同一个原子块里，中间没人能插进来
少卖     → 扣减成功才记录，不会出现"扣了没记"或"记了没扣"
重复下单 → SISMEMBER + SADD 天然去重，一人一单
```

### 5.5 回到真题：为什么现在不会超卖了

作者把镜头拉回那道题，做了一次「推演」：

```
两个请求同时进来，Redis 串行执行：

请求 A：查库存 = 1 → 扣减 → 库存变 0 → 返回 1（成功）
请求 B：查库存 = 0 → 直接返回 0（售罄）

超卖？根本不可能发生。
```

> **这就是答案。** 也就是说，真题第三问「结合 Redis 列举至少 3 个高并发优化策略」，**你现在已经能答出第一条了。**

### 5.6 Lua 的代价：它会阻塞 Redis

**问：Lua 脚本会不会阻塞 Redis？**

**答：会。** 因为脚本原子执行，**执行期间别的命令都得排队**。

所以两条纪律：

| 纪律 | 原因 |
|---|---|
| **脚本要短、要快** | 微秒级返回没问题，本课这段四五行完全 OK |
| **不能带大循环** | 你要是写个脚本去遍历 10 万个 key，**那就是比较严重的生产事故** |

> 📌 **补充**：Redis 有个 `lua-time-limit`（默认 5 秒），超时后 Redis 会开始对其他命令返回 `BUSY` 错误，但**它不会自动杀掉脚本**（因为会破坏原子性），只能 `SCRIPT KILL`（脚本没写过数据时）或 `SHUTDOWN NOSAVE`。所以「脚本要短」不是风格建议，是**运维红线**。

## 6. 第六章 WATCH 乐观锁与 Stream 削峰：别改错，别挤爆

作者把这两样东西合在一页讲，因为它们合起来正好覆盖秒杀的两个侧面。**先记住这一句：**

> **WATCH 管「别改错」，Stream 管「别挤爆」。**

### 6.1 WATCH：不加锁的乐观锁

还是用上厕所的比喻，作者做了对照：

| | 悲观锁 | 乐观锁（WATCH） |
|---|---|---|
| 厕所版 | **我进去之前先锁门**，别人只能在外面等 | **我不锁门，谁想进谁进**；出来的时候**核对一下**：中途没人动过就没事，**有人动过就这次不算、重来一次** |

### 6.2 代码：WATCH → MULTI → EXEC

```java
jedis.watch("stock:1001");                       // ① 盯住这个 key

int stock = Integer.parseInt(jedis.get("stock:1001"));
if (stock <= 0) {
    jedis.unwatch();
    return 0;                                    // 售罄
}

Transaction tx = jedis.multi();                  // ② 开事务
tx.decrBy("stock:1001", 1);                      //    扣减（此时不执行，先入队）

List<Object> result = tx.exec();                 // ③ 提交

if (result == null) {                            // ⚠️ 返回 null
    // 期间被别人改过 → 本次失败
    // 自己决定：重试，还是放弃
}
```

**关键点：`EXEC` 返回 `null`，说明 WATCH 的 key 在 `WATCH` 之后被改过，本次事务失败。**

这就是「**提交时才校验**」——它不拦着你读，只在最后结算的时候核对一次。

### 6.3 这是真题第二问在缓存层的落点

作者点明了一件事：**这套乐观锁思想，正是真题第二问「乐观锁的实现方案」在缓存层的体现。**

| 层次 | 乐观锁的实现 | 校验依据 |
|---|---|---|
| 应用层（Java） | 版本号 version 字段 | `UPDATE ... WHERE version = 读到的那一版` |
| DBMS 层 | 条件更新（CAS 语义） | `UPDATE ... WHERE number > 0` |
| **缓存层（Redis）** | **WATCH + MULTI + EXEC** | **EXEC 返回 null** |

三者本质相同：**都是「先干事，提交时才发现冲突，然后失败重来」。**（细节见第 7 章 Q2。）

### 6.4 Stream：抢到了，也别急着写数据库

**这一半很重要，很多人第一次听会愣一下：**

> **Redis 里扣减成功，只是「抢到名额」而已，不等于这个订单已经生成了。**
>
> **真正的下单请求，我们把它扔到队列里，让后台慢慢地消费、慢慢地落库。**

```
【没有队列】
1 万请求/秒 ──────────────────→ MySQL（被打死）

【有队列】
1 万请求/秒 → Redis 扣减 → 队列 ▓▓▓▓▓▓▓▓▓▓▓ → 后台 200/秒 → MySQL（很平静）
```

作者的说法：

> 本来一秒钟 1 万个请求砸进来，现在变成后台每秒稳定处理 200 个。
> **就像景区门口一样，我们不让 1 万个人一起冲进去，而是排队分批放行。**

**代码就两行：**

```java
Map<String, String> msg = new HashMap<>();
msg.put("skuId",  "1001");
msg.put("userId", "u_9527");

redis.opsForStream().add("order:stream", msg);   // 扔进队列，剩下的交给消费者
```

> 作者原话：**「就这么简单，但它是整个架构能不能扛住的关键。」**

### 6.5 为什么这一步不能省

| 如果省掉队列 | 后果 |
|---|---|
| Redis 扣减成功就直接写库 | 扣减是 10 万 QPS 级别的动作，写库是 4000 QPS 级别的动作 → **队列消失，等于没削峰** |
| 落库失败没有补偿 | Redis 显示卖掉了，数据库没有订单 → **数据不一致**（第 10 章的核心问题） |

> 📌 **补充**：队列削峰带来一个新问题——**「Redis 扣了，但落库失败」**。生产上的标准解法是：①队列要能持久化 + 支持 ACK 重投；②落库失败进「死信/补偿表」；③以数据库为准做**定时对账回补**。这三条在本课第 10 章会被一句话点破。

## 7. 第七章 回答案题：三问三答（考试直接可用）

### 7.1 问题 1：按行为分类，列出至少两种悲观锁并分析差别

#### 先解释什么叫「悲观」

> **悲观锁的思想：假设冲突一定会发生，所以读数据之前就先把数据锁上，别的事务只能排队等。**
>
> 就像你去办事儿，**宁可先在门口排号，也不愿意冲进去发现办不了。**

#### 分类：有两种分法，但题目问的是「行为」

| 分类维度 | 类别 |
|---|---|
| 按**粒度** | **表级锁**、**行级锁** |
| 按**行为** | **共享锁（S 锁）**、**排他锁（X 锁）** |

> **题目问的是「行为」，所以主答共享锁 / 排他锁。**
> **但两种都答上，稳赚不赔。关键是你每一类都要把差别说清楚。**

#### 四行表格（考试就写这个）

| 类别 | 锁住什么 | 优点 | 缺点 | 比喻 |
|---|---|---|---|---|
| **表级锁** | **整张表** | 开销小、实现简单 | **并发度最低** | 图书馆要整理一本书，干脆**把整个阅览室关了**——是快，但所有人都得等 |
| **行级锁** | **被访问的那些行** | 并发度高、冲突概率小 | **加锁开销大**，还要小心**死锁** | 只把**那一本书**拿走，别人照样看其他的书 |
| **共享锁（S 锁）** | 读锁 | **多个事务可以同时读** | **谁都不能写** | 大家都能看，但没人能改 |
| **排他锁（X 锁）** | 写锁 | 独占，最安全 | **读写全互斥**，互斥性最强，**也最容易阻塞** | 我一个人站着，其他谁也不能碰 |

> 📌 **补充**：S 锁和 X 锁的相容矩阵——S 与 S 相容（可并发读），S 与 X 不相容，X 与 X 不相容。InnoDB 里的 `SELECT ... LOCK IN SHARE MODE` 加 S 锁，`SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` 加 X 锁。答题时补这一句，显得你真的用过。

### 7.2 问题 2：乐观锁的实现（应用层 + DBMS 层）与悲观/乐观对比

> 作者提醒：**这题分值全场最高，而且它问了两层——第一层「怎么实现」（还是两个层面），第二层「怎么比」。很多人只答了对比、忘了实现，一半分数就没了。**

#### 第一层 A：应用层实现 —— 版本号

```sql
-- ① 读的时候，把 version 一起读出来
SELECT id, stock, version FROM stock WHERE id = 1001;
-- 假设读到 stock = 100, version = 3

-- ② 更新的时候带上条件，同时 version 自己 +1
UPDATE stock
   SET stock = stock - 1,
       version = version + 1
 WHERE id = 1001
   AND version = 3;
```

**如果期间被别人改过，版本对不上，这条 UPDATE 的「影响行数」就是 0。**

作者的生活化比喻：

> 就像你去取快递，**报手机号后 4 位 + 取件码**。如果这期间有人把件取走了，取件码就失效了，系统直接告诉你「这个码已经用过了」。
> **版本号就相当于那个取件码。**

#### 第一层 B：DBMS 层实现 —— 条件更新（CAS 语义）

```sql
UPDATE stock
   SET number = number - 1
 WHERE sku_id = 1001
   AND number > 0;
```

**核心思想：把「判断」塞进 `WHERE` 里，让数据库自己去保证原子性。**

> 注意 `number > 0` 这个条件：**就算前面所有环节全出问题，这一句话也能保证最后不会被扣成负数。**
> 这就是我们说的「**最后一道兜底**」。

#### 两种实现本质是同一件事

| 实现 | 怎么表达「没被改过」 | 失败信号 |
|---|---|---|
| 应用层版本号 | `AND version = 读到的版本` | **影响行数 = 0** |
| DBMS 条件更新 | `AND number > 0`（把业务约束写进条件） | **影响行数 = 0** |

> **失败之后是「重试」还是「直接告诉用户抢完了」——那是业务决定的，不是技术决定的。**

#### 第二层：六维对比表（考试按这个维度答）

| 维度 | 悲观锁 | 乐观锁 |
|---|---|---|
| **加锁时机** | **读之前先锁** | **提交时才校验** |
| **适用场景** | 写多读少、**冲突频繁** | 读多写少、**冲突较少** |
| **并发性能** | 阻塞等待，**吞吐量偏低** | 不阻塞，失败重试，**吞吐量高** |
| **数据一致性** | **强一致**（锁住了就没人能改） | **最终一致**（靠失败重试收敛） |
| **主要风险** | **死锁、锁等待** | **冲突太激烈 → 重试过多 → 白耗 CPU** |
| **典型实现** | InnoDB **行锁** | **版本号、CAS、Redis 的 WATCH** |

**一句话总结（作者原话）：**

> **读多写少用乐观锁，写多读少用悲观锁。**

### 7.3 问题 3：结合 Redis，列举至少 3 个高并发优化策略

题目要求「至少 3 个」，作者说：**那我们就答出完整的三组。**

#### 先看漏斗：请求从上游到下游，一层一层被削掉

```
                        10 万请求
                           │
                  ┌────────▼────────┐
                  │ ① 网关限流       │  挡住刷单脚本 / 恶意流量
                  └────────┬────────┘
                           │ 8 万
                  ┌────────▼────────┐
                  │ ② 热点数据预加载 │  挡掉 9 成读请求（商品详情、库存）
                  └────────┬────────┘
                           │ 8000
                  ┌────────▼────────┐
                  │ ③ 库存预扣减     │  原子操作，防超卖
                  └────────┬────────┘
                           │ 1000（真正抢到的）
                  ┌────────▼────────┐
                  │ ④ 分布式锁       │  同一商品互斥（需要时）
                  └────────┬────────┘
                           │
                  ┌────────▼────────┐
                  │ ⑤ 消息队列削峰   │  拉平瞬时洪峰
                  └────────┬────────┘
                           │ 200/秒
                  ┌────────▼────────┐
                  │ ⑥ 数据库条件更新 │  最后兜底
                  └─────────────────┘
```

#### 归成三条主线来答（这就是标准答法）

| 主线 | 手段 | 解决了什么问题 |
|---|---|---|
| **① 缓存层** | 商品详情、库存**提前加载**到 Redis | **把流量挡在数据库前面**。绝大多数请求在缓存这一层就返回了，数据库根本没被碰到 |
| **② 操作层** | **原子命令**（`DECR`）、**Lua 脚本**、**分布式锁** | **让扣减本身不出错**。把「读—判断—写」合成一个**不会被打断**的动作 |
| **③ 架构层** | **消息队列削峰填谷**、**计数器 / zset 限流**、**哨兵或集群避免 Redis 单点故障** | **削峰、限流、保高可用** |

> **答题格式建议（作者强调）：每一条答案都写成「手段 + 解决了什么问题」。这样一眼就能看到得分点。**

#### 写法示例（可直接抄）

> 1. **缓存层**：将商品详情与库存预热到 Redis，读请求在缓存层直接返回，把绝大部分流量拦截在数据库之前，降低数据库压力。
> 2. **操作层**：使用 Redis 原子命令 `DECR` 或 Lua 脚本，将「判断库存 + 扣减 + 记录用户」合并为一次原子执行，从根本上消除「读和写之间被插入」的窗口，防止超卖与重复下单。
> 3. **架构层**：通过消息队列（Stream/List）把瞬时下单请求异步化，削峰填谷；通过计数器或 zset 滑动窗口做接口限流，拦截脚本刷单；通过哨兵/集群避免 Redis 单点故障导致缓存层整体失效。

## 9. 第九章 缓存三大坑：穿透、击穿、雪崩

> 作者说这是「新手比较容易踩的坑」。三个名字极容易混，先看这张总表。

| | 数据存不存在 | 触发原因 | 打到哪里 | 后果 |
|---|---|---|---|---|
| **穿透** | **不存在** | 查一个**数据库里也没有**的 key | 每次都穿到 DB | 被脚本刷，**能把数据库打穿** |
| **击穿** | **存在** | **某一个热点 key 刚好过期** | 那一瞬间几万请求同时冲 DB | 单点瞬时不均 |
| **雪崩** | 存在 | **一大批 key 同一秒过期**（或 Redis 整个挂了） | 大面积同时冲 DB | **相当于击穿的集体版** |

### 9.1 缓存穿透：查一个根本不存在的东西

**定义：你查一个根本不存在的数据，缓存永远不命中，每次请求都穿到数据库去了。**

**典型攻击场景：**

> 有人拿一个**不存在的商品 ID 疯狂地刷**。他**不用登录**，拿个脚本跑就行。
> 这类攻击阴的地方在于：**成本极低，但能把你的数据库打穿。**

**两个解法：**

| 方案 | 做法 | 要点 |
|---|---|---|
| **缓存空值** | 数据库也没查到 → 往 Redis 里写一个「空」 | **必须设一个短过期时间**（比如 60 秒），让「没有这个商品」这件事也能进缓存 |
| **布隆过滤器** | 请求进来先过布隆过滤器 | 说不存在就一定不存在，直接挡掉，**连 Redis 都不查** |

> 📌 **补充**：布隆过滤器有两个必须知道的限制——① **有误判率**：说「存在」可能是假阳性（概率很低）；② **标准布隆不支持删除**。所以它一般放在最前面做「粗筛」，不能当唯一判据。

### 9.2 缓存击穿：一个热点 key 刚好过期

**定义：某一个热点 key 刚好过期了，那一瞬间几万个请求同时冲向数据库。**

**和穿透的区别（作者特意点出，这是最容易答错的地方）：**

> **穿透是「查不存在的数据」；击穿是「数据存在，但热点 key 过期了」。**

```
t=0      缓存里有 item:1001，QPS 5 万全部命中，DB 零压力
t=1800   过期时间到了，key 消失
t=1800+  5 万个请求同时未命中 → 5 万个请求同时打向 DB → DB 瞬间被打穿
t=1801   第一个请求回源成功，写回缓存 → 恢复正常
```

**解法（📌 补充，视频只点了名）**：

| 方案 | 做法 |
|---|---|
| **互斥重建** | 只放一个请求回源（用分布式锁），其他请求等结果 → 正好用上第 4 章的锁 |
| **逻辑过期** | 不设 TTL，value 里存一个「逻辑过期时间」，过期后异步重建，读到的仍是旧值 |
| **热点永不过期** | 后台定时刷新 |

### 9.3 缓存雪崩：一大批 key 在同一秒过期

**定义：一大批 key 在同一秒过期；或者更狠——整个 Redis 挂掉。**

**为什么会有「同一秒过期」？**

> 因为很多人写缓存的时候，**过期时间统一设的是 30 分钟**。那么 30 分钟前的那一批 key，就**全在同一秒失效**了。
> 这就是「**缓存击穿的集体版**」。

**解法：**

| 方案 | 做法 |
|---|---|
| **过期时间加随机值打散** | 30 分钟 ± 5 分钟随机浮动 |
| **本地缓存兜底** | Redis 挂了，本地还有一层（Caffeine 之类） |
| **哨兵 / 集群** | 避免 Redis 单点故障 |

## 10. 第十章 最关键的一句认知：缓存可以丢，账不能错

> 作者说：**「这是今天比较关键的一句认知。」**

### 10.1 分工：Redis 只做预扣，数据库才是真数据源

```
Redis  = 预扣（抢名额）
MySQL  = 真正的数据源（账本）
```

**当两者不一致时，一律以数据库为准，去做对账回补。**

```
❌ 错误方向：拿 Redis 去修 MySQL
✅ 正确方向：拿 MySQL 去修 Redis
```

作者的原话：

> Redis 崩了、数据对不上了，没关系——**MySQL 里的账是真的**，我们拿数据库去修 Redis，而不是反过来。
> 这一点想通了，整个系统的信念就建立起来了：**缓存是可以丢的，但是账是不能错的。**

### 10.2 最重要的一句：Redis 不解决并发

> **Redis 不解决并发，它只是把并发挡在了数据库前面。**

怎么理解？

```
并发不会消失。
一秒钟 1 万个请求，就是一秒钟 1 万个请求。
Redis 不会把这些请求变少。
它做的是：把它们拦下来、排队、过滤，
让数据库只看到它承受得住的那一部分。
```

**所以以后你设计高并发系统的时候，要问自己的不是：**

> ❌「怎么让 Redis 更快？」

**而是：**

> ✅「**我把什么，挡在了哪一层？**」

作者说：**「这个我觉得是比较重要的。」**

> 📌 **补充**：这句话其实可以推广成一条通用的架构原则——**高并发系统的设计，本质是「分层拦截 + 逐层降级」**。每一层只做它最擅长的那件事，并且假设它下面那层一定会挂。Redis 挡不住的时候要有本地缓存，本地缓存挡不住要有网关限流，网关挡不住要有降级页面。**没有任何一层是"最后防线"，除了数据库的正确性。**

## 11. 速查卡：命令 / 场景 / 返回码一页查完

### 11.1 五种结构 + 秒杀用法

| 需求 | 类型 | 命令 |
|---|---|---|
| 缓存库存 / 计数器 | string | `SET stock:sku:1001 100`、`DECR stock:sku:1001`、`INCR views:1001` |
| 验证码 / token | string | `SET code:138xxx 482913 EX 300`、`GET code:138xxx` |
| 商品详情 | hash | `HSET item:1001 title "XX"`、`HGET item:1001 price`、`HINCRBY item:1001 stock -1` |
| 购物车 | hash | `HINCRBY cart:u_9527 sku_1001 1` |
| 订单排队 / 简单队列 | list | `LPUSH order:queue x`、`RPOP order:queue`、`BRPOP order:queue 0` |
| 已购名单（防重复） | set | `SADD bought:sku:1001 u_9527`、`SISMEMBER bought:sku:1001 u_9527` |
| 排行榜 / 延迟队列 / 限流 | zset | `ZADD rank 99 u1`、`ZREVRANGE rank 0 9`、`ZRANGEBYSCORE delay 0 <now>` |
| 签到 | bitmap | `SETBIT sign:u1 20261115 1`、`BITCOUNT sign:u1` |
| 可靠队列 | stream | `XADD order:stream * skuId 1001 userId u_9527`、`XREADGROUP`、`XACK` |
| UV 统计 | HyperLogLog | `PFADD uv:20261115 u1`、`PFCOUNT uv:20261115` |

### 11.2 分布式锁三件套

| 步骤 | 正确写法 | 为什么 |
|---|---|---|
| 加锁 | `SET lock:xxx <requestId> NX EX 10`（**必须一条命令**） | 两条命令之间有间隙 → 可能死锁 |
| 解锁 | Lua：`GET` 比对 `== ARGV[1]` 才 `DEL` | 直接 `DEL` 会误删别人的锁 |
| 生产 | Redisson `tryLock(等待时间)` + 看门狗 | 可重入 + 自动续期 |

### 11.3 秒杀 Lua 脚本的三个返回码

| 返回码 | 含义 | 业务动作 |
|---|---|---|
| **1** | 成功 | 进入下单流程（写订单、发 MQ） |
| **0** | 售罄 | 直接拒绝 |
| **-1** | 重复下单 | 幂等拦截 |

### 11.4 WATCH 乐观锁

| 步骤 | 命令 | 说明 |
|---|---|---|
| 监视 | `WATCH stock:1001` | 盯住这个 key |
| 读 | `GET stock:1001` | 读到值 |
| 开事务 | `MULTI` | 后续命令入队，不立即执行 |
| 入队 | `DECRBY stock:1001 1` | |
| 提交 | `EXEC` | **返回 `null` = 期间被改过 = 失败** |

### 11.5 三大缓存问题的解法对照

| 问题 | 触发 | 解法 |
|---|---|---|
| **穿透** | 查不存在的数据 | 缓存空值（短 TTL）+ 布隆过滤器 |
| **击穿** | 热点 key 过期 | 互斥重建（分布式锁）、逻辑过期、热点永不过期 |
| **雪崩** | 大批 key 同时过期 / Redis 挂 | 过期时间 + 随机值打散、本地缓存兜底、哨兵/集群 |

### 11.6 答题模板（三问速记）

| 问题 | 关键词 |
|---|---|
| Q1 悲观锁分类 | **按粒度**：表级/行级；**按行为**：共享锁 S / 排他锁 X；每类说清「锁什么 + 优缺点 + 并发度」 |
| Q2 乐观锁 | **实现**：应用层版本号 + DBMS 条件更新（CAS）；**对比**：加锁时机/场景/性能/一致性/风险/实现 六维；**结论**：读多写少乐观，写多读少悲观 |
| Q3 Redis 策略 | **缓存层**（预热拦截）+ **操作层**（原子/Lua/锁）+ **架构层**（削峰/限流/高可用）；每条写成「手段 + 解决什么问题」 |

## 12. 自测题（含答案）

先自己答，再看答案。

<details>
<summary><b>Q1：库存只有 1 件，两个请求同时进来，为什么最后会变成 -1？</b></summary>

因为「`GET` 查库存」和「`SET` 扣减」是**两条命令，中间有空隙**。两个请求都在对方写回之前读到了库存 1，于是都执行了扣减。

**根源一句话：读和写之间，被别人插了一脚。**

解法：把「读—判断—写」压缩成一个**原子动作**（`DECR`、Lua 脚本、`SET NX` 锁），空隙消失。
</details>

<details>
<summary><b>Q2：加锁为什么必须 <code>SET k v NX EX 10</code>，不能先 SET 再 EXPIRE？</b></summary>

两条命令之间存在间隙。如果程序在 `SET` 之后、`EXPIRE` 之前崩溃或断电，这把锁就**永远没有过期时间 → 死锁**，整条业务线被卡死。

`SET ... NX EX` 是**单条命令**，Redis 保证原子执行，没有间隙。
</details>

<details>
<summary><b>Q3：解锁为什么一定要用 Lua？直接把 key 删掉不行吗？</b></summary>

不行。因为存在这个时间线：

```
A 拿到锁（10s）→ A 业务卡住 → 锁自动过期 → B 拿到锁 → A 业务跑完，执行 DEL
                                                        ↑ 删掉的是 B 的锁
```

这叫**误删**。正确做法是「先比对 value 是不是我自己的 requestId，是才删」——而这需要 `GET` + `DEL` 两步，又有间隙，所以必须用 Lua 把两步合成一次原子执行。
</details>

<details>
<summary><b>Q4：Lua 脚本是事务吗？出错会回滚吗？</b></summary>

**不是事务，不会回滚。**

Lua 保证的是**「不被打断」**（原子性 = 不可分割），**不保证「出错自动撤销」**。所以脚本必须写成「先判断，后执行」，把可能出错的部分放在最前面。

**代价**：脚本执行期间其他命令全部排队 → 脚本必须短、快，不能带大循环。
</details>

<details>
<summary><b>Q5：WATCH 乐观锁里，EXEC 返回 null 是什么意思？</b></summary>

表示 `WATCH` 之后、`EXEC` 之前，被监视的 key **被别人改过**，本次事务**没有执行**（失败）。

接下来是重试还是放弃，由**业务**决定，不是技术决定。
</details>

<details>
<summary><b>Q6：抢到了为什么不能立刻写数据库？</b></summary>

因为 Redis 扣减是 10 万 QPS 级别的动作，MySQL 写库是 4000 QPS 级别的动作。**如果扣减成功就直接写库，等于没有削峰**，1 万请求/秒照样能把数据库打死。

正确做法：扣减成功只是「抢到名额」，真正的下单请求**扔进消息队列**，后台消费者以稳定速率（比如 200/秒）慢慢落库。
</details>

<details>
<summary><b>Q7：悲观锁和乐观锁，一句话怎么选？</b></summary>

**读多写少用乐观锁，写多读少用悲观锁。**

展开一点：冲突少 → 乐观锁（不阻塞、吞吐高、失败重试代价小）；冲突频繁 → 悲观锁（避免大量无效重试白耗 CPU）。
</details>

<details>
<summary><b>Q8：缓存穿透、击穿、雪崩，一句话分别说清？</b></summary>

- **穿透**：查**不存在**的数据，缓存永远不命中，每次穿到 DB（常被脚本恶意刷）。
- **击穿**：数据**存在**，但**某一个热点 key 刚好过期**，瞬间几万请求同时冲 DB。
- **雪崩**：**一大批 key 在同一秒过期**（或 Redis 整个挂了），是击穿的集体版。
</details>

<details>
<summary><b>Q9：Redis 挂了，Redis 里的库存数据和 MySQL 不一致，以谁为准？</b></summary>

**以 MySQL 为准。**

Redis 只做**预扣**，MySQL 才是**真正的数据源**。不一致时用 MySQL 的数据去**对账回补** Redis，而不是反过来。

**缓存可以丢，账不能错。**
</details>

<details>
<summary><b>Q10：「Redis 解决了高并发」这句话对吗？</b></summary>

**不对。** 并发不会消失，1 万请求/秒还是 1 万请求/秒。

Redis 做的是**拦截、排队、过滤**，让数据库只看到它承受得住的那部分。

所以设计时要问的不是「怎么让 Redis 更快」，而是「**我把什么挡在了哪一层**」。
</details>

## 13. 📌 补充：视频没展开但一定会踩的坑

> 以下为原讲解之外的延伸，按重要性排序。

### 13.1 八个技术点里，视频没展开的四个

视频的技术地图列了 8 个，正文只展开了锁、Lua、WATCH、Stream。其余四个补在这里：

| 技术 | 典型命令 | 关键点 |
|---|---|---|
| **过期策略** | `EXPIRE k 300`、`TTL k`、`PERSIST k` | Redis 的过期是**惰性删除 + 定期删除**，**不保证到点立刻消失**。所以不要用 TTL 做精确的业务定时 |
| **管道 Pipeline** | 客户端批量发送，一次收全部回复 | 只减少**网络往返（RTT）**，**不保证原子性**，中间可能插入别的命令。和「事务」「Lua」是三件不同的事 |
| **消息队列** | `XADD` / `XREADGROUP` / `XACK` | 用 Stream 才支持**消费组 + ACK + 重投**；纯 `list` 做队列，消费失败就丢了 |
| **限流** | `INCR` + `EXPIRE`（固定窗口）、`zset`（滑动窗口） | 固定窗口有**临界突刺**问题（窗口边界前后各打满一次）；`zset` 滑动窗口更准，但内存开销大 |

> 📌 一句话辨析三兄弟：**Pipeline 省网络、事务保隔离、Lua 保原子。** 面试常考这个区别。

### 13.2 `DECR` 单独用，其实也不够

很多人以为「用 `DECR` 就防超卖了」，这话**只对一半**：

```bash
DECR stock:sku:1001     # 库存 0 的时候再减，会变成 -1
```

`DECR` 是原子的，但它**不判断**。库存已经 0 了，`DECR` 照样给你减成 -1。

所以真正的写法有两种：

| 写法 | 说明 |
|---|---|
| **Lua 脚本** | 判断 + 扣减在同一个原子块里（本课的主推方案） |
| **`DECR` 后检查返回值** | `DECR` 返回减完后的值，如果 `< 0` 就 `INCR` 回补 + 返回售罄。**但这中间又出现了空隙**：回补之前别人可能已经读到了负数 |

> 结论：**`DECR` 只是"一步原子"，Lua 才是"一段原子"。** 秒杀场景请用 Lua。

### 13.3 幂等键应该放哪一层

本课用 `set`（`SADD` + `SISMEMBER`）做「一人一单」。补充三点：

| 点 | 说明 |
|---|---|
| **幂等键要有业务含义** | `skuId + userId` 比 `requestId` 更可靠——后者只能防"同一次请求重复提交"，防不了"用户点两次" |
| **集合要设过期** | 活动结束后 `bought:sku:1001` 不会自己消失，会一直吃内存。给整个 set 设一个大于活动时长的 TTL |
| **最终幂等靠数据库** | Redis 的 set 只是**第一道拦截**；真正的幂等靠数据库**唯一索引**（`uk_sku_user`）。缓存丢了，唯一索引还在 |

### 13.4 「先扣 Redis 再落库」的三个必答题

这套架构一旦上生产，一定会被问到这三件事：

| 问题 | 标准答法 |
|---|---|
| **Redis 扣了，落库失败怎么办？** | 消息进队列要**持久化 + ACK**，失败重投；超过重试次数进**死信表**人工/定时补偿 |
| **Redis 挂了，恢复后库存怎么算？** | 以 MySQL 为准，**定时对账**，用「已售数量」反推 Redis 剩余库存，重新预热 |
| **用户看到"抢到了"，但最终没订单？** | 这是**超卖的反面（少卖）**，用户体验更差。所以「抢到」的提示要么延后到落库成功，要么明确告知"排队中" |

> 这就是第 10 章那句「缓存可以丢，账不能错」的工程落地版本。

### 13.5 分布式锁的三种替代方案

不是所有并发问题都要用 Redis 锁：

| 方案 | 适用 | 代价 |
|---|---|---|
| **数据库唯一索引** | 防重复插入（一人一单） | 简单可靠，但有写库开销，冲突时抛异常 |
| **乐观锁（版本号 / 条件更新）** | 冲突少的更新 | 冲突多时重试成本高 |
| **Redis 分布式锁** | 跨服务、跨资源的互斥 | 多一次网络往返，要处理锁超时 |

> 秒杀扣库存的主流做法其实是 **Lua 直接在 Redis 里完成扣减**，**根本不用锁**。锁是用在「必须串行跑一段复杂业务」的场景（比如缓存重建、券码发放）。

### 13.6 关于 QPS 的数字

本课的「MySQL 4000 QPS / Redis 10 万 QPS」是**量级示意**，不是标准答案。真实数字取决于：

- 机器配置、磁盘类型（SSD / NVMe）
- 查询复杂度（有没有 join、有没有回表）
- 数据量、索引命中率
- 网络 RTT、连接池大小

**考试/面试时写「差一个数量级以上」比写具体数字更安全；如果一定要写数字，就说明「单机、简单查询、理想条件下」。**

## 14. 一句话总结

> **这道题问了三层——数据库的锁、应用的乐观锁、缓存的 Redis；但三层问的其实是同一件事：读和写之间，怎么才能不被人插一脚。**
>
> **悲观锁是「进去先锁门」，乐观锁是「出来再核对」，Lua 是「把三件事焊成一件」。**
>
> **Redis 不解决并发，它只是把并发挡在了数据库前面。一秒钟 1 万个请求不会变少，只是被拦下、排队、过滤，让数据库只看到它扛得住的那一部分。**
>
> **所以设计高并发系统时，要问的不是「怎么让 Redis 更快」，而是「我把什么，挡在了哪一层」。**
>
> **缓存是可以丢的，账是不能错的。**
