## 0. 先给结论：pi-agent 到底是什么

### 0.1 一句话

> **pi-agent 是一个以「极简 + 可扩展」为设计哲学的开源 coding agent；因为它的内核被拆成了可复用的包，所以它同时也是一个 Agent 开发基座（框架）。**

注意这个顺序很重要，视频里反复强调：

> 「其他 Agent 框架就只是框架，而 pi-agent **首先是一个牛逼的智能体，是一个成熟的产品，然后才是一个 Agent 框架**。」

顺序反了，你得到的只是一堆抽象；顺序对了，你拿到的是**一个已经跑通的生产级产品的内核**，改 Prompt 和工具就能变成自己的 Agent。

写作原则：**转写里没有的，一律标「视频未说明」，不替它补。**

## 1. 开场：为什么值得花 35 分钟讲一个「循环」

视频用两句话定调：

> 「我大胆估计，真正理解智能体本质上是什么的**不超过 10%**。」
>
> 「在最近的一期访谈中，有位大佬说：**如果你不能用 300 行代码构建出一个 coding agent，说明你最多只是一个初级工程师**，因为你不理解智能体的底层原理。」

所以全片的目标只有一个：**把「智能体」这个词祛魅，还原成一个你可以亲手写完的循环；然后再看一个 70k star 的项目是怎么把这个循环工程化的。**

这个叙事结构值得单独记一笔，因为它就是本片的骨架：

```
① 祛魅：Agent = 模型 + 工具 + 循环（300 行能写完）
        ↓
② 现实：demo 一星期，上线一年（循环好写，harness 难写）
        ↓
③ 抄作业：pi-agent 怎么解这三件事
        循环维护 / 上下文管理 / 工具调用
        ↓
④ 为己所用：不 fork、不改源码，用它当基座做二开
```

## 2. 三重用法：产品 / 教材 / 基座

视频明确说「关于 pi-agent 有三种用法」，这三重是**递进**的，不是并列的：

| # | 用法 | 你在用它当什么 | 门槛 | 视频里的原话/例子 |
|---|---|---|---|---|
| 1 | **当产品用** | Claude Code / Codex 的**替代品** | 最低，装上就能用 | 「这在社区很受欢迎。由于可以自己拓展功能，所以它有非常多的玩法」 |
| 2 | **当教材读** | 学「怎么开发一个**生产级** Agent」 | 中，要读 TS 源码 | 「相比另外一个知名项目 Claude Code，pi 会**更好入门**」 |
| 3 | **当基座用** | 构建**自己的**智能体（像 OpenClaw 那样） | 中高，要懂扩展机制 | 「我就用它搭了一个 **data agent**，非常的好上手」 |

三句话把三重的差别说透了：

- **用法 1 的胜负手是「扩展」**：默认极简，缺什么自己装。所以它不是一个「功能齐全的成品」，而是一个「可以长成你想要样子的成品」。
- **用法 2 的胜负手是「包分层」**：`ai` / `agent` / `coding-agent` 三层，你可以只读 `agent` 那一层（几百行），就理解循环；Claude Code 是闭源打包好的，只能看行为不能看实现。
- **用法 3 的胜负手是「内核与 CLI 解耦」**：视频后面专门澄清了一句——「pi 本身的 coding agent 功能是一个 **CLI 应用**，这些 CLI 应用是在**内核的基础上又封装了几层**，我们是基于**内核**进行二次开发的，所以这些 CLI 应用大部分不会污染我们的 Agent。」

> 这三重用法合起来，回答了一个常见问题：**「开发 Agent 要用什么框架？」** 视频的答案是——「那就不如试试 pi 吧」。理由不是它功能多，而是**它先是一个产品**。

📌 补充：「框架 vs 产品」这个区分在选型时很好用。纯框架（LangChain 这类）给你的是抽象，你得自己填业务、自己踩工程坑；产品型基座给你的是**已经被真实用户捶过的默认值**（重试、压缩、截断、错误回灌），你只需要覆盖掉不该继承的部分。代价是：你得先搞清楚「哪些默认值必须覆盖」，这正是第 11 章那张表的作用。

## 3. 上手：安装、接模型、启动、扩展生态

这一段是纯操作，视频讲得很快，这里按「点一下鼠标」的粒度还原。

### 3.1 安装

> 「来到 pi 的**官网**，根据你属于哪个平台，对应执行这里的安装命令，就可以安装上了。」

- 安装入口：**官网**，按平台（macOS / Linux / Windows）给不同命令。
- ⚠️ **视频没有念出具体命令**（转写里也没有），所以本文不编。请以官网为准。
- 📌 补充：这类 CLI 工具常见的分发方式是「安装脚本 / 包管理器 / 单文件二进制」三选一；如果官网给的是 `curl | bash` 形态，注意先看一眼脚本内容再执行。

### 3.2 接模型：`models.json`

这是全片**唯一一个明确给出路径**的配置，务必记住：

> 「我们来到**系统用户目录**下，找到 **`.pi`** 文件夹，进入 **`agent`** 文件夹，新建 **`models.json`** 配置文件。在配置文件中，我们参考这一段，写入你自己的模型配置。」

还原成路径：

```text
<系统用户目录>/
└── .pi/
    └── agent/
        ├── models.json        ← 你要新建的模型配置文件
        └── ...                ← 其他 agent 级配置/会话数据
```

| 平台 | 实际路径 |
|---|---|
| macOS / Linux | `~/.pi/agent/models.json` |
| Windows | `C:\Users\<你的用户名>\.pi\agent\models.json` |

配置内容（**按口述还原**，视频只说要「参考官网那一段」，字段名以官网为准）：

```jsonc
{
  "providers": {
    "my-provider": {
      "baseUrl": "https://your-endpoint/v1",   // 标准 OpenAI 兼容地址
      "apiKey": "sk-...",                       // 也可以走环境变量
      "models": [
        {
          "id": "your-model-id",
          "contextWindow": 128000,              // 上下文长度，压缩阈值要用
          "maxTokens": 8192
        }
      ]
    }
  }
}
```

**视频特意提醒的一个坑**：

> 「如果你是使用 **coding plan**，那要看一下是否支持 pi。比如说 **GLM 的 coding plan 套餐，它就不支持 pi**。」

- 这句话的分量比它听起来重：coding plan 这类**订阅制套餐**往往只对「白名单客户端」开放（官方 CLI / 指定 IDE 插件），你拿 API key 去接第三方 harness 会被拒。
- 判断顺序应当是：**先确认套餐条款允许第三方客户端 → 再折腾配置**，否则会卡在一个看起来像「配置写错了」的 401/403 上。

### 3.3 启动与切模型

```bash

cd /path/to/your-project

# 2) 启动

# 3) 在 TUI 对话框里切换模型（视频原话：输入「杠 model」）
/model
```

- 「剩下的用法跟 Claude Code 等软件差不多，就是一问一答」——所以视频**没有**再讲基本交互。
- 记住 `/model`：二开时你会频繁在「强模型调逻辑 / 便宜模型跑回归」之间切。

### 3.4 极简主义：默认**没有**什么

这是 pi-agent 最反直觉、也最应该先知道的一点：

> 「pi-agent 崇尚的是**极简理念**，默认的功能非常简洁，连我们常见的**子智能体、MCP、计划模式**这些**都没有**。pi 认为这些都是**非必要的**。」

| 别的 harness 默认自带 | pi-agent 默认 | 想要怎么办 |
|---|---|---|
| Sub-agent（子智能体） | ❌ 没有 | 装扩展 / 自己写扩展 |
| MCP（Model Context Protocol）接入 | ❌ 没有 | 装扩展（扩展榜里有「MCP 应用及管理」类） |
| Plan mode（计划模式） | ❌ 没有 | 装扩展 / 用提示词模板替代 |
| Web UI | ❌ 没有 | 装 Web UI 扩展 |
| 上下文管理增强 | 基础版有（截断 + 压缩） | 装扩展增强，或订阅事件自己接管 |

> 这套取舍的逻辑，视频用一句话对比了 Claude Code：
>
> 「Claude Code 之类的软件是**把它觉得好的功能塞给你**，不管你实际是不是需要；而 pi-agent 是**鼓励你按照自己的习惯构建自己的 coding agent**。」
>
> 「适合**喜欢折腾的人**。」

📌 补充：极简的代价要提前认清——**默认装完的 pi-agent，能力上限低于 Claude Code**。它卖的不是「开箱即用」，是「开箱即改」。如果你的团队没人愿意维护扩展，那第 1 重用法（当产品用）会很快撞墙；反过来，如果你要做垂直 Agent，这份「空」正是优点：**没有一堆你不需要的默认行为跟你抢方向盘。**

### 3.5 扩展生态：四种类型 + 一个重点

> 「pi 的扩展生态分为四种类型，分别是 **skill、提示词模板（prompt template）、主题（theme）和 extension**。」
>
> 「其中 **extension 是最重要的，这是代码扩展**，可以用来定制 coding agent 的各种功能。」

| 类型 | 是什么 | 有没有代码 | 典型用途 | 重要度 |
|---|---|---|---|---|
| **extension** | 代码扩展，能挂事件、改行为、加工具 | ✅ 有 | 定制循环、上下文、工具、UI | ★★★ 核心 |
| **skill** | 能力合集，**触发时才加载** | 通常是 Markdown + 资源 | 教会 Agent 一套流程/领域知识 | ★★ |
| **prompt template** | 提示词模板 | ❌ 纯文本 | 常用指令一键复用 | ★ |
| **theme** | 主题（配色/外观） | ❌ 配置 | 让 TUI 好看点 | ☆ |

- 官方收录量：**「目前应该有四五千个了」**（视频口述，2026-08 时点）。
- 视频对下载量**前 20 名**的扩展做了归类，主要功能集中在：**上下文管理、子 Agent 的应用、MCP 应用及管理**等。
- 一句话理解 extension：「你简单理解这是一个**软件包**，装上去之后就可以有对应的功能。」——机制先不管（第 7、12 章再讲）。

**安装与查看**：

```bash
# 安装：复制扩展页给的命令，直接在命令行里跑
<官网扩展页给出的安装命令>

# 之后启动 pi，就能在启动界面/扩展列表里看到装了哪些扩展
```

### 4.2 三个包的职责

| 包 | 管什么 | 为什么值得单独成包 | 你要不要动它 |
|---|---|---|---|
| **`ai`** | 模型调用 | 模型服务太多，**输入输出都不一样**，需要一层封装「用统一方式调不同模型」 | 二开时基本不动（除非内网模型不兼容，见 11.2） |
| **`agent`** | **只维护一个智能体的循环** | 循环「太基础了」，基础到值得单独一个包 | ⭐ 二开主战场 |
| **`coding-agent`** | 编程场景的具体业务：**工具定义、系统提示词** | 场景相关的东西不该污染内核 | ⭐ 二开主要**覆盖**对象 |

### 4.3 为什么「模型调用」要单独一个包

视频自问自答：

> 「为什么模型调用也要专门做一个包呢？因为市面上的模型服务实在是太多了，不同的模型有不同的调用方式，具体来说就是这些模型服务的**输入和输出都不一样**。pi 对此做了一层封装，以便可以使用**统一的方式**调用不同的模型。」
>
> 「这个功能其实挺常见的，比如说 **OpenAI 包**也是这个功能。」

📌 补充：这类包的技术难点不在「发请求」，而在**四件脏活**：① tool call 的 JSON 在不同厂商的返回结构里位置不同（`tool_calls` / `content` block / `functionCall`）；② 流式增量的拼接与中断恢复；③ `usage`（token 计数）字段各家不统一甚至缺失；④ 参数命名差异（`max_tokens` vs `max_output_tokens`、`system` vs `systemInstruction`）。这些差异正是第 11.2 节「内网模型为什么不兼容」的根因。

### 4.4 为什么「循环」值一个包：一句原话

> 「`agent` 这个包**只负责维护一个智能体的循环**，而 `coding-agent` 这个包才是关于编程这个场景的具体业务实现。」
>
> 「这是一个**非常清晰的架构**：`ai` 和 `coding-agent` 这两个包很好理解，一个管模型调用、一个管具体功能实现。那 `agent` 这个包你可能看着有点困惑——**什么是智能体的循环？为什么智能体的循环需要一个包来单独维护？**」
>
> 「**这个就是我们今天的重点**。」

于是全片进入原理段。

## 5. 原理主线：Agent = 模型 + 工具 + 循环

### 5.1 模型使用的三种方式（只有第三种才算 Agent）

视频把「用模型」拆成三种，前两种**严格来说都不算智能体**：

| # | 方式 | 谁决定流程 | 谁决定何时结束 | 算 Agent 吗 |
|---|---|---|---|---|
| 1 | **单轮调用** | 没有人（就一次） | 一次就结束 | ❌「这时候给你答复的是**模型**，不是智能体」 |
| 2 | **工作流（workflow）** | **你**（预先定好几个步骤） | 你（流程走完） | ❌「模型的单轮调用只是其中一个环节」 |
| 3 | **Agent 循环** | **模型**（要不要调工具、调几次） | **模型**（不再调工具就结束） | ✅ |

> 「私底下大部分人对模型的开发应用其实就是上述两种，但严格来说，这两个**并不算是智能体**。」

**第三种的具体形状**（视频原话的精确复述）：

> 「你输入一段提示词给模型，模型决定**要不要调用工具**；如果要，那程序就执行工具；执行完工具之后，**把工具的结果再送回模型**，模型再决定下一步怎么做。如此循环，**直到模型觉得不再需要工具了，会给出最终答复**，那么这个循环就结束了。」

两条判据（这是区分 Agent 与 Workflow 的硬标准）：

1. **模型不是单轮调用，而是多轮的**；
2. **中间要经历什么流程、什么时候结束，是模型决定的，不是人类预设的。**

### 5.2 一个编程场景的实例

> 「你说我要改某个程序，模型可能会先调用 **read 工具**阅读相关的文件、理解这个需求，然后调用 **edit 工具**写入文件，不断地读、不断地写，直到完成工作，然后给出答复。」

```
用户：把这个函数改成支持异步
   │
   ├─ turn 1：模型 → tool_call(read, "src/foo.ts")      → 工具返回文件内容
   ├─ turn 2：模型 → tool_call(read, "src/bar.ts")      → 工具返回文件内容
   ├─ turn 3：模型 → tool_call(edit, old_string→new_string) → 工具返回「已修改」
   ├─ turn 4：模型 → tool_call(read, "src/foo.ts")      → 复核
   └─ turn 5：模型 → 纯文本「改好了，说明如下…」         → 循环终止
```

> 「在这个流程中，模型就是**反复地调用工具进行读写**而已。」
>
> 「因此有人总结：**智能体 = 模型 + 工具 + 循环**。」

### 5.3 整体运行图（一次用户请求的完整调用链）

这张图是全篇最该背下来的一张：**从键盘敲下回车，到屏幕上出现答案，中间到底发生了什么。**

```
 ┌──────────┐
 │  用户输入 │  "给 utils.py 加一个斐波那契函数"
 └────┬─────┘
      ▼
 ┌─────────────────────────────────────────────────────────────────────┐
 │ ① 组装上下文（harness 的活）                                         │
 │   System Prompt ＋ 工具 schema 清单 ＋ 历史消息 ＋ 本轮用户消息        │
 └────┬────────────────────────────────────────────────────────────────┘
      ▼
 ┌─────────────────────────────────────────────────────────────────────┐
 │ ② trace 开始  ──► [事件] trace_start                                 │
 │                                                                     │
 │   ┌───────────────────── turn N 开始 ─────────────────────┐          │
 │   │  ──► [事件] turn_start                                │          │
 │   │  ──► [事件] model_call_start                          │          │
 │   │  ③ ai 包：发请求（streaming / SSE）                    │          │
 │   │  ──► [事件] model_call_delta（流式增量）               │          │
 │   │  ──► [事件] model_call_end                            │          │
 │   │         ↓ 得到 message                                │          │
 │   │  ④ 判定：message 里有 tool_call 吗？                   │          │
 │   │     ├─ 没有 → return 纯文本 → 循环结束（trace_end）     │          │

 │   │     ──► [事件] tool_call_end                          │          │
 │   │  ──► [事件] turn_end                                  │          │
 │   └───────────────────────────────────────────────────────┘          │
 │         ↓ append(工具结果) 到消息列表，回到 ②'（下一个 turn）          │
 │                                                                     │
 │   ──► [事件] trace_end（记录时长、token、结果）                       │
 └────┬────────────────────────────────────────────────────────────────┘

 └──────────┘
```

📌 补充：图里 ④ 那个「没有 tool_call 就 return」是整个架构的**唯一天然出口**。所有「Agent 停不下来」的事故，最终都是因为这个出口没被触发（模型一直调工具），或者被人为堵住（错误处理把异常吞成了新的工具调用）。第 6 章讲它为什么成立，第 9 章讲怎么保证它还能被打通。

### 5.4 300 行极简版 coding agent（视频现场写的那个）

视频用一个 demo 证明「高大上的智能体背后就这么朴实无华」。这段代码**用的是 Python**（跑在魔搭的 Notebook 上，「不用自己安装环境」），注意它和 pi-agent 本体（TS）不是一套代码，只是**同构**。

代码结构一共 6 块，视频的讲解顺序就是这 6 块：

| 顺序 | 代码块 | 作用 | 视频原话 |
|---|---|---|---|
| 1 | 定义模型 | 选一个支持 function calling 的模型 | 「目前主流模型基本都可以随便填」 |
| 2 | 定义工具（3 个） | read / list / edit | 「都是 Python 标准库的函数而已」 |
| 3 | 写工具 schema | 给模型看的调用说明 | 「**必备的**，没有这个说明，模型就不知道有什么工具、怎么使用」 |
| 4 | 写系统提示词 | 人设 + 工具清单 + 做事方法 | 「一段简洁的系统提示词」 |
| 5 | 写循环 | 核心 | 「最后就是核心的代码」 |
| 6 | 跑测试 | 验证 | 见 5.5 |

**（1）模型与工具定义（按口述还原）**

```python
# ── 1. 定义要使用的模型 ────────────────────────────────────────
MODEL = "your-model-id"          # 视频：主流模型基本都可以随便填

# ── 2. 三个工具，全是标准库 ───────────────────────────────────
def read_file(path: str) -> str:
    with open(path, "r", encoding="utf-8") as f:
        return f.read()

def list_dir(path: str = ".") -> str:
    return "\n".join(os.listdir(path))

def edit_file(path: str, old_text: str, new_text: str) -> str:
    # 视频：编辑的本质就是「把旧文本替换为新文本」，也就是一个 replace
    src = read_file(path)
    if old_text not in src:
        return f"ERROR: old_text not found in {path}"
    with open(path, "w", encoding="utf-8") as f:
        f.write(src.replace(old_text, new_text, 1))
    return f"OK: edited {path}"
```

> 「从代码来看，这 3 个工具的实现都很简单，都是 Python 标准库的函数而已。要说有点复杂度，**最复杂的是这个编辑工具**——编辑文件的本质是将旧文本替换为新文本，也就是一个 `replace` 函数的事情。」

**（2）工具 schema（给模型看的「说明书」）**

```python
TOOLS = [
  {"type": "function", "function": {
      "name": "read_file",
      "description": "读取指定文件的完整内容。在修改文件前应先读取它。",
      "parameters": {"type": "object",
                     "properties": {"path": {"type": "string", "description": "文件路径"}},
                     "required": ["path"]}}},
  {"type": "function", "function": {
      "name": "list_dir",
      "description": "列出目录下的文件，用于了解项目结构。",
      "parameters": {"type": "object", "properties": {"path": {"type": "string"}}}}},
  {"type": "function", "function": {
      "name": "edit_file",
      "description": "把文件中的 old_text 替换为 new_text（只替换第一处）。",
      "parameters": {"type": "object",
                     "properties": {"path": {"type": "string"},
                                    "old_text": {"type": "string", "description": "必须精确匹配"},
                                    "new_text": {"type": "string"}},
                     "required": ["path", "old_text", "new_text"]}}},
]
```

> 「然后编写工具的 **schema 说明**，这是给模型看的**工具调用说明**，是**必备的**。没有这个说明，模型就不知道有什么工具、怎么使用。」

**（3）系统提示词**

```python
SYSTEM_PROMPT = """你是一个极简的 coding agent，工作目录是当前项目。

你可以使用三个工具：
- list_dir：先看目录结构
- read_file：改文件之前必须先读
- edit_file：用 old_text / new_text 做精确替换

做事方法：
1. 先弄清结构，再动手；
2. 每次只做一处最小修改；
3. 改完要复核；
4. 不需要工具时，直接给出最终答复。
"""
```

> 「接下来是一段**简洁的系统提示词**，设定了模型的**人设**，告诉模型**有哪些工具**以及**基本的做事方法**。」

📌 补充：注意这四件事的顺序——**人设 → 工具 → 方法 → 退出条件**。第 4 条「不需要工具时直接给出最终答复」看着像废话，其实是在**显式强化第 6 章那个停止条件**。生产级的 System Prompt 里，退出条件通常单独成段。

**（4）核心循环（全片最重要的 20 行）**

```python
def run(user_input: str):
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user",   "content": user_input},
    ]

    while True:
        # ① 发起一次模型调用
        resp = client.chat.completions.create(
            model=MODEL, messages=messages, tools=TOOLS,
        )
        msg = resp.choices[0].message
        messages.append(msg)                     # 把 assistant 消息记进历史

        # ② 没有工具调用 → 直接结束循环
        if not msg.tool_calls:
            return msg.content

        # ③ 有工具调用 → 逐个执行
        for call in msg.tool_calls:
            fn   = call.function.name
            args = json.loads(call.function.arguments)
            try:
                result = DISPATCH[fn](**args)     # 真正执行
            except Exception as e:
                result = f"ERROR: {e}"            # ★ 失败也当结果返回
            # ④ 把结果拼回消息列表
            messages.append({
                "role": "tool",
                "tool_call_id": call.id,
                "content": result,
            })
        # ⑤ 进入下一轮循环（把工具结果送回模型）
```

视频逐步拆过这段，逐句对应：

| 步骤 | 视频原话 | 代码位置 |
|---|---|---|
| 首次调用 | 「根据用户的提问发起第一次模型调用，得到模型返回的结果就是这个 message」 | `while` 第一行的 `create` |
| 判空出口 | 「判断 message 里面是否有工具调用指令，**如果没有，那就直接 return 结束循环**」 | `if not msg.tool_calls: return` |
| 提取全部调用 | 「如果有工具调用指令，就从 message 中**提取出所有的工具调用指令**，然后**逐个执行**工具」 | `for call in msg.tool_calls` |
| 拼结果 | 「这里有个 **append**，表示将所有的工具执行结果**拼起来**，然后**进入下一个循环**」 | `messages.append({...})` |
| 回灌 | 「在下一个循环就会将**所有工具的执行结果发送给模型**，由模型决定下一步操作」 | 回到 `create` |

> 「整体来看是非常简洁的代码，跟我们之前说的一样，就是三个要素：**模型 + 工具 + 循环**。」

⚠️ 视频里**没有**给这段代码的逐字全文（它只在屏幕上过了一遍，并说「代码我会放到评论区中，大家自取」）。上面是**按口述还原**的等价实现，结构一一对应，函数名/字段名以你用的 SDK 为准。

### 5.6 那「不同智能体的区别」到底是什么

这是全片一个容易被跳过、但很关键的自问自答：

> 「那不同智能体之间的区别是什么呢？我觉得，**最大的区别在于给智能体配置不同的提示词和不同的工具**，以便支撑不同的场景应用。」
>
> 「当然，此外还有**上下文管理方式、工具应用方式**等工程细节，**这个就是所谓的 harness 工程**。」

| 层次 | 差异来源 | 可复制性 |
|---|---|---|
| 内核 | 模型 + 工具 + 循环 | **零差异**，都一样 |
| 场景 | 提示词 + 工具集 | 高，抄+调 |
| 工程 | 上下文管理、工具调用可靠性、错误处理、可观测 | **低**，这是护城河 |
| 产品 | 交互（TUI/Web）、权限、协作、部署 | 中 |

**给了一条很实用的开工路径**：

> 「在实际开发中，你可以尝试参考这个案例，**设定一段提示词，给定一批工具，先把这个循环跑起来看看效果**，然后**根据出现的问题再不断地打补丁**。」

> 这句话就是「demo 一周，上线一年」的另一面：**先跑起来，再补工程**。别一上来就设计一套完美的 harness——你不知道会漏什么。

## 6. 循环为什么能停：停止条件不是天上掉的

这是全片**最有思想密度**的一段，视频自己抛出了那个所有人都在用、但很少有人问的问题：

> 「智能体的循环本身是很好理解的，但你有没有一个困惑：**为什么模型不再调用工具，我们就认为可以终止这个循环的呢？**」
>
> 「这其实是**人类在代码中定义的规则**。换句话说，**为什么模型不再调用工具就一定是完成任务的呢？** 难道模型不会单纯地说『我看到工具结果了，让我再想一想』吗？」

答案是**对齐训练**：

> 「但是在模型的**对齐训练阶段**，模型就学会了：它**要么得调用工具，要么得给出最终答复**。如果不调用工具、又没给出最终答复，那么它在这一轮对齐训练中会**得到低分**。久而久之，模型就学会了：它得调用工具获取充分的信息，**直到它完成任务、可以给出最终的答复，才可以停止调用工具**。」

```
训练时的评分函数（概念化）
┌────────────────────────────────────────────────────────────┐
│ 输出 = tool_call（继续干活）           → 中性/正分            │
│ 输出 = 最终答复（文本）                 → 正分                │
│ 输出 = 既无 tool_call 又是空/半截文本   → ★ 低分              │
└────────────────────────────────────────────────────────────┘
        ↓ 反复训练后固化为「要么调工具、要么交答卷」的先验
┌────────────────────────────────────────────────────────────┐
│ 推理时：只要 message 里没有 tool_call，就默认它是「最终答复」  │
│         → harness 可以安全地 return，循环终止                │
└────────────────────────────────────────────────────────────┘
```

一个很漂亮的补充定义：

> 「当然，这里的**完成任务不一定是解决用户的问题**，能够**准确地回答『不知道』也是完成任务**。」
>
> 「正所谓**知之为知之，不知为不知，是知也**。」

📌 补充：这段对工程有三点直接后果，值得记住——
> 1. **停止条件是可被破坏的**。如果你给模型的工具描述里写了「必须一直用工具验证」，或者错误处理把异常包装成「请继续调用工具」，模型就可能无限循环。所以第 7 章那个「turn 数超 100 就停」的钩子不是保险，是**必需品**。
> 2. **「不知道」要能被表达**。如果 System Prompt 逼着模型「必须解决问题」，它就会为了不交白卷而乱调工具。留一句「信息不足时直接说明缺什么」比多加三个工具更有用。
> 3. **不同模型的「停手倾向」不一样**。有的模型偏早停（任务没完就交答卷），有的偏晚停（反复验证）。这也是为什么 harness 需要 turn 上限 + 进度检测。

## 7. 循环维护：trace / turn 与 10 个可干预节点

### 7.1 先过渡：为什么循环好写、上线难

> 「Agent 开发有个共识：**出 demo 只要 1 星期，但是上线要 1 年**。为什么呢？出 demo 很快，是因为只要选定靠谱的模型、设定了合适的系统提示词、再配上一些工具，那么在给定的测试场景下，这个 Agent 就能跑起来了。但是真的上线了之后，**脱离了测试场景，各种你想到或想不到的坑就都来了**。」

怎么办：

> 「通常来说，这些坑我们可以**走一步看一步**慢慢解决，但是更好的建议是**摸着别人的项目过河**。那么这个已经斩获了 70k stars 的开源项目 pi-agent 就是一个不错的过河项目——它**以极简著称，任何它看得上的功能，那自然是极其重要的**，非常适合我们循序渐进地学习。」

于是锁定三个问题（这就是后半段的大纲）：

| # | 问题 | 对应章节 |
|---|---|---|
| 1 | **如何维护 Agent 的循环** | 第 7 章 |
| 2 | **如何进行上下文管理** | 第 8 章 |
| 3 | **如何有效地进行工具调用** | 第 9 章 |

> 「内容不少，但是全程通俗易懂，我会**只说框架，技术细节我另外放在文档里面**。」

### 7.2 两个基础概念：trace 与 turn

> 「我们细拆一下这个流程，首先有两个概念你要了解，分别叫 **trace** 和 **turn**。」

| 概念 | 定义（视频原话） | 边界 |
|---|---|---|
| **trace** | 「从你输入一个问题，到模型最终给出答复」 | 一次完整的任务交互 = 1 个 trace |
| **turn** | 「在一个 trace 中，模型会被不断地调用，**每一次模型调用都称为一个 turn**」 | **以模型调用为分界点** |

最容易被搞错的一条，视频专门强调：

> 「注意 **turn 是以模型调用为分界点的**。如果在某次模型调用中也需要调用工具，那么**这次工具和上一次模型调用属于同一个 turn**。」

意思是：**工具执行不算新 turn，下一次模型调用才算。** 于是每个 turn 可以再拆成两个环节：

```
trace
├── turn 1 ┬─ 模型调用环节
│          └─ 工具执行环节（可能 0 个、也可能 N 个工具）
├── turn 2 ┬─ 模型调用环节
│          └─ 工具执行环节
└── turn 3 ── 模型调用环节（无工具 → 输出最终答复 → trace 结束）
```

📌 补充：这个定义顺便解释了为什么「turn 数上限」是有意义的护栏——**turn 数 ≈ 模型调用次数 ≈ 钱**。而工具数不是，一个 turn 里并发 5 个工具和 1 个工具的模型成本差不多。

### 7.3 10 个可干预节点（全片枢纽）

> 「那么在 pi 的设计中，**一个 trace 从开始到结束总共有 10 个地方**，你可以对这个循环进行干预。」

```
                        ┌──────────────── trace_start ①
                        │
   ┌────────────────────┼────────────────────┐
   │  turn_start ③      │                    │
   │   ┌────────────────┼──────────────┐     │
   │   │ model_call_start ⑤            │     │
   │   │   model_call_delta ⑥（流式）   │     │
   │   │ model_call_end ⑦              │     │
   │   └────────────────┬──────────────┘     │
   │        ↓ 有 tool_call？                  │
   │   ┌────────────────┼──────────────┐     │
   │   │ tool_call_start ⑧             │     │
   │   │   （执行中）⑨                 │     │
   │   │ tool_call_end ⑩               │     │
   │   └────────────────┬──────────────┘     │
   │  turn_end ④        │                    │
   └────────────────────┼────────────────────┘
                        │  （循环下一个 turn）
                        └──────────────── trace_end ②
```

| # | 节点 | 你能在这里干什么（视频举的例子） |
|---|---|---|
| ① | **trace 开始** | 记开始时间 → 算出**一次响应时长**，后续拿来优化 |
| ② | **trace 结束** | 记结束时间、落库、统计 token/成本 |
| ③ | **turn 开始** | 取当前是第几个 turn；**超过 100 轮就停下来，防止模型被无限调用** |
| ④ | **turn 结束** | 累计本轮用量、判断是否该压缩上下文（见第 8 章） |
| ⑤ | **模型调用前** | 改写即将发出的上下文（注入/裁剪） |
| ⑥ | **模型调用时** | 处理流式增量：**敏感词检测**、逐字转发前端 |
| ⑦ | **模型调用后** | 检查/修正模型输出，统计 usage |
| ⑧ | **工具执行前** | **判断这个工具是不是有害的**（data agent 场景：`delete`、`drop` 按住） |
| ⑨ | **工具执行时** | 进度上报、中断信号（第 11.4 节） |
| ⑩ | **工具执行后** | 结果脱敏、截断、格式调整（第 9.4 节） |

> 「简单来说，你可以在这 10 个环节**插入代码，做任何你想做的事情**。」
>
> 「总而言之，你能想到的需求，大部分可以通过在 Agent 循环的这 10 个节点进行相应的改造，实现相关的功能。**这个就是你自己的 harness**。」

视频举的四个例子，正好对应四类典型需求：

| 例子 | 节点 | 需求类型 |
|---|---|---|
| 记时间算响应时长 | ①② | **可观测**（Observability） |
| 第 100 轮强制停 | ③ | **安全阀**（Guardrail） |
| 输出 message 时做敏感词检测 | ⑥ | **合规**（Compliance） |
| 工具调用前判断 delete/drop | ⑧ | **权限/风控**（Permission） |

> 顺带一段吐槽，说明「敏感词检测」为什么在流式阶段做：
>
> 「像那个豆包啊，有次我跟他边开车边聊历史，经常聊到一半他动不动就说『我们换个话题吧』，也不知道触发了他啥机制。」
>
> —— 这就是**边生成边拦截**的体感：等到全文生成完再拦，用户已经看完了。

### 7.4 「大部分框架都有，只是 pi 写得优雅」

> 「其实**大部分 Agent 框架都有这个功能**，只不过 pi 的设计很优雅，让你可以通过**很简洁的代码**来实现。那这个我们后续再介绍以 pi 为基座进行二次开发的时候会详细说明。」

📌 补充：这句话是整篇「原理 → 二开」的接缝。判断一个 harness 成熟不成熟，有个很省事的标准：**它有没有把这 10 个点暴露成稳定的事件**。只有 3~4 个钩子的框架，你早晚要 fork；10 个点都有的，你基本只需要写业务。第 12 章会讲 pi 暴露这些点的两种姿势（可改行为 / 只旁观）。

## 8. 上下文工程：截断与压缩

### 8.1 两句话定义上下文工程

> 「AI 领域的名词很多，炒概念的不少，但是**上下文工程**的确是我比较喜欢的一个，因为它**一定程度上揭示了 Agent 是否有效的关键**。」
>
> 「你想，既然 Agent 的本质是循环调用模型，那么**关键点就两个**：第一个是**模型本身的能力**，另外一个就是在**每一轮模型调用中，你提交给模型的提示词**，这个就是**上下文**。」

核心归纳成两点（这句可以直接背）：

| 原则 | 含义 | 不做的后果 |
|---|---|---|
| **该给的信息要给齐** | 「针对给定的任务，任何完成这个任务所需的信息都要尽可能地提供，**不要跟模型打信息差**」 | 模型靠猜，做错了你还怪它没悟性 |
| **不用给的信息不要给** | 「担心**占用模型的上下文**，**分散模型的注意力**」 | 贵、慢、变笨（Lost in the Middle） |

> 然后是一段全片最好笑的类比（也是最好记的）：
>
> 「从这个角度讲，很多**领导的上下文工程其实都不咋样**，动不动给你转发一个消息，其余啥都不说，全靠你猜，做错了就全怪你没有悟性。所以领导是不会喜欢 AI 的，**AI 哪有牛马好用**？AI 没有足够的上下文就干不了活，而**牛马会自动帮领导补齐上下文**。」

📌 补充：这个类比之所以成立，是因为它点出了上下文工程的本质——**它不是「写 Prompt 的技巧」，而是「信息供给的设计」**。你要决定：谁在什么时机、以什么粒度、把哪一块信息递给模型。这也是为什么它跟第 7 章的 10 个节点是同一件事：**节点是「时机」，截断/压缩/注入是「内容」。**

### 8.2 pi 做的第一件事：工具输出截断

> 「第一点是对**工具输出内容进行截断**。有些工具的输出很长，如果不加以限制，可能**一下子就把上下文撑爆了**。比如说 **read 工具**读某个文档，或者某些 **bash 工具**返回一个命令的结果，可能都会很长。」

机制（三步，很值得抄）：

```
① 工具产出超长结果
        ↓
② 完整结果写入本地文件（落盘）
        ↓
③ 给模型的是：截断后的文本 ＋ 本地文件路径
        ↓
④ 由模型自己评估：要不要去读完整内容（再发一次 read）
```

| 设计点 | 做法 | 好处 |
|---|---|---|
| 落盘 | 全文写文件 | **信息不丢**，可回溯 |
| 只给指针 | 截断文本 + 路径 | 上下文可控 |
| 交还决策权 | 模型自己决定读不读 | 不用你猜「哪些该留」 |

> 「那这个方法看起来简单，但**其实细节很多**：比如说**按字符截断还是按字节截断**，**保留前面的还是保留后面的**，这些都是要根据不同的场景去具体分析的。」

| 细节 | 选项 | 什么时候选 |
|---|---|---|
| 计量单位 | 字符 / 字节 / **token** | 中文场景按字节会砍出乱码；按 token 最贴近真实成本 |
| 保留方向 | 头部 / 尾部 / 头尾各一半 | 日志看尾部（最近的错误），源码看头部（imports/声明） |
| 截断标记 | 必须显式写「已截断，全文见 xxx」 | 否则模型会以为文件就这么短，作出错误判断 |
| 落盘位置 | 会话工作目录下（可被后续工具读到） | 保证模型能用 read 取回 |

⚠️ **视频把这块的细节「整理成了文档」而没有在视频里展开**，上面表格是按它口述的方向 + 常见做法归纳，属📌 补充。

### 8.3 第二件事：上下文压缩（Compaction）

> 「第二点很常见，就是**上下文压缩**，这个几乎是开发 Agent 肯定要考虑的问题了。」

视频把它拆成三个问题，逐个回答：

#### 问题 1：为什么要压缩？

| # | 原因 | 视频原话 |
|---|---|---|
| 1 | **装不下** | 「模型的上下文有限，但是 Agent 在多轮循环过程中不断调用各种工具，**上下文累积得非常快**，很容易超过模型的上下文，**当超过的时候就会报错**」 |
| 2 | **变笨 + 不划算** | 「随着上下文越来越长，**模型会越来越笨**，但是**历史上下文中的信息其实是越来越少的**，这时候我们也会考虑**提前压缩**」 |

> 第 2 条那个观察很精辟：**上下文越长，信噪比越低**。不是因为模型记不住，而是因为「有用的旧信息」被大量「无用的旧过程」稀释了。

#### 问题 2：什么时候压？

> 「pi-agent 会设定一个 **token 阈值**，结合**模型的上下文长度**和**当前上下文的长度**，判断当前**剩余 token 的可用量**。当**剩余 token 可用量低于某个阈值**时，就主动发起压缩，**防止模型报错**。」

```text
剩余可用 = 模型上下文长度(contextWindow) − 当前上下文长度(已用 token)

if 剩余可用 < 阈值:      # 例如 < 20% 或 < 固定 N k
    触发压缩
```

再给了一条**体验层**的建议，很实用：

> 「这里也给个建议：为了提升用户体验，这个上下文压缩**可以提前进行**，比如**在模型完成上一轮任务之后就判断是否要压缩**。如果你是在**下一轮任务开始时才开始压缩**上下文，那么就会让用户**陷入一个无聊的等待**，体验就不好。」

| 时机 | 用户体感 | 建议 |
|---|---|---|
| 上一轮任务刚结束就压 | 无感（用户在看结果/打字） | ✅ 首选 |
| 下一轮开始时才压 | 卡住等几秒~几十秒 | ❌ |
| 撞到上下文上限才压 | 报错后才补救 | ❌ 底线 |

#### 问题 3：压成什么样？

> 「压缩成什么样子其实**没有确定的答案**。pi-agent 给的建议是**按照结构化的模板来压缩**。」

它给的模板（5 段）：

| # | 段落 | 装什么 |
|---|---|---|
| 1 | **用户目标** | 这次任务到底要达成什么 |
| 2 | **约束条件** | 不能碰什么、必须遵守什么 |
| 3 | **工作流程** | 已经做了哪几步、顺序如何 |
| 4 | **关键决策** | 做过哪些选择、为什么这么选 |
| 5 | **下一步计划** | 接下来要做什么 |

> 「但是这个**是 coding agent 的场景**。具体到你自己的场景，比如说 **data agent 场景**，这个模板长什么样，还得你自己去思考。」

> 「但说实话，**有些时候我也懒得去想，就直接给模型一个方向，让它自由发挥，其实也会有不错的效果**。」

📌 补充：这段「结构化模板 vs 自由发挥」的取舍可以说得更明确——**结构化模板赢在稳定（每次压出来的形状一致，下游可解析、可对比），自由发挥赢在信息保留（不会因为模板里没有这一栏就把关键信息丢掉）**。折中做法是「给模板 + 允许追加一节『其他重要信息』」。

#### 问题 4：压完怎么用？

> 「那就很简单了：**在下一次对话的时候，将压缩后的结果替代被压缩的那部分上下文，完成上下文的重组**，那就可以了。」

```
压缩前：[System][历史 turn 1..20（超长）][当前用户消息]
                    ↓ 压缩
压缩后：[System][压缩摘要（结构化 5 段）][最近 N 轮原文][当前用户消息]
                          ↑ 替代了被压的那部分          ↑ 近期原文通常保留不压
```

### 8.4 第三件事（视频只点了一句）：缓存命中率

> 「上下文工程其实还有一个特点，就是要**通过合理的编排尽可能地提升缓存命中率**。比如**系统提示词如何分层**、**什么信息放前面什么信息放后面**、**如何尽量避免提示词的前缀变化**等等。」
>
> 「那这一点的话，其实 **Claude Code 就做得很好**，花了很多心思做了这个处理，大家有兴趣的话也可以拓展看看。」

| 手段 | 一句话 |
|---|---|
| 系统提示词分层 | 稳定的在前、易变的在后 |
| 排序 | 变了会「污染前缀」的东西往后放（时间戳、随机 ID、cwd） |
| 前缀稳定 | 只追加、不改写 |

📌 补充：这一块在你的《EP02 Agent 上下文分层管理》里是主线（分层 + 前缀 diff 为空 + 压缩只发生在缓存分界线之后）。**本篇只把它当一句话带过，是因为 pi-agent 的卖点不在这里**——pi 把「什么时候压、压成什么」交给扩展，缓存编排的责任也随之下放给使用者。这是两篇笔记最需要对齐的差异点。

## 9. 工具调用管理：可靠性是一层层兜出来的

> 「作为整个 Agent 循环的**重头戏**，工具可不是简单的执行那么简单，要**用一套严谨的机制来维护**。」

### 9.1 基本流程：三步

| 步骤 | 做什么 | 目的 |
|---|---|---|
| 1 | **定义工具 schema**：名字、描述、参数说明 | 「让模型知道**怎么使用**工具」 |
| 2 | **把 schema 塞进提示词**，发起模型调用 → 模型返回**工具调用指令** | 让模型「点菜」 |
| 3 | **解析指令**，拿到工具名和参数，**执行** | 真正干活 |

> 「在整个流程里面，我们的**核心工作是如何千方百计地确保工具调用的可靠性**。」

### 9.2 前两个显而易见的手段

| # | 手段 | 为什么有效 |
|---|---|---|
| 1 | **写清楚 schema** | 「这是要**降低模型的理解负担**」 |
| 2 | **选一个靠谱的模型** | 「具备 **function calling** 能力的模型肯定是标配了」 |

但视频马上补了一刀：

> 「但是如果经过前两步的努力，模型**依然传回错误的工具指令**，要怎么办呢？**这就是第三阶段要做的事情了。**」

### 9.3 pi 的四段式可靠性管线

> 「pi-agent 设计了一套流程来进行工具调用，这套流程分别是：**参数验证 → 调用前的安全检查 → 调用时的错误处理 → 调用后的结果调整**。」

```
            模型返回 tool_call
                    │
        ┌───────────▼───────────┐
        │ ① 参数验证             │
        │  · JSON 字符串 → 对象   │
        │  · schema 类型校验/转换 │
        └───────────┬───────────┘
                    │ 通过（不通过就尽量兜底修好）
        ┌───────────▼───────────┐
        │ ② 调用前安全检查        │  ← 10 节点里的 ⑧
        │  · 危险指令？           │
        │  · 越权路径？           │
        └───────────┬───────────┘
                    │
        ┌───────────▼───────────┐
        │ ③ 执行 + 错误处理       │  ← 10 节点里的 ⑨
        │  · 失败 → 错误当结果     │
        └───────────┬───────────┘
                    │
        ┌───────────▼───────────┐
        │ ④ 结果调整              │  ← 10 节点里的 ⑩
        │  · 截断 / 脱敏 / 格式化  │
        └───────────┬───────────┘
                    │
              回灌给模型 → 下一个 turn
```

#### ① 参数验证：两种，都很常见

> 「pi 做了两种参数验证。第一种比较常见：有些模型在返回 JSON 调用指令的时候**会把 JSON 给序列化成字符串**，这时候 pi 检测到了就会**直接给转化成准确的 JSON 格式**。」
>
> 「第二种就比较常见了，是要进行 **schema 验证**。比如说参数要求传的是**数值型**，但是结果返回的是**文本型**，这时候 pi 就会帮忙**直接进行转化**。」

| # | 问题 | 现象 | pi 的处理 |
|---|---|---|---|
| 1 | **JSON 双重序列化** | `"arguments": "{\"path\":\"a.ts\"}"`（值是字符串，不是对象） | 检测到就再解一次，转成真 JSON |
| 2 | **类型不符** | schema 要 `number`，模型给了 `"10"` | 按 schema 做类型转换 |

> 「在参数验证的阶段，pi 的原则是：**尽量地给模型兜底，能解决的问题就都给解决掉**。」

📌 补充：这条原则值得单独记住——**「能自动修的就别报错，修不了再报错」**。因为每一次报错都意味着一个 turn 被浪费（模型要重新生成一遍），而 token 是钱、延迟是体验。但反过来也要注意：**过度兜底会掩盖 schema 写得烂的事实**，如果某个工具天天触发类型转换，应该改的是 schema 描述，不是加转换规则。

#### ② 调用前 / 调用后：就是那 10 个节点

> 「接下来工具调用前和调用后也可以进行干预，这个其实就是我们前面提到的 **10 个阶段中的两个阶段**。比如说看一下**工具调用前是否有危险指令、是否访问了不该访问的文件**；在**调用之后还可以对返回的结果进行处理**。」
>
> 「比如说你构建了一个 **data agent**，那么你就可以**校验一下返回的结果中有没有敏感信息、要不要脱敏**。」

| 节点 | 检查什么 | 典型动作 |
|---|---|---|
| 调用前 ⑧ | 危险指令（`drop` / `delete`）、越权路径、参数合理性 | 拦截 / 要求确认 / 改写参数 |
| 调用后 ⑩ | 敏感信息、超长、格式 | 脱敏 / 截断 / 结构化 |

#### ③ 出错怎么办：把错误当结果（本节最重要）

> 「最后一个关于工具要介绍的，我觉得是很有意思的一点，就是**工具执行出错了怎么处理**。」
>
> 「在工具调用阶段一般是要返回工具调用结果的，但如果**工具执行失败、没有结果**，那怎么办？**那就把工具的报错信息当成结果返回给模型。**」

所以要建立一个认知：

```
工具执行成功 → 返回结果   ┐
                          ├──► 模型都能收到「结果」，循环不中断
工具执行失败 → 返回报错   ┘
```

> 「所以不管是调用工具成功或者失败，**模型都能够收到结果，这个 Agent 的循环不会被中断**。那么模型就可以**根据报错信息重新生成准确的调用指令**。」

data agent 的例子（视频原话的因果链，非常清楚）：

> 「比如你做 data agent，如果模型生成的某条 SQL **用了不存在的字段**，那么你就可以把这个**报错信息再提交给模型**；模型看到这个报错信息，可能就会意识到**它要重新去读表结构**，然后生成准确的 SQL。」

```
模型生成 SQL:  SELECT user_name FROM orders      ← 字段不存在
      ↓ 执行失败
工具返回:      ERROR: column "user_name" does not exist
               HINT: orders 表的可用字段为 id, uid, amount, created_at
      ↓ 回灌
模型下一步:    tool_call(get_table_schema, "orders")   ← 自己回去读表结构
      ↓
模型重新生成:  SELECT uid FROM orders
```

> 「那么在实际的开发过程中，你可以**根据不同的工具尽可能地预定义好可能的错误信息**，**说清楚这是什么错误、要怎么处理**，这样模型才能尽可能地纠正自己的错误。」
>
> 「那实在不行、没有办法穷举所有错误的话，**也要返回一条通用的报错信息**。」

| 错误信息质量 | 模型能否自愈 |
|---|---|
| 只返回 `Error` / 空 | ❌ 只能瞎猜 |
| 返回原始异常栈 | ⚠️ 信息过载，容易被噪声带偏 |
| **结构化：what + why + how to fix** | ✅ 高概率一次自愈 |
| 预定义常见错误码 + 处理建议 | ✅✅ 最佳 |

> 「总而言之，对工具出错处理的基本原则是：**要把错误的信息返回给模型，而不是终止循环**，要给模型**继续纠错的机会**，这样这个 Agent 才会稳定，也才会**看起来更智能**。」

### 9.4 四段管线串起来看

| 阶段 | 一句话 | 失败时的兜底 |
|---|---|---|
| 参数验证 | 能修就修 | 修不了 → 报错回灌 |
| 调用前检查 | 不该做的拦住 | 拒绝 + **说明原因**给模型 |
| 执行 | 真干活 | 异常捕获 → 错误当结果 |
| 结果调整 | 别把垃圾灌回去 | 截断 / 脱敏 |

📌 补充：这四段和「工具 schema 写清楚 + 选好模型」是**两层防御**——前者是**预防**（让模型少犯错），后者是**容错**（犯了错也能回来）。很多团队只做预防（狂改 Prompt），不做容错，结果就是「模型偶尔抽风 → 整个任务崩掉 → 被判定为不可用」。**生产可用性的差距，八成在容错这一层。**

## 10. 二开（总纲）：为什么不用 fork

### 10.1 一句话理由：先产品，后框架

> 「市面上 Agent 框架那么多，为什么要选择 pi-agent 呢？**其他 Agent 框架就只是框架，而 pi-agent 首先是一个牛逼的智能体、是一个成熟的产品，然后才是一个 Agent 框架。**」
>
> 「这意味着使用 pi-agent 进行二次开发，能够让你的智能体**一下子拥有顶尖智能体的内核**。」

最省事的起步形态（视频原话）：

> 「最简单的情况下，**你修改 pi 的系统提示词、配置不一样的工具**，就可以把自己的智能体跑起来了。」

剩下的活它都包了：

|---|---|
| 定义人设 | — |
| 选工具 | — |
| 写业务流程 | — |
| — | 「**模型调用出错自动帮你重试**」 |
| — | 「**上下文过长自动帮你压缩**」 |
| — | 「帮你构建了 **Agent 运转起来所需的基本能力**」 |

> 「这些宝贵的工程经验全部无偿送给你使用，太爽了。」

### 10.2 「要改源码吗？」——不用

> 「但你可能有点担忧：在别人的产品上进行二次开发，**得修改源码吧**，那岂不是很麻烦？**完全不用。** 官方直接坦诚地告诉大家：**你不用 fork 这个仓库，不用修改源码，就可以实现你自己的需求。**」

这是全篇最该记住的一句产品设计判断。它背后是三层解耦：

```
┌────────────────────────────────────────────────────────────┐
│ ① CLI 应用层（TUI 交互、命令、主题）                         │
│    与你的二开基本无关（「不会污染我们的 Agent」）              │
├────────────────────────────────────────────────────────────┤
│ ② 配置 / 覆盖层  ← 你主要在这里动手                          │
│    · 基础人设（参数传入）                                    │
│    · 工具集（关内置 + 传自定义）                             │
│    · 会话存储（关掉默认 JSON，改数据库）                      │
│    · 模型配置（models.json / 兼容性声明）                     │
├────────────────────────────────────────────────────────────┤
│ ③ 扩展层（事件订阅）  ← 需要改行为时在这里动手                │
│    · 订阅 10 个节点中的任意一个                              │
│    · 拦截、改写、注入、上报                                  │
├────────────────────────────────────────────────────────────┤
│ ④ 内核（ai / agent）  ← 你不碰                                │
└────────────────────────────────────────────────────────────┘
```

**为什么"不用 fork"是硬需求**（📌 补充，视频未展开）：fork 的代价不是第一次改动，而是**每一次上游更新都要 merge**。一个 70k star 的活跃项目，你 fork 之后三个月就会变成「一个基于旧版的私有分支」，享受不到任何上游修复。**在扩展点上写代码 = 你只拥有差异，不拥有副本。**

## 11. 二开（手册）：一个 data agent 的四步改造

### 11.1 实战需求与结果

视频现场用 skill 从零搭了一个 **data agent**，需求三条：

| # | 需求 | 说明 |
|---|---|---|
| 1 | 基于 **Web** 的应用 | 前端能对话 |
| 2 | **数据由 AI 自己造** | 省去准备数据 |
| 3 | **拦截危险 SQL** | 不让它 `drop` / `delete` |

结果（视频原话）：

> 「AI 根据这个 skill 查询 pi-agent 的用法，**从 0 开始搭建环境，很快就完成了这个项目**。」
>
> 「我们体验一下，随便问个问题，**智能体能够正常答复**。」
>
> 「这个页面看起来丑了一点，可以理解，因为我们**没有提美观需求**。主要是这个开发过程是**一步到位**的，**不需要修复 bug**。」
>
> 「这个就是另外一个好处：由于使用的是**成熟的框架**，所以 **AI 的 bug 率低了很多**。」

⚠️ 这一段是**演示**，视频没有贴完整代码。下面四步是它**逐个讲过的改造点**，代码均为「按口述还原」的骨架。

### 11.2 第 1 步：配置模型（含内网兼容性，这里最容易翻车）

**表面很简单**：

> 「配置模型本身很简单，无非是设定模型的 **URL、API key** 等参数，写在某个配置文件或者传入某个参数，这些没什么特别的，**各大框架都大差不差**。」

**真正的坑在内网**：

> 「但重点是，如果你打算在**企业内网**使用，得知道你内网的模型**能不能接入 pi-agent**。很多企业会**自己部署私有模型，并且按照自己的需要封装模型接口**，最后导致内网的模型接口规范可能**千奇百怪**，跟标准的模型接口有很大差异。」

具体差异（视频举的三类）：

| # | 差异 | 后果 |
|---|---|---|
| 1 | **不支持 function calling** | 工具调用直接废掉 |
| 2 | **message 字段格式不一样** | 请求构造失败 / 解析失败 |
| 3 | **不支持某些特定参数** | 报错 |

> 「而 pi-agent 是**按照标准的模型接口规范来开发的**，因此内网的这些具有独特规范的模型接口**可能不一定能够适用**。」

视频把兼容性分成**两档**，这个分档非常实用：

| 档位 | 例子 | 不具备的后果 | 能不能救 |
|---|---|---|---|
| **必须项**（没有就不行） | **流式输出**；**URL 必须符合标准格式** | 核心功能不可用 | ❌ 救不了，得改网关 |
| **可选项**（有更好） | **`usage` 参数**（token 统计） | **无法统计 token 使用量**，「但这个影响不大」 | ✅ 能救 |

救的办法：

> 「但你需要**做个说明，让 pi-agent 绕过这个参数**，否则可能会报错。pi-agent 在模型配置中**专门有个参数让你说明差异**，你把不具备的参数做个说明就行了。」
>
> 「为了方便大家做判断，我把这个功能写到 skill 中：你只要提供**模型接口文档**，AI 会输出一份**模型配置文件**，你拿过去试试看就行了。」

骨架（**按口述还原**，参数名以官方文档为准）：

```jsonc
// ~/.pi/agent/models.json
{
  "providers": {
    "corp-gateway": {
      "baseUrl": "http://llm-gateway.corp/v1",     // ★ 必须项：标准 OpenAI 兼容路径
      "apiKey": "${CORP_LLM_KEY}",
      "compat": {
        "supportsUsage": false,                    // ★ 可选项：不返回 usage → 关掉统计
        "supportsStreaming": true,                 // ★ 必须项：没有流式就别接了
        "supportsToolCall": true                   // ★ 必须项：function calling
        // 其余差异项按网关文档逐条声明
      },
      "models": [
        { "id": "qwen-corp-72b", "contextWindow": 32768, "maxTokens": 4096 }
      ]
    }
  }
}
```

⚠️ **视频没有念出这个「兼容性参数」的具体名字**（转写为「专门有个参数」），上面 `compat` 及字段名是按语义还原的占位，**请以官方 models.json 文档为准**。

📌 补充：排查内网兼容问题有个高效的顺序——
> 1. 先用 `curl` 打一次**非流式**的 `/chat/completions`，确认能通；
> 2. 再打**流式**（`stream: true`），看 SSE 分块格式是不是标准 `data: {...}\n\n`；
> 3. 再带 `tools` 打一次，看返回里有没有 `tool_calls`；
> 4. 最后才配进 pi。
>
> 直接配框架再看报错，等于让框架替你做协议排查，效率最低。

### 11.3 第 2 步：写系统提示词（5 段结构，改第 1 段）

**pi 的系统提示词由 5 部分组成**：

> 「pi-agent 的系统提示词由这 **5 个部分**组成，其中**基础人设是必须的**——pi-agent 默认设置了一套 **coding agent 的基础人设**，**这个我们得改掉**。另外几个是**可选的**，pi-agent 会**从指定的这些文件读取文档内容，然后拼接在一起**，形成最终的系统提示词。」

```
最终 System Prompt
┌──────────────────────────────────────────────────┐
│ ① 基础人设（必填，参数直接传入）        ★ 你改这里 │
├──────────────────────────────────────────────────┤
│ ② 文件 A 的内容（可选，从指定路径读取）            │
│ ③ 文件 B 的内容（可选）                            │
│ ④ 文件 C 的内容（可选）                            │
│ ⑤ 文件 D 的内容（可选）                            │
└──────────────────────────────────────────────────┘
        ↑ 拼接顺序即上面的顺序
```

> 「对我们开发**垂直智能体**来说，主要是定义这个**基础人设**。pi 提供了这么一个**参数**来接收你定义的基础人设，你只要定义这个参数，**然后把后面路径的文件全部删掉就行了**。」

骨架（**按口述还原**）：

```ts
const agent = await createAgent({
  // ★ 基础人设：整个垂直 Agent 的「你是谁」
  systemPrompt: `
你是「数知」，一个企业数据分析助手。

职责：把用户的自然语言问题，翻译成 SQL 并在只读库上执行，然后用业务语言解释结果。

铁律：
1. 只能执行 SELECT；任何 DDL/DML 一律拒绝。
2. 不确定表结构时，先查表结构，不要猜字段名。
3. 查不到就说不确定，并说明缺什么信息。
4. 回答里不要出现原始 SQL，除非用户明确要求。
`,
  // ★ 默认的几个「文件型」上下文全部置空 —— 否则 coding agent 的人设会混进来
  contextFiles: [],
});
```

| 要不要改 | 内容 | 不改的后果 |
|---|---|---|
| ✅ 必改 | 基础人设 | 你的 data agent 会以为自己在写代码、动不动 `read_file` / `edit_file` |
| ✅ 建议清空 | 4 个可选文件（项目约定/规范类） | coding 场景的规范（比如「提交前跑 lint」）会被塞进你的场景 |
| ⚠️ 按需 | 若要复用某些文件型上下文，保留并改写内容 | 混入无关约束，浪费 token |

📌 补充：为什么 pi 用「**人设 + 文件拼接**」而不是一个大字符串？因为**文件型上下文可以按项目变化**（换个仓库换一套约定），而人设是产品级的。这个设计和 EP02 里讲的「分层」是同一个思路：**稳定的走参数，易变的走文件。**

### 11.4 第 3 步：设计工具（关内置 + defineTool）

**第一件事：把内置工具全关掉。**

> 「与系统提示词一样，它**内置了若干个工具**，这些工具**我们通常都不需要**，所以我们要做的第一件事情是**把内置的这些工具给关掉**。只要设定这个参数，表示**内置工具通通不要**。然后**写一个你自定义的工具，配置到这个参数里面**，表示这是你要启用的工具。」

```ts
const agent = await createAgent({
  builtinTools: [],        // ★ 关掉全部内置工具（参数名按语义还原）
  tools: [runSqlTool],     // ★ 只启用你自己的
});
```

**第二件事：用 `defineTool` 定义工具。**

> 「pi 提供了一个叫 **`defineTool`** 的函数来定义工具，这几个用来定义**函数的名字、描述和参数**等。这个 **`execute` 方法**用来定义函数的**具体功能**。」

```ts
import { defineTool } from "pi-agent";   // 包名以官方为准

const runSqlTool = defineTool({
  name: "run_sql",
  description: "在只读数据仓库上执行一条 SELECT 查询，返回结果表格。只允许 SELECT。",
  parameters: {
    type: "object",
    properties: {
      sql: { type: "string", description: "一条合法的 SELECT 语句" },
    },
    required: ["sql"],
  },

  // ★ execute：真正干活的地方
  async execute({ sql }, ctx) {
    const check = assertSelectOnly(sql);        // 二次校验（不只靠提示词）
    if (!check.ok) {
      return { error: `REJECTED: ${check.reason}. 只允许 SELECT。` };
    }
    const rows = await db.query(sql, { timeout: 10_000 });
    return { rows, rowCount: rows.length };
  },
});
```

> 「比如对于 data agent 来说，可以通过这个方法中的**这个参数**来获取大模型传进来的 **SQL**，对 SQL 进行**安全校验**之后**执行 SQL 拿到结果**，这个就是它的功能。」

**第三件事（视频单独夸的一段）：工具执行过程中的用户体验。**

> 「**SDK 的使用很简单，但我觉得更有意思的是，pi 还考虑到了工具执行过程中的用户体验。** Agent 执行某个工具可能要很久，这时候有**两个问题**：1、**如何让用户知道当前的进度**，否则用户还以为程序挂了；2、**如何让用户终止工具调用**呢？」

pi 在 `execute` 里给了**两个参数**：

| 参数（语义） | 解决什么 | 机制（原话） |
|---|---|---|
| **进度回调** | 用户看不到进度 | 「你可以用这个参数定义**要发送到前端的内容**，pi 会**触发某个事件**，后端程序**监听这个事件**就可以拿到数据，然后发到前端去」 |
| **终止信号** | 用户想停 | 「用户点击前端的**停止按钮**之后，pi 可以接收到来自前端的**终止信号**，然后**一层层传入到工具中**，工具接收这个信号**执行终止**」 |

```ts
async execute({ sql }, { onUpdate, signal }) {
  onUpdate?.({ stage: "validating", message: "正在校验 SQL…" });
  if (signal?.aborted) throw new Error("用户已取消");

  onUpdate?.({ stage: "querying", message: "正在查询，预计 10s…" });
  const rows = await db.query(sql, { signal });   // 把 signal 一路透传下去

  onUpdate?.({ stage: "formatting", message: `拿到 ${rows.length} 行` });
  return { rows };
}
```

⚠️ 视频**没有念出这两个参数的名字**（转写为「这个参数」「那个参数」），上面 `onUpdate` / `signal` 是按语义还原的占位名。

> 「所以你看，**为什么我喜欢 Agent 呢**？实际 Agent 开发过程中，我们并不都是在调 Agent，还要考虑到**产品的应用性**。pi-agent 真的是**千方百计地让你聚焦到业务本身**，其他**脏活累活能干的都帮你干了**。」

> 「此外，pi 的工具调用还有很多优秀的机制，比如说**参数格式错误、或者工具调用错误，就会自动将错误信息提交给模型进行二次纠错**等等，很多细节我们不细说了，大家自行看文档。」

### 11.5 第 4 步：拦截危险 SQL（事件订阅的第一个真实用例）

需求很朴素：

> 「直观地来看，这个需求很简单，就是**在执行任何 SQL 之前，检查一下有没有 `drop`、`delete` 等非法关键字**。」

> 「这个工作可以用 pi-agent 的**事件订阅机制**来处理。pi-agent 会**发出各种事件**，**你可以订阅某个事件**，Agent 执行到这个事件时就会**通知你**，让你可以执行预设的任务。」

```ts
// 订阅「工具执行前」这个事件
agent.on("tool_call", async (event) => {
  // 只关心 run_sql 这个工具
  if (event.toolName !== "run_sql") return;

  const sql = String(event.args?.sql ?? "");
  const verdict = checkDangerous(sql);   // 查 drop / delete / truncate / update ...

  if (!verdict.safe) {
    // ★ 拒绝执行，并把原因反馈给模型
    return {
      block: true,
      reason: `该语句包含危险操作（${verdict.hit}），已被策略拦截。请改为 SELECT 查询，或向用户确认。`,
    };
  }
});
```

> 「这段代码的含义是：**在执行工具之前，判断一下是不是要运行 SQL；如果是要运行 SQL，就检查代码的安全性；如果不安全，就拒绝执行并反馈原因给模型。**」

| 要点 | 说明 |
|---|---|
| 订阅的事件 | `tool_call` = 「**工具执行前**这个时间节点」（10 节点里的 ⑧） |
| 判断对象 | 工具名 + 参数 |
| 拒绝方式 | 返回拒绝标记 + **原因**（原因会进上下文，让模型自己改） |
| 为什么不能只靠提示词 | 提示词是「请求」，拦截是「强制」；生产环境必须有后者 |

> 「这样就实现了上述需求。**有了事件订阅机制，大部分你需要的个性化操作都可以轻松完成。**」

视频列的可订阅场景（都是 10 节点的直接映射）：

| 你想做的事 | 订阅哪个节点 |
|---|---|
| **自定义上下文压缩的方法** | 压缩/上下文相关事件（对应 turn 结束 ④ 附近） |
| **在某个地方注入上下文** | 模型调用前 ⑤ |
| 记录 trace 时长、落库 | trace 开始 ① / 结束 ② |
| 防无限循环 | turn 开始 ③ |
| 流式敏感词检测 | 模型调用时 ⑥ |
| 危险工具拦截 | 工具执行前 ⑧ |
| 结果脱敏/截断 | 工具执行后 ⑩ |

> 「常见的事件和场景**我都在 skill 中做了整理**，真的非常丰富。说真的我自己都**没有一一去看完过**，反正**需要用的时候就直接交办给 AI**，AI 自己决定要订阅哪个事件。」

## 12. 事件订阅：参与者与观察者

这是二开机制里**唯一需要理解「两种订阅」差别**的地方，也是视频最后讲的一个技术点。

### 12.1 两种订阅方式

> 「顺便说一下，还有另外一种订阅方式……**SDK 的用法有点差异，但差异不大**，还是定位出事件名，然后写入业务逻辑。」

| | **订阅 A（可拦截）** | **订阅 B（只观察）** |
|---|---|---|
| 能否改变 Agent 行为 | ✅ 能 | ❌ 不能 |
| 有没有返回值 | 有（返回值影响流程） | 「**有返回数据，它也不要**」 |
| pi 的角色 | 把控制权交给你 | 「**只负责将数据发给这类订阅者**，至于订阅者干嘛，它不管，也不要自己直接进行下一步操作」 |
| 典型用途 | **拦截工具、修改系统提示词**、改压缩策略 | **打印前端信息、日志记录** |
| 一句话定位 | **参与者（participant）** | **纯粹的观察者（observer）** |

> 「一个是**参与者**，一个是**纯粹的观察者**，可以这么简单的理解。」

```
                 ┌──────────────────────────────┐
   事件发生 ───► │  订阅 A（参与者）             │──► 可以「改道」
                 │  返回值 = 指令（block / 改写） │     （拦截、替换、注入）
                 └──────────────────────────────┘
                 ┌──────────────────────────────┐
   事件发生 ───► │  订阅 B（观察者）             │──► 只读，结果被丢弃
                 │  返回值 = 无人接收             │     （日志、埋点、推前端）
                 └──────────────────────────────┘
```

### 12.2 怎么选：一张判据表

| 你的需求 | 该用哪种 | 理由 |
|---|---|---|
| 拦截危险 SQL | **A** | 必须能「否决」 |
| 改系统提示词 / 注入上下文 | **A** | 必须能「改写」 |
| 自定义压缩策略 | **A** | 必须能「替换」压缩结果 |
| 把每条消息打到前端 | **B** | 只需要「看到」 |
| 日志 / trace 上报 / 计费统计 | **B** | 绝不能影响主流程 |
| 调试时打印每个 turn 的 token | **B** | 同上 |

> 「因此，pi 的这类机制通常也叫**扩展（extension）**，可以**扩展 Agent 的功能**。」
>
> 「现在你应该能够体会到，为什么说用 pi 做二次开发很方便了吧。在这样的机制下，当我们有一个个性化需求时，**可能唯一的问题就是：我要订阅哪个事件呢？**」

📌 补充：「唯一的问题是订阅哪个事件」这句话是**整个二开体验的真实瓶颈**。10 个节点听起来少，但每个节点上可做的事、可读的字段、可返回的指令都不一样。实践建议：**先打印（用 B 型订阅把所有事件和 payload 打一遍），看清时序，再改成 A 型去拦截。** 上来就写拦截，十有八九拦错位置。

### 12.3 skill 为什么还值得用（视频的收尾论证）

> 「其实你**不需要使用任何 skill**，直接跟 AI 说『基于 pi-agent 进行开发』，它也会去**搜索官方文档**然后完成开发。那我们为什么还要使用这个 skill 呢？」

| # | 理由（原话） | 实际价值 |
|---|---|---|
| 1 | 「这样可以**节省 token 与时间**」 | 少一轮「搜文档 → 试错」 |
| 2 | 「我不仅介绍了 SDK 的用法，也把**我从 pi-agent 源码中提炼出来的最佳实践和我踩过的坑**都写了进去」 | 输出质量更高 |
| 3 | 「如果有个功能你不知道怎么设计，也可以使用这个 skill 让 AI **搜索同类的扩展进行参考**」 | 「AI 搜到同类项目后，会**自行解读源码**，结合你的项目给你一个解决方案」 |

第 2 条有个具体例子（也呼应第 9 章）：

> 「比如在**设计工具的章节**，我就特别说明：**处理工具报错的最佳实践是——预估可能的错误，将这个报错原因和解决办法封装成工具调用提交给模型。** 所以在我们之前的案例中，AI 就会按照这个思路去设计工具。」

收尾一句很有信息量：

> 「因此我觉得这个 skill 还是很适合新手的。这个 skill 我也会**持续完善**，至于**什么时候停止维护，那就取决于大模型什么时候内化这个 skill 吧**。」

📌 补充：这句话其实给了「Prompt / Skill 类资产」的生命周期判据——**它们是被模型能力追赶的临时补丁**。所以写 skill 时应当追求「把判断标准写清楚」，而不是「把步骤写死」；前者模型内化后仍然有效，后者模型一升级就过时。

### 13.2 三个「必须覆盖」的默认值

视频明确点了两个，又补了第三个，这里合并成一张表——**这是二开最容易被忘的一步**：

> 「在刚刚的介绍中，我们**两次提到系统提示词和工具是 pi 原生就有的，你得覆盖掉**。那么你可能会想到，**还有没有什么其他东西也是必须覆盖掉的？还真的有一个**，那就是**会话记录保存的机制**。」

| # | 默认行为 | 为什么必须覆盖 | 怎么覆盖 |
|---|---|---|---|
| 1 | **coding agent 的系统提示词** | 你的场景不是写代码 | 传自定义基础人设 + 清空文件型上下文 |
| 2 | **内置工具集** | `read` / `edit` / `bash` 对 data agent 是风险 | 关全部内置，只挂自己的 |
| 3 | **会话记录存 JSON 文件** | 垂直 Agent 通常要进数据库 | 「接入这么一个**配置**，pi-agent 就**不会将会话记录保存为文件**了」 |

> 「pi 会**默认将会话记录以 JSON 文件的方式保存在磁盘中**，但是我们开发自己的垂直 Agent 一般想**保存在数据库里**，怎么办呢？你只需要接入这么一个配置……**至于怎么保存到数据库中呢，那就是另外一件事情了**，其实也很简单，无非就是**拿到对话数据，然后存入数据库**，这我们就不展开了。」

⚠️ 这三个配置项的**具体参数名视频都没有念**（转写为「这个参数」「这么一个配置」）。落地时去官方文档搜关键词：`systemPrompt` / `tools` / `session` / `storage`。

📌 补充：把这三件事做成一个「**开机自检清单**」，比记 API 有用得多：
> ```
> 启动时打印：
>   systemPrompt 长度 = ?      （是不是还在用默认 coding 人设）
>   已启用工具 = [...]          （有没有混进 read/edit/bash）
>   session 存储 = file | db    （是不是还在写本地 JSON）
>   model compat = {...}        （有没有声明 usage 缺失）
> ```
> 这四行能挡掉二开阶段 80% 的「莫名其妙」问题。

### 13.3 坑表

| # | 坑 | 现象 | 规避 |
|---|---|---|---|
| 1 | **coding plan 套餐不支持第三方客户端** | 配好了但 401/403 | 先确认套餐条款（视频点名 GLM coding plan 不支持 pi） |
| 2 | **内网模型不兼容** | 请求报错 / 工具调用不生效 | 按「必须项/可选项」分档评估；先 curl 验流式与 `tool_calls` |
| 3 | **忘改基础人设** | Agent 张口就「我先看看项目结构」 | 二开第一步就换人设 |
| 4 | **忘关内置工具** | data agent 试图 `edit_file` | `builtinTools: []` |
| 5 | **会话仍在写本地 JSON** | 部署到容器后会话丢失 | 关默认落盘，接数据库 |
| 6 | **把拦截写成观察者** | 危险 SQL 照样执行 | 用能返回指令的订阅 A |
| 7 | **只靠提示词防危险操作** | 模型绕过 / 幻觉出 `DROP` | 提示词 + 代码层拦截 + 数据库只读账号，三道 |
| 8 | **工具报错直接抛出** | 循环中断，任务崩 | 错误当结果回灌（第 9.3 节） |
| 9 | **无限循环** | token 烧穿 | turn 上限（如 100）+ 进度检测 |
| 10 | **压缩放在下一轮开头** | 用户干等 | 上一轮结束就压（第 8.3 节） |
| 11 | **截断不留指针** | 模型以为文件就这么短 | 必须写「已截断，全文见 path」 |
| 12 | **进度回调没接前端** | 长任务看起来像卡死 | 后端订阅事件 → 推 SSE/WebSocket |
| 13 | **终止信号没往下透传** | 点了停止，SQL 还在跑 | `signal` 一路传到 db 驱动 |
| 14 | **误解 turn 的边界** | turn 计数/成本估算全错 | 记住：**工具不算 turn，下一次模型调用才算** |
| 15 | **fork 了仓库** | 三个月后无法 merge 上游 | 用配置 + 扩展，不改源码 |

## 15. 📌 补充：视频没展开但动手就会撞上的部分

> 以下**全部是本文的延伸**，不是视频原意。视频明确说「技术细节我另外放在文档里面」。

### 15.1 「300 行」到底怎么算

视频的说法是「300 行能写出一个 coding agent」，但那个 demo：**3 个工具 + 1 个循环 + 1 段提示词**。真实项目里 300 行会迅速膨胀，膨胀点按顺序是：

| 膨胀点 | 大概增量 | 为什么 |
|---|---|---|
| 工具数量（3 → 10） | +200 行 | 每个工具的 schema + 实现 + 错误分支 |
| 流式输出 | +100 行 | SSE 解析、增量拼接、中断 |
| 上下文截断/压缩 | +150 行 | 阈值、落盘、模板、替换 |
| 重试与限流 | +80 行 | 429/5xx、指数退避 |
| 会话持久化 | +100 行 | 序列化、恢复、并发写 |
| 权限与沙箱 | +200 行 | 路径校验、命令白名单 |

> 结论：**「300 行」是理解门槛，不是交付门槛。** 这也正是第 11 章「不要自己写，用 pi 当基座」的论据。

### 15.2 压缩的三种失败模式

视频讲了「怎么压」，没讲「压坏了怎么办」：

| 失败模式 | 表现 | 对策 |
|---|---|---|
| **丢约束** | 压完之后 Agent 开始违反最初的要求 | 约束条件**永不压缩**（core 区） |
| **丢指针** | 摘要说「已修改 foo.ts」，但没说改成什么 | 摘要里保留**文件路径 + 关键 diff 片段** |
| **反复压缩** | 压完又涨，涨了又压，越压越糊 | 记录压缩次数；超过 2 次就换新 session |

### 15.3 事件订阅的调试姿势

| 步骤 | 做法 |
|---|---|
| 1 | 先全量打印（**观察者**订阅所有事件），看清时序 |
| 2 | 确认事件名与 payload 字段**真的存在**（别照抄旧版本文档） |
| 3 | 再改成**参与者**订阅，**先只 return `undefined`**，确认不炸 |
| 4 | 最后才加 `block` / 改写逻辑，并为每次拦截**打日志** |
| 5 | 拦截逻辑要**幂等且快**——它在关键路径上，慢 100ms 就是每个工具调用慢 100ms |

### 15.4 用 AI 读文档写扩展的风险边界

视频推荐「让 AI 读项目文档、按需求开发扩展」。有效，但有三个前提：**文档是当前版本的**（模型对旧 API 的记忆会污染输出，且它不会告诉你「已废弃」）；**你能读懂产出的代码**（扩展跑在关键路径上，读不懂等于交出控制权）；**有最小验证**（装完先跑一个必然触发它的用例，而不是等线上发现没生效）。

### 15.5 与 Claude Code 的取舍（一句话版）

pi 是「**给你机制，其余你自己长**」，Claude Code 是「**给你成品，你用就行**」。要造自己的 Agent 选前者，要立刻干活选后者——这也是第 2 章三重用法能成立的根本原因。

## 16. ✅ 动手清单

> 用法：从零到「跑通第一个自定义工具」，按顺序打勾。**第 1~4 步不加任何自定义代码，目的是先建立一个能对比的基线。**

**A. 先把它当产品用（建立基线）**

- [ ] **1.** 去官网按你的平台装好 pi，终端里敲 `pi` 能进 TUI。
- [ ] **2.** 建 `~/.pi/agent/models.json`，接一个**支持 function calling** 的模型；`/model` 能切到它并正常对话。
- [ ] **3.** 在一个真实项目目录里让它干一件小事（比如「读一下 README，总结三个要点」），**观察它调了哪些工具、调了几轮**——这就是第 7 章的 trace/turn 实物。
- [ ] **4.** 装一个官方扩展（建议先装 Web UI），确认「装扩展 → 启动可见 → 能用」这条链路通。

**B. 读源码（把原理对上号）**

- [ ] **5.** 在源码里找到 `ai` / `agent` / `coding-agent` 三个包，**确认 `agent` 包只做循环**（找出那个 `while` 或递归入口）。
- [ ] **6.** 在 `agent` 包里把 **10 个节点**对应的常量/类型找出来，抄成一张自己的清单（名字可能与我写的不同）。
- [ ] **7.** 找到**上下文截断**的实现，确认它「落盘 + 只回路径」的两个动作分别在哪。
- [ ] **8.** 找到**压缩触发**的那段判断，看清它用的是「剩余可用 token」还是「已用比例」。

**C. 跑通二开（第一个自定义 Agent）**

- [ ] **9.** 新建一个空项目，装上依赖，用 SDK 起一个最小 Agent：**只传自定义基础人设，关掉全部内置工具**。
- [ ] **10.** 写第一个工具：**一个只读的 `run_sql`（或任何你的领域动作）**，用 `defineTool` 定义 name / description / parameters / execute。
- [ ] **11.** 故意让工具报错一次（传个不存在的字段），**确认模型收到了报错并自己纠正**——这是第 9.3 节那条原则的验收。
- [ ] **12.** 给 `execute` 接上**进度回调**，前端（或控制台）能看到「正在查询…」；再接上**终止信号**，点停止能真的停。
- [ ] **13.** 订阅 `tool_call`，**拦截一次 `DROP` / `DELETE`**，确认模型收到的是「被拒绝 + 原因」而不是崩溃。
- [ ] **14.** 关掉默认的 **JSON 会话落盘**，把对话写进数据库（哪怕先用 SQLite）。
- [ ] **15.** 跑一次「**开机自检**」：打印人设长度、启用工具列表、session 存储位置、model 兼容声明——四项都对，才算二开完成。

## 17. 🔗 与其他笔记的关系

本文是独立成篇的（单独放在 `pi-agent/` 目录），但和 `agent/` 目录下的 4 篇是**同一个知识网络**里的不同切片：

- **《从零到一设计 Agent：结合生产实践（Pi / Claude Code 综述）》**：给的是 **8 层架构总图**（L0 模型底座 / L1 内核 / L2 行动 / L3 记忆 / L4 上下文 / L5 边界 / L6 协作 / L7 工程 / L8 进化）。本文对应的是其中 **L1 内核 + L2 行动**的**单项目源码级展开**——那一篇说「内核要极小、只有四种设计模式」，本文给了一个 70k star 项目的具体实现：内核就是一个包，只维护循环。

- **《Agent 上下文分层管理：结合 Pi、Claude Code 与生产实际的 Harness 设计》**：讲 **L4**，是**产品视角的横向综述**（五家对比）。本文第 8 章与它的交集最大，但**结论的落点不同**：那一篇讲「分层 / 按需 / 压缩 / 保护 / 隔离」五件套的方法论，本文讲「pi 只做了截断 + 压缩两件，其余交给扩展」。读的时候建议对照着看——**EP02 说「Pi 把策略交给你写」，本文第 12 章告诉你「那个『交给你写』的接口是事件订阅」。**

- **《Agent Memory 记忆管理》**：讲 **L3**（存什么、怎么取）。本文与它的接触点只有一个：**会话记录默认落 JSON 文件，二开时要改成数据库**（第 13.2 节）。那一篇管「记忆怎么设计」，本文只管「这个默认值必须被覆盖」。

- **《用 Langfuse 搭建评测闭环》**：讲 **L7 可观测与评测**。本文与它的接缝是**第 7 章的 10 个节点**——① trace 开始/结束记时长、③ turn 计数、⑦ 统计 usage，这三处就是埋点的天然位置。**先有节点，才有 trace；先有 trace，才有评测。**

一句话串起来：**总图给坐标系 → 本文填 L1/L2 的具体实现 → EP02 补 L4 的方法论 → EP03 管 L3 的进出 → EP04 验证前面所有改动。**

> **Agent 的本质就是「模型 + 工具 + 循环」这三件事，300 行就能写完；真正难的是这个循环外面的 harness——pi-agent 的价值不在于它替你写循环，而在于它把这 10 个可干预节点、上下文截断与压缩、工具调用的四段容错，全都做成了你不用 fork 就能覆盖的默认值。**
