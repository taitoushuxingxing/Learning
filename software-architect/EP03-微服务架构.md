## 1. 第一章 为什么需要微服务：从一场大促事故说起

本章用四个问题推进：

| 问题 | 一句话答案 |
|---|---|
| 单体架构真的过时了吗？ | 没有，它在小规模下是**最优解** |
| 微服务拆的到底是什么？ | 拆的是**运行时边界**，不是代码目录 |
| 拆完会多出哪些新麻烦？ | 6 个，正好对应 Spring Cloud 的 9 个组件 |
| 什么样的团队该拆、什么时候不该拆？ | 疼了才拆；不疼就继续写单体 |

### 1.1 开场事故：一行优惠券代码，全站挂了 40 分钟

故事是这样的（作者说这个例子是他编的，现实里不会有 40 万行的单体，只为讲清道理）：

一家电商公司有一个标准的单体应用：**40 万行代码、一个 Git 仓库、打成一个包部署**。订单、商品、库存、会员、优惠券全在这一个包里。

| 时间 | 发生了什么 |
|---|---|
| 大促前一天 23:00 | 一个开发改了**一行**优惠券的判断条件 |
| 23:00 - 03:00 | 走公司流程：打包 → 跑**全量回归测试** → 灰度 → 审批，几个小时 |
| 凌晨 03:00 | 上线 |
| 第二天大促高峰 | 优惠券模块抛了一个**空指针** |
| 之后 40~50 分钟 | 空指针在循环里不断抛出，把**线程池占满** → 商品详情页打不开 → 下单也挂了 → **全站不可用** |

**代价清单**：约 **200 分钟的全量回归** + **40~50 分钟的全站故障**（还是大促期间）+ 公关危机。全是一行代码换来的。

**但作者要你注意的不是「他写错了代码」。**

> 写错代码在哪里都会发生，微服务里也一样会有 bug。
> **问题在于：在单体应用里，任何一行代码都属于同一个「部署单元」。**

什么叫部署单元？就是**发布时的最小整体**。你没有「只发布优惠券」这个选项——改一行，就要把整个包重新走一遍流程。

```
单体应用（一个 JVM 进程）
┌──────────────────────────────────────────────┐
│  线程池（共享）  堆内存（共享）  连接池（共享）  │
│  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ │
│  │ 优惠券  │ │ 商品   │ │ 订单   │ │ 支付   │ │
│  │  💥    │ │  ✗     │ │  ✗     │ │  ✗     │ │
│  └────────┘ └────────┘ └────────┘ └────────┘ │
└──────────────────────────────────────────────┘
   一个模块「失血」，全身都要「输血」
```

作者的原话很形象：「一个模块它炸掉了，它失血了，可能就要给全身都输血。」

你可能会想：那把优惠券拆出去不就行了？——**思路是对的，但「拆」这个字里面有很深的玄机。** 很多人拆了很多东西，最后拆出一堆更难维护的东西，反而给工作带来更大麻烦。

### 1.2 给单体说句公道话：它真的是个好东西

| 优点 | 具体表现 | 为什么值钱 |
|---|---|---|
| **① 一次打包，一次部署** | 本地跑一个 `main` 方法整个应用就起来了，一个数据库一个缓存就没了 | 不用先启动注册中心、再启动配置中心、再启动几个服务才能调试一个功能 |
| **② 调用就是方法调用** | 订单调库存就一行 `orderService.create()`，不走网络、不走序列化、没有超时 | 它们在**同一个 JVM**；出了异常，一条堆栈从 controller 打到 mapper，几分钟定位 |
| **③ 事务就是一个注解** | 扣库存和扣余额在同一个库里，一个 `@Transactional` 数据库就保证要么都成功要么都失败 | 不用担心「扣到一半失败」——**这件事在单体里基本不存在** |
| **④ 重构成本最低** | 改一个类名，IDE 一键重命名，全项目生效 | 不会出现「另一个服务还引用着我的旧接口」 |

**结论（顺理成章）**：团队 10 人以内、流量平稳、产品还在验证期、方向每周都在变 → **单体就是最优解**。

> 作者原话（很狠）：「你今天拆好了 5 个服务，明天需求一改，5 个服务要一起动——**那不是架构，那是在给你自己上刑**。」

所以：**微服务不是用来纠正错误的，它是用来应对增长的。单体要等规模起来了，才需要去还一些单体会出现的债。**

### 1.3 单体的五道坎：症状 → 后果

规模一大，单体就开始「生病」。五个症状，每个都有一个后果，这五条就是后面「拆」的正当性来源。

| # | 症状 | 具体表现 | 后果 | 欠的是哪笔债 |
|---|---|---|---|---|
| 1 | **部署耦合** | 代码打成一个包，没有「只发布这一块」的选项；改优惠券要跑全站回归 | 回归从 1 小时变成一两百分钟 → 发布频率被迫降下来 → 业务迭代被卡脖子 | 发布效率 |
| 2 | **故障放大** | 所有模块共享同一个 JVM 的线程池、内存、连接池 | 任何一个模块死循环、内存泄漏、线程占满，都会**传染给所有模块** | 可用性 |
| 3 | **扩容粒度太粗** | 秒杀大促只有订单和库存压力大，但扩容最小单位是**整个应用** | 只能把整个应用复制 10 份 | 资源成本 |
| 4 | **技术栈锁死** | 所有模块共用一个运行环境 | 想把某模块升 Java 17，但别的模块是 Java 8 依赖，就升不了；想用 Python 写推荐算法，几乎不可能 | 技术演进 |
| 5 | **组织协作** | 上百个开发提交同一个仓库 | 合并冲突天天有，上线排队到下周 → 大家策略变成「公共代码谁也别动」→ 代码开始腐烂 | 组织 |

第 3 条有一句特别好记的话：**「3% 的代码承担了流量，但 100% 的代码都消耗了机器。」**

第 2 条对应开场那个事故：**故障是没有隔离墙的。这是单体应用的第二笔债。**

第 5 条最隐形也最要命：「这已经不是技术问题了，而是组织问题。**但归根结底，它依然是架构的问题。**」

📌 **补充**：第 5 条的准确名字叫 **康威定律（Conway's Law）**——「系统架构会逐渐长成组织沟通结构的形状」，作者在第 2、4 章会正面用到它。它的逆命题（康威逆定律）也成立：**你想让架构变成什么样，就先把团队切成什么样**。这也是为什么很多公司拆微服务之前，先拆组织（按业务域组队，而不是按前端/后端/测试分层组队）。

### 1.4 微服务到底是什么：一句话 + 三个「独立」

**定义（作者原句）**：把一个大应用拆成**一组小服务**，每个服务**独立开发、独立部署、独立运行**，服务之间通过**轻量协议**相互调用。

最重的词是 **「独立」**，展开成三个特征：

| 特征 | 含义 | 解决了哪道坎 |
|---|---|---|
| **① 独立部署** | 改完只发优惠券服务，10 分钟上线；其他服务的人不用等你；回归只跑优惠券范围 | 部署耦合（几百分钟的全量回归**直接消失**） |
| **② 独立进程** | 每个服务跑在自己的 JVM，有自己的线程池、自己的堆内存 | 故障放大（优惠券崩了，商品详情页**毫发无伤**——故障有了隔离墙） |
| **③ 按业务能力划分** | 一个服务对应一个业务能力：订单、库存、账户各是一个服务 | 这是拆分的关键，第 2 章细讲 |

**两个反例**：

> **微服务不是把 controller 层拆成一个服务、service 层拆成一个服务**——那是**技术分层**，不是**业务拆分**。
> **「微」不是代码少**——你拆出一个 200 行的服务但到处依赖别人，那不叫微服务，**那叫麻烦**。这个「微」指的是**职责小、边界清楚**。

**一个好用的比喻：老式大内科 vs 分科医院**

| 医院 | 对应架构 | 表现 |
|---|---|---|
| 老式大内科（一个全科医生看所有病） | 单体 | 医生一请假，整个科停诊 |
| 分科之后（各科独立排班出诊） | 微服务 | 心内科停诊，**不影响骨科** |

但**分科是有代价的**，而且代价刚好就是微服务的三件麻烦事：

| 分科的代价 | 对应的技术问题 | 对应组件 |
|---|---|---|
| 病人在科室之间**要走动** | 服务之间要**网络调用** | 注册中心 + OpenFeign |
| 疾病史有时要**跨科共享** | **数据一致性** | Seata / 最终一致 |
| 大厅要有**导诊台**告诉病人去哪 | **统一入口** | API 网关 |

> **这三种麻烦，在小诊所（单体）里根本不存在。** 它们全都是「分科」这个动作带来的新增成本。而这三个麻烦加上另外几个，就构成了 **Spring Cloud 全家桶存在的理由**。

### 1.5 拆的到底是什么：模块化 ≠ 微服务

你的单体应用是不是也分了包？`com.shop.order`、`com.shop.stock`，包名清清楚楚，模块之间尽量不互相引用。**那算不算微服务？差得还比较远。**

| 维度 | 左边：模块化（同一个包分目录） | 右边：微服务（真拆） |
|---|---|---|
| 运行位置 | 同一个 JVM | **独立进程**，独立端口 |
| 打包 / 发布 / 回滚 | 打同一个 jar，整体一起 | **各打各的包，各自独立** |
| 数据库连接池 | 共享 | 各用各的 |
| 订单调库存 | 一行方法调用 | **网络调用** |
| 数据库 | 一个库 | **各有一个库** |
| 解决什么问题 | **代码可读性** | **运行时的隔离与自治** |

**区别就一句话**：**左边崩的是「进程」，右边崩的只是「其中一个进程」。**

所以判断标准非常简单，作者让你记下来（还补了一句「可以拿它回去检验一些微服务项目，**包括你自己准备写在简历上的项目**」）：

> **这个模块能不能单独重启、单独发版、单独扩容？能，才叫微服务。**

**反例三：分布式单体（Distributed Monolith）**

市面上很多「微服务项目」：服务拆成了 5 个，但 **5 个服务连着同一个数据库**、**发版必须凑齐一起发**（接口之间有隐式依赖）。

> 它是把单体的耦合**原封不动保留了 5 份**，还额外附赠了**网络调用**这个不稳定因素。**所以它有时候比单体更糟糕。**

**回到事故：答案是什么**

| 层次 | 结论 |
|---|---|
| 问题不在哪 | 不在代码，在**部署单元** |
| 只要什么成立 | 只要所有模块还在同一个进程里，改一行就要全量回归，一个 bug 就可能让全站陪葬 |
| 解法不是 | 把优惠券代码搬个包 |
| 解法是 | **把优惠券这个进程独立出去** |

> **微服务拆的是「运行时的边界」，不是「代码的目录」。**

### 1.6 拆完多出 6 个麻烦：Spring Cloud 存在的理由

| # | 麻烦 | 具体的疼 | 追问 |
|---|---|---|---|
| 1 | **调用会失败** | 单体里方法调用不会「失败」，最多抛异常（那是代码写错了）。服务间走网络：会超时、丢包、对方在发布、对方内存满了 | 对方不回我怎么办？重试几次？等多久？业务怎么办？ |
| 2 | **地址会变** | 库存服务今天在 8082，明天扩到 5 台，后天缩回 3 台，还有一台挂了 | 地址写死在配置里，第一次扩容就得改代码发版 |
| 3 | **配置满天飞** | 20 个服务 × 3 套环境，数据库地址、超时、开关上百个配置散在几十个文件 | 改一个数据库地址要改 20 个文件、发 20 次版 |
| 4 | **数据不再一家说了算** | 库存一个库、账户一个库，一个 `@Transactional` 管不了两张表 | 扣库存成功、扣余额失败，数据库不会帮你回滚 |
| 5 | **出了问题找不到原因** | 一次下单穿过 6 个服务，日志散在 6 台机器 | 用户说下单失败，你连他在哪一步失败的都不知道 |
| 6 | **入口没人把守** | 100 个服务都暴露公网？鉴权写 100 遍？限流做 100 份？ | 需要统一入口和统一认证 |

**这张表和后面的组件一一对应（全课最重要的一张映射）**：

| 麻烦 | 解法 | 组件 |
|---|---|---|
| 1 调用会失败 | 超时 / 重试 / 熔断 / 降级 | Sentinel |
| 2 地址会变 | 注册中心（动态通讯录） | Nacos Discovery |
| 3 配置满天飞 | 配置中心 | Nacos Config |
| 4 数据不一致 | 分布式事务 / 最终一致 | Seata、MQ |
| 5 找不到原因 | 链路追踪 + 日志聚合 | Micrometer Tracing + SkyWalking/Zipkin + ELK |
| 6 入口没人把守 | 统一网关 | Spring Cloud Gateway |
| （服务怎么互相调用） | 声明式调用 + 负载均衡 | OpenFeign + LoadBalancer |

> **作者的核心判断**：「Spring Cloud 其实不是什么高科技的发明，**它就是这 6 个麻烦的标准答案**。你理解了麻烦，工具自然水到渠成。如果你不理解这个麻烦，你单纯去背组件名，**可能也会用不对**。」

## 2. 第二章 微服务的全景：先看骨架，再看配饰

### 2.0 为什么「结构」要优先于「框架」

这一章**不碰任何具体技术**，只看结构和原则。为什么？

> 「你先把『为什么需要网关』想明白，那 Spring Cloud Gateway 的配置其实就十几分钟的事情。反过来，就算你背熟了网关所有的配置项，**但你不知道它该站在哪儿，上线照样会出错**。」

一句话：**结构是骨架，框架只是外面的配饰。** 本章四个问题：系统由哪些零件组成（2.1）、服务怎么拆（2.2）、怎么通信（2.3）、数据一致性怎么办（2.4）。

### 2.1 一张图看懂微服务系统

**看图方法**：**左边**是请求走过的路（从上到下），**右边**是每个服务都要用的公共能力（横着贯穿所有服务）。

```
                  ┌─────────────────── 横切能力：贯穿所有服务，缺了跑不稳 ───────────────────┐
                  │  服务注册与发现   配置中心    熔断限流    链路追踪    日志聚合           │
                  │  （Nacos）      （Nacos）  （Sentinel） （Tracing）  （ELK）             │
                  └───────────────────────────────────────────────────────────────────────┘

   APP    网页    小程序    合作伙伴系统
     │      │       │            │
     └──────┴───────┴────────────┘
                  │  所有流量都从这里进
                  ▼
        ┌──────────────────────┐
        │      API 网关         │  路由 · 鉴权 · 限流 · 灰度 · 日志(traceId)
        │   （唯一入口）         │  任何请求都别想绕过它
        └──────────┬───────────┘
                   │
     ┌─────────────┼─────────────┬──────────────┐
     ▼             ▼             ▼              ▼
 ┌────────┐   ┌────────┐   ┌────────┐   ┌──────────┐
 │ 订单    │   │ 库存    │   │ 账户    │   │  通知     │
 │ 服务    │   │ 服务    │   │ 服务    │   │  服务     │
 └───┬────┘   └───┬────┘   └───┬────┘   └────┬─────┘
     │            │            │             │
     ▼            ▼            ▼             ▼
 ┌────────┐   ┌────────┐   ┌────────┐    （无库，纯消费）
 │ 订单库  │   │ 库存库  │   │ 账户库  │
 │ MySQL  │   │ MySQL  │   │ MySQL  │
 └────────┘   └────────┘   └────────┘

           ┌────────────────┐      ┌────────────────┐
           │ Redis 缓存/锁   │      │  MQ 异步解耦    │
           └────────────────┘      └────────────────┘
```

**逐层读**：

| 层 | 是什么 | 关键点 |
|---|---|---|
| 客户端 | APP / 网页 / 小程序 / 合作伙伴系统 | **所有流量都从这里进** |
| **API 网关** | 把门的（对应第 6 个麻烦「入口没人把守」） | 四件事：**路由**（按路径决定转发给谁）、**鉴权**（验明你是谁）、**限流**（把刷量的挡掉）、**灰度**。任何请求都别想绕过它 |
| 服务层 | 订单 / 库存 / 账户 / 通知 | 见下表 |
| 数据层 | 订单库、库存库**分开的两个 MySQL** + Redis（缓存/分布式锁）+ MQ（异步） | 「第 4 个麻烦——数据不再一家说了算——**就是从这里开始的**」 |

**服务层每一条「那句话」特别重要**：

| 服务 | 它拥有什么 | 作者的原话 |
|---|---|---|
| 订单服务 | 订单相关的所有事，包括订单库 | 「订单相关的所有事都归他」 |
| 库存服务 | 库存数，**只有它有权改** | 「只有他有权去改库存数」 |
| 账户服务 | 钱的账 | 「钱的账只认他」 |
| 通知服务 | 短信、站内信 | 「它挂了，**也不影响下单**」 |

最后一句话就是「按业务重要性分级」的思路。

**右栏 5 个公共能力，每一个对应一个麻烦**：

| 公共能力 | 解决的麻烦 |
|---|---|
| 服务注册与发现 | 地址会变 |
| 配置中心 | 配置满天飞 |
| 熔断限流 | 调用会失败 |
| 链路追踪 + 日志聚合 | 出了问题找不到原因 |

> **左边 + 右边 = 一套完整的微服务系统。**
> 「如果缺右边这一栏，左边那条路也能跑，**但是你跑不稳**。很多团队缺乏公共能力，就算把服务拆出来了，也可能天天出故障、天天救火。」

### 2.2 服务怎么拆：三条原则 + 三条建议

**这是微服务里最难、也最不可逆的一步。**

> 「代码写错了，改一行就完事了。**边界划错了，未来每一次发版都要去还债。**」

#### 原则一：按业务能力拆，不是按技术分层

| | 正确 | 错误 |
|---|---|---|
| 拆法 | 订单服务里装着订单的 controller、service、DAO **全套** | 所有 controller 拆成「接口服务」，所有 service 拆成「逻辑服务」 |
| 能力 | 一个服务能独立完成「下单、取消、查询」完整业务链 | 每次操作都要跨服务 |
| 调用次数 | 一次下单 = 一次方法调用 | 一次下单 = **两次网络调用** |
| 结果 | 业务自治 | 性能更差、故障点更多，**什么好处都没换回来** |

> 「所以拆分的目的是**业务自治**，不是**目录好看**。」

#### 原则二：高内聚——经常一起改的放一块

作者给了一个极度实用的判断方法：**回想最近三个需求，每次改需求通常要动哪几块代码？那几块就该属于同一个服务。**

| 观察 | 结论 |
|---|---|
| 每次调优惠券规则，都要同时改「优惠券计算」和「营销页展示」 | 这两块应该在一起 |
| 每次改需求都要**跨三个服务一起发版** | 边界大概率画错了 |

#### 原则三：边界看数据归属——谁拥有这份数据，谁就是主人

订单表归订单服务，库存表归库存服务，账户表归账户服务。**别人想改你的数据，只能调你的接口。**

这条反过来用更好使：**把公司的数据归属表画出来，哪些表属于哪个业务域——服务边界基本上就出来了。**

#### 三条落地建议

| # | 建议 | 说明 |
|---|---|---|
| 1 | **起步先拆 3~5 个服务** | 把天然独立的分开就行，别一上来拆二三十个 |
| 2 | **一个服务由 2~8 人的小团队端到端负责** | 这是 **康威定律**：系统结构最终会长成组织的沟通结构。**你把服务切给谁，架构就会长成什么样** |
| 3 | **拆错了比不拆更贵** | 共享数据库、必须一起发版的「微服务」，等于把耦合复制了好几份，还附赠网络不稳定 |

### 2.3 服务之间怎么说话：同步还是异步

先上一个比喻（这套课最生活化的类比之一）：

| 方式 | 比喻 | 行为 |
|---|---|---|
| **同步调用** | **打电话** | 必须等对方接，你一句我一句，对方说完才挂 |
| **异步消息** | **发 QQ / 发微信** | 发完就去干别的，对方什么时候回，那是他自己的事 |

#### 同步调用：像调本地方法，但有天生的代价

场景：下单时订单服务调库存服务扣库存，**等**库存返回扣成功，订单才能往下走。

| 维度 | 说明 |
|---|---|
| 好处 | 实时，结果立刻知道，代码直观；OpenFeign 配一下，就像调本地方法 |
| 代价 | **对方慢你也慢，对方挂你也挂** |
| 具体数字 | 库存从 50ms 变 5s → 下单接口从 100ms 变 5s；库存直接宕机 → 下单也下不了 |
| 所以 | **同步调用必须配防护**：超时、重试、熔断、降级 |

#### 异步消息：别让「锦上添花」的事堵住主流程

场景：下单成功后还要发短信、加积分、更新统计报表。**用户需要立刻看到吗？不需要。**

解法：订单服务往队列发一条「订单已创建」的消息，**立刻返回**。通知服务什么时候消费、消费得怎么样，主流程不关心。

| 好处 | 说明 |
|---|---|
| **解耦** | 通知服务挂三天，消息在队列里安安静静排着，恢复后接着消费，**一条都不丢** |
| **削峰** | 大促瞬间 10 万个请求涌进来，队列顶在那里，下游按自己的能力慢慢处理 |
| **代价** | **最终一致，不是立刻一致**：积分可能晚 10 秒到账，你要接受这一点 |

作者顺手指了一个生活细节：「你平时在购物网站买东西，是不是会看到『积分将在几分钟到一天内到账』？**那后面可能都是有消息队列在做异步通信的。**」

#### 口诀：一句话选型

> **先问一句：这一步失败了，业务还能继续吗？**

扣库存、扣款不能继续 → **同步**；发短信晚 10 秒、积分晚 1 分钟不影响 → **异步**。
「用这样的一个判断，就能够解决很多的场景。」

### 2.4 数据库拆开之后：一致性怎么办

这是微服务**最容易翻车**的地方。

| 时代 | 结构 | 保证方式 |
|---|---|---|
| 单体时代 | 库存和余额在**同一个数据库** | 一个 `@Transactional`，数据库保证原子性 |
| 微服务时代 | 库存一个服务一个库，账户另一个服务另一个库 | **没有东西替你保证了** |

具体场景：库存扣成功了，账户那边网络超时——**库存扣掉的这个数，找谁退回去？数据库帮不了你，因为两个数据库谁也不认识谁。**

#### 三个策略（按推荐顺序）

**① 能不用分布式事务就别用（最容易被忽略）**

先**质疑业务本身**：这两步真的必须在同一个事务里吗？**改业务设计——先冻结，后确认**：

| 步骤 | 做什么 | 事务类型 |
|---|---|---|
| 1 | 下单时先**冻结**库存额度 | 本地事务 |
| 2 | 支付成功，再**真正扣减** | 本地事务 |
| 3 | 支付失败，**解冻** | 本地事务 |

> 冻结和扣减各自都是本地事务，**根本不需要跨服务事务**。这就把「技术问题」变成了「业务设计问题」——**往往是最便宜的解法**。

**② 最终一致（互联网业务的主流做法）**

核心思想：**可以接受中间几百毫秒两边数据不一致**，用消息 + 补偿把状态最终推齐。

```
扣库存成功 → 发一条消息 ──▶ 余额服务消费 → 扣余额
                    │
                    ├─ 消费失败 → 重试
                    └─ 重试还不行 → 反向补偿（把库存加回去）

用户看到「状态更新中」，几百毫秒后一切就绪。
```

**③ 用框架管（Seata）**：给跨服务的操作套一层**全局事务**，框架自动记录数据快照，哪一步失败就按快照自动回滚。**代码改动最小**，就一个注解的事。但「天底下没有免费的午餐」——要多部署一个协调者组件，有**性能开销**。

#### 两条铁律（比选哪个方案更重要）

| 铁律 | 含义 |
|---|---|
| **① 一个数据只有一个主人** | 两个服务同时写一张表，就是分布式事故的温床 |
| **② 不许幻想强一致** | 网络会超时、消息会重复、服务会重启——这些**基本都算「一定会发生」**。你的方案必须假设它们会发生，并且能够**自愈** |

## 3. 第三章 Spring Cloud 全家桶：9 个组件，9 个麻烦

### 3.0 定调：它不推翻你已经会的东西

> **Spring Cloud 不是一个新的框架，它是一组工具集。**

Spring Boot 项目照常写，controller / service / mapper 照常写，**变的只是「服务之间怎么协作」**。落地动作只有两个：**多引几个 starter，多加几行配置。**

本章顺序：先讲**版本体系**（很多人学 Spring Cloud 卡住，其实是被版本坑了），再讲 **9 个组件**，每个都回答「解决前面哪个麻烦、怎么用、什么时候不需要它」。

### 3.1 版本体系：三层联动，最容易翻车的地方

| 层 | 是什么 | 角色 |
|---|---|---|
| **Spring Boot** | 你熟悉的脚手架 | 地基 |
| **Spring Cloud** | 分布式工具集（抽象与规范） | 框架 |
| **Spring Cloud Alibaba** | 国内常用的**实现**（Nacos、Sentinel、Seata 都在这） | 落地件 |

> **这三层的版本是联动的，不是你想升哪个就升哪个。**

| Spring Boot | Spring Cloud | Spring Cloud Alibaba |
|---|---|---|
| 2.7.x | 2021.0.x | 2021.0.5.0 |
| 3.2.x | 2023.0.x | 2023.0.1.0 |

**为什么必须严格对应**：

> 「Spring Cloud 是在**特定版本**的 Spring Boot 基础上去编译的。版本错配，JVM 会告诉你 **`NoSuchMethodError`**——某个方法不存在。报错指向的类你可能都没听说过，**堆栈里全是你没写过的代码**。」

这种错误的体验是：**完全不知所措**。所以正确动作是：**先对版本表。**

**三条建议**：

| # | 建议 | 理由 |
|---|---|---|
| 1 | **新项目直接上 Spring Cloud Alibaba** | Nacos 管注册 + 配置，Sentinel 管熔断限流，Seata 管分布式事务——**一套整齐活**，中文资料多，出问题好搜 |
| 2 | **Netflix 那套别再用了** | Eureka、Hystrix、Ribbon **都已停止维护**。新项目引入它们，等于**主动买技术债**，将来要还 |
| 3 | **升级要三层联动** | 升之前先查对应表（以官方 Release Note 为准） |

📌 **补充**：Netflix 组件停更后的标准替代关系，面试常问——Eureka → **Nacos**；Ribbon → **Spring Cloud LoadBalancer**；Hystrix → **Sentinel**（或 Resilience4j）；Zuul 1 → **Spring Cloud Gateway**。

### 3.2 不要一次把 9 个组件全用上

| 阶段 | 需要什么 |
|---|---|
| 刚起步的微服务项目 | **注册中心 + 网关**就够了 |
| 后面补 | 链路追踪、配置中心 |
| 真出现对应故障时再引入 | 熔断、分布式事务 |

> **「技术不是越全就越安全。很多多余的能力，本身其实也是一种负担。」**

### 3.3 组件① 注册中心 Nacos：动态通讯录

**问题陈述**：单体时代 `orderService.create()` 这个类**就在那儿**，永远找得到。微服务时代，库存服务今天在 8082 那台，明天大促扩到 5 台，后天挂掉 1 台。**你把 IP 写死在配置里，第一次扩容就得发版。** 所以调用方需要的是一份**动态的通讯录**。

**五步工作机制**：

```
① 服务启动：上报「服务名 + IP + 端口」到 Nacos     → 服务注册
② Nacos 维护名单：stock-service 名下现在有哪几台活着
③ 心跳：每 5 秒打一次卡
     15 秒没打卡 → 标记为「不健康」
     30 秒没打卡 → 从名单摘掉
④ 调用方按服务名拉名单，缓存在本地，定期更新
⑤ 调用时从名单里挑一台（挑哪台 = 负载均衡的事）
```

**三个要点里的第二个最反直觉**：

> **服务重启期间，调用方可能短暂地找不到人。** 为什么？心跳还没超时，名单还没更新。
> **所以你的调用代码必须能容忍「偶尔找不到人」，要加重试。这不是 bug，这是这套机制天然的属性。**

```yaml
# application.yml
spring:
  application:
    name: stock-service        # 服务名，全局唯一且稳定
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
```

```java
@SpringBootApplication
@EnableDiscoveryClient          // 就这一个注解
public class StockApplication {
    public static void main(String[] args) {
        SpringApplication.run(StockApplication.class, args);
    }
}
```

> 「相当于你的服务就有了一个动态通讯录，就上到通讯录里去了。」

**两个提醒**：

| 提醒 | 说明 |
|---|---|
| **服务名要全局唯一、要稳定** | 它是服务之间互相认识的**唯一凭据**。今天叫 `stock-service`，明天改叫 `inventory-service`，**所有调用方都要跟着改** |
| **注册中心本身不一定是单点** | Nacos 支持集群部署，生产环境至少 **3 节点** |

### 3.4 组件② 配置中心 Nacos：同一个 Nacos 的第二个身份

> **同一个 Nacos，既能当注册中心，又能当配置中心。**

**问题**：20 个服务 × 3 套环境，配置散在几十个文件里。改一个数据库地址 → 20 个文件改一遍 → 20 个服务重新打包重启。

**思路**：**配置不放在代码库里，统一放 Nacos，服务启动时来拉取。**

```
① 服务启动 → 从 Nacos 拉配置     ② 本地生效
③ 在 Nacos 控制台改一条配置       ④ Nacos 通过「长轮询」秒级通知到服务
⑤ 服务动态刷新 —— 不重启
```

> **「不重启」这三个字非常有含金量。** 比如限流阈值想调大、某个功能开关想打开，改完立即生效——**这在单体时代是要发版才能做到的事。**

**三个好处**：

| 好处 | 具体 | 价值 |
|---|---|---|
| **① 环境彻底分开** | `namespace` 隔离 dev/test/prod，`group` 隔离业务线，`dataId` 对应服务名——**三级定位** | 生产配置**不再会误提交到 Git**，这本身就是对安全事故的预防 |
| **② 动态刷新** | 限流阈值、开关、超时时间改完立即生效 | 不用发版 |
| **③ 可审计可回滚** | 谁改的、什么时候改的、改了什么全有记录；一键回滚上一版 | **生产故障时能救命** |

**🔴 红线：配置中心不是保险箱**

> 数据库密码、API 密钥这类敏感信息，要配合**加密**或**专用密钥管理**。别以为放到 Nacos 就安全了——**Nacos 控制台是谁登录谁都能看得到的。**

```yaml
# bootstrap.yml（注意：不是 application.yml！）
spring:
  application:
    name: order-service
  cloud:
    nacos:
      config:
        server-addr: 127.0.0.1:8848
        namespace: prod          # 环境隔离
        group: shop              # 业务线隔离
        file-extension: yaml     # dataId = order-service.yaml
```

```java
@RefreshScope   // 配置变了，这个 Bean 会重建，@Value 自动刷新
@Component
public class RateLimitProperties {
    @Value("${shop.rate-limit.qps:100}")
    private int qps;
}
```

> **为什么必须写在 `bootstrap.yml`，不能写在 `application.yml`？**
> 因为**加载顺序**：`bootstrap` 先加载，服务才知道去哪里找配置中心。如果写在 `application.yml` 里，**等读到它的时候，配置加载阶段已经过去了**。「这个坑，初学者很容易踩到。」

📌 **补充**：Spring Cloud 2020 之后还需要额外引入 `spring-cloud-starter-bootstrap` 依赖，`bootstrap.yml` 才会生效。很多人「写了没反应」，其实是漏了这个依赖——这也属于作者说的「能卡你半天」的坑。

### 3.5 组件③ 网关 Spring Cloud Gateway：唯一入口

**问题**：100 个服务，难道都直接暴露公网？鉴权写 100 遍？限流做 100 份？

**思路**：**所有流量先过网关，它是整个系统唯一的入口。** 把「每个服务都要做的事」——鉴权、限流、日志、跨域——**全部收到网关，只做一次**。

**三大组件**：

| 组件 | 作用 | 一句话 |
|---|---|---|
| **路由 Route** | 一条路由规则 = **一个断言 + 一组过滤器 + 一个目标** | 请求该去哪 |
| **断言 Predicate** | 判断请求该不该走这条路由 | 按 **Path / 域名 / 请求方法 / 请求头 / 时间** 都能判（比如「工作时间才放行某个接口」） |
| **过滤器 Filter** | 请求转发前做一遍，响应回来后做一遍 | 网关**最丰富**的地方：转发前验 token、记日志、限流；响应回来改响应头；**把 userId 塞进请求头传给下游**，下游就不用再解析身份 |

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-route                        # 路由名
          uri: lb://order-service                # 目标：注意 lb://
          predicates:
            - Path=/api/order/**                 # 断言：路径以 /api/order 开头
          filters:
            - StripPrefix=1                      # 过滤器：去掉第一段路径再转发
```

**细节：为什么是 `lb://` 而不是 `http://127.0.0.1:8081`**

> `lb` 是 **loadbalance**：按**服务名**去**注册中心**拿实例表，然后负载均衡挑一台。

```
网关 ──(lb://order-service)──▶ 注册中心（拿实例表）──▶ 负载均衡挑一台 ──▶ 真实实例
```

> **「网关和注册中心，在这里就握上了手。」** 这正是「地址不写死」这个原则在网关层的体现。

**🔴 红线：网关只做和业务无关的通用的事**

> 有人会把「判断优惠券能不能用」写进网关过滤器——**这很危险**。**网关是门卫，不是业务员。**

### 3.6 组件④ OpenFeign + 负载均衡：像调本地方法一样调远程

> 「OpenFeign 是你日常写微服务代码时摸得最多的东西。」

**以前的写法有多难受**：

```java
// 手写版：拼 URL、组请求体、调 RestTemplate、解析返回
String url = "http://127.0.0.1:8082/stock/deduct";
Map<String, Object> body = new HashMap<>();
body.put("skuId", skuId);
body.put("count", count);                       // ← 对方改成 quantity 了呢？
HttpEntity<Map<String, Object>> entity = new HttpEntity<>(body, headers);
ResponseEntity<Map> resp = restTemplate.postForEntity(url, entity, Map.class);
Map data = resp.getBody();
if ((Integer) data.get("code") != 200) { ... }  // ← 还要从 Map 里掏业务字段
```

| 问题 | 后果 |
|---|---|
| URL 写死了 IP 和端口 | 一扩容就得改代码 |
| 对方把字段 `count` 改成 `quantity` | **编译照样通过，运行时才发现，而且不知道错在哪儿** |

**Feign 的写法**：

```java
@FeignClient(name = "stock-service", path = "/stock")
public interface StockClient {

    @PostMapping("/deduct")
    Result<Void> deduct(@RequestBody DeductRequest request);
}
```

```java
@Service
public class OrderService {

    @Resource
    private StockClient stockClient;

    public void createOrder(Long skuId, int count) {
        // 像调本地方法一样调远程服务
        Result<Void> r = stockClient.deduct(new DeductRequest(skuId, count));
        if (!r.isSuccess()) throw new BizException("库存不足");
    }
}
```

**它是怎么做到的：动态代理**

```
① 启动时：为接口生成一个动态代理
② 调用 stockClient.deduct(...) 时，代理替你做：
   ├─ 拼 HTTP 请求（URL、方法、请求体、请求头）
   ├─ 拿服务名 stock-service 去注册中心查实例列表
   ├─ 负载均衡器挑一台 → 发请求
   └─ 把 JSON 响应解析成你声明的返回类型
```

> **「你写的是接口，但是跑的是整套的远程调用。」**

**三个组件的分工（把前面的知识串起来）**：

| 组件 | 负责什么 | 一句话 |
|---|---|---|
| **OpenFeign** | 让远程调用「像本地方法一样」 | 门面 |
| **Nacos** | 找到「人在哪儿」 | 通讯录 |
| **LoadBalancer** | 从名单里「挑一台」 | 调度 |

> 三个组件各干各的事，组合出了**透明的远程调用**。「这就是我们说的：你理解了麻烦，工具自然水到渠成。」

**三种负载均衡策略**：**轮询（默认）**、**加权 / 随机**（机器配置不同时按权重分流）、**响应时间最短**。

**🔴 红线：超时必须显式配置**

```yaml
spring:
  cloud:
    openfeign:
      client:
        config:
          default:
            connectTimeout: 1000     # 建连 1s
            readTimeout: 2000        # 读 2s（默认对生产太宽了）
```

> **Feign 默认的超时对生产环境太宽了。下游一卡，你的线程就跟着全卡住。** 这会导致**雪崩**——正是下一个组件要管的事。

📌 **补充**：Spring Cloud OpenFeign 4.x（对应 Boot 3.x）里配置前缀从 `feign.client.config` 变成了 `spring.cloud.openfeign.client.config`，老教程两个写法混用是高频踩坑点。另外 `readTimeout` 要大于下游 P99 耗时，否则会出现「下游明明成功了，上游却报超时」的假故障。

### 3.7 组件⑤ Sentinel：熔断、降级、限流

**先看它防的灾难：雪崩**

```
库存服务：50ms → 5s（变慢了，但还活着）
订单服务：每处理一个请求，就有一个线程卡在那儿等 5 秒
并发 200 → 200 个线程全部卡死
   ├─ 用户开始重试 → 又进来一批新请求
   └─ 线程不够用了 → 订单服务瘫了
结果：库存只是「慢」，订单却「死」了。
```

> **这就叫雪崩：故障沿着调用链向上不断放大**，像蝴蝶效应一样，最后拖垮上游。

**熔断器 = 家里的保险丝**，三个状态：

```
        错误率 / 慢调用比例 超阈值（如 50% 的调用都在超时）
   ┌──────────────┐  ───────────────────────────────▶  ┌──────────────┐
   │   关闭 CLOSED │                                     │   打开 OPEN   │
   │  正常放行     │  ◀───────────────────────────────  │  直接拒绝     │
   │  偷偷统计     │        试探成功，恢复正常             │  快速失败     │
   └──────────────┘                                     └───────┬──────┘
          ▲                                                     │ 熔断时间到
          │                                                     ▼
          │            放一小撮请求过去试探            ┌──────────────┐
          └────────────────────────────────────────── │ 半开 HALF_OPEN│
                     成功 → 回关闭 / 失败 → 继续打开    └──────────────┘
```

**关闭**时请求正常通过，但 Sentinel **一直在偷偷统计**错误率和慢调用比例；**打开**时请求根本不往库存服务发，直接快速失败，线程**立刻释放**，订单服务就保住了；**半开**时放一小撮请求试探，成功回关闭、失败继续打开。

**Sentinel 干三件事**：

| 能力 | 保护什么 | 一句话 |
|---|---|---|
| **流量控制（限流）** | 保护自己不被**刷爆** | 超过 QPS 阈值直接拒 |
| **熔断降级** | 保护自己不被**下游卡死** | 下游不行就快速失败 |
| **系统自适应保护** | 按整机 CPU / load **兜底** | 系统快撑不住时自动限流 |

**降级：熔断之后不能就这么死掉**——要走 fallback，给用户一句「当前下单较多，请稍后重试」，或者去**读缓存里的旧数据**。

```java
@Service
public class OrderService {

    @SentinelResource(
        value = "createOrder",
        blockHandler = "createOrderBlocked",   // 被限流/熔断时走这里
        fallback = "createOrderFallback"       // 业务异常时走这里
    )
    public Result<Long> createOrder(Long skuId, int count) {
        stockClient.deduct(new DeductRequest(skuId, count));
        return Result.ok(orderId);
    }

    public Result<Long> createOrderBlocked(Long skuId, int count, BlockException ex) {
        return Result.fail("当前下单人数较多，请稍后重试");
    }

    public Result<Long> createOrderFallback(Long skuId, int count, Throwable t) {
        return Result.fail("下单失败，请稍后重试");
    }
}
```

**🔴 红线：降级的本质**

> **宁可给用户一个「不那么好但能用」的结果，也不要让他等 30 秒的超时。**
> 「我们在架构设计的时候，**很多策略本质都是这一句**。」

📌 **补充**：限流 / 熔断 / 降级三个词经常混着说，面试要能分清——**限流**是主动拒绝一部分请求（按 QPS/并发数），保护**自己**不被流量打死；**熔断**是主动切断对下游的调用（按错误率/慢调用比例），保护**自己**不被下游拖死；**降级**是提供一个兜底结果，让用户还能看到「能用的东西」。**限流和熔断是「开关」，降级是「开关按下之后走哪条路」。**

### 3.8 组件⑥ Seata：跨库事务的快照 + 反向补偿

**问题**：跨两个服务、两个库，各自的事务该怎么办？

**AT 模式：两阶段**

```
【一阶段】
  每个参与服务执行自己的 SQL
       ├─ 同时，框架偷偷把「改之前的数据」拍一份快照 → 存到 undo_log 表
       └─ 立刻提交本地事务  ← 注意「立刻」，不会长时间攥着锁
  这一步结束时：库存和余额其实已经各自改了

【二阶段】
  ├─ 全部分支成功 → 通知大家把快照删掉 → 全局事务完成 ✅
  └─ 任何一步失败 → 通知所有分支按 undo_log 反向改回去
       库存加回去，余额也加回去，跟什么也没发生过一样 ↩️
```

> **「跨库回滚——数据库自己做不到的事情，Seata 用『快照 + 反向补偿』给做到了。」**

**三个角色**：

| 角色 | 全称 | 是谁 | 干什么 |
|---|---|---|---|
| **TC** | Transaction Coordinator | **独立部署的 Seata Server** | 协调者，负责**拍板**：全局提交还是回滚 |
| **TM** | Transaction Manager | 通常是**订单服务** | 事务**发起方**，用 `@GlobalTransactional` 声明「从这里开始是全局事务」 |
| **RM** | Resource Manager | 每个**参与的分支**（库存、账户） | 资源管理者，管自己的 undo_log |

```java
@Service
public class OrderService {

    @GlobalTransactional(name = "create-order", rollbackFor = Exception.class)
    public void createOrder(Long skuId, Long userId, int count) {
        orderMapper.insert(...);                                  // 分支 1
        stockClient.deduct(new DeductRequest(skuId, count));       // 分支 2（库存服务）
        accountClient.debit(new DebitRequest(userId, amount));     // 分支 3（账户服务）
    }
}
```

> **「这个就是 AT 模式的魅力」**——加了注解，业务代码一行都不用改。

**用之前先问三个问题**：

| # | 问题 | 结论 |
|---|---|---|
| 1 | 这点不一致，业务能不能容忍？ | 能忍就**别用**，发消息做最终一致更轻便 |
| 2 | 并发高不高？ | AT 模式有**全局锁**，热点数据高并发时全局锁会排队，**有性能瓶颈** |
| 3 | 能不能改业务设计绕过？ | 先冻结额度、支付成功再扣减——把一个分布式事务化成两个本地事务 |

**运维代价**：**TC 是要独立部署、独立运维的组件**，不是引个依赖就完事。**TC 要是挂了，你所有的全局事务都可能挂。**

📌 **补充**：AT 模式有三个视频没展开但上线一定会遇到的细节——① 每个业务库都必须建 `undo_log` 表；② **表必须有主键**（AT 靠主键定位要回滚的行，无主键表无法回滚）；③ 全局锁只锁「被修改的行」，挡得住**脏写**但挡不住**脏读**——别的服务在本地提交后、全局提交前读到的是**中间态**，这也是为什么作者强调「先问业务能不能容忍这点不一致」。

### 3.9 组件⑦ 链路追踪 + 日志聚合：给每个请求发一张身份证

> **严格来说它不是「组件」，而是一种「能力」。**

**问题**：一次下单穿过 4 个服务，日志散在 4 台机器上。用户投诉「下单失败了」，你怎么查？

> 你总不能登录 4 台机器、按时间戳**人肉拼日志**吧？**那样的话，时钟都不一定能对得齐。**

**解法：一句话——给每一个请求发一张「身份证」，叫 `traceId`。**

```
用户在网关点下「提交订单」
      │
      ▼
  网关：生成 traceId = A1B2C3   （写进网关日志，并通过 HTTP Header 往下传）
      │
      ▼
  订单服务：日志里带 A1B2C3 ────┐
      │                        │  一次完整的调用链 = trace
      ▼                        │  其中每一段 = span
  库存服务：日志里带 A1B2C3 ────┤
      │                        │
      ▼                        │
  账户服务：日志里带 A1B2C3 ────┘
```

**查这次失败，只要做一件事**：在日志里搜 `A1B2C3`。四台机器的日志按顺序排好，**哪一步错了、每一步耗时多少，一目了然**。

| 名词 | 含义 |
|---|---|
| **trace** | 一次**完整的调用链** |
| **span** | 链路里的**一个环节**（比如「调库存服务」这一段，记录耗时和结果） |
| **traceId** | 靠 **HTTP Header** 一路传递的那个 ID，**框架自动做** |

**⚠️ 唯一的坑：异步任务**——**线程池里跑的代码，`traceId` 不会自动跟过去，要手动传。** 这是「`traceId` 断了」**最常见的原因**。

📌 **补充**：手动传的做法是 **MDC（Mapped Diagnostic Context）**：主线程把 traceId 放进 MDC，提交任务时用装饰器（`TaskDecorator`）或 `TransmittableThreadLocal` 一起复制到子线程，任务结束清理。`@Async`、`CompletableFuture`、MQ 消费线程、定时任务这四处最容易断链，上线前建议逐个检查。

**落地组合拳**：

| 环节 | 选型 | 特点 |
|---|---|---|
| **采集** | Micrometer Tracing（加依赖**自动埋点**） | 不用改代码 |
| **存储展示** | **Zipkin** | 轻量、好上手 |
| | **SkyWalking** | 功能全，**带告警和拓扑图**，国内用得多 |
| **日志聚合** | **ELK** | 把所有机器的日志收进一个地方 |

**🔴 如果今天只带走一个行动项，就带走这个**：

> **把所有服务的日志格式，都加上 `traceId`。**
> 「这件事**半天就可以做完**。做完之后，你们排查故障的效率立刻就上了一个台阶。所以我是说，今天只能带走一个，**你就带走它**。」
> 「很多团队的可观测性建设，就是从这一步开始的。」

### 3.10 组件⑧ 消息驱动 MQ：发完就返回

**场景**：下单成功后还有 4 件事——发短信、加积分、更新统计、通知仓库。**很多团队会把它们串在下单接口里**：

| 环节 | 耗时 |
|---|---|
| 下单 | 500 ms |
| 发短信 | 800 ms |
| 加积分 | 300 ms |
| **接口总耗时** | **约 3 秒** |

**更要命的是耦合**：

> 短信通道挂了，**下单接口跟着报错**。发短信本来是锦上添花的事，**你凭什么让它拖垮整个下单接口？**

**解法**：

```
订单服务 ──「订单已创建」──▶ MQ ──┬──▶ 通知服务（发短信）
   │                            ├──▶ 积分服务（加积分）
   └─ 立刻返回给用户              └──▶ 统计服务（更新报表）
```

| 收益 | 说明 |
|---|---|
| **① 解耦** | 明天要加「下单送优惠券」，**写一个新的消费者就行，订单服务一行不用改** |
| **② 削峰** | 大促瞬间 10 万条消息堆在队列里，下游按自己的能力慢慢消化，不会被瞬时流量打死 |
| **③ 最终一致** | 跨服务的状态同步，**主要靠它** |

**但消息不是免费的，三个代价**：

| 代价 | 怎么做 |
|---|---|
| **① 消息不能丢** | **三个环节都要管**：生产者要**确认发送成功**；MQ 自己要**持久化**（别重启一下就没了）；消费者**处理完要手动 ack**（别还没处理完就 ack）。**任何一个环节松了，消息就无影无踪了** |
| **② 重复消费要幂等** | MQ 的承诺是**「至少一次」**：消费者处理成功了但确认消息在网络里丢了，MQ 会再发一次。所以消费逻辑**必须幂等**——加积分前先查「这笔订单的积分加过没有」，**用数据库唯一键兜底最简单** |
| **③ 顺序与积压** | **顺序**：同一订单的消息必须按顺序处理（先创建后支付），用**订单号做分区键**；**积压**：必须**监控告警**，积压半小时 = 用户半小时后才收到短信 = **事故** |

📌 **补充**：「消息不能丢」在工程上有更严格的实现——**本地消息表**或 **RocketMQ 事务消息**。因为「业务写库」和「发消息」本身就是两个操作，会出现「库写成功、消息没发出去」的裂缝。本地消息表的做法是把消息和业务数据写在**同一个本地事务**里（消息落到 `t_message` 表），再由后台任务扫描发送，发成功后标记。这是「最终一致」最朴素也最可靠的实现。

### 3.11 组件⑨ 统一认证与安全：公网只进网关

**原则**：**公网只能进网关，业务服务只在内网互相调用。**

```
① 用户登录
   客户端 ──账号密码──▶ 认证服务 ──校验通过──▶ 签发 JWT
                                               （Header.Payload.Signature 三段式）
② 客户端每次请求都带上：
   Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjEwMDEsInJvbGUiOiJ1c2VyIn0.xxxxx
                            └──── 头 ────┘ └──────── 载荷 ────────┘ └ 签名 ┘

③ 网关收到请求，做两件事：
   ├─ 验签：用密钥验证「是自家签发的」「没被改过」「没过期」  ← 纯计算，非常快
   └─ 解析：从令牌里取出 userId 和角色

④ 网关把 userId / 角色写进请求头，转发给下游
   下游服务直接从请求头取身份，专心写业务
```

| 点 | 说明 |
|---|---|
| 网关**不查数据库** | 验签是纯计算，非常快 |
| 鉴权逻辑**只写一次** | 剩下 100 个服务都不用重复写 |
| 下游服务**变得非常简单** | 它们只管业务 |

**🔴 安全常识：JWT 不是加密的**

> JWT 有三段，**前两段（头和载荷）只是 Base64 编码，不是加密**。**任何人拿到令牌，都能解码看到内容。**
> 所以手机号、身份证这类东西，**绝对不要放到 payload 里**——放进去等于**明文广播**。

**服务之间互相调用怎么做：四条**

| # | 规矩 | 为什么 |
|---|---|---|
| 1 | **网络隔离是前提** | 业务服务只在内网，公网根本摸不到 |
| 2 | **服务间调用要带内部令牌或双向证书** | 防止有人**绕过网关直接打内网接口** |
| 3 | **下游不要信任「来路不明」的请求头** | 像 `X-UserId` 这种头，**必须是来自网关注入的**——靠第 1 条的网络隔离保证 |
| 4 | **认证 ≠ 授权** | 「你是谁」网关解决；「**你能不能看这条数据**」必须**在业务服务里校验** |

第 4 条作者举的例子：销售能不能查看**别的区域**的客户？这需要**授权**，只有业务服务才懂业务规则。**把认证和授权混为一谈，就可能造成权限方面的事故。**

## 4. 第四章 从 0 到上线：把零件装成一台机器

前面三章讲的是「为什么要拆」「长什么样」「每个组件怎么用」，但知识是散的。这一章装起来：工程怎么分（4.1）、9 步下单全程（4.2）、本地联调（4.3）、上线与落地（4.4 / 4.5）。

### 4.1 工程怎么分模块：一个仓库多个模块

```
shop-cloud/                        # 父工程（父 POM）
├── pom.xml                        # ★ 三个 Spring 版本只在这里改一次
├── shop-common/                   # 公共：DTO、工具类、统一异常、统一返回
├── shop-api/                      # ★ 所有 Feign 接口定义 = 服务之间的「契约」
├── shop-gateway/                  # 网关
├── shop-order/                    # 订单服务
├── shop-stock/                    # 库存服务
├── shop-account/                  # 账户服务
└── shop-notify/                   # 通知服务
```

**单个服务的内部结构**跟 Spring Boot 项目几乎一样：`controller` / `service` / `mapper` / 启动类，**唯一的新东西是 `resources` 里多一个 `bootstrap.yml`**（放注册中心和配置中心的地址）。

**为什么起步用「单仓库多模块」（monorepo）**：

| 场景 | 单仓库 | 5 个独立仓库 |
|---|---|---|
| 给 DTO 加一个字段 | **一次提交，所有模块编译时立刻可见** | 改 5 次、发 5 个版本，还要保证版本之间互相兼容 |

> 「在起步阶段，这（多仓库）单纯就是一个负担。**等团队大了、服务边界稳定了，再去拆仓库也不迟。**」

**四条团队约定（建议直接写进团队规范）**：

| # | 约定 | 不遵守的后果 |
|---|---|---|
| 1 | **每个服务只连自己的库** | 谁跨库 join，**谁就负责修线上事故** |
| 2 | **`shop-common` 只放 DTO 和工具** | 有人在里面写业务规则 → **所有服务被迫一起重新发布** → 公共模块变成**新的耦合** |
| 3 | **Feign 接口统一放 `shop-api`** | 防止服务之间**互相依赖对方的实现**，产生循环依赖 |
| 4 | **三个 Spring 版本只在父 POM 改一次** | 这就是前面说的「版本联动」 |

### 4.2 一次下单请求的 9 步全程（本集最重要的图）

```
用户点击「提交订单」
  │
  ▼
① 网关 ── 验 token / 判权限 / 限流 / 记日志带 traceId / 按路径路由
  │
  ▼
② 订单服务 ── 创建订单（状态=待支付）        ← 本地事务，写订单库很快
  │
  ▼
③ 订单 → 库存 ── stockClient.deduct()       ← Feign 声明式调用
  │                                             （服务名查注册中心 + 负载均衡挑一台）
  ▼
④ 库存服务 ── 扣减库存                      ← 受 Sentinel 保护
  │                                             （熔断中则快速失败，不挂住订单线程）
  ▼
⑤ 订单 → 账户 ── accountClient.debit()      ← 可能失败：余额不足 / 网络超时
  │
  ▼
⑥ Seata 全局事务收口 ── 账户分支失败
  │                     ├─ 通知库存分支按 undo_log 反向补偿（加回库存）
  │                     └─ 订单分支标记「已关闭」
  │                     → 全程用户无感知的一致性
  ▼
⑦ 全部成功 ── 往 MQ 发「订单已创建」── 立刻返回给用户（主流程：一两百毫秒）
  │
  ▼
⑧ 下游各自消费 ── 通知发短信 / 积分加积分 / 数据服务更新统计
  │                （注意幂等：用订单号做唯一键兜底）
  ▼
⑨ 返回订单号；本次请求的 traceId 贯穿所有服务日志
```

| 步 | 谁 | 做什么 | 对应知识点 |
|---|---|---|---|
| **1** | 网关 | 验 token、判权限、限流、记日志带 traceId、按路径路由给订单服务 | 网关的断言 + 路由 + 过滤器；统一认证 |
| **2** | 订单服务 | 创建订单记录，状态「待支付」 | **本地事务**，写订单库很快 |
| **3** | 订单 → 库存 | `stockClient.deduct(...)` | OpenFeign 声明式调用 → 服务名查注册中心 → 负载均衡挑一台 |
| **4** | 库存服务 | 扣减库存 | 受 Sentinel 保护；**熔断中则快速失败**，而不是把订单的线程挂住 |
| **5** | 订单 → 账户 | 扣款 | 失败场景：**余额不足 / 网络超时** |
| **6** | Seata | 全局事务收口 | 账户分支失败 → 通知库存按 undo_log 反向补偿 → 订单标记关闭 |
| **7** | 订单服务 | 发「订单已创建」到 MQ，立刻返回 | 异步解耦；主流程只耗一两百毫秒 |
| **8** | 下游消费者 | 发短信、加积分、更新统计 | 幂等（订单号做唯一键） |
| **9** | 全体 | 返回订单号，traceId 贯穿所有日志 | 链路追踪；几个月后出问题，一条 ID 查到底 |

**回到开场那个事故**：

| 问题 | 答案 | 为什么 |
|---|---|---|
| 同样的优惠券 bug，还能炸全站吗？ | **不能** | 每个服务是独立进程，**故障有隔离墙** |
| 改一行代码还要全量回归吗？ | **不用** | 每个服务**独立发布** |
| 出了问题还能 5 分钟定位吗？ | **能** | 全链路**留痕** |

> 「这些，大家都可以通过理解，自己都能答上来了。」

### 4.3 本地怎么把 5 个服务 + 3 个中间件跑起来

**建议：中间件全部用 Docker 起，别装在电脑上。**

```yaml
# docker-compose.yml
services:
  nacos:
    image: nacos/nacos-server:v2.3.2
    environment:
      MODE: standalone
    ports:
      - "8848:8848"
      - "9848:9848"
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: root
    ports:
      - "3306:3306"
  redis:
    image: redis:7
    ports:
      - "6379:6379"
```

```bash
docker compose up -d      # 一条命令全起来
docker compose down -v    # 想删掉重来，也是一条命令
```

> 「你的电脑保持干净的环境，随时都可以复现。」

**MySQL 建 4 个 schema，一个服务一个库**：`shop_order` / `shop_stock` / `shop_account` / `shop_notify`。

> **从第一天就遵守「一个库对应一个服务」。别想着「先共用一个库，以后再拆」——那样拆出来的就是分布式单体。**

**启动顺序是有讲究的**：

| 顺序 | 起什么 | 为什么 |
|---|---|---|
| 1 | **中间件**（Nacos / MySQL / Redis） | 先确认 **Nacos 控制台打得开** |
| 2 | **被依赖的服务**（库存、账户） | 订单要调它们 |
| 3 | **订单服务** | 起订单时 Feign 要去注册中心找库存，**找不到就会报错** |
| 4 | **网关** | 最后起，前面都通了才有意义 |

**检查点**：Nacos 服务列表里有 **4 个服务名，每个实例数为 1** → 就绪。

**三个联调技巧**：

| # | 技巧 | 为什么 |
|---|---|---|
| 1 | **只起你改的那个服务** | 改库存服务？订单、账户直接连**测试环境**的注册中心，本地只起库存 → **省内存、省时间** |
| 2 | **本地打断点时把 Feign 超时调大** | 你在断点上停 30 秒，下游早就超时报错了，**你会误以为代码有 bug** |
| 3 | **给每个服务规定固定端口并写进 Wiki** | 乱用端口就是浪费时间 |

| 端口 | 服务 | | 端口 | 服务 |
|---|---|---|---|---|
| 8081 | 订单 | | 8083 | 账户 |
| 8082 | 库存 | | 8084 | 通知 |
| 9000 | 网关 | | 8848 | Nacos |

**⚠️ 常见的坑（每一个都能卡你半天）**：`8080` 被占用、**服务名拼错**（`stock-service` 写成 `stock-servcie`）、**`bootstrap.yml` 放错位置**。

### 4.4 上线：微服务、Docker、K8s 到底是什么关系

| | 微服务 | Kubernetes（K8s） |
|---|---|---|
| 是什么 | **架构风格** | **运行平台** |
| 回答什么问题 | 服务**怎么切分** | 服务**怎么跑** |
| 能不能离开对方 | 能：三五个服务、几台虚拟机照样跑 | 能：很多公司拿 K8s 管**一个巨大的单体** |

**三个阶段演进**：

| 阶段 | 形态 | 好处 | 局限 |
|---|---|---|---|
| **1** | **一台机器多个 jar + 启动脚本** | 简单，能用很久 | 扩缩容靠手动，挂了要人工重启；**服务少时完全够用** |
| **2** | **Docker 容器化**（一服务一镜像） | **开发、测试、生产环境完全一致**——「在我电脑上明明能跑」从此消失 | 容器只解决**打包和隔离**；谁来做调度？挂了谁重启？怎么滚动发布？**容器回答不了** |
| **3** | **K8s** | 见下表 | 复杂度高，需要人兜底 |

**K8s 接管了什么**：

| 能力 | 说明 |
|---|---|
| **自愈** | 容器挂了自动拉起；整台机器挂了，把容器**挪到别的机器** → **不用半夜爬起来重启服务** |
| **滚动发布** | 新版先起一个实例，**探活通过**再逐个替换旧实例 → 发布过程**用户无感** |
| **弹性伸缩** | 按 CPU 或自定义指标**自动加减副本** |

**K8s 和 Nacos 冲突吗？不冲突**——**K8s 管进程的生死，Nacos 管调用的地址**，Pod 照样可以起来，照样可以注册。

**⚠️ 什么情况先别上 K8s**：

| 情况 | 建议 |
|---|---|
| 团队三五个人、只有 4 个服务、没有专职运维 | **Docker Compose + 脚本就够了** |
| 没人兜底 | K8s 出问题**不是某个服务的问题，是整个集群的问题**——它给你的复杂性和损失可能**大于收益** |
| 业务还没跑通 | 上 K8s 是**方向搞反了** |

> **「先让业务活着，再谈基础设施怎么变得优雅。」**
> **「K8s 解决的是规模问题。如果规模没到，它能给你带来的只有复杂度。」**

📌 **补充**：K8s + Nacos 有一个高频生产坑——**Pod 还没就绪就已经注册到 Nacos 了**，网关把流量打过来，一堆 502/503。正确做法是把注册时机绑定到 `readinessProbe` 通过之后（配合 `spring.cloud.nacos.discovery.register-enabled`，或在 `ApplicationReadyEvent` 之后再注册），同时用 `preStop` 钩子**先在 Nacos 摘除实例、再优雅停机**，避免滚动发布时的请求丢失。

### 4.5 落地路线：三个阶段 + 五个坑

| 阶段 | 时间 | 做什么 | 具体动作 | 收益 |
|---|---|---|---|---|
| **一** | 头 3 个月 | **不拆进程，先做模块化** | 单体里按业务域划清包边界；**禁止跨域直接访问对方的表**；哪怕同一个库，也把 **schema 按域分开**；访问入口收拢 | **成本几乎为零**，但给未来拆分铺好路——到时候「拆」就只是**把模块挪出去** |
| **二** | 3~9 个月 | **拆 3~5 个核心服务** | 优先级看两个指标：**流量大的**、**变化快的**（商品、订单、库存通常先走）；同时建地基：注册中心、配置中心、网关 | 核心链路的**发布效率立刻改善**，初步尝到甜头、建立信心 |
| **三** | 9 个月之后 | **补齐治理** | 链路追踪、熔断降级、统一鉴权，再加 Seata 这类分布式事务；**最后才是 K8s** | 系统能扛住规模 |

> **顺序原则**：**治理能力要跟着服务的数量走。服务多了，才有治理的需求。顺序反了，团队可能天天都陷在救火里。**

**五个坑（大概率会踩）**：

| # | 坑 | 表现 |
|---|---|---|
| 1 | **为拆而拆** | 切得太细，一次下单跨好几个服务，排查一个 bug 要开十几个窗口 |
| 2 | **共享数据库** | 图省事 → 得到**分布式单体**，**比单体还难维护** |
| 3 | **只拆服务不改组织** | 服务拆了，团队还是按技术分层做一块 → **康威定律会以故障的形式再给你讨回来** |
| 4 | **没有可观测性就上量** | 没 traceId、没告警，**出问题靠用户投诉来发现** |
| 5 | **一步到位上 K8s** | 服务和集群两头学，**两头都学不明白** |

> **这五个坑的共同点是：顺序错了。**
> 「所以对于架构师来讲，**一半是要选技术，一半是要排顺序**，都是非常重要的。」

### 5.1 16 个词速过

| # | 词 | 一句话 |
|---|---|---|
| 1 | **单体架构** | 一个应用一个包，很简单，但改动和故障都是**全局**的 |
| 2 | **微服务** | 按业务能力切，独立部署、独立运行、**进程隔离**；拆的是**运行时边界** |
| 3 | **服务注册与发现** | Nacos 维护一份**动态通讯录** |
| 4 | **配置中心** | 配置**集中管理**，**动态刷新** |
| 5 | **API 网关** | **唯一入口**，鉴权限流的**收口** |
| 6 | **声明式调用** | OpenFeign 让远程调用**像本地方法一样** |
| 7 | **负载均衡** | 从实例名单里**挑一台** |
| 8 | **熔断降级** | 下游不行就**快速失败**，给一个**兜底结果** |
| 9 | **限流** | 保住**自己**不被刷爆 |
| 10 | **分布式事务** | Seata，**快照 + 反向补偿** |
| 11 | **最终一致** | 允许**短暂不一致**，靠消息和补偿把状态**推齐** |
| 12 | **链路追踪** | **traceId 串起全链路** |
| 13 | **消息解耦** | 发完就返回；**但幂等是它的前提** |
| 14 | **网关鉴权** | 公网只进网关，**身份由它注入**，验完再注入请求头给下游 |
| 15 | **分布式单体** | 共享数据库、必须一起发版的**假微服务**（重点反例） |
| 16 | **康威定律** 📌 | 系统结构会长成组织的沟通结构——**你切给谁，架构就长成什么样** |

> 📌 **补充**：作者口播是「16 个词」，但转写稿里能逐个点到的只有 15 个。按上下文，第 16 个大概率是他全课强调过两次的「康威定律」，这里补上；以视频为准。
> 作者的用法建议：「你可以回去对照着项目一个一个去问：**这一条我做到了吗？我需要吗？**」

### 5.2 带走三句话

**第一句：先问我疼不疼，再问要不要拆。**
> **微服务是治病的，不是给你做补品的。** 前面那「单体的五道坎」，**你项目里没中，就继续写你的单体。**

**第二句：拆的是进程和边界，不是文件夹。**
> 判断标准只有一句：**能不能单独重启。** 共享数据库的那种微服务，是更贵的单体——**分布式单体**。

**第三句：复杂度不会消失，只会转移。**
> 微服务是把**代码的复杂度**，转成了**运维、治理、协作的复杂度**。所以它必须**按阶段来**，要**配得上你当前的团队规模**。
> **技术选型的本质，从来不是「哪个先进用哪个」，而是「哪种复杂度你供得起」。**

**最后一页上的那一行字**：

> **框架会更替，判断不会。**
> 「Netflix 退场了，还会有别的进场；还会有别的也会退场。**但是边界怎么画、代价怎么权衡，永远都是架构师自己的事情。**」

### 6.1 组件全景表（最该背下来的一张）

| # | 组件 | 解决的麻烦 | 一句话记住 | 关键配置/注解 |
|---|---|---|---|---|
| 1 | **Nacos Discovery** | 地址会变 | 动态通讯录 | `spring.cloud.nacos.discovery.server-addr` + `@EnableDiscoveryClient` |
| 2 | **Nacos Config** | 配置满天飞 | 配置集中、动态刷新 | **`bootstrap.yml`** + `@RefreshScope` |
| 3 | **Gateway** | 入口没人把守 | 唯一入口；路由=断言+过滤器+目标 | `uri: lb://service-name` + `Path=` |
| 4 | **OpenFeign** | 调用难写 | 像调本地方法 | `@FeignClient` + `@Resource` |
| 5 | **LoadBalancer** | 挑哪台 | 轮询 / 加权 / 响应时间 | `lb://` 前缀 |
| 6 | **Sentinel** | 调用会失败 | 保险丝：关闭→打开→半开 | `@SentinelResource(fallback=...)` |
| 7 | **Seata** | 数据不一致 | 快照 + 反向补偿 | `@GlobalTransactional` + `undo_log` 表 |
| 8 | **Tracing + Zipkin/SkyWalking** | 找不到原因 | 给每个请求发身份证 | 日志格式里加 `traceId` |
| 9 | **MQ** | 主流程被拖慢 | 发完就返回 | 生产者确认 + 持久化 + 手动 ack + 幂等 |
| 10 | **网关鉴权（JWT）** | 鉴权写 100 遍 | 验签在网关，授权在服务 | `Authorization: Bearer <token>` |

### 6.2 六个麻烦 → 六个解法

| 麻烦 | 症状 | 解法 | 关键数字/原则 |
|---|---|---|---|
| 调用会失败 | 超时、丢包、对方发布中 | 超时 + 重试 + 熔断 + 降级 | 错误率 >50% → 熔断 |
| 地址会变 | 扩容/缩容/宕机 | 注册中心 | 心跳 5s / 15s 不健康 / 30s 摘除 |
| 配置满天飞 | 20 服务 × 3 环境 | 配置中心 | namespace / group / dataId 三级 |
| 数据不一致 | 跨库回滚不了 | 冻结确认 > 最终一致 > Seata | 一个数据一个主人 |
| 找不到原因 | 日志散在 N 台机器 | traceId + 日志聚合 | trace / span / traceId |
| 入口没人把守 | 100 个服务暴露公网 | 网关统一鉴权限流 | 网关是门卫不是业务员 |

### 6.3 同步 vs 异步 / 分布式事务三选一

| 判断 | 选型 | 例子 |
|---|---|---|
| 这一步失败，业务**不能**继续 | 同步 | 扣库存、扣款 |
| 这一步失败，业务**能**继续 | 异步 | 发短信、加积分、更新统计、通知仓库 |

| 方案 | 一致性 | 性能 | 代码改动 | 什么时候用 |
|---|---|---|---|---|
| **改业务设计**（先冻结后确认） | 强（本地事务） | 最好 | 中（改流程） | **优先考虑** |
| **最终一致**（消息 + 补偿） | 最终 | 好 | 中 | 主流互联网业务 |
| **Seata AT** | 强（全局锁） | 有瓶颈 | **最小（一个注解）** | 并发不高、必须强一致 |

## 7. 面试自测题（含答案）

先自己答，再看答案。

<details>
<summary><b>Q1：单体应用有什么好？为什么小团队不该上微服务？</b></summary>

四个好处：**一次打包一次部署**、**调用就是方法调用**（不走网络、不序列化、没有超时、堆栈能一路打到底）、**事务就是一个 `@Transactional`**（同库原子性由数据库保证）、**重构成本最低**（一键重命名全项目生效）。

小团队（10 人以内、流量平稳、产品还在验证期）**单体就是最优解**。因为微服务把「代码复杂度」换成了「运维 + 治理 + 协作复杂度」，规模不够时你只是在**提前支付成本**。

一句话：**微服务不是用来纠正错误的，是用来应对增长的。**
</details>

<details>
<summary><b>Q2：单体应用规模变大后会出现哪五道坎？</b></summary>

| # | 症状 | 后果 |
|---|---|---|
| 1 | 部署耦合 | 改一行要全量回归 → 发布频率被迫下降 → 迭代被卡脖子 |
| 2 | 故障放大 | 共享线程池/内存/连接池，一个模块崩全站崩（**没有隔离墙**） |
| 3 | 扩容粒度太粗 | 只有订单库存压力大，却要复制整个应用（**3% 代码扛流量，100% 代码吃机器**） |
| 4 | 技术栈锁死 | 一个模块想升 Java 17 升不了；想用 Python 写推荐几乎不可能 |
| 5 | 组织协作 | 上百人一个仓库，冲突天天有 → 「公共代码谁也别动」→ 代码腐烂 |
</details>

<details>
<summary><b>Q3：我把单体按包名分成了 com.shop.order / com.shop.stock，算微服务吗？</b></summary>

**不算，这叫模块化。**

它们还在同一个 JVM、打同一个 jar、共享同一个数据库连接池，订单调库存还是一行方法调用。它解决的是**代码可读性**，不是运行时隔离。

崩的时候崩的是**进程**，进程里装着所有模块 → 依然牵一发而动全身。

**判断标准只有一句：能不能单独重启、单独发版、单独扩容。**
</details>

<details>
<summary><b>Q4：什么是「分布式单体」？为什么它比单体更糟？</b></summary>

服务拆成了 N 个，但仍然：**连着同一个数据库**、**发版必须凑齐一起发**（接口之间有隐式依赖）。

它把单体的耦合**原封不动复制了 N 份**，还额外附赠了**网络调用**这个不稳定因素——所以你付出了微服务的全部代价，却没拿到微服务的任何好处。**它比单体更糟。**
</details>

<details>
<summary><b>Q5：微服务的「微」指的是什么？拆分的目的是什么？</b></summary>

**「微」不是代码少**，而是**职责小、边界清楚**。拆出一个 200 行的服务但到处依赖别人，那不叫微服务，那叫麻烦。

**拆分的目的是业务自治，不是目录好看。**

最典型反例：把 controller 拆成一个服务、service 拆成一个服务——那是技术分层。结果一次下单从 1 次方法调用变成 2 次网络调用，**性能更差、故障点更多，什么都没换回来**。
</details>

<details>
<summary><b>Q6：服务拆分的三条原则是什么？</b></summary>

1. **按业务能力拆，不按技术分层**——一个服务里装着 controller/service/DAO 全套，能独立完成一条完整业务链。
2. **高内聚——经常一起改的放一块**。实用判断法：回想最近三个需求，每次要动哪几块代码；如果每次都要**跨三个服务一起发版**，边界大概率画错了。
3. **边界看数据归属**——谁拥有这份数据谁就是主人，别人要改只能调你的接口。反过来：**把公司数据归属表画出来，服务边界基本就出来了。**
</details>

<details>
<summary><b>Q7：什么时候用同步调用，什么时候用异步消息？</b></summary>

**口诀：先问一句「这一步失败了，业务还能继续吗？」**

- 不能 → **同步**（扣库存、扣款）。代价是「对方慢你也慢，对方挂你也挂」，所以必须配超时、重试、熔断、降级。
- 能 → **异步**（发短信、加积分、更新统计）。好处是解耦 + 削峰；代价是**最终一致**，积分可能晚 10 秒到账。

比喻：同步是**打电话**（必须等对方接、一句接一句），异步是**发微信**（发完就去干别的）。
</details>

<details>
<summary><b>Q8：库存扣成功了，账户扣款超时了，怎么处理？</b></summary>

三个策略，**按推荐顺序**：

1. **先质疑业务**——这两步真的必须在同一个事务里吗？改成「**先冻结后确认**」：下单冻结额度、支付成功真扣减、失败解冻。冻结和扣减**各自都是本地事务**，根本不需要跨服务事务。**把技术问题变成业务设计问题，往往最便宜。**
2. **最终一致**——扣库存成功发消息，账户服务消费；失败重试，重试不行就**反向补偿**（把库存加回去）。用户看到「状态更新中」，几百毫秒后就绪。
3. **Seata AT**——`@GlobalTransactional` 一个注解，框架靠 undo_log 快照自动反向补偿。但多一个 TC 组件、有全局锁性能开销。

**两条铁律**：一个数据只有一个主人；不许幻想强一致（网络会超时、消息会重复、服务会重启，方案必须假设它们会发生且能自愈）。
</details>

<details>
<summary><b>Q9：Spring Boot 2.7 该配哪个版本的 Spring Cloud？配错了会怎样？</b></summary>

| Spring Boot | Spring Cloud | Spring Cloud Alibaba |
|---|---|---|
| 2.7.x | 2021.0.x | 2021.0.5.0 |
| 3.2.x | 2023.0.x | 2023.0.1.0 |

配错会报 **`NoSuchMethodError`**——因为 Spring Cloud 是在**特定版本**的 Spring Boot 上编译的。报错指向的类你可能都没听说过，堆栈里全是没写过的代码，非常难查。

**升级必须三层联动**（Boot / Cloud / Alibaba），升之前先查官方 Release Note 的对应表。
</details>

<details>
<summary><b>Q10：注册中心的心跳机制是怎样的？为什么服务重启时调用方会「短暂找不到人」？</b></summary>

Nacos 的机制：服务启动上报「服务名 + IP + 端口」→ **每 5 秒心跳** → **15 秒**没心跳标记不健康 → **30 秒**没心跳从名单摘除。调用方按服务名拉名单缓存本地，定期更新。

重启期间调用方短暂找不到人，是因为**心跳还没超时、名单还没更新**。

> **这不是 bug，是这套机制天然的属性。** 所以调用代码必须能容忍「偶尔找不到人」，要**加重试**。
</details>

<details>
<summary><b>Q11：配置中心的地址为什么必须写在 bootstrap.yml，不能写在 application.yml？</b></summary>

因为**加载顺序**：`bootstrap` 先加载，服务才知道「去哪里找配置中心」。

如果写在 `application.yml` 里，等读到它的时候，**配置加载阶段已经过去了**，配置中心等于没生效。

📌 补充：Spring Cloud 2020 之后还需要额外引入 `spring-cloud-starter-bootstrap`，否则 `bootstrap.yml` 根本不生效——这是「写了没反应」的常见原因。
</details>

<details>
<summary><b>Q12：网关的三大组件是什么？为什么 uri 要写 <code>lb://order-service</code> 而不是 IP？</b></summary>

**路由 = 断言 + 过滤器 + 目标**。断言判断「该不该走这条路由」（Path / 域名 / 请求方法 / 请求头 / 时间），过滤器在请求转发前和响应回来后各做一遍处理。

`lb` 是 **loadbalance**：按**服务名**去**注册中心**拿实例表，再由负载均衡挑一台。所以这里其实是**网关和注册中心握了手**——这就是「地址不写死」在网关层的体现。

**红线**：网关只做和业务无关的通用的事。把「优惠券能不能用」写进网关过滤器很危险——**网关是门卫，不是业务员。**
</details>

<details>
<summary><b>Q13：OpenFeign 是怎么做到「像调本地方法一样」的？</b></summary>

**动态代理**。启动时为接口生成代理；调用 `stockClient.deduct(...)` 时，代理替你做：拼 HTTP 请求 → 拿服务名去注册中心查实例列表 → 负载均衡挑一台 → 发请求 → 把 JSON 响应解析成你声明的返回类型。

**三个组件的分工**：Feign 负责「像本地方法」，Nacos 负责「人在哪儿」，LoadBalancer 负责「挑哪台」。

**红线**：**超时必须显式配置**。Feign 默认超时对生产太宽，下游一卡你的线程全卡住 → 雪崩。
</details>

<details>
<summary><b>Q14：什么是雪崩？熔断器的三个状态是怎么流转的？</b></summary>

**雪崩**：库存服务从 50ms 变 5s（只是慢，没死），订单服务每个请求一个线程卡 5 秒，并发 200 → 200 线程全卡死 → 用户重试再来一批 → 订单服务瘫了。**库存只是慢，订单却死了**——故障沿调用链向上放大。

熔断器三态（像家里的保险丝）：

| 状态 | 行为 |
|---|---|
| **关闭 CLOSED** | 正常放行，但偷偷统计错误率/慢调用比例 |
| **打开 OPEN** | 超过阈值（如 50% 超时）后，请求**根本不发出去**，直接快速失败，线程立刻释放 |
| **半开 HALF_OPEN** | 熔断时间到，放一小撮请求试探；成功 → 关闭，失败 → 继续打开 |

**降级的本质**：宁可给用户一个「不那么好但能用」的结果，也不要让他等 30 秒超时。
</details>

<details>
<summary><b>Q15：Seata AT 模式的「两阶段」具体做了什么？为什么它敢「立刻提交本地事务」？</b></summary>

**一阶段**：每个参与服务执行自己的 SQL，同时框架**偷偷把改之前的数据拍一份快照**存进 `undo_log` 表，然后**立刻提交本地事务**——不长时间攥着锁。

**二阶段**：全部分支成功 → 通知大家删快照，全局完成；任何一步失败 → 通知所有分支**按 undo_log 反向改回去**。

敢立刻提交，是因为它不需要「一直持有锁到全局结束」，而是靠**「快照 + 反向补偿」事后补救**。代价是引入了**全局锁**保障隔离性，热点数据高并发时会排队。

**三个角色**：TC（独立部署的协调者，拍板提交/回滚）、TM（发起方，订单服务，`@GlobalTransactional`）、RM（每个参与分支）。
</details>

<details>
<summary><b>Q16：链路追踪里 trace、span、traceId 分别是什么？最常见的坑是什么？</b></summary>

- **trace**：一次完整的调用链
- **span**：链路里的一个环节（如「调库存服务」这一段），记录耗时和结果
- **traceId**：靠 HTTP Header 一路传递的 ID，框架自动做

**最常见的坑**：**线程池里跑的异步代码，traceId 不会自动跟过去，要手动传。** 这是「traceId 断了」最常见的原因。

**如果只做一个行动项**：把所有服务的**日志格式**都加上 traceId。半天就能做完，排查故障效率立刻上一个台阶。
</details>

<details>
<summary><b>Q17：消息队列的三个收益和三个代价分别是什么？</b></summary>

**三个收益**：解耦（加新消费者，订单服务一行不改）、削峰（10 万消息堆在队列，下游按自己能力消化）、最终一致（跨服务状态同步的主要手段）。

**三个代价**：
1. **消息不能丢**——三个环节都要管：生产者确认发送、MQ 持久化、消费者手动 ack；
2. **重复消费要幂等**——MQ 承诺「至少一次」，同一条消息可能送两次，用数据库唯一键兜底；
3. **顺序与积压**——同一订单的消息必须按顺序（用订单号做分区键）；积压要监控告警（积压半小时 = 事故）。
</details>

<details>
<summary><b>Q18：JWT 放在前端安全吗？为什么手机号不能放进 payload？</b></summary>

JWT 三段：Header.Payload.Signature。**前两段只是 Base64 编码，不是加密**——任何人拿到令牌都能解码看到内容。

所以**手机号、身份证这类敏感信息绝对不能放进 payload**，放进去等于**明文广播**。签名只保证「没被篡改」，不保证「看不见」。

另外：认证（你是谁）在网关做，**授权（你能看哪条数据）必须在业务服务里做**——只有业务服务懂业务规则。把两者混为一谈就会出权限事故。
</details>

<details>
<summary><b>Q19：微服务和 K8s 是什么关系？什么情况不该上 K8s？</b></summary>

**微服务是架构风格**（回答「服务怎么切」），**K8s 是运行平台**（回答「服务怎么跑」）。两者互不依赖：微服务可以用几台虚拟机跑，K8s 也可以管一个巨大的单体。

K8s 提供：自愈、滚动发布、弹性伸缩。它和 Nacos **不冲突**——**K8s 管进程生死，Nacos 管调用地址**。

**不该上的情况**：三五个人四个服务、没有专职运维 → Docker Compose + 脚本就够了；K8s 出问题是**整个集群**的问题，没人兜底时复杂度大于收益；业务还没跑通就上 K8s 是方向反了。

**K8s 解决的是规模问题，规模没到，它能给你的只有复杂度。**
</details>

<details>
<summary><b>Q20：微服务落地的正确顺序是什么？五个最常见的坑是什么？</b></summary>

**三阶段**：
1. **头 3 个月**：不拆进程，先做**模块化**（按业务域划包边界、禁止跨域访问对方的表、schema 按域分开）。成本几乎为零，未来「拆」只是把模块挪出去。
2. **3~9 个月**：拆 **3~5 个核心服务**，优先选**流量大的**和**变化快的**；同时建地基（注册中心、配置中心、网关）。
3. **9 个月之后**：补齐治理（链路追踪、熔断降级、统一鉴权、分布式事务），**最后才是 K8s**。

**五个坑**：为拆而拆、共享数据库、只拆服务不改组织、没有可观测性就上量、一步到位上 K8s。

**共同点：顺序错了。** 治理能力要跟着服务数量走。
</details>

## 8. 📌 补充：视频没细讲但一定会踩的坑

> 以下为原讲解之外的延伸，按重要性排序。

### 8.1 三种分布式事务方案对比（视频只细讲了 AT）

| | **2PC/XA** | **TCC** | **Saga** | **AT（Seata）** |
|---|---|---|---|---|
| 思路 | 数据库层两阶段提交 | 业务层写 Try/Confirm/Cancel 三个方法 | 一串本地事务 + 反向补偿 | 快照 + 自动反向补偿 |
| 一致性 | 强 | 强（最终） | 最终 | 强（有全局锁） |
| 性能 | 差（锁到全局结束） | 好 | 好 | 中（全局锁排队） |
| 侵入性 | 低 | **极高**（每个分支写三个方法） | 中 | **极低**（一个注解） |
| 适用 | 强一致、低并发 | 资金类、要求高 | 长流程、跨多服务 | 一般业务快速接入 |

一句话选型：**能用业务设计绕开的绕开；绕不开又要强一致的，资金用 TCC、普通业务用 AT；长流程用 Saga。**

### 8.2 CAP / BASE：为什么 Nacos 能当注册中心，Zookeeper 不太合适

注册中心本质是「**可用性优先**」的场景：服务列表偶尔旧一点没关系（大不了重试一次），但**注册中心自己不能不可用**。

| 系统 | 取向 | 后果 |
|---|---|---|
| **Nacos（AP，默认）** | 可用性 + 分区容忍 | 网络分区时仍能读旧列表，服务还能调 |
| **Zookeeper（CP）** | 一致性 + 分区容忍 | 分区选主期间**整个注册中心不可用**，服务发现直接瘫 |
| **Eureka（AP）** | 同 Nacos | 但已停止维护 |

**BASE** 就是这套思路的名字：**B**asically **A**vailable（基本可用）、**S**oft state（软状态）、**E**ventually consistent（最终一致）。微服务的绝大多数设计（注册中心、配置中心、最终一致）都建立在 BASE 上，而不是 ACID 上。

### 8.3 RPC 框架选型：Feign / Dubbo / gRPC

| | **OpenFeign** | **Dubbo** | **gRPC** |
|---|---|---|---|
| 协议 | HTTP/1.1 + JSON | 自定义 TCP + 二进制 | HTTP/2 + Protobuf |
| 性能 | 一般 | **高** | **高** |
| 跨语言 | 天然支持 | 支持（多语言 SDK） | **最好** |
| 调试 | 浏览器/curl 直接调 | 要工具 | 要工具 |
| 适合 | 内部业务、对外 API | 内部高频调用（Java 生态） | 跨语言、流式、移动端 |

**一条经验**：**优先 Feign**（简单、好调试、生态好），**性能真成瓶颈再换 Dubbo/gRPC**。因为「一次下单穿过 6 个服务」的场景里，网络往返次数才是大头，协议省下的那点序列化开销通常不是瓶颈。

### 8.4 服务网格（Service Mesh）/ Istio：把治理从代码里搬出去

视频里的治理能力（熔断、限流、重试、追踪）都是**写在业务代码/依赖里**的——换个语言就得重写一遍。**服务网格**的思路是：每个 Pod 旁边放一个 **Sidecar 代理**（Envoy），所有进出流量都经过它，**治理策略由控制面统一下发**。

| | SDK 模式（Sentinel） | Mesh 模式（Istio） |
|---|---|---|
| 语言绑定 | 有（Java 生态最好） | **无**，任何语言都行 |
| 升级治理策略 | 要改依赖、重新发版 | 改配置，**不动业务** |
| 代价 | 侵入代码 | 多一跳网络、运维复杂度高 |

📌 一句话：**服务网格是「微服务治理的下一步」，但它和 K8s 一样属于「规模到了才划算」的东西。**

### 8.5 分布式单体的自查清单

拿这 6 条去检查你手上的「微服务项目」，中 3 条以上基本可以判定是分布式单体：

| # | 自查项 | 是 → 危险 |
|---|---|---|
| 1 | 多个服务连同一个数据库、同一个 schema | ☠️ |
| 2 | 服务之间存在跨库 JOIN 或直接读对方的表 | ☠️ |
| 3 | 发版必须「凑齐一起发」，否则接口不兼容 | ☠️ |
| 4 | 公共模块（common）里有业务逻辑 | ⚠️ |
| 5 | 任何一个服务挂掉，全站不可用 | ☠️ |
| 6 | 只有一套部署流水线，无法单独发布某个服务 | ☠️ |

### 8.6 两个隐形的设计约束

**① 服务名为什么必须稳定**：它同时出现在注册中心实例列表、`@FeignClient(name=...)`、网关的 `lb://...`、配置中心的 `dataId`、监控追踪的服务名标签、告警规则里。**改一次服务名等于同时改 6 个地方，且没有编译期检查**——所以服务名要在立项时定死，跟数据库表名同等对待。

**② 为什么「可观测性」应该更早做**：作者把「日志加 traceId」列为「如果今天只带走一个行动项」。这背后有一条更硬的逻辑——**没有可观测性的微服务，不是「架构升级」，是「故障放大器」**。单体时代你至少能 `tail -f` 一个日志文件；拆成 6 个服务后，故障的表现从「报错」变成了「慢」「偶发失败」「数据对不上」，没有 traceId 几乎无法定位。所以业界的经验比视频里的三阶段路线更激进：**可观测性要跟着第一个拆分动作一起上，而不是等到第三阶段。**

## 9. 一句话总结

> **今天我们走了四段路：为什么拆、拆完长什么样、用什么工具、怎么装成一台机器。**
>
> **微服务不是先进技术，它是一份「用运维复杂度换组织扩展性」的交易合同。**
>
> **拆的是进程和边界，不是文件夹；判断标准只有一句——能不能单独重启。**
>
> **共享数据库的微服务，是更贵的单体。**
>
> **复杂度不会消失，只会转移。技术选型的本质，从来不是哪个先进用哪个，而是哪种复杂度你供得起。**
>
> **框架会更替，判断不会。**
