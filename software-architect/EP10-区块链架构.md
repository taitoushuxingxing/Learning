## 0. 课程地图：四份数据库，零份共识

### 0.1 开场事故：一批特种钢材，四个相关方

一家建材集团有一批特种钢材出了质量问题，要追责。涉及到四个相关方，每一方都掏出了「证据」：

| 相关方 | 掏出来的东西 | 问题出在哪 |
|---|---|---|
| **采购方** | 电子合同，标准写的是**国标** | 有电子签章，说自己是原件 |
| **供应商** | 另一份电子合同，写的是**按样品交付** | 也有电子签章，也说自己是原件 |
| **物流方** | 温控记录**完好** | 系统自建、数据自存自管 → 等于自己说自己的系统没问题，追责现场不被认可 |
| **质检方** | 报告**确实出过** | 但在不同渠道转了好几手，说不清哪份没被改过 |

注意：双方**未必是故意造假**，很可能只是版本管理错乱。但从这一刻起，**谁也说服不了谁了**。

最后只能打官司，鉴定费花很多。而鉴定机构能做什么、不能做什么，作者这句总结特别关键：

> **鉴定机构能证明这份文件「现在」是什么样、现在的哈希值是多少；但它证明不了这份文件「从签的那天起」就没被改过。**
> 因为这份文件，一直躺在利益相关方自己的服务器里。

### 0.2 事故的一句话总结

```
4 个相关方  +  4 份数据库  +  0 份共识
```

他们每一次对峙，问的都是同一个问题：

> **「你的那份，我凭什么信？」**

这就是区块链要回答的问题。不是「数据存得不好」，而是「该信任谁」这件事，在架构层面没有答案。

### 0.3 今天要走的四段路

| 段 | 主题 | 内容 |

| **第一段** | 从每天写的代码说起 | 从你天天写的 `insert` 出发，一步步把「区块链是什么」拼出来 |
| **第二段** | 互不信任时，规则说了算 | 把共识、智能合约、账本这些术语列成一张表，一次扫清 |

## 1. 第一章 从一条 insert 到一条链

本章回答四个问题：

1. 你每天写的 `insert`，离区块链到底差几步？
2. 账本抄给所有人，为什么就改不动了？
3. 区块链和比特币、和「发币」到底是什么关系？
4. 什么代价？什么时候**不该**用？

### 1.1 先替中心化数据库说几句公道话

作者特意先讲这个，因为大多数人一上来就被告知「区块链更先进」，这是错的。

**你每天都在享受 MySQL 带来的四个好处：**

| 好处 | 具体表现 |
|---|---|
| **快** | 一次主键查询毫秒级返回；写吞吐上万是家常便饭 |
| **能改** | 数据错了，一个 `update` 搞定，还能事务回滚 |
| **可控** | 权限、备份、审计，全在自家运维手里 |
| **便宜** | 一台 8 核 16G 就能撑起日活百万的业务 |

> **这四样好处，区块链一个都给不了你。**
> 因为链比数据库**慢得多、贵得多，而且不能改**。

**再看什么时候中心化数据库就是最优解（四个「别上链」的信号）：**

| 场景 | 为什么不需要链 |
|---|---|
| 数据只在**一家机构内部**流转 | 没有多方互信问题，链没有存在意义 |
| 参与方**愿意认一个共同担保人**（平台 / 银行 / 监管） | 有裁判就不需要「大家投票当裁判」 |
| 业务要求**可修正可修改**（用户注销、错账冲正） | 链上没有 `update` / `delete`，你会被业务逼死 |
| 只是想要**日志不可改** | 数据库审计日志 + **WORM 存储**（一次写入、多次读取）就够了，又便宜又合规。用区块链是**杀鸡用牛刀** |

### 1.2 本章的题眼

> **区块链从来不是「更好的数据库」。它慢、它贵、它不能改。** 这些特性在**单机构场景**里全是缺点。
> 它的价值只有一个：**在多方互不信任、又没有人有资格当担保人的时候，才凸显出来。**

记住这句话，后面所有的技术细节都是它的注解。

### 1.3 中心化世界的三道坎

什么情况下「信任」会变成刚需？作者列了三道坎：

| 坎 | 表现 |
|---|---|
| **① 多方不信任** | 跨机构各存各的账。像开场那个事故，同一批货有 4 份记录、4 个版本，只能靠**人工对账**，一旦出错就开始扯皮 |
| **② 自证清白** | 账本在利益方手里。**签章能证明「这份文件是谁签的」，但证明不了「签完之后有没有被改过」**。数据在利害相关方的服务器上，**日志记得再全，那也是自己证明自己** |
| **③ 历史追责** | 找个**中立平台**记账？平台要收费（中介费吃掉交易额 **1%~3%**）、需要授权（授权本身又是一次信任）、可能跑路（单点风险），而且**谁来监督这个担保人？——无限套娃** |

#### 三道坎的共同点

> **它们都不是「数据存得不好」的问题，而是「该信任谁」在架构层面没有答案。**
> **数据库只解决了「记得对」，它解决不了「大家信」。**

### 1.4 两个容易被忽略的隐形成本

| 隐形成本 | 具体 | 为什么难量化 |
|---|---|---|
| **对账的人力** | 两边财务每月对一次账，差一笔就要拉群、打电话、翻存证，**好几天** | **这笔钱不在任何一张报表上，但它真实发生** |
| **合规的边界** | 跨机构共享数据，牵涉「**谁能看谁的什么东西**」 | 中心化架构里无解——**一旦集中，就等于全部可见**（联盟链的「群组隔离」就是解这个的） |

### 1.5 解法第一步：把账抄给所有人 = 分布式账本

它的正式名字叫**分布式账本**。定义只有一句话：

> 别只存一家了，四家每家都存一份。
> 每次来一笔新记录，立刻广播给所有人。
> **谁的手里都是全量的，谁也不比谁多一份原始数据。**

#### 用你会的东西实现它

作者说得很实在：不用什么黑科技。

```
每一方部署一个记录服务（就是 Spring Boot + 一张表）
        ↓
业务发生一笔，接口同步调用所有参与方的服务，各自 insert 一条
        ↓
相当于把这个数据库的 binlog 全量互推给了对方
```

再立一条铁规矩：

```sql
-- 这张表只允许 INSERT
-- 没有 UPDATE，没有 DELETE
-- 写错了？追加一条更正记录
INSERT INTO ledger (id, biz_no, content, created_at) VALUES (...);
```

#### 一个精确的类比：Git

> 就好像我们用 Git：**人人都有一份完整的克隆，谁在本地改了什么，一下子就能知道。**

#### 它解决了什么

回到那个问题：「你的那份我凭什么信？」

**现在不需要单独信你了。**

> 因为我看的是同一份。你的每一次写入都同步到了我这里，**四方手里就是同一本账**。

但这还不够——大家都抄了账本，**怎么发现有人偷偷改了自己那一份副本？** 这就需要引入下一个工具。

### 1.6 解法第二步：哈希，给每一页盖指纹

#### 定义

> **哈希函数：把任意内容（一段文字、一个文件、一部电影）压缩成一个固定长度的指纹。**

以 **SHA-256** 为例：不管输入是一部电影还是一个字符，输出永远是 **64 个十六进制字符**。

**内容变一点点，指纹就面目全非。**

一句话记法：**内容定指纹，指纹验内容。**

#### 三条性质（每条都有用）

| 性质 | 含义 | 在账本里有什么用 |
|---|---|---|
| **确定性** | 同样的输入永远得到同样的输出，算一万次都一样 | 指纹能「认人」的前提 |
| **雪崩效应** | 输入改一个字，输出的 64 位整个变掉，跟原来毫无关联 | 改动**无法隐藏**，哪怕只改一个标点 |
| **单向性** | 内容 → 指纹瞬间完成；指纹 → 内容在数学上做不到 | 原文不用上链，链上放指纹也不泄露内容 |

作者对「单向性」的比喻很生动：**你可以通过指纹认出来一个人，但你没有办法通过指纹长出来一个人**——你能鉴定他的身份，但你不知道他长什么样。

#### 怎么用它发现改账

```
① 每条重要记录，额外存一份它的哈希
② 对峙的时候，把双方拿来的账本重新算一遍指纹
③ 和当初存的一比：
      一致   → 没改过
      不一致 → 改了，而且能定位到哪一条
```

### 1.7 解法第三步：区块与链，把指纹串起来

新问题：账本那么长，难道每条记录都单独核对一遍？

**能不能给整本账做一个总的校验？** 可以——把指纹串成链。

#### 为什么要「打包」

一条条算指纹、存指纹太琐碎。工程上的做法是**攒一批、打一个包**：

> 就像批量提交——1 万条 `insert` 攒成一批一起提交，省成本。

在区块链上，这个包叫**区块（Block）**。

#### 区块的四个字段（本课最核心的一张图）

```
┌──────────────────────────────────────────┐
│  Block #N                                │
├──────────────────────────────────────────┤
│  data        │  这批记录（业务数据）      │  ← 要存的内容
│  prevHash    │  上一块的指纹              │  ← ★ 整个设计的灵魂
│  hash        │  本块内容的指纹            │  ← 出生那一刻就定死
│  timestamp   │  出块时间                  │
└──────────────────────────────────────────┘
```

#### 链是怎么串起来的

```
   块 1                块 2                块 3
┌──────────┐      ┌──────────────┐    ┌──────────────┐
│ data  D1 │      │ data      D2 │    │ data      D3 │
│ prev 000 │      │ prev     AAA │    │ prev     BBB │
│ hash AAA │ ←────│ hash     BBB │←───│ hash     CCC │
└──────────┘      └──────────────┘    └──────────────┘
        ↑ 首块 prevHash 填全 0（约定）      ↑ 一环扣一环
```

**规则只有一条**：新块的 `prevHash`，必须填**当前末尾块的 `hash`**。

就是这一行赋值，把所有块串成了一条链。

#### 篡改为什么会被发现

假设有人偷偷改了**第 2 块**里的一个字：

```
第 2 块内容变了
   → 第 2 块的 hash 变了（雪崩效应，全变）
   → 第 3 块里存的 prevHash 对不上了   ⚠️ 报警
   → 第 3 块 hash 也跟着变
   → 第 4 块 prevHash 也对不上了      ⚠️ 报警
   → …… 后面所有块连环失效
```

> **改一个字，等于要同时伪造后面所有块的指纹，还要瞒过所有人手里的副本。**
> 理论上有可能，**工程上不可能**。

#### 区块链的完整定义（作者原话）

> **多方各存一份全量账本，只允许追加，页与页之间用哈希相扣的账本。改任何一条历史记录，都会被全体立刻发现。**

拆开就是三件套：

```
① 人人一份全量账本          （分布式账本）
② 每一页都有指纹            （哈希）
③ 页与页之间指纹相扣        （链）
        = 区块链
```

### 1.8 回到开场事故：正确的做法是什么

```
签署合同的瞬间
   → 把文件的哈希值写入多方共同维护的这条链
   → 原文各自留存（不上链）

日后任何一方
   → 拿出原文，重算哈希
   → 和链上那条记录对比
   → 相等 = 从签下的那一刻起，一个字都没改过
```

> **这样的证明，它依赖于数学**，而不是依赖于「你信我」。
> 很多司法存证平台的底层，都是这个结构。

### 1.9 泼两盆冷水

账本拼完了，但作者立刻泼两盆冷水：**第一盆是它不是什么，第二盆是它要付出什么。**

#### 第一盆：区块链不是什么

| 它不是 | 真相 |
|---|---|
| **不是更好用的数据库** | 查询、统计、事务，样样不如 MySQL |
| **不是防泄密的保险箱** | 链上数据人人有份，大家都能看。敏感数据**不要放上去** |
| **不是万能的可信** | 它只保证「记上去的没被改」，**不保证「记上去的是真的」**。假的、垃圾的放进去，取出来还是垃圾 |

#### 第二盆：四个代价

| 代价 | 原因 | 应对 |
|---|---|---|
| **① 慢** | 写一条数据要经过：全网广播 → 共识确认 → 多节点落盘。而 MySQL 只需要本机事务提交。MySQL 轻松上万 TPS，区块链大多数情况是**上千级别** | 链上只放凭证 |
| **② 膨胀** | 每个节点都要存**全量**账本，历史只增不减，不能像普通数据库那样清理归档 | **图片、视频这类大文件绝对不要上链，只存哈希** |
| **③ 隐私难** | 账本人人一份。采购价、成本价、客户名单，不能让对手看到，也不能让其他利益相关方看到 | 靠**群组隔离 + 权限 + 加密**，在架构层重新设计 |
| **④ 改不了**（最容易被低估） | 业务写错了怎么办？用户要行使删除权怎么办？没有 `update` / `delete`，旧数据永远躺在那儿 | **上链前严格把关，纠错靠冲正记录** |

> 作者特别提醒：很多人把「不可篡改」当纯优点。
> **对架构师来说，它同时是一笔债**——你必须在设计阶段就把「怎么纠错」想清楚。

## 2. 第二章 互不信任时，规则说了算

回到事故现场：四个机构各跑一个节点，各记各的，账对不上的时候**听谁的**？

本章回答四个问题：

1. 账本分叉，听谁的？→ **共识机制**
2. 挖矿到底在挖什么？
3. 智能合约到底是什么？→ **一句话：账本的公共存储过程**
4. 公链 / 联盟链 / 私链怎么区分？

### 2.1 共识机制的定义

> **共识机制：两个节点的账不一样的时候，按什么规则去定输赢。**
> 它要回答两个问题：**① 谁来记账（记账权归谁）？② 几个节点同意才算数？**

四种主流机制，一张表看完：

| 机制 | 全称 | 怎么选记账人 | TPS 量级 | 能耗 | 典型场景 |
|---|---|---|---|---|---|
| **PoW** | Proof of Work 工作量证明 | 全网算力竞赛，谁先解出难题谁记 | 个位数 ~ 十几 | **极高** | 比特币（完全匿名的公网） |
| **PoS** | Proof of Stake 权益证明 | 按质押权益 + 随机选取，作恶罚没质押 | 较高 | 低 | 以太坊等公链 |
| **PBFT** | Practical Byzantine Fault Tolerance 实用拜占庭容错 | 点名投票，提案需 **2/3 以上**同意 | 上千 ~ 上万 | 低 | **企业级联盟链首选** |
| **Raft** | 领导者选举 + 日志复制 | 选主，主节点写日志复制给从 | 上万 | 低 | Nacos、etcd 底层同类协议 |

#### PoW 的定位 / PoS 里「作恶」到底指什么

PoW 是为**完全匿名的陌生网络**设计的：在这样的公网上，你不知道对方是谁，**大家只能靠算力说话**。

PoS 里的「作恶」，作者用大白话解释了一遍——节点为了私利做下面这些事，就是作恶：

| 作恶行为 | 通俗说法 |
|---|---|
| 篡改历史、篡改已确认的区块数据 | 偷偷改账 |
| 故意不打包交易 | 故意晾着你 |
| 疯狂发垃圾交易堵塞网络 | **拒绝服务** |
| 故意搞乱网络状态，让大家数据不一致 | 搅浑水 |

> **一句话：节点试图欺骗系统、篡改数据、破坏网络正常运行的违规行为，就是干坏事。**
> 在 PoS 里作恶被发现就**罚没你质押的权益**；但这条路走的是公网，**企业场景基本碰不到**。

#### PBFT 与「拜占庭」这个名字

「拜占庭」是个地名，来自一个经典难题：

> 几个将军围了一座城，只能靠传令兵沟通。但传令兵当中可能**混着叛徒**，会传假消息。这时候还怎么统一行动？

换到计算机语境就是：**有的节点会作恶，账还能不能记对？**

PBFT 的答案很朴素：**点名投票，一个提案 2/3 以上同意才能通过。**

```
4 个节点，最多容忍 1 个叛徒 → 剩下 3 个（75% > 2/3）仍能把账记对 → 容忍度 = 1/3
```

### 2.2 挖矿到底在挖什么

#### 先讲本质

> **每一块账本只能由一个节点来记，这个名额叫「记账权」。挖矿就是去抢这个名额。**
> **所谓不同的共识机制，其实就是不同的抢法。**

#### PoW 的抢法：一道算术题

```
找一个数 nonce，使得：
        SHA256( 块内容 + nonce ) 的结果，开头 N 位全是 0
```

关键点：**哈希是没有规律的**，你没法推导，只能一个一个数去试。

| 难度（前 N 位为 0） | 普通电脑耗时 |
|---|---|
| 4 位 | 几十毫秒 |
| 6 位 | 秒级 |
| 比特币全网难度（前十几位） | **平均 10 分钟**解出一次，且消耗巨额电费 |

> **挖矿的真相：用电费去换记账权。**

#### 为什么公链要「故意这么慢」

这是本课最漂亮的一个因果链：

```
10 分钟出一个块
   → 你要篡改一个历史块，必须在 10 分钟内追平全网算力、重挖后面所有块
   → 成本 ≈ 烧掉全网的算力与电费
   → 几乎不可能
```

> **公链慢，不是技术不行，是故意的。它是用出块速度，去换作恶成本。**

### 2.3 公链 / 私链 / 联盟链：三个比喻

| | **公链 = 完全开放的公共广场** | **私链 = 企业内部的闭门会议室** | **联盟链 = 行业俱乐部** |
|---|---|---|---|
| 准入 | 有电脑和网络就能随时加入、下载数据、发起交易 | 需要许可，完全由某一个组织控制，外人进不来 | **半开放**，多个企业/机构组成联盟，成员**经审批**才能加入 |
| 记账权 | 任何人可竞争（比特币挖矿、以太坊质押） | 高度集中，只有指定节点能记 | 联盟内指定节点共同参与（如 10 家银行里 5 家作节点共同确认交易） |
| 本质 | 任何人能提交写操作的超级大型公共数据库 | **本质上还是中心化的**，和 MySQL 集群没太大区别，只多了防篡改的链式账本 | **多中心化**，兼顾隐私、效率与一定的去中心化信任 |
| 速度/隐私 | 数据公开透明，效率**极低** | 写入非常快，隐私性很强（像内网系统：管理员能写，员工只能读） | TPS **远高于公链** |
| 典型技术 | Bitcoin、Ethereum | 各厂商私有方案 | Hyperledger Fabric、**FISCO BCOS** |
| 企业该选谁 | 基本不选 | 建议别浪费这个钱 | **几乎都选它** |

### 2.4 智能合约：账本的公共存储过程

#### 一句话定义

> **智能合约就是一段部署在链上的公共代码。所有节点共同执行，规则提前写死，谁也改不了。**

#### 三个类比，一层比一层准

**类比一：MySQL 的存储过程**

如果你写过存储过程，那智能合约干的就是同一套事情：**存数据、查数据、加校验**。

区别只有一个，但很关键：

> **它跑在每家机构的节点上，而不是某一家的数据库里。**

**类比二：自动售货机**

规则印在机器上，人人可见。**投币就出货，没有人能暗箱操作，因为机器不偏心。**

**类比三：多方共用的规则书**

四家机构现在都调**同一个合约**：

```
不用互相写接口  ← 接口就是合约本身
不用互相信任    ← 执行结果是所有节点各算一遍、对答案
```

#### 什么时候才需要写合约

> **多方的业务规则经常变，而且大家都要认账**的时候。

#### 坑：合约上线就改不了

> **规则一旦上线，就改不了了。**

所以如果你的业务规则经常变化，这个场景要**特别小心**：

| 做法 | 说明 |
|---|---|
| 把可变参数做成**链外配置** | 合约只写不变的部分，阈值/费率/名单从链下喂进来 |
| 或者干脆**别放合约** | 不是所有规则都值得写进链 |

> **改规则的灵活性，和不可篡改的公信力，天然是一对矛盾。**
> 设计的时候要想清楚：**把哪一边放在链上。**

### 2.5 术语表：一次扫清所有行话

| 术语 | 大白话 |
|---|---|
| **公链** | 谁都能进。比特币、以太坊用「抢答赛」那套，慢，但**谁也关不掉** |
| **联盟链** | 机构实名准入，用「投票」那套，快、能追责。**企业落地几乎都选它** |
| **私链** | 一家公司自己玩，其实就是一个**带审计的高级数据库**，建议别浪费这个钱 |
| **节点** | 跑着账本的一台服务器（也可以理解成一个 Spring Boot 实例） |
| **钱包** | 管密钥的工具。**里面装的不是钱，是钥匙** |
| **签名** | 用私钥给数据盖章，证明这笔确实是我发的 |
| **分叉** | 两份账对不上了 |
| **出块** | 打包一批记录成一块 |
| **Gas** | 公链上执行代码的**手续费**。联盟链没有，所以企业场景大多数不用管它 |

> 注意最后一条 Gas：**企业用的链，可以一分钱的代币都没有。**
> 这是本章开头第三个问题的答案——**区块链 ≠ 比特币 ≠ 发币**。

## 3. 第三章 实战：把存证系统升级成联盟链（重点）

> 作者先交底：**全章只有两小段代码**——一个 14 行的迷你链、一个 18 行的 Spring Boot 接口，每行都有中文注释，其余全是图和流程。目的是**抛砖引玉**。

路线三步：

```
① 先看清一个传统的存证系统（Spring Boot + MySQL）
② 把那张表升级成一条链，亲手做一次篡改实验
③ 从单机到联盟链，从 demo 到生产
```

### 3.1 什么是存证系统

> **存证系统本质上是一套防篡改的电子证据保管箱。**
> 它利用密码学和区块链技术，把**易被修改、易丢失**的电子数据固定下来（合同、交易日志……），让它具备法律效力，能在纠纷中作为证据使用。

为什么需要它：

| 普通做法 | 问题 |
|---|---|
| 存在硬盘或中心化服务器 | 容易被篡改、伪造、删除 |
| 发生纠纷时提供截图/后台数据 | **对方可以不信**——那是你自己系统里的东西 |

> **所以存证系统的核心任务，就是解决「自证清白」这个难题。**

### 3.2 起点：一个你完全能看懂的流程

```
用户上传合同
   → 后台算 SHA-256（拿到 64 位指纹）
   → 原文存进对象存储（OSS / S3）
   → 指纹存进 cert 表
   → 返回一张回执（"你的文件我收到了"）
```

作者原话：**每个项目都是这样的结构，没有一行你不了解的东西。**

#### 它有两个致命的缺口

| 缺口 | 具体表现 |
|---|---|
| **① 数据库在你手里，别人凭什么信？** | DBA、运维，甚至一个 SQL 工单，都能改这行记录。对手方要的是「**你没改过**」的证明，**你自己说了不算** |
| **② 只有你一家存，历史说不清** | 中间有没有被替换过？**没有任何机制能回答** |

#### 升级要补的就是这两条

```
缺口① → 账本各方各存一份，不再是「谁也改不了的独家记录」
缺口② → 指纹连成链互相验证，改一处就全线报警
```

> 这两个缺口，其实也是很多存证平台**招标文件里的需求**：「第三方可验证」对应缺口①，「历史可追溯」对应缺口②。以前这两个需求得靠**公证处背书**——费钱，而且效率低。

### 3.3 第一段代码：14 行的迷你链

把 `cert` 表升级成一条链。核心只有两个东西：**一个块**，和**一条链**。

```java
// ============ 一个区块：就三个字段 ============
class Block {
    String prevHash;   // 上一块的指纹（★ 灵魂字段）
    String data;       // 本块的业务数据
    String hash;       // 本块自己的指纹

    Block(String prevHash, String data) {
        this.prevHash = prevHash;
        this.data = data;
        // 对象一出生，指纹就算好了、算死了、锁死了
        this.hash = sha256(prevHash + data);
    }
}

// ============ 一条链：只追加 ============
class Chain {
    List<Block> blocks = new ArrayList<>();

    void append(String data) {
        // 新块的 prevHash = 当前末尾块的 hash
        String prev = blocks.isEmpty() ? "0" : blocks.get(blocks.size() - 1).hash;
        blocks.add(new Block(prev, data));   // ← 这一行，把块串成了链
    }
}
```

#### 三个必须记住的关键点

| 关键点 | 说明 |
|---|---|
| **① `prevHash` 是灵魂** | 没有它，你就只是个列表（List），不是链（Chain） |
| **② 出生就算指纹** | 篡改立刻暴露——因为 `data` 变了，重算的 `hash` 和存的旧 `hash` 对不上 |
| **③ 只追加，不修改** | 没有 `update`，没有 `delete`。这**不是为了省事，而是我们互相取得信任的来源** |

> 作者对照了一句：**字段还是那些字段，数据还是那些数据，变的只是——它再也改不动了。**

### 3.4 亲手把它弄坏一次：篡改实验

作者说这段不放代码，**强烈建议回去自己跑一遍**。三步：

```
第 1 步：偷偷改第一块的 data
        （反正是你自己的库，你想改就改）

第 2 步：重新算哈希
        → 新的指纹，和块里存的旧指纹对不上
        → 第一块当场报警 ⚠️

第 3 步：看第二块
        → 第二块里记的 prevHash 对不上第一块了
        → 第三块、第四块……全线报警 ⚠️⚠️⚠️
```

> **你想神不知鬼不觉地改，就要把后面每一块全部重算一遍。**
> **改一块，等于重做整条链。**

#### 那公链为什么还要再加一道 PoW

```
公链：重算每块都得做几亿次哈希运算（苦力活）
     → 篡改成本从「改一个字段」变成「烧掉几百万电费」

联盟链：节点是实名的，作恶可以追责
     → 用投票就够了
```

> **这就是联盟链快、公链慢的根本原因。**
> 记住这句话：**PoW 证明的是「成本」；联盟链证明的是「身份」。**

### 3.5 从单机到多节点：五个步骤

> 一条链只跑在你一个节点上，**和普通的账本没有区别**。
> 只有前面事故里的四家各跑一份、互相通报，才叫**分布式账本**。

```
① A 节点记一笔
② 先校验：重算指纹、核对 prevHash —— 对不上就直接丢
③ 广播给同伴节点（行话叫 peer）—— 就是一个 HTTP 调用
④ 收到的人再转给认识的人（像传八卦）—— 行话叫 gossip 协议，全网秒级同步
⑤ 四家各存一份完整的账本
```

```
        ┌────────┐
        │ 节点 A │  ← 记账
        └───┬────┘
     ┌──────┼──────┐
     ▼      ▼      ▼
┌────────┐┌────────┐┌────────┐
│ 节点 B ││ 节点 C ││ 节点 D │
└───┬────┘└───┬────┘└───┬────┘
    └─────────┴─────────┘
        gossip 继续扩散，直到全网一致
```

#### 用微服务的经验来理解

| 概念 | 对应物 |
|---|---|
| 节点 | 一个 **Spring Boot 实例** |
| 节点间通信 | 互相 **HTTP 调用** |
| 需要 MQ 吗 | **不需要** |
| 需要注册中心吗 | **不需要** |

#### 唯一要记住的安全底线

> **先校验，再转发。**
> **不校验就转发，你一个坏的块就可能污染全网。**

#### 新问题：分叉

A 和 B **同时**各记了一块、同时广播：

```
有的节点先收到 A 的  → 账本版本 1
有的节点先收到 B 的  → 账本版本 2
        → 分叉（两份账对不上）
```

**靠转发解决不了。必须有一条大家都服的裁决规则——这就是共识。**

> 好消息：**真链把共识内置了**，你写代码不用操心这个。

### 3.6 第二段代码：18 行的 Spring Boot 接口

把链接进你最熟悉的三层结构。核心是一个 Controller、两个接口：

```java
@RestController
@RequestMapping("/cert")
public class CertController {

    @Autowired private ChainService chainService;

    // 接口一：存证
    // 收到文件 → 算 SHA-256 指纹 → 调 addBlock 上链
    // → 把「块哈希 + 时间戳」当回执返回
    @PostMapping("/store")
    public Receipt store(@RequestParam("file") MultipartFile file) {
        String hash = sha256(file.getBytes());
        Block block = chainService.addBlock(hash);
        return new Receipt(block.hash, block.timestamp);
    }

    // 接口二：验证
    // 传一个哈希进来 → 链上查「有没有、什么时候存的」
    @GetMapping("/verify")
    public VerifyResult verify(@RequestParam String hash) {
        return chainService.findByHash(hash);
    }
}
```

> **其实就这么点事儿。**

#### 一套最小的存证系统 = 三个接口

| 接口 | 作用 |
|---|---|
| 存证 | 上传 → 算指纹 → 上链 → 返回回执 |
| 验证 | 传指纹 → 查是否存在、何时存的 |
| 按哈希回溯查询 | 用指纹定位到原记录 |

#### 上线前必须补的三件事（作者强调：这不是链的事）

| 补什么 | 为什么 |
|---|---|
| **接口加鉴权、限流** | 谁能调、调多快，链本身管不了 |
| **按文件指纹做幂等** | 重复上链直接返回原回执，别浪费共识 |
| **每次调用写审计日志** | 谁在什么时候存了什么 |

> **这三条不是链的事情，而是大家每天要做工程的基本功。**
> **你上链，也不能改变这些工程纪律。**

### 3.7 关键设计：链要挂在哪一层

这是本课最重要的一句架构结论：

> **把链当成一个特殊的「持久层」。**

```
改造前：  Controller → Service → DAO → MySQL
改造后：  Controller → Service → ChainService → 一条链
                                    ↑
                          上面的业务代码，一行都不用改
```

> **这就是「换持久层、不换业务」的思路，也是链能够落地的一个关键。**

如果你把链硬塞进业务层，那这个项目基本活不过第二次需求变更。

### 3.8 智能合约上场：业务规则老是要改怎么办

#### 还是那台售货机

规则提前写死、人人可见、投币就出货、没人能暗箱操作、谁都能用。

> 四家机构调**同一个合约**，不用互写接口，也不用互信——**机器是不偏心的**。

#### 存证合约只有两个「按钮」

| 按钮 | 做什么 | 隐藏价值 |
|---|---|---|
| **`store(hash)`** | 登记一次存证 | 同一指纹重复投币**会被拒** → **机器替你做幂等** |
| **`verify(hash)`** | 查询「谁、什么时候」存过 | 公开可查，不需要问任何一方 |

#### 事件（Event）

> 登记成功之后，合约还要**喊一嗓子**通知链下系统——这个就叫做**事件**。

```
合约 store() 执行成功
    → emit CertStored(hash, sender, blockNo, timestamp)
    → 链下 Java 监听 → 落库 → 生成回执
```

#### Java 侧对接的四步

| 步骤 | 做什么 |
|---|---|
| **① 建客户端** | 引官方 SDK，建客户端，配数据源之类的东西 |
| **② 加载合约** | 用**合约地址**加载出一个 Java 对象，之后**调它就像调本地 Service** |
| **③ 读写分离** | 写操作走共识，**几百毫秒**；读操作走本机，**毫秒级**——和读写分离是一个思路 |
| **④ 落库 + 密钥** | 监听事件落库回执；**私钥放密钥管理服务（KMS），不要放到 Git 里** |

#### 这一步最容易出的坑

> **监听事件是异步的，服务一重启就可能漏消息。**

生产上必须配**漏单补偿**机制：

```
定时任务：拿本地「待确认」的记录，去链上反查
   → 链上有、本地没有  → 补
   → 链上没有、本地有    → 报错
```

作者那句总结要记住：

> **链给了你事件，但可靠性还是要靠你自己的工程去兜底。**

### 3.9 搭一条真正的联盟链：FISCO BCOS

要搭多方的联盟链，有现成的开源轮子：**FISCO BCOS**（国产、免费、文档比较全）。

#### 四步

| 步骤 | 做什么 |
|---|---|
| **① 生成链** | 一条命令生成 **4 个节点**的链，本机就能模拟 4 家机构，一键启动 |
| **② 看块高、发交易** | 用官方控制台敲两行命令：看块高、发一笔存证——**几十毫秒就出块** |
| **③ 装网页控制台** | 装 **WeBASE**，点几下就能管链、发合约、看交易 |
| **④ 做停节点实验** | 停 1 个节点，链照常出块；停 2 个，共识停止 |

#### 四个必须理解的概念（全是大白话）

| 概念 | 大白话 |
|---|---|
| **① 准入靠证书** | 谁能连这条链，是机构们**投票定的**——这是一个**管理问题**，不是技术问题 |
| **② 群组（Group）** | 一条链上切出**多个独立账本**，就像 MySQL 一个实例可以分多个库。不同合作圈用不同群组，**数据天然隔离** |
| **③ 共识节点 vs 观察节点** | 共识节点参与投票；**观察节点只看不投**——它适合**监管方**接入 |
| **④ 为什么至少 4 个节点** | PBFT 只容忍 **1/3** 作恶。要容忍 **1 个**坏节点，至少需要 **4 个** |

#### 亲手感受「1/3 容忍度」

```
4 个节点，停掉 1 个 → 剩 3 个，3/4 > 2/3 → 链照常出块 ✅
4 个节点，停掉 2 个 → 剩 2 个，2/4 < 2/3 → 共识停止    ❌
```

> 作者建议一定要自己停一次。**「容忍度 1/3」这句话，只有亲手停过节点才是真的懂了。**

### 3.10 什么东西上链，什么东西上链下

回到前面泼的冷水：

| | 链上 | 链下 |
|---|---|---|
| 特性 | **慢、贵，但谁也改不了** | **快、便宜，而且归你管** |
| 放什么 | **只放存在证明**：文件指纹、谁、什么时候（几十个字） | 合同原文（对象存储）、业务数据（MySQL 做查询统计） |

#### 个人信息删除权怎么办

这是一个真实的法律问题，作者的解法很实用：

```
链下原文：可以删 ✅
链上哈希：追加一条「失效记录」 ✅
        → 既遵守个人信息保护规则
        → 又保证审计链条是连续的
```

#### 四步串起来（完整闭环）

```
① 用户上传合同原文 → 进对象存储
② 指纹上链 → 几秒出块 → 拿到区块号 + 交易号
③ 链上事件异步通知 Java → 监听后回执落库
④ 每天凌晨对账 → 逐条比对「链下记录」和「链上凭证」→ 漏记、篡改立刻暴露
```

#### 判断一个字段要不要上链：只问一句

> **「将来发生争议的时候，第三方需要验证它的什么？」**
> 只要验证它**存在过、没改过** → **哈希上链就够了**；要**频繁读取内容** → 留链下。

还有一条铁律：

> **前端展示永远查库，不上链。** 链每秒只能写上千 TPS，你拿它当查询库，会非常非常慢。

### 3.11 性能与安全

**性能**：联盟链出块**百毫秒级**、吞吐**每秒约千笔交易**，对大多数多方业务够用。前提是**链上只放凭证，大文件大字段一律链下**；写之前先做幂等，**重复数据别去浪费共识**。

#### 安全（四条）

| 措施 | 说明 |
|---|---|
| **私钥进 KMS** | 绝不落到代码库 |
| **证书定期轮换** | 联盟链的身份是有有效期的 |
| **合约代码能短则短** | 上线就改不了，**短就是安全**（攻击面小、审得完） |
| **审计日志照常记** | 上链不能豁免工程纪律，要一并对待 |

## 4. 第四章 从 demo 到生产

> **demo 能跑，和能上生产之间，隔着一堆工程问题。**

五个问题：代码怎么分模块、一次请求怎么走完全程、哪些场景值得上、怎么部署运维、落地怎么排期。

### 4.1 代码怎么分层：五目录四模块

| 目录 | 职责 | 关键约束 |
|---|---|---|
| **`chain-core`** | 领域模型：`Block`、`Cert`、哈希工具 | **不依赖 Spring 的纯 Java** |
| **`chain-contract`** | 合约源码 + 部署脚本 | **独立构建**，产物放配置 |
| **`chain-api`** | Spring Boot 应用：REST 接口、鉴权、幂等 | 对外入口 |
| **`chain-sync`** | 事件监听、对账、回执落库 | **长期运行的后台任务** |
| **`chain-common`** | DTO、异常、工具类 | **只被依赖，不依赖别人** |

```
┌──────────────────────────────────────────────────┐
│  chain-api (无状态，可弹性伸缩)                    │
│      ↓              ↓                            │
│  chain-core  ←  chain-common                      │
│      ↑                                           │
│  chain-sync (长期后台任务，独立伸缩节奏)            │
└──────────────────────────────────────────────────┘
          ↓ 部署产物
   chain-contract (合约，独立发布 + 版本化)
```

#### 为什么这么分：三条理由

| 问题 | 理由 |
|---|---|
| **`chain-sync` 为什么独立** | 事件监听和对账是**长期运行的后台任务**，伸缩节奏和 API 完全不同：API 白天高峰、晚上空闲，**SYNC 24 小时匀速跑**。放一个进程里，**扩容 API 时会顺手多起几个 SYNC，重复消费事件**。分开之后将来能独立拆成独立进程 |
| **`chain-contract` 为什么独立发布** | 合约改一次要**多方评审、重新部署、更新地址**，节奏和 Java 服务完全不同。所以**合约版本化**，把「API + 地址」放进**配置中心**，服务不用重启就能切到新合约——**合约升级不需要停业务** |
| **`chain-core` 为什么不依赖 Spring** | 领域逻辑保持纯 Java，**单元测试毫秒级跑完**，不用启动 Spring 容器。前面那条迷你链，其实就是 `chain-core` 里 `Block` 的雏形 |

### 4.2 一次请求走完全程：九步

场景：甲公司 + 乙公司 + 公证处 + 监管方，一共 4 方，签了一份合同要存证，将来可能有纠纷要打官司。

| 步 | 做什么 | 关键细节 |
|---|---|---|
| **①** | 网关收请求 | 鉴权（确认是这家机构）+ 限流（防刷）+ 校验格式与大小（如 20MB 以内，只收 PDF 和图片）。**这是上链前第一道关：别把垃圾扔进链** |
| **②** | 算哈希、原文入库 | 服务端算 SHA-256 得 64 位；原文进对象存储；业务记录落 MySQL，**只记 key 不记原文** |
| **③** | 幂等检查 | 拿哈希查是否存过（同一份合同甲乙双方可能各传一次），已存在直接返回原回执，**不重复上链** |
| **④** | 签名发交易 | SDK 从 KMS 取这家机构的私钥签名，哈希写进合约。**私钥不在应用内存里，应用只「请求签名」** |
| **⑤** | 共识出块 | 交易广播到 4 个节点 → PBFT 投票（提案 → 预投票 → 预提交）→ 拿到 **2/3** 同意出块，约几百毫秒 |
| **⑥** | 合约执行 | 四节点**各自**执行同一份 `store`：record 校验 → 写 mapping → emit 事件。★ 不是一台算完广播结果，而是**每台算一遍，算完对答案** |
| **⑦** | 回执落库（异步） | `chain-sync` 监听 `CertStored` 事件，拿区块号 + 交易哈希 + 合约地址 + 时间落进回执表。⚠️ 可能比第 ⑧ 步**晚几秒** |
| **⑧** | 返回用户回执 | 回执编号在**业务侧**生成，不是链上生成。凭证：回执编号 + 时间 + 哈希 + 区块号——★ 这是产品层看得见的价值，**用户拿到它，心里就踏实** |
| **⑨** | 日后验证（可能几年后） | 甲乙双方、公证处、法院，任何一方把手上的合同重算 SHA-256，与链上记录比对：一致 = 从签署那天到现在**一个字都没改过** |

> 第 ⑥ 步的「各自执行」值得单独记：**链不是「一台机器算完告诉大家结果」，而是「每台机器都算一遍，然后对答案」。** 这就是「不信任任何单个节点」在代码层面的样子。

> 作者的建议：**拿你手上的一个典型请求，把九步套一遍。**

### 4.3 四个落地场景：每个都问三句

判断标准统一是三个问题：

```
① 痛点是什么？
② 链在当中要扮演什么角色？
③ 是不是非链不可？
```

| 场景 | 痛点是什么 | 链扮演什么角色 | 非链不可？ |
|---|---|---|---|
| **① 司法存证**（最成熟） | 电子证据易改易失效，**你自己证明自己，法院很难采信** | 签署瞬间**哈希上链 + 时间戳**，法院认链上记录作证据（已有实践） | **非链莫属**：同时满足「多方」+「防篡改刚需」 |
| **② 供应链溯源** | 批次信息各环节**自己上报**，出问题查不到源头 | 每环节把**批次号 + 检验哈希**上链，全程可回溯、责任可定位 | **可以用，但别承诺「上链就保真」** |
| **③ 供应链金融**（联盟链价值最大之一） | 核心企业信用**传不到 2、3 级供应商**，中小企业融资贵融资难 | 应收账款凭证上链流转、**可拆分**，金融机构据此放款；**重复质押被彻底杜绝**（一笔账款押给两家银行，过去是常态） | 多方互信 + 监管要求，**非常合适** |
| **④ 数字身份 / 证书** | 资质验证靠打电话发函，**慢且不可靠** | 颁发机构把证书哈希上链，验证方**秒级核验**；**机构解散了证书依然可验**（验证不依赖它的服务器，只依赖数学和链） | 规模小时中心化发证更便宜；**跨机构 + 长生命周期**才值得上链 |

两条要单独拎出来说的话：

> ⚠️ **场景②的话术陷阱**：**链只保证「记录没改过」，它不保证「记录是真的」。**
> 对外承诺「上链就保真」，是这个行业最常见的翻车方式。

> **场景③的天然属性**：**它天生是联盟**。核心企业、银行、供应商、监管，**一家都少不了**。

#### 三问的结论

> **跨机构吗？需要防篡改背书吗？数据源头可信吗？**
>
> **这三问下来你会发现：其实很多场景下，不用区块链才是更正常、更正确的答案。**

### 4.4 部署与运维

| 环境 | 怎么做 | 铁律 |
|---|---|---|
| **本地 / 测试** | 链节点 + WeBASE + MySQL + Redis，**一条 docker 命令全部起起来** | **永远不要手工搭链，要用脚本一键重置**——你手工搭的链，可能第二天你自己都复现不出来 |
| **生产 · 优先** | 用云厂商的 **BaaS**：节点托管、证书轮换、监控告警都是现成的 | 能省下运维成本 |
| **生产 · 自建** | 上 K8s 时注意：**链节点是有状态服务**，需要数据盘、需要稳定的网络标识 | **不要当无状态服务让它到处漂移**。你的 `chain-api`、`chain-sync` **才是无状态的**，可以随便弹性伸缩 |

#### 原则：节点要「稳」，不要「弹」

```
共识节点频繁重启 → 触发视图切换（view change） → 出块间隔抖动 → 严重时整个链卡住
```

> 所以**节点的副本数、调度策略、滚动升级，都要按「稳定」的需求来设计，不能按「弹性」的需求来设计。**

#### 监控：盯四类指标

| 类别 | 看什么 | 不看的后果 |
|---|---|---|
| **① 出块** | 高度是否在增长？出块间隔抖不抖？ | **高度不涨，这个链就是死的** |
| **② 节点** | 进程在不在？磁盘满没满？peers 数够不够？ | 单节点掉线还不知道 |
| **③ 交易** | TPS、失败率、有没有积压队列 | 业务侧开始报错才发现 |
| **④ 业务** | 回执落库延迟、对账差异条数 | 链是健康的，业务是坏的 |

> 前三类是「链的视角」，第四类是「**业务视角看链的健康程度**」——这一类最容易被漏掉。

#### 治理：技术解决不了的部分

> **治理这件事情，技术上没法解决，必须落到书面章程上。**

| 章程要写清什么 | 具体问题 |
|---|---|
| **新成员准入流程** | 谁来批准？要多久？要什么材料？ |
| **作恶 / 违约处置** | 罚多少？怎么退出？ |
| **合约升级签名规则** | 需要几个人签？**谁有否决权？** |

> **这些是通过章程来约束「人」，不是约束代码。**

### 4.5 三期路线：顺序反了会天天出事

| 阶段 | 时间 | 做什么 | 产出 |
|---|---|---|---|
| **第一阶段** | **0~3 个月** | **存证先行，单场景验证**。挑一个最痛的场景（合同、检测报告、验收单），把它们的哈希上链。起步用云 BaaS，或者 4 节点小集群 | 一条**有背书的完整链路** |
| **第二阶段** | **3~9 个月** | **多方扩员，立好规矩**。让更多机构入网；群组划分；治理章程签署；WeBASE 运维体系和告警建起来 | 一个**能自我运转的联盟** |
| **第三阶段** | **9 个月以后** | **深化集成，治理进化**。合约升级体系、隐私计算、跨链互认、和业务系统深度集成、数据产品化 | 链变成**基础设施** |

#### 顺序为什么不能反

一上来就让 8 家机构都入网，章程还没签，结果：**一家想退、一家作恶、一家说「我的数据不能给别人看」——项目直接停摆。**

```
先证明单点价值  →  再扩员  →  再深化
```

### 4.6 五个坑（可以当检查表用）

| # | 坑 | 后果 | 解法 |
|---|---|---|---|
| **1** | **为了链而链** | 老板说上就上，单机构场景硬上，维护成本全打水漂 | 自查三问：数据是不是只在内部流转？有没有共同担保人？业务要不要可删可改？ |
| **2** | **原文上链** | 大文件直接塞链上 → 存储爆炸、同步变慢、隐私全无 | **哈希上链，原文入库** |
| **3** | **先搭链后立规矩** | 节点谁出钱、作恶怎么罚都没说清楚就开张，后面扯皮只是时间问题 | **先签章程，再搭链** |
| **4** | **密钥放进 Git** | 开发密钥顺手提交，身份可被冒用。**这不只是你自己出事，整个联盟都会出事** | **KMS + CI 私钥扫描** |
| **5** | **赌合约不会改** | 上线前发现 bug，合约不可热修，业务被迫停摆 | **数据逻辑分离 + 多方签名升级**，而且**第一版就要设计进去**，不能等出了事再补 |

### 4.7 一页 PPT 回顾：四组关键词

| 组 | 关键词 |
|---|---|
| **架构与边界** | 分布式账本、哈希链、记账权、共识机制 |
| **调用与治理** | 拜占庭容错、智能合约、联盟链、去币存链 |
| **故障与数据** | 哈希上链、事件回执、存证回执、数字签名 |
| **可观测与接入** | 群组隔离、冲正记录、链上链下协同、分布式单体 |

> 「**去币存链**」是本课的立场：**企业用的链，可以一分钱代币都没有。**「**分布式单体**」则被作者放在这一组里当反面提醒——**链拆分得再漂亮，业务还是一个大单体，那问题一个都没解决。**

### 4.8 三句话收尾

> **第一句：先问「多方互不信任吗」，再问「要不要链」。** 没有多方的情况下，区块链就是一个**昂贵的摆设**。
>
> **第二句：链上存共识，链下存业务。** **哈希上链是工程和法务的共同语言**——工程上它是最省成本的证据，法务上它是可采信的凭证。
>
> **第三句：不可篡改是数学给的，信任是人管出来的。** 密钥、章程、治理，一个都不能少。

作者最后那段话值得原样留着：

> **技术能保证「改了会被发现」，但它保证不了「没人敢改」。**
> **真正能让一个联盟活下来的，是章程、是准入、是处置机制——那是大家坐下来谈出来的规矩。链，只是把规矩写成了代码。**

## 5. 全局视角：一次存证请求的九步全景

把四章的所有碎片，压缩到一张图里看：

```
┌──────────── 链下：快、便宜、归你管 ────────────┐
│ 用户 → 网关(①鉴权/限流/校验) → 应用           │
│        (②算SHA-256 + 原文进对象存储)          │
│        (③幂等查重)                            │
│              │ ④ 从 KMS 取私钥签名             │
└──────────────┼────────────────────────────────┘
               ▼
┌──────────── 链上：慢、贵、改不了 ──────────────┐
│ 节点1┐                                        │
│ 节点2┼─⑤ PBFT 2/3 投票(几百ms)                │
│ 节点3┤                                        │
│ 节点4┘─⑥ 四节点各自执行 store() → emit 事件    │
│ 账本：[块N-1] ←prev─ [块N] ←prev─ [块N+1]      │
└──────────────┼────────────────────────────────┘
               │ ⑦ 事件异步回调
               ▼
┌──────────── 链下 ─────────────────────────────┐
│ chain-sync 监听 → 回执落库 → ⑧ 返回用户凭证    │
│        └→ 每天凌晨对账：链下记录 vs 链上凭证   │
│              差异 = 漏记 or 篡改 ⚠️            │
│ ⑨ 几年后：任一方重算 SHA-256 → 与链上比对      │
└───────────────────────────────────────────────┘
```

### 5.1 分层职责

| 层 | 放什么 | 为什么 |
|---|---|---|
| **接入层** | 鉴权、限流、格式校验 | 别把垃圾扔进链，共识很贵 |
| **业务层** | 幂等、回执编号、对账 | 这些是工程纪律，上链不能豁免 |
| **持久层** | `ChainService` 背后是一条链 | 换持久层，不换业务 |
| **链上层** | 只放哈希 + 谁 + 什么时候 | 慢、贵、不可改，只适合放凭证 |
| **存储层** | 原文、业务数据 | 快、便宜、可删可改、可查询统计 |
| **治理层** | 章程、准入、处置、升级签名 | **技术解决不了的部分** |

## 6. 速查卡：术语 / 场景 / 参数一页查完

### 6.1 核心术语

| 术语 | 一句话 |
|---|---|
| 分布式账本 | 多方各存一份全量账本，每笔新记录广播给所有人 |
| 哈希 | 任意内容 → 固定长度指纹。SHA-256 输出 64 位十六进制 |
| 哈希三性质 | 确定性、雪崩效应、单向性 |
| 区块 | 一批记录的包。四字段：`data` / `prevHash` / `hash` / `timestamp` |
| 链 | 后一块的 `prevHash` 指向前一块的 `hash` |
| 记账权 | 这一块由谁来记的名额。挖矿就是抢它 |
| 共识机制 | 两个节点的账不一样时，按什么规则定输赢 |
| 分叉 | 两份账对不上（通常是两个节点同时出块） |
| 智能合约 | 部署在链上的公共代码，所有节点共同执行，上线改不了 |
| 事件 | 合约执行成功后「喊一嗓子」，通知链下系统 |
| 数字签名 | 用私钥给数据盖章，证明这笔确实是我发的 |
| 钱包 | 管密钥的工具，装的是钥匙不是钱 |
| Gas | 公链上执行代码的手续费。联盟链没有 |
| 群组 | 一条链上切出的多个独立账本，数据天然隔离 |
| 观察节点 | 只看不投的节点，适合监管方接入 |
| 冲正记录 | 写错了不能改，只能追加一条更正记录 |

### 6.2 三种链怎么选

| 判据 | 选它 |
|---|---|
| 数据只在一家机构内部 | **MySQL**（不要用链） |
| 有公认的担保人（平台/银行/监管） | **MySQL** |
| 业务需要可改可删 | **MySQL** |
| 只是要日志不可改 | **MySQL + WORM 存储** |
| 多方、互不信任、无人有资格担保 | **联盟链** |
| 要完全公开、谁都能参与、不怕慢 | 公链 |
| 一家公司自己玩、想要链式审计 | 私链（**作者建议：别浪费这个钱**） |

### 6.3 数字速查

| 指标 | 数值 |
|---|---|
| SHA-256 输出长度 | 64 个十六进制字符 |
| MySQL 写吞吐 | 上万 TPS |
| 区块链写吞吐（普遍） | 上千 TPS |
| 公链出块 | 平均 10 分钟/块（比特币） |
| 联盟链出块 | 百毫秒级（FISCO BCOS 实测几十毫秒） |
| PBFT 容错 | 1/3，**容忍 1 个坏节点至少需 4 个节点** |
| 中介平台抽成（被替代的对象） | 交易额的 1% ~ 3% |
| 建议上传文件上限（示例） | 20MB，只收 PDF 和图片 |

## 8. 面试自测题（含答案）

先自己答，再看答案。

<details>
<summary><b>Q1：区块链比 MySQL 先进，新项目是不是该直接上链？</b></summary>

**不是。** 区块链**从来不是更好的数据库**——它慢、它贵、它不能改，这三条在单机构场景里全是缺点。

只有同时满足「**多方**」+「**互不信任**」+「**没人有资格当担保人**」三个条件，它的价值才凸显。否则就是昂贵的摆设。
</details>

<details>
<summary><b>Q2：只要把数据存到多个节点上，就是区块链了吗？</b></summary>

**不是。** 三件套缺一不可：**① 人人一份全量账本**（分布式账本）**② 每一页都有指纹**（哈希）**③ 页与页之间指纹相扣**（`prevHash` 指向上一块的 `hash`）。

少了第 3 条，你只是「多副本数据库」。
</details>

<details>
<summary><b>Q3：为什么改一个区块，后面所有区块都会失效？</b></summary>

因为 `prevHash` 是**写进下一块内容里**的：改第 N 块的 `data` → 第 N 块 `hash` 变（雪崩效应）→ 第 N+1 块里存的 `prevHash` 对不上 → 第 N+1 块 `hash` 也跟着变 → …… 连环失效。

所以要神不知鬼不觉地改，必须**重算后面所有块**，**还要瞒过所有人手里的副本**。
</details>

<details>
<summary><b>Q4：PoW 到底在算什么东西？为什么要故意算得那么慢？</b></summary>

找一个 `nonce`，使得 `SHA256(块内容 + nonce)` 的结果**前 N 位全是 0**。哈希没有规律，只能一个一个试。

**慢是故意的**：10 分钟一块，意味着你要篡改历史块，必须在 10 分钟内追平全网算力、重挖后面所有块——成本 ≈ 烧掉全网的电费。

**一句话：PoW 用出块速度换作恶成本。**
</details>

<details>
<summary><b>Q5：为什么联盟链不用 PoW，用 PBFT？PBFT 又为什么至少要 4 个节点？</b></summary>

因为**联盟链的节点是实名的**，作恶可以追责、罚没、踢出联盟：**PoW 证明的是「成本」**（我不知道你是谁，只能让你烧钱），**PBFT 证明的是「身份」**（我知道你是谁，投票就够了）。**这就是联盟链快、公链慢的根本原因。**

PBFT 容忍 **1/3** 作恶，要容忍 **1 个**坏节点需 `n/3 >= 1` 即 `n >= 4`。3 个节点时剩 2 个只有 2/3，**不够严格大于 2/3**。
</details>

<details>
<summary><b>Q6：链上能不能存合同原文？</b></summary>

**不能。** 三个理由：**膨胀**（每节点存全量，历史只增不减，不能归档）、**慢**（大文件拖累广播与同步）、**隐私**（链上人人有份）。

正确做法：**哈希上链，原文进对象存储**。要证明「没改过」，哈希完全够用。
</details>

<details>
<summary><b>Q7：用户要求删除个人信息，但数据已经上链了，怎么办？</b></summary>

**链下原文可以删，链上追加一条「失效记录」。**

这样既遵守个人信息保护规则，又保证审计链条连续——**你能证明「这条记录在某年某月某日被依法作废了」，而不是「它凭空消失了」。**
</details>

<details>
<summary><b>Q8：链已经保证了不可篡改，为什么还要写审计日志、做幂等、加限流？</b></summary>

因为**这些不是链的事，是工程基本功**：**幂等**（重复上链是在浪费共识，共识很贵）、**鉴权限流**（链不知道「谁能调多快」）、**审计日志**（链只记「哈希被存过」，不记「谁在后台查了什么」）。

**你上链，也不能改变这些工程纪律。**
</details>

<details>
<summary><b>Q9：为什么 `chain-sync` 要独立成一个模块？</b></summary>

因为它的**伸缩节奏和 API 完全不同**：API 白天高峰、晚上空闲，SYNC **24 小时匀速跑**。放在一个进程里，**扩容 API 时会顺手多起几个 SYNC，重复消费事件**。独立之后能拆成独立进程，各自按自己的节奏伸缩。
</details>

## 9. 📌 补充：视频没细讲但一定会踩的坑

> 以下为原讲解之外的延伸，按重要性排序。

### 9.1 📌 默克尔树（Merkle Tree）：区块里其实不是一条条哈希

视频里讲的是「一个区块 = 一批记录 + 一个哈希」，这是**教学简化版**。真实实现里，一个区块的上千笔交易会两两配对做哈希、逐层向上，最后收敛成一个根哈希（**Merkle Root**），写进区块头：

```
              Merkle Root
             /           \
        H(1,2)            H(3,4)
       /      \          /      \
    H(tx1)  H(tx2)   H(tx3)  H(tx4)
```

好处有三个：**O(log n) 的存在性证明**（证明「这笔交易在块里」不用给出全部交易，只给出同层兄弟节点的哈希，即 **Merkle Proof**）、**只改一笔就整块失效**（任何叶子变动都传导到根）、**轻节点友好**（只存区块头几十字节）。

这就是「**全节点 vs 轻节点**」的区别来源：全节点存全量账本、独立验证一切；轻节点只存区块头、按需向全节点要证明。

### 9.2 📌 UTXO 与账户模型：两种记账方式

视频没有展开，但这是区块链账本的两大流派：

| 模型 | 怎么记 | 类比 | 代表 |
|---|---|---|---|
| **UTXO**（未花费交易输出） | 不记余额，只记「这笔钱从哪来、到哪去」，一笔交易的输入是上一笔的输出 | 现金：你花的是**具体的钞票**，不是账户里的数字 | Bitcoin |
| **账户模型** | 直接记 `address → balance`，还有 nonce 防重放 | 银行卡：记的是**余额** | Ethereum、FISCO BCOS |

**对企业架构师的实际影响**：联盟链几乎都用**账户模型**，因为业务语义更接近传统系统（「这个账户有多少额度」比「这些 UTXO 归谁」好理解得多）。**选型时这一条比共识算法更影响开发效率。**

### 9.3 📌 Fabric 的 Channel 和 FISCO BCOS 的群组，不是一回事

视频把两者都归到「群组隔离」，方向对，但细节有差别：

| | Hyperledger Fabric | FISCO BCOS |
|---|---|---|
| 隔离单位 | **Channel（通道）** | **群组（Group）** |
| 隔离强度 | 每个 Channel 是**独立的账本 + 独立的成员集合**，链码按通道实例化 | 一条链内多个群组，**各自独立账本与共识**，节点可归属多群组 |
| 比喻 | 一栋楼里隔出几个**互不相通的房间** | 一个 MySQL 实例里分几个**库** |

**踩坑点**：跨群组/跨通道查询**不能**直接 join，必须在应用层拼装。设计群组划分时就要想清楚「哪些数据会被一起查」，否则后期拆不动。

### 9.4 📌 跨链、Layer2、状态通道、分片：它们各自解决什么

视频只提了「跨链互认」一嘴。补一张定位表：

| 技术 | 解决什么 | 代价 |
|---|---|---|
| **跨链** | 两条独立的链之间转移资产/消息 | 需要中继、公证人或多签桥，**桥本身是新的信任点**（历史事故高发区） |
| **Layer2 / Rollup** | 主链太贵太慢，把计算搬到链下、只把结果或证明写回主链 | 提款有延迟；需要信任排序器或有效性证明 |
| **状态通道** | 双方高频小额交互，只在开关通道时上链 | 只适合**固定参与方**，且需要资金锁定 |
| **分片（Sharding）** | 把账本横向切开，各分片并行处理 | **跨分片交易**复杂度暴涨；安全性按分片稀释 |

**对企业的判断**：如果你的场景是「几家企业之间的低频高价值凭证」，这四个**一个都不需要**。它们的核心驱动力都是「公链太慢太贵」，而联盟链本来就不慢不贵。

### 9.5 📌 「不可能三角」的正确解读

业界常说的「去中心化 / 安全 / 可扩展性三者不可兼得」，经常被误用成「所以区块链一定慢」。更实用的解读是：

```
去中心化 ↑  →  参与验证的人多  →  达成一致的成本高  →  慢
安全     ↑  →  作恶成本高      →  通常靠冗余和算力  →  慢且贵
可扩展   ↑  →  少验证、快确认   →  信任集中         →  去中心化 ↓
```

**联盟链的选择是：主动放弃「去中心化」这一角**（节点是实名且有限的），换来安全和可扩展。这不是妥协，是**明确了「信任边界在联盟内部」**。

### 9.6 📌 51% 攻击、双花：在联盟链里还存在吗

| 攻击 | 公链 | 联盟链 |
|---|---|---|
| **51% 攻击** | 掌握过半算力即可重组链 | PBFT 下需控制 **>1/3 节点**（更严格，但节点是实名机构，作恶可追责） |
| **双花** | 同一笔钱花两次，靠确认数防 | 同样靠共识防；但**业务层还要做幂等**（同一份凭证重复提交，那是业务双花，链不管） |

> **关键提醒**：链能防「账本层面的双花」，**防不了「业务层面的重复提交」**。所以前面说的「按文件指纹做幂等」不是可选项，是必选项。

### 9.7 📌 国密支持：国内落地的硬要求

视频里没提，但国内很多项目招标文件会明确要求：

| 项 | 国际算法 | 国密算法 |
|---|---|---|
| 哈希 | SHA-256 | **SM3** |
| 非对称签名 | ECDSA / secp256k1 | **SM2** |
| 对称加密 | AES | **SM4** |

FISCO BCOS 原生支持国密版（编译时开启）。**如果你的场景涉及政务、金融、司法，选型阶段就要确认这一条**——事后切换等于重搭一条链。

### 9.8 📌 存证的法律效力，不只看「上链」这一步

视频提到「很多司法存证平台底层都是这个结构」，这里补一层实践认知：

| 环节 | 容易被忽略的要求 |
|---|---|
| **上链前** | 要能证明「原文 → 哈希」这一步没被污染（时间源、设备、操作日志） |
| **上链时** | 谁签的名？机构身份是否可验证？（这就是「准入靠证书」的意义） |
| **上链后** | 验证过程要可复现——第三方拿同样的原文和算法，能算出同样的哈希 |
| **出证时** | 通常还需要**司法鉴定/公证**把「链上记录」翻译成法庭认的形式，链本身不直接等于判决 |

> **技术给的是「可验证性」，法律给的是「可采信性」，这两件事不能互相替代。**

### 9.9 📌 Token / NFT / DAO：本课为什么不讲

作者明确「一个字都不聊投资」。从架构角度只补一句定位：三者分别是**同质化权益凭证**、**唯一性凭证**、**用合约编码治理规则的自治组织**。企业场景的相关度都很低——**「凭证」不需要做成可交易的 token，唯一性资产用「哈希上链 + 数据库唯一索引」更简单，治理靠章程和公司法不靠合约**。

> **记住本课立场：去币存链。** 联盟链可以一分钱代币都没有，这不影响它解决信任问题。

### 9.10 📌 一个视频没提但很现实的成本：节点的钱谁出

联盟链最少 4 个节点，每个节点要数据盘、要带宽、要人运维。**这笔钱怎么摊，是项目最容易死的地方**：一家全包（主导方撤资链就停）、各家自建（小机构不愿出，规格参差）、第三方托管（回到「依赖平台」，但这是**运维依赖**不是**信任依赖**，可以接受）。

> 这就是为什么第四章强调「**治理要落到书面章程**」——**节点谁出钱、作恶怎么罚、想退出怎么办**，这三条不写清楚，技术上再完美也活不过一年。

## 10. 一句话总结

> **区块链不是一个更好的数据库，它是一个在「多方互不信任、又没人有资格当担保人」时才值得付的代价。**
>
> **它慢、它贵、它不能改——这三条在单机构场景里全是缺点，在多方场景里却正好是「谁也无法单方面抵赖」的来源。**
>
