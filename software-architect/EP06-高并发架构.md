## 0. 课程地图：从一台扛不住的 Spring Boot，到一套扛得住大促的系统

### 0.1 全课唯一的观点

门槛很低：**不需要你用过消息队列、不需要你用过缓存**，会写 Java、用过 Spring Boot、做过哪怕很小的项目就能听懂。目标只有一句：`一台扛不住的 Spring Boot → 一套扛得住大促的系统`。

而全课只有一个观点：

> **高并发不是加机器。**

作者打的比方很重：**架构是错的话，你加机器，就好像用更多的水桶去接一个即将要决堤的大坝。**

因为加机器只解决「应用层」的问题——应用无状态，复制 100 份毫无障碍；但**数据库是有状态的**，只有一个副本，连接数、行锁、磁盘 IO 三条约束一条都逃不掉。加 10 台应用服务器，只是让它们排更长的队去敲同一扇数据库的门。

真正的解法是：

> **让流量在到达数据库之前，被一层一层挡掉。**

```
10 万请求 → [CDN 挡 6 成] → [网关限流] → [缓存再挡 9 成] → [MQ 排队] → 数据库只剩 800 QPS
```

**这一层一层挡下去的过程，就是这节课的全部内容。**

> 📌 **补充**：这句话在中文技术圈常被表述为「架构的本质是分层」。视频给的漏斗是一个**具体的、可量化的**分层——每一层的输入输出都有数字，这也是它比「分层」这种抽象说法更好用的原因：你可以拿它去对账。

### 0.2 开场事故：1047 台手机

某电商做一场大促，**1000 台手机秒杀**。系统日常 **300 QPS**，从来没出过事，于是团队判断：「挂个横幅就行，不用改代码。」

| 时间 | 发生了什么 |
|---|---|
| 活动前 | 1000 台手机，日常 300 QPS，团队判断「挂个横幅就行」 |
| 00:00:00 | **10 万人**同时点抢，**8 万个请求在同一秒**涌向下单接口 |
| 00:00:01 | 系统还是单体，**数据库只有 50 个连接**，第 51 个请求开始排队 |
| 00:00:0x | 用户转圈 → 刷新 → 重试 → **重试又变成新请求** → 继续排队 |
| 00:01:00 | 连接全部占满，**一分钟内全站瘫痪** |
| 00:20~00:30 | **二三十分钟里，一单都没成交** |
| 事后盘点 | 卖了 **1047 台**，库存只有 **1000 台**，**超卖 47 台** |

雪球的机制是这样的，它是本课最该记住的一张图：

```
连接打满 → 用户等待超时 → 用户刷新/重试
     ▲                            │
     │                            ▼
   更堵  ◀──────  重试产生新请求（流量翻倍）
```

**用户的重试不是「再试一次」，是「再打你一拳」。** 系统越慢，重试越多；重试越多，系统越慢。

### 0.3 为什么会超卖 47 台

当时的库存逻辑是三行代码：

```java
int stock = stockMapper.selectStock(skuId);   // ① 查库存
if (stock > 0) {                              // ② 判断
    stockMapper.updateStock(skuId, stock - 1); // ③ 减库存
}
```

**单线程跑 1 万次都不会出错。** 问题出在零点那一秒：

```
库存只剩 1：线程 1..47 ──读(1)──→ 全都在 0.5 秒的缝隙里读到「还剩 1 件」
                                 → 各自判断通过 → 各自减一次 → 库存 -46
```

作者把这段缝隙量化了：**查库存 0.3 秒，扣库存 0.2 秒，中间 0.5 秒的缝隙里，大家谁都以为是有货的。**

这个 bug 有专业名字，叫 **check-then-act（先检查后执行）**。它不是代码写得丑，而是**检查和执行之间有时间缝隙，高并发能从这个缝隙里挤进来**。

> **不是设计这个系统的程序员不会写代码，而是他没有算过，同一秒会有这么多只手伸向同一行数据。**

而这道题**有标准答案**：

> **库存的判断和扣减，必须合并成一个原子动作。**

怎么合并？3.6 节给两种写法，第 4 章把它装进秒杀链路。

## 1. 第一章 重新认识高并发：先把「大」翻译成数字

### 1.1 为什么叫「重新认识」

「重新」两个字是有意的。很多人对高并发的理解是「流量大」——**这个理解没法指导任何工程实践**：流量大到什么程度？要几台机器？缓存多大？限流阈值定多少？「流量大」三个字一个都答不出来。

这一章回答四个问题，**全部用你已有的知识就能答**：① 高并发到底是多大的数（三个指标 + 一个公式）→ ② 一台服务器能扛多少（一道除法题）→ ③ 为什么崩的总是数据库（三个硬约束）→ ④ 架构师手里有哪几张牌（三板斧 + 五层漏斗）。

### 1.2 三个指标：并发数 / QPS / RT

作者用**快递驿站**做比方：

| 指标 | 驿站画面 | 准确含义 | 衡量的是 |
|---|---|---|---|
| **并发数** | 此刻**正在柜台前办事的人数** | 同一时刻正在处理中的请求数 | 系统的**瞬时压力** |
| **QPS** | 每秒**办完多少单** | 每秒处理的请求数 | 系统的**吞吐量** |
| **RT** | **办一单要多久** | 单个请求的响应时间 | 系统的**快慢** |

关键认知：**压垮系统的不是一天的总流量，而是某一瞬间挤进来的那一批。** 双 11 一天 10 亿 PV 并不可怕，可怕的是零点那一秒的 8 万——一天的流量可以摊平，一秒的流量摊不平。

### 1.3 全课最重要的一个公式

```
并发数 ≈ QPS × RT
```

物理意义：**每秒处理 QPS 个请求，每个请求要在系统里待 RT 秒，那么同一时刻系统里就一定有 QPS × RT 个请求正在被处理。**

```
正常：  QPS = 2000，RT = 50ms  = 0.05s  →  并发 = 2000 × 0.05 = 100  个连接
变慢：  QPS = 2000，RT = 500ms = 0.5s   →  并发 = 2000 × 0.5  = 1000 个连接
                                  ↑ 某条 SQL 索引没用对
```

**注意这里最反直觉的一点：QPS 一点没涨，只是变慢了，系统就挂了。** 资源占用直接翻 10 倍，线程池瞬间拉满。

所以：

> **你要把 RT 打下来，就能把整个并发压力打下来。**

这也解释了后面所有手段的共同本质——**它们都在动这条公式**：

| 手段 | 作用在公式的哪一项 |
|---|---|
| 缓存 | RT 从 100ms 降到 1ms |
| 索引 | RT 从 1800ms 降到 3ms |
| 异步 / 消息队列 | 用户感知的 RT 从 800ms 降到 50ms |
| 线程池调优 | 提高「可同时处理的并发数」这个上限 |

### 1.4 一台机器能扛多少：一道除法题

要看单机容量，先看**线程模型**：Spring Boot 内嵌 Tomcat，**默认 200 个工作线程**，每个请求占一个线程，处理完才还回去。

```
请求 1..200 ──→ [线程 1..200] ──→ 处理中 ──→ 返回，线程归还
请求 201    ──→ 没有线程了 → 在 accept 队列里排队 ⏳
```

于是：

```
单机 QPS ≈ 线程数 ÷ RT
```

| 场景 | RT | 计算 | 单机 QPS |
|---|---|---|---|
| 接口很快 | 50 ms | 200 ÷ 0.05 | **4000** |
| 接口里有条不走索引的 SQL | 500 ms | 200 ÷ 0.5 | **400** |

**同一台机器、同样的代码，只因为一条 SQL 没走索引，容量掉了 10 倍。**

为什么？作者点出了那个关键词：

> 线程在等数据库的那 500ms，**其实什么也没干**，但是**它的坑位是不让给别人的**。

这个现象叫 **「等待也占坑」**，它直接推出两个结论：

```
① 单机必有天花板 —— 这不是调优能突破的，只能加机器 / 加层
② 线程等待是纯浪费 —— 所以要管线程池，要把「等」变成「不用等」
```

### 1.5 为什么崩的总是数据库

单机有天花板，第一反应一定是「加机器」。但加机器解决不了应用层之外的那个东西——**数据库**。复盘任何一次大促故障，**最先报警的多半都是数据库**，因为它有三个硬约束，**三条全是物理/协议层面的，加机器完全绕不过去**：

| 硬约束 | 具体现象 | 为什么加应用机器没用 |
|---|---|---|
| **① 连接数有上限** | MySQL 默认 **151** 个连接，而应用有 200 个线程 | 平时流量小，排队没人注意；大促一冲，连接瞬间耗尽，然后就是重试雪球 |
| **② 热点行锁是独木桥** | 同一行库存的更新只能**一个一个排队** | 你有 100 个连接也没用，同一行数据在那一刻只有一条路 |
| **③ 查询可能碰到磁盘** | 内存是**纳秒级**，磁盘是**毫秒级**，差好几个数量级 | 缓存没命中 → 回表 → 落盘，RT 直接上一个量级 |

把三条放一块：

```
Java 应用：无状态 → 复制 100 份都毫无障碍
数据库  ：有状态 → 唯一副本，每条约束都是硬上限
```

> **这就是全课的总纲领：让请求最好别到数据库。后面所有的手段，都是从这句话推出来的。**

📌 **补充**：MySQL 的 `max_connections` 默认值在不同版本/发行版有差异（常见 151，部分云镜像会调到 500~1000）。但它**不是越大越好**——每个连接都占线程栈和内存，真正并发执行的还是那点 CPU 核数。把 151 调到 2000，通常只是把「在应用侧排队」变成「在数据库侧排队」，顺便把数据库内存吃光。方向是**减少到达数据库的请求**，不是**让更多请求同时挤进去**。

### 1.6 三板斧与五层漏斗

> **缓存挡读，异步挡写，水平扩展兜底。**

| 层 | 手段 | 挡掉多少 | 剩余 | 本质 |
|---|---|---|---|---|
| 0 | 客户端（用户手机） | — | 10 万 | 让请求别发出来（第 4 章） |
| 1 | **CDN** | 静态资源约 **6 成** | 4 万 | 静态的东西不该进机房 |
| 2 | **网关限流** | 超额部分痛快拒绝 | — | 舍卒保车 |
| 3 | **缓存** | 剩余流量再挡 **9 成** | — | 重复的提问在内存里回答 |
| 4 | **消息队列** | 洪峰摊成细水 | — | 必须落库的写请求先排队 |
| 5 | **数据库** | — | **800 QPS** | 终于吃得下 |

> **没有哪一个数据库天生就能扛住 10 万的 QPS，但是你可以让到达它的只有 800。**

这张图不只是讲原理，它是个**排查工具**：

> 以后遇到高并发问题，**先别急着搜方案**。先画这张漏斗，自己查一遍：到底是在哪一层出了问题？哪一层没有做好防备？**位置找准了，手段自然就出来了。**

📌 **补充**：这个思路在现场叫「按层下钻」，第 4.5 节压测给的是同一套方法论：**哪一层的队列在堆积，瓶颈就在哪一层**。它的价值是避免「凭感觉优化」——很多人一遇到慢就加缓存，结果瓶颈其实在行锁，白加。

### 1.7 算账：动手之前先知道要扛多少

> 你不知道要扛多少，就不知道**缓存该多大**、**限流阈值该多少**、**机器该买几台**。

比方是开火锅店：**先算周末晚高峰有多少桌，再决定摆几张桌子。** 四步：

| 步骤 | 公式 | 本例 | 说明 |
|---|---|---|---|
| ① 摸清日均总量 | 日活 × 人均次数 | 100 万 × 20 = **2000 万/天** | 核心接口要**单独拎出来算** |
| ② 二八法则 | 总量 × 0.8 ÷ (86400 × 20%) | 2000 万 × 0.8 ÷ **17280** ≈ **926 QPS** | 80% 流量挤在 20% 时间里 |
| ③ 乘峰值系数 | 日常 × 3 | 926 × 3 ≈ **2800 QPS** | 这就是**设计目标** |
| ④ 按层拆解 | 应用按 **70% 水位**，数据库只接缓存没挡住的部分 | — | 留 30% 余量 |

> 秒杀这种脉冲场景是**更尖的尖峰**，系数要另算（第 4 章的秒杀是 10 万 QPS 级别，完全不是一个量级）。

作者对这套算法很清醒：

> **算出来的数大概率是不准的，但是没有关系。它的价值，是把「这个系统究竟要有多强」变成一个团队都认的数字。**

然后靠压测对账：`估算 → 设计目标`，`压测 → 实测容量`，**两个数对上了，系统才算设计完成**（最后总结第二句）。

## 2. 第二章 缓存：投入产出比最高的一斧

### 2.1 先泼一盆冷水

缓存性价比高到离谱：**500 QPS 的接口，加一层缓存就能扛到 5000。** 但紧接着就是那盆冷水：

> **缓存意味着一份数据存两处。**

于是就有了那些「灵异事件」：后台改了价格，**页面刷新还是旧价**；运营下架了商品，**用户还能下单**；库存明明清零了，**还有人抢到**。

> 「为什么改了价格页面没有变？」这种事，到最后可能发现**都是缓存造成的**。

所以这一章先学**规矩**：`① 能放哪几层 → ② 标准读写姿势 → ③ 三大经典故障 → ④ 一致性`。学完才能安全地加缓存。

### 2.2 缓存能放哪几层

一提到缓存大家先想到 Redis，但作者说了一句会让人愣一下的话：

> **Redis 只是第五层。**

| 层 | 位置 | 延迟 | 挡什么 | 谁维护 |
|---|---|---|---|---|
| **① 浏览器 + CDN** | 用户侧 / 边缘节点 | 10~50 ms（**连机房都不用进**） | 图片、JS、CSS、静态 HTML | 前端 + 运维 |
| **② 网关缓存** | Nginx / API 网关 | 亚毫秒~毫秒 | 合并热点请求 | 运维 |
| **③ 本地缓存** | JVM 堆内（Caffeine） | **纳秒级**（比 Redis 快几百倍） | 超热数据 | 后端 |
| **④ Redis** | 独立服务 | 亚毫秒~毫秒 | **跨实例共享**（主力） | 后端 |
| **⑤ 数据库** | MySQL | 毫秒~秒 | —— **它不是缓存，它是最终数据源** | DBA |

**每一层的意义，都是让下一层看到的流量少一个数量级。** 注意 ⑤ 那条线不能模糊：前四层全丢了，数据还得从它这里重建。

### 2.3 选型口诀：先问「允许多旧」，再问「放哪层」

| 数据特征 | 放哪 | 例子 | 为什么 |
|---|---|---|---|
| 跨实例共享、变更不频繁 | **Redis** | 用户信息、商品详情、配置 | 多台机器看到的必须是同一份 |
| 极热、允许秒级延迟 | **本地缓存** | 首页类目、热门榜单 | 省掉网络往返，纳秒级 |
| 基本不变的页面 | **CDN** | 详情页静态部分、活动页 | 请求连机房都不用进 |
| **一秒变好几次** | **哪层都别放**（或极短 TTL） | **库存、余额** | 不一致窗口 = **超卖** |

> 库存一秒变好几次，**这种情况你就不能放本地缓存**，因为不一致的窗口会导致超卖。

KPI 只有一个：**命中率。90% 的命中率，数据库就只能看到 1/10 的流量。**

📌 **补充**：命中率要按**请求数**算，不能按 key 数算。100 万个 key 里 99 万个能命中，但剩下 1 万个是每秒被查 100 次的热 key，实际命中率可能只有 1%。所以命中率要配合**热 key 排行**一起看。

### 2.4 标准姿势：Cache Aside

> **九成的缓存问题，都是因为你没有按照标准姿势来做。**

核心是**缓存和数据库都由业务代码维护，缓存不主动加载数据**。

```
读路径：① 查缓存 ─ 命中 → 返回（9 成请求到这就结束）
                 └ 未命中 → ② 查库 → ③ 回填缓存（必须设 TTL）

写路径：① 更新数据库 → ② 删除缓存     ← 是删除，不是修改
```

```java
public Product getProduct(Long id) {
    String key = "product:" + id;
    String cached = redis.get(key);
    if (cached != null) return JSON.parseObject(cached, Product.class);   // ① 命中

    Product p = productMapper.selectById(id);                             // ② 回源
    int ttl = 1800 + ThreadLocalRandom.current().nextInt(600);            // ③ 回填
    redis.setex(key, ttl, JSON.toJSONString(p));
    return p;
}

@Transactional
public void updatePrice(Long id, BigDecimal price) {
    productMapper.updatePrice(id, price);   // ① 先更新库
    redis.del("product:" + id);             // ② 再删缓存（失败要进 MQ 重试）
}
```

### 2.5 两个「为什么」

**为什么是「删除」而不是「修改缓存」？**

并发写的时候，两次回写缓存**可能乱序到达**：

```
数据库侧（顺序正确）：t1 改成 A；t2 改成 B      → 最终值应是 B
缓存侧（网络乱序）：  B 的回写先到 → 缓存 = B
                      A 的回写后到 → 缓存 = A   ❌ 留下旧值，要等到过期
```

而且这个错误**很难发现**——数据库是对的，只有缓存是错的。第二个理由更工程化：

> **很多缓存是「聚合算出来的」**。一个商品详情页可能联了好几张表，你根本没法「改缓存」，只能整体重算。**所以删除最安全，下次读自然就回填了。**

**为什么是「先更新数据库，再删缓存」，不能反过来？**

```
【错误：先删缓存，再更库】
删缓存 → ← 插进来一个读请求 → 读到【旧值】→ 回填旧值 → 更库完成
        结果：缓存躺旧值，要等过期        不一致窗口：分钟级 ❌

【正确：先更库，再删缓存】
更库（新值）→ 删缓存 → 即使中间有读请求，读到的也是新值，回填也是新值
                                     不一致窗口：几毫秒 ✅
```

两个必须养成的**习惯**：**所有 key 都要设 TTL**（TTL 是最后兜底，脏也只会脏一会儿）；**空结果也要缓存一个短 TTL**（否则就是下一节的穿透）。

### 2.6 三大经典故障

> 三个问题的共同点，**都是请求越过了缓存砸向数据库**。**但是成因完全不同**，所以解法也完全不同。

| | 触发条件 | 缓存里有数据吗 | 流量特征 |
|---|---|---|---|
| **穿透** | 查的数据**根本不存在** | 永远不会有 | 分散、量大、ID 随机 |
| **击穿** | **单个热点 key 过期** | 有过，刚过期 | 集中在一个 key |
| **雪崩** | **一大批 key 同时过期** / **Redis 宕机** | 大面积没有 | 全局性 |

**① 穿透：查无此人**

攻击者拿乱造的 ID 疯狂请求，每一个都「缓存没有 → 查库 → 库里也没有 → 不回填」，**缓存永远建不起来，每次都打到数据库**。解法：**空结果也缓存一个短 TTL**（当「空标记」），或**前面加布隆过滤器**（不存在的 ID 直接被拒）。

| 方案 | 优点 | 缺点 |
|---|---|---|
| 缓存空值 | 3 行代码，够用 | 被随机 ID 攻击时会塞满空 key（要配短 TTL + 内存上限） |
| 布隆过滤器 | 内存极省，能挡海量随机 ID | **有误判率**，**标准版不支持删除** |

📌 **补充**：实战通常是**两个一起上**——布隆挡第一道（拦住 99% 的随机 ID），空值缓存挡漏网的（拦住误判那部分）。单用任何一个都有短板。

**② 击穿：热点过世**

一个热点 key 过期的**那一瞬间**，几毫秒内成千上万个并发同时发现「缓存没了」，**一起去查数据库**，数据库被打穿。

```java
// 解法 A：互斥锁（只放一个请求回源）
String cached = redis.get(key);
if (cached != null) return cached;

if (redis.set("lock:" + key, "1", "NX", "EX", 3)) {
    try {
        Product p = productMapper.selectById(id);
        redis.setex(key, 1800, JSON.toJSONString(p));
        return p;
    } finally { redis.del("lock:" + key); }
} else {
    Thread.sleep(50);           // 短暂等待
    return getProduct(id);      // 重试读缓存
}
```

```
解法 B：逻辑过期 —— key 物理上永不过期，value 里自带 expireAt
        ├─ 未逻辑过期 → 直接返回
        └─ 已逻辑过期 → 返回【旧值】+ 异步起线程刷新
        好处：读请求永远有值可拿，一次都不会被打穿
        代价：会有一段时间的脏数据
```

| | 互斥锁 | 逻辑过期 |
|---|---|---|
| 用户等待 | 会等几十毫秒 | 不等，立刻返回 |
| 数据新鲜度 | 强 | 弱（可能拿到旧的） |
| 适合 | 对数据敏感、能接受短暂等待 | 极热 key、绝对不能等 |

**③ 雪崩：集体殉职**

**一大批 key 在同一时刻过期**，或**整个 Redis 宕机**，所有流量一起涌向数据库。

```java
// ❌ 全都设 30 分钟 → 30 分钟后集体失效
redis.setex(key, 1800, value);

// ✅ 25 ~ 35 分钟之间随机分布
redis.setex(key, 1800 + ThreadLocalRandom.current().nextInt(600), value);
```

作者的原话：**「TTL 设 30 分钟，但别把这一批都设成 30 分钟，要让它在 25~35 分钟之间分布，别让它们集中在同一时刻过期。」**

第二道是 **Redis 高可用（哨兵集群）**：单机挂了所有流量直接砸库；有哨兵就能自动主从切换。但作者紧跟着补了第三道，最容易被忘：

> **缓存层挂了，至少别让数据库也跟着走。** 所以要加上**熔断限流**兜底。

所以雪崩是**三级防线**：摊开 TTL（预防）→ 高可用（减少概率）→ 熔断限流（最后兜底）。

**三句口诀（作者要求背下来）：**

| 故障 | 口诀 | 解法 |
|---|---|---|
| 穿透 | **查无此人** | **堵入口**（布隆 / 空值缓存） |
| 击穿 | **热点过世** | **锁住回填**（互斥锁 / 逻辑过期） |
| 雪崩 | **集体殉职** | **摊开 TTL + 备份高可用** |

### 2.7 一致性：先接受一个残酷结论

> **只要你用了缓存，就没有绝对的一致。**

因为「更新数据库」和「改缓存」是**两个系统里的两个步骤**，中间随时可能被并发插一脚。我们能做的只是**把不一致窗口压到业务无感**。

| 方案 | 做法 | 不一致窗口 | 结论 |
|---|---|---|---|
| ① 先删缓存，再更库 | del → update | **分钟级**（中间被读请求回填旧值） | ❌ **弃用** |
| ② 先更库，再删缓存 | update → del | **几毫秒** | ✅ **主流** |
| ③ 延迟双删 | update → del → **sleep 500ms** → del | 毫秒级 | ✅ 要求更高的场景 |

方案 ② 还有个真实的坑：**删缓存本身也可能失败**（网络原因，删除命令没到 Redis）。两种补救：**丢 MQ 重试**，或**订阅 binlog 自动删**（Canal）。

延迟双删的第二次删到底在清什么？作者说得很明确：**清掉「空档期被回填的旧值」。**

最后是判断标准，作者在这里「划重点」了：

| 数据类型 | 走缓存吗 | 理由 |
|---|---|---|
| **余额、库存** | ❌ **根本不要走缓存读路径** | 强一致，宁可慢也不能错 |
| 商品详情、排行榜 | ✅ 可以 | 能接受毫秒级窗口 |

📌 **补充**：库存其实有个中间态——**Redis 里存库存不是当「缓存」用，而是当「计数器」用**（3.6 节的预扣就是这个思路）。区别在于：缓存是「数据库的副本，可以丢」，计数器是「扣减的权威凭证，不能丢」。这两个角色长得像，但持久化策略、淘汰策略、故障处理完全不一样，别混为一谈。

## 3. 第三章 剩下的手段：一页一个标准动作

缓存挡住了读的大头，剩下的流量分四块解决。作者说这一段是**全课最重要的**，每个手段都是「一页一个标准动作」：解决什么麻烦、坑在哪儿。

```
① 线程池      → 「等待也占坑」怎么破
② 限流 / 熔断 → 系统的保命机制（也是事故率最高的地方）
③ 消息队列    → 把洪峰变成细水（削峰填谷）
④ 数据库四张牌 → 防超卖 / 分布式锁 / 分库分表 / 无状态扩容
```

### 3.1 线程池：最容易被忽视的一环

很多人用过 `ThreadPoolExecutor`，但**只知道它方便，对它具体的运行机制一无所知**：核心线程数给多少？队列多长？满了怎么办？

> **如果你不了解它们，那线程池对你来说究竟是来服务你的，还是给你系统埋了一颗定时炸弹，都是说不好的。**

**参数 ①：核心线程数——不要拍脑袋，按「在等还是在算」决定**

| 任务类型 | 公式 | 理由 |
|---|---|---|
| **CPU 密集** | `核数 + 1` | 线程基本不阻塞，多了只是抢 CPU；+1 顶偶发缺页 |
| **IO 密集** | `核数 × (1 + 等待时间 / 计算时间)` | 线程大部分时间在等，多开几个把坑位占住 |

作者的实例：接口 80% 时间在等数据库，**等 400ms、算 100ms**，8 核机器 → `8 × (1 + 400/100) = 8 × 5 = 40` 个线程。

> **这比你拍脑袋直接给 200 个要科学得多。**

📌 **补充**：这个公式（Brian Goetz 在《Java 并发编程实践》里给的）算的是**理论上限**，实际取值还要看下游能接多少。40 个线程同时打库 = 40 个连接，如果连接池只给了 20，那另外 20 个还在等连接池——**瓶颈只是换了个地方排队**。线程池大小必须和连接池大小一起定，这就是「按层下钻」要查的第二层。

**参数 ②：队列——必须有界**

```
无界队列 = 永远不拒绝 = 请求越堆越多 = 最后 OOM
```

> `Executors.newFixedThreadPool()` 的队列**就是无界的**（`LinkedBlockingQueue` 默认容量 `Integer.MAX_VALUE`）。**这也是很多公司禁止在生产上使用它的原因。**

📌 **补充**：阿里《Java 开发手册》原文是「**【强制】线程池不允许使用 Executors 去创建**」。四个工厂方法全中招：`newFixedThreadPool` / `newSingleThreadExecutor` 队列无界（OOM），`newCachedThreadPool` / `newScheduledThreadPool` 最大线程数是 `Integer.MAX_VALUE`（海量线程）。所以要手写 `ThreadPoolExecutor`。

**参数 ③：满了怎么办——拒绝策略**

| 策略 | 行为 | 评价 |
|---|---|---|
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException` | 调用方要自己 catch，容易漏 |
| `DiscardPolicy` | **静默丢弃** | 最危险，请求凭空消失，查都查不到 |
| `DiscardOldestPolicy` | 丢掉队列里最老的 | 老请求被无声牺牲 |
| **`CallerRunsPolicy`** | **谁提交谁执行** | ✅ **生产常用**，天然降速 |

> **谁提交谁干，它天然降速。** Tomcat 的工作线程自己跑去执行任务，就没法再接新请求 → **上游自然被拖慢** → 压力反向往回传，这是**自带反馈的背压**。

核心思想只有一句：**要让被拒绝的请求体面地走**——宁可给用户一个明确的「系统繁忙」，也不要让他挂在那儿转圈，更不要静默吞掉。

**上线后盯三个指标**：`活跃线程数`、`队列堆积数`、`拒绝次数`。**后两个只要不为 0，就证明容量已经到顶了。**

### 3.2 限流：舍卒保车

> **容量有上限，流量没上限。** 与其让超额流量进来把所有人都拖垮，不如**主动拒绝一部分**——舍卒保车。

**四种算法**

```
固定窗口  每分钟数人头 → 59s 和 61s 各放 100 个，2 秒挤进 200 个（临界突刺）
滑动窗口  1 分钟切 6 个 10 秒小格，看最近 6 格 → 消除突刺（Redis+Lua 常用）
漏桶      进桶排队、恒速流出、桶满拒绝 → 出口永远匀速，适合怕猛的下游（支付）
令牌桶    恒速发令牌，拿牌才放行，攒下的令牌允许突发 → 主流选择
```

| 算法 | 限平均速率 | 容忍突发 | 复杂度 | 典型用途 |
|---|---|---|---|---|
| 固定窗口 | ✅ | ❌ 边界会翻倍 | 最低 | 粗粒度兜底 |
| 滑动窗口 | ✅ | 部分 | 中 | **通用业务限流** |
| 漏桶 | ✅ | ❌ 强制匀速 | 中 | 保护脆弱下游 |
| **令牌桶** | ✅ | ✅ **可配突发** | 中 | **通用业务限流（首选）** |

> **一般业务，选令牌桶或者滑动窗口就可以了。** 令牌桶的价值就在于：**既能控制平均速率，又不是一刀切地拒绝突发。**

**三个维度——别只算「接口级」**

| 维度 | 含义 | 防什么 |
|---|---|---|
| **全局** | 整个接口一共多少 QPS | 总量过载 |
| **单机** | 每台实例限多少 | 负载不均 |
| **用户级** | 每个用户每秒几次 | **防刷、防爬** |

最后一行作者说「非常容易被忽略，但也很重要」：**假如一个用户自己弄了 10 万个请求，是不是也会把系统搞崩溃？** 用户级限流跟容量无关，跟「有人故意搞你」有关。

**挡在哪一层**

| 层 | 做什么 | 好处 |
|---|---|---|
| **网关** | 粗略挡全站，按 IP / 用户配额 | **被挡的请求连业务资源都没消耗** |
| **服务层** | 细控接口，用 Sentinel | 业务语义清楚，能按接口配 |

**Sentinel 的三种流控形态**

| 形态 | 行为 | 场景 |
|---|---|---|
| **快速失败**（默认） | 超了直接拒 | 绝大多数场景 |
| **Warm Up 预热** | 阈值从低慢慢爬升 | **冷启动** |
| **排队等待** | 匀速放行 | 类似漏桶 |

关于预热，作者打了个很生动的比方：

> 刚启动的时候缓存全是空的，你直接放开全量流量，**等于让没热身的人跑几百米**。所以冷启动时，**阈值要从低慢慢爬升**。

**阈值定多少：压测极限的 80%**，留两成余量。（第 4.5 节的压测里还会再出现一次：设在**拐点的八成**。）

**额外一件武器：Redis + Lua 做集群级限流**

Sentinel 有个天然局限：**它是单机口径，每台各管各的**。但有些预算是**全局**的，比如「**全站每秒最多调第三方支付接口 1000 次**」——这种计数器必须放 Redis 全站共享。

```lua
-- KEYS[1]=限流 key   ARGV[1]=阈值   ARGV[2]=窗口秒数
local current = redis.call('INCR', KEYS[1])
if current == 1 then redis.call('EXPIRE', KEYS[1], ARGV[2]) end
if tonumber(current) > tonumber(ARGV[1]) then return 0 end   -- 拒绝
return 1                                                     -- 放行
```

> **为什么用 Lua？因为它能保证「读、判断、写」这三步是原子执行的。** 不然多台机器并发，就会搞成一团糟。

结论只有两个字，但要求一定要记住：**「原子」。**

### 3.3 熔断与降级：保命的另一半

限流管的是**流量太多**，熔断降级管的是**下游挂了**。作者的比喻是家里的保险丝：**电流异常就立刻断开，牺牲局部，但是能保整栋楼。**

**事故现场**：电商的**推荐服务**挂了，但**商品页不能跟着挂**。

```
❌ 没有熔断：
商品页请求 → 调推荐服务（已挂）→ 傻等 30 秒超时
                             ↑ 这 30 秒里 Tomcat 线程被活活占住
                             ↓ 200 个线程 30 秒全被拖死 → 商品页也挂了 → 全站雪崩
```

> **一个下游故障，如果处理不好，就可能滚成全站的雪崩。**

**熔断器的三个状态**

```
  CLOSED（闭合，正常放行 + 统计失败率）
      │ 失败率 > 阈值
      ▼
  OPEN（断开，请求不再发出、直接降级）
      │ 静默期结束
      ▼
  HALF_OPEN（半开，放几个试探请求）── 成功 → 恢复 CLOSED
                                  └─ 失败 → 继续 OPEN
```

| 状态 | 行为 |
|---|---|
| **CLOSED（闭合）** | 正常放行，同时**统计失败率** |
| **OPEN（断开）** | 失败率超阈值 → 请求**不再发出**，直接走降级 |
| **HALF_OPEN（半开）** | 静默期后**放开几个试探请求**：成功 → 恢复；失败 → 继续断开 |

> **整个过程是自动完成的，不需要人为地半夜去切换。**

**跳闸之后，用户看什么——三种降级**

| 降级方式 | 做法 | 例子 |
|---|---|---|
| **① 返回兜底数据** | 给个默认值 | 推荐挂了 → 给**默认精选**；评价服务挂了 → **隐藏评价区块** |
| **② 简化流程** | 短路非核心链路 | 大促把**积分计算、优惠券计算**短路，页面显示「大促期间积分暂停发放」 |
| **③ 写请求排队** | 进 MQ 慢慢处理 | 「抢购人数过多」→ 进排队队列 |

第 ② 种的关键在**用户观感**：页面显示「大促期间积分暂停发放」，**用户其实观感还是好的，最起码没有给他转圈**。

**两条铁律：**

> **熔断是保护自己，降级是保住用户体验，所以必须成对出现。**
> **跨服务的调用必须设超时，不能让它无限等待。**

📌 **补充**：超时值不是拍脑袋。它应该由下游的 **P99 RT** 决定，一般取 P99 的 1.5~2 倍。太短 → 正常请求被误判失败，熔断器乱跳；太长 → 就是上面那个「线程被拖死」的场景。另外**重试次数也要算进总预算**：超时 1 秒 + 重试 2 次 = 最坏 3 秒，这个 3 秒才是线程被占用的真实时长。

### 3.4 消息队列：把洪峰变成细水

> **消息队列，就是把「现在必须做完的事」变成「晚点做完也行的事」，把洪峰变成细水。**

```
【同步】[下单] → [扣库存] → [减优惠] → [发短信] → 返回
        8000 QPS 的写流量直接灌进数据库 → 扛不住

【异步】[下单] → [预扣库存] → 扔消息到 MQ → 立刻返回「排队中」
        ↓
   消息队列（蓄水池）→ 消费者按 2000 QPS 平稳消费 → [减优惠][发短信][生成订单]
```

| | 峰值 | 落库 |
|---|---|---|
| 同步 | **8000 QPS** | **8000 QPS**（数据库直接被砸） |
| 异步 | **8000 QPS** | **2000 QPS**（队列削平） |

> **洪峰是 8000 QPS，但是落库只是 2000 QPS，中间这个峰值就被队列这个蓄水池给消化掉了。** 用户看到「排队中」、几秒出订单，**这种情况其实也是可以接受的**。

**第二重收益：解耦**

```
下单服务 → 只认 MQ（它不知道后面有谁在消费）
要加「下单后发优惠券」→ 只加一个消费者 → 下单服务一行代码都不用改
```

**但异步不是免费的：三个代价**

| 代价 | 表现 | 应对 |
|---|---|---|
| **① 延迟** | 数据要几秒才落库 | 明确告知「排队中」，别假装实时 |
| **② 复杂度** | **MQ 本身成了新的依赖**（它挂了怎么办？消息丢了怎么办？） | 高可用部署、消息持久化、死信队列 |
| **③ 幂等** | 消息会重复投递，消费者必须保证**同一条消息只干一次活** | 用**订单号做唯一键**（唯一索引 / 去重表） |

> **幂等，就是保证同一张小票只干一次活。** 如果一个用户点了好几次，你总不能让他多抢几次吧？

注意作者的言外之意：**你省下的峰值，会以「重复订单」的形式还回来。异步不是把问题消灭了，是把「并发问题」换成了「重复问题」。**

📌 **补充**：MQ 选型视频没展开，给个坐标：**Kafka** 追吞吐（日志、埋点、大数据管道，百万级 QPS）；**RocketMQ** 追业务可靠性（事务消息、顺序消息、延迟消息，电商订单的默认答案）；**RabbitMQ** 追路由灵活（复杂 exchange）。秒杀这种「削峰 + 可靠投递」的场景，RocketMQ 是最常见的落点。

### 3.5 数据库第一课：别让 SQL 全表扫描

> **一句话：B+ 树把「200 万行逐行对比」，变成了 3~4 次的页访问。**

量级差距：`毫秒级 → 微秒级`，`500 QPS → 5 万 QPS`。

```sql
-- ❌ 索引失效：在时间列上套了 DATE() 函数
SELECT * FROM orders WHERE DATE(create_time) = '2026-11-11';    -- 全表扫描 1.8 秒

-- ✅ 改写成范围条件，索引可用
SELECT * FROM orders
WHERE create_time >= '2026-11-11 00:00:00'
  AND create_time <  '2026-11-12 00:00:00';                     -- 走索引 3ms
```

> **同一条查询，写法差一行，性能差 600 倍。**

**慢 SQL 自查清单（7 条）**

| # | 检查项 | 说明 |
|---|---|---|
| 1 | **WHERE 列有没有索引** | 最基本的 |
| 2 | **满不满足最左前缀原则** | 联合索引 `(a,b,c)`，`WHERE b=1` 用不上 |
| 3 | **索引列上有没有函数** | `DATE(col)`、`SUBSTRING(col)` 都会失效 |
| 4 | **有没有隐式类型转换** | `varchar` 列传数字、`int` 列传字符串，都会失效 |
| 5 | **是不是 `SELECT *`** | 多读无用列，可能触发回表、无法覆盖索引 |
| 6 | **有没有深度分页** | `LIMIT 100000, 20` 要扫 10 万行 |
| 7 | **有没有大事务** | 长事务持锁、拖慢主从同步 |

**两条纪律**：① **开慢查询日志**，每周清理 Top 10 慢查询；② **上线卡点**——**扫描超 10 万行必须走索引，不过就不发版**。

**一个顺序，别搞反：**

> **先索引，再缓存，数据量真的很大了才分库分表。不要一上来就去拆库。**

📌 **补充**：深度分页的常见解法是「游标分页」（`WHERE id > last_id ORDER BY id LIMIT 20`）或「延迟关联」（先用覆盖索引查出主键，再回表）。前者要求有序且不跳页，后者兼容跳页但要写两条 SQL，两种都比 `LIMIT 100000, 20` 好一个数量级。

### 3.6 防超卖：把「查 + 判 + 减」压成一个原子动作

回到开场那个 47 台的事故。根因是 **check-then-act**：

```java
int stock = selectStock(skuId);      // 读：还剩 1
if (stock > 0) {                     // 判：通过
    updateStock(skuId, stock - 1);   // 减：写回 0
}
```

```
线程 1  读(1) → 判(通过) → 减(0)
线程 2  读(1) → 判(通过) → 减(-1)
  ...
线程47  读(1) → 判(通过) → 减(-46)
本质：查和减之间有时间缝隙，高并发从这个缝隙里插进来了
```

**解法一：数据库行内自减（1 行 SQL 解决）**

```sql
UPDATE stock
SET stock = stock - 1
WHERE sku_id = #{skuId}
  AND stock > 0;          -- ← 判断条件写进 WHERE，和减法在同一条语句里
```

```java
int affected = stockMapper.deduct(skuId);
if (affected == 0) return Result.fail("已售完");
// affected == 1 → 扣减成功
```

为什么就不可能超卖？

```
行锁保证同一行同一时刻只有一条 UPDATE 在执行：
  第 1 条：stock=1 → 0，affected=1  ✅
  第 2 条：WHERE stock>0 不成立，affected=0  ❌
```

> **这样一行 SQL，超卖在数学上就已经不可能实现了。**

**解法二：Redis + Lua 预扣（挡掉 99% 的流量）**

```lua
-- KEYS[1] = stock:sku:1001    ARGV[1] = 购买数量
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock < tonumber(ARGV[1]) then return 0 end   -- 库存不足
redis.call('DECRBY', KEYS[1], ARGV[1])
return 1                                                          -- 预扣成功
```

> **Redis 单线程执行，天然是原子的。**

**实战上分层：两层原子，层层兜底**

```
10 万请求
   ▼
① Redis + Lua 原子预扣   ← 挡掉 99%（10 万 → 1000）
   ▼ 预扣成功的少数请求
② 消息队列               ← 只承接「库存数量级」的流量
   ▼
③ 数据库行内自减          ← 第二层原子兜底（WHERE stock > 0）
```

> **两层原子，层层兜底，就杜绝了超卖的问题。**

回到开场事故：**它既没有做 Redis 预扣，数据库那行也没有写成原子写法**，所以才会超卖。

📌 **补充**：Redis 预扣有个必须补的环节——**失败补偿**。预扣成功后如果落库失败（MQ 丢消息、订单服务崩了），Redis 的库存少了一份但数据库没少，这叫「**少卖**」。标准做法是预扣时写「预扣流水」（`orderNo + skuId + qty + 时间`），由定时任务对账，把超过 N 分钟仍未落库成功的预扣回滚掉。只做「防超卖」不做「防少卖」，线上会变成「库存明明有，就是抢不到」。

### 3.7 分布式锁：本地锁为什么拦不住

```java
synchronized (this) { ... }   // 锁住的是「这个 JVM 里的这把对象锁」
```

```
单机 1 台：所有线程在同一个 JVM → 抢同一把锁 → 互斥成立 ✅
部署 5 台：A 机的锁锁住 A 的 100 个线程，B 机的锁锁住 B 的 100 个线程
          两把锁互相完全不认识 → 5 个独立的内存世界 → 等于没锁 ❌
```

> **你要把这个锁，放到一个大家都看得见的地方。** 那就是分布式锁。工具二选一：**Redis（Redisson）** 或 **ZooKeeper**。

**什么时候真的需要它**（都是「全集群只能有一个人干」）

| 场景 | 为什么本地锁不行 |
|---|---|
| 防重复提交 | 用户两次请求可能落到不同机器 |
| 定时任务只跑一份 | 5 台机器都会触发定时器 |
| **没法合并成原子操作**的兜底 | 业务太复杂，一行 SQL 搞不定 |

**Redisson 的三个要点**

```java
RLock lock = redissonClient.getLock("lock:order:" + orderNo);
try {
    boolean ok = lock.tryLock(3, TimeUnit.SECONDS);   // ① 带超时，抢不到快速失败
    if (!ok) return Result.fail("系统繁忙，请稍后重试");
    doBusiness();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();   // ③ unlock 必须在 finally
}
```

| 要点 | 说明 |
|---|---|
| ① `tryLock` 带超时 | **抢不到就快速失败，绝不能无限等待** |
| ② key 带业务语义，**粒度越小越好** | `lock:order:12345`，不是 `lock:order` |
| ③ `unlock` 放 `finally` | **抛异常也要解锁** |

**看门狗：锁 30 秒过期，业务跑 40 秒怎么办**

```
第 30 秒锁自动释放 → 别人拿到锁进来 → 第 40 秒你还在改数据 → 互斥彻底失效

Redisson 的答案：
后台线程每 10 秒检查一次「任务还活着吗」
  ├─ 活着 → 自动续期，把过期时间拉回 30 秒
  └─ 进程崩了 → 续期自然停止 → 30 秒后锁自动释放
```

> **既防止了「没干完锁就没了」，又防止了「崩了但锁没释放」的死锁。**

为什么别自己手搓？**Redis 的 `SETNX` 手搓锁会有很多坑**（超时、误删、续期、可重入、主从切换丢锁），**而 Redisson 全帮你填满了**。

**但最重要的一条原则：**

> **能用原子操作，就别用锁。** 上一页的行内自减就是无锁方案，**锁是兜底，不是默认选项。**

📌 **补充**：看门狗只在「不指定 `leaseTime`」时生效（`tryLock(3, TimeUnit.SECONDS)`）。写成 `tryLock(3, 10, TimeUnit.SECONDS)` 时锁固定 10 秒过期，**看门狗不会启动**——这是最常见的误用。两者语义不同：前者是「我活着就一直续」，后者是「我保证 10 秒内跑完，跑不完是我的 bug」。

### 3.8 数据库扩容：先摊读，再摊写

> 索引和缓存都做完了，数据库还扛不住，最后一张牌才是分库分表。**顺序是：先摊读，再摊写。**

**第一张：读写分离（摊读）**

```
        ┌──────────┐
  写 ──→ │   主库   │ ──主从同步──→ 从库 1 / 从库 2 / ... / 从库 N
        └──────────┘                └── 读流量（一般占 9 成）──┘
```

读流量一般占 9 成，摊到 N 台从库上，主库瞬间就轻松了。**代价是主从延迟**：写完立刻读，可能路由到从库读到旧数据。

> **解法：改完之后如果需要立刻读，强制走主库。**

**第二张：分库分表（摊写）**

**什么时候用**：**单表超过千万行**。按分片键（如 `userId`）哈希到 N 个库、N 张表。三个代价：

| 代价 | 说明 |
|---|---|
| **① 跨库查询要聚合** | 原来一条 SQL，现在查 N 个库再内存 merge |
| **② 需要分布式 ID** | 每张表都自增 → **ID 会重复** |
| **③ 分片键选错就白做** | 见下 |

分布式 ID 的两条路：**雪花算法**（趋势递增、无中心化，但依赖机器时钟）或 **Redis INCR**（简单，但多一次网络往返、Redis 成强依赖）。

**第三张：分片键——决定成败的一次选择**

| 分片键 | 效果 |
|---|---|
| **订单按 `user_id` 分** | ✅ 同一用户的订单永远在同一张表 → **「查我的订单」只碰一个分片** |
| 订单按 `create_time` 分 | ❌ 大多数查询**打到所有分片** → 分库分表白做 |

> **规则：让最高频的查询只命中一个分片。**

**第四张：归档（最容易忘的一条）**

> 让订单表**只留近一年的热数据**，历史数据搬走。
>
> **很多以为自己要分库分表的情况，其实用归档就可以完全解决。尽量不用分库分表，因为它很贵。**

完整的性价比排序：

```
索引 → 缓存 → 归档 → 读写分离 → 分库分表
（最便宜）                     （最贵）
```

📌 **补充**：分库分表的主流中间件是 **ShardingSphere**（Sharding-JDBC 客户端模式 / Sharding-Proxy 代理模式）。客户端模式把分片逻辑放在应用里，**要管好版本一致性**；代理模式多一跳网络但应用无感。另外拆库后**分布式事务**会成为新问题（Seata 或业务最终一致），这一点在动手前必须想清楚。

### 3.9 无状态与水平扩展

> **很多人加了机器，但容量没加多少——因为服务是有状态的。**

| 东西 | 存在哪 | 出什么事 |
|---|---|---|
| **Session** | Tomcat 内存 | A 机登录，下一个请求轮到 B 机 → **B 没有 session → 未登录** |
| **本地缓存** | JVM 堆 | 当成唯一数据源 → 换机器数据就没了 |
| **文件 / 图片** | 本地磁盘 | 换机器图片 404 |
| **定时任务** | 本机进程 | 5 台机器跑 5 遍 → 重复执行 |

作者对「会话粘滞」的评价很狠：

> 本能的解法是让**会话粘滞**（同一用户永远路由到同一台）。但**那基本上是饮鸩止渴**：**负载不均匀**，而且**机器一挂，登录状态就全没了**。

本质只有一句话：

> **把「只此一份」的东西，放进「随时可以替换」的机器之外。**

| 有状态的东西 | 外置到 |
|---|---|
| Session | **Redis**（Spring Session） |
| 文件 | **OSS / 对象存储** |
| 定时任务 | **分布式调度**（XXL-JOB / ElasticJob） |
| 本地缓存 | 只做**可重建的加速层**（丢了能重建，不能当数据源） |

做到之后，每台实例都可以随时替换，**扩容从 10 台到 50 台，容量线性增长**。

**三问自检**：① 重启任何一台机器，用户会不会掉线？② 删掉本地文件，业务会不会坏？③ 流量全切走，功能会不会缺失？**三问全「不会」，才算无状态。**

## 4. 第四章 秒杀实战：把所有零件装进一个场景

### 4.1 为什么是秒杀

> **秒杀是高并发的极限考试。** 因为它让**三个最难的条件同时出现**。

| 条件 | 具体 |
|---|---|
| **① 流量极尖峰** | 一秒内涌入 **10 万个请求** |
| **② 热点行** | 所有人都在抢**同一件商品**（同一行数据） |
| **③ 绝对不能超卖** | 少卖可以忍，超卖是资损 + 舆情 |

> 这三个都解决了，这场考试就算通过。**对其他场景，就都是降维打击。**

本章回答四个问题：`① 架构长什么样 → ② 一次请求怎么走完全程 → ③ 前端能帮什么忙 → ④ 怎么证明它扛得住`。

### 4.2 三层漏斗

```
                      10 万请求
                          │
   ┌──────────────────────▼──────────────────────┐
   │ 第一层：让请求【别发出来】                    │
   │  按钮置灰 / 一次性 token / 商品页静态化推 CDN  │  ← 砍掉约 8 成
   └──────────────────────┬──────────────────────┘
                          │ 约 2 万
   ┌──────────────────────▼──────────────────────┐
   │ 第二层：让进不来的【痛快走】                  │
   │  API 网关限流 / 鉴权 / 黑名单 → 超限返回 429   │
   └──────────────────────┬──────────────────────┘
   ┌──────────────────────▼──────────────────────┐
   │ 第三层：让进来的【公平抢】                    │
   │  资格校验 → Redis+Lua 原子预扣                │
   │      ├─ 失败 → 立即返回「已抢完」              │
   │      └─ 成功 → 扔 MQ → 返回「排队中」          │
   └──────────────────────┬──────────────────────┘
                          │ 只剩 1000（库存数量级）→ 订单服务落库
        数据库从头到尾，只见到 1000 多个请求
```

三个关键判断，作者都给了理由：

| 判断 | 理由 |
|---|---|
| 按钮为什么置灰 | **最好的限流发生在用户的手机上，请求不发出来，成本是 0** |
| 超限为什么立刻 429，不能排队 | **排队容易滋生重试，这就变成了二次攻击** |
| 预扣失败为什么立刻返回 | **别让用户等一个已经注定失败的结果** |

### 4.3 一次请求的完整旅程

```
① 点击「立即抢购」  按钮置灰 + 一次性 token
      ▼
② API 网关          限流 / 鉴权 / 黑名单 → 超限 429
      ▼
③ 秒杀服务          资格校验：活动起止？是否已抢过？（一人一单）
      ▼
④ Redis + Lua       原子预扣 ──失败──→ 返回「已抢完」⏹
      ▼ 成功
⑤ 投递 MQ → 立刻返回「排队中」 → ⑥ 订单服务消费（幂等校验）
      ▼
⑦ 数据库真实扣减（UPDATE ... WHERE stock > 0）
      ▼
⑧ 支付 / 回填 → ⑨ 前端轮询 → ⑩ 事后对账（Redis 预扣 vs 实扣）
```

> **整个完整流程走完，对于秒杀场景来说是非常从容的。**

注意 ④ 和 ⑦ 的关系：**Redis 预扣是第一层原子，数据库自减是第二层原子**，任何一层出问题另一层兜着。

### 4.4 前端能帮的四个忙

> **最好的限流，是发生在用户的手机上的。不发出来的请求，成本是 0。**

| # | 手段 | 做法 | 收益 |
|---|---|---|---|
| **①** | **页面静态化 + CDN** | 详情页预渲染成**纯 HTML 推 CDN**，动态数据只剩**查库存 + 下单**两个接口 | **CDN 命中率 90%+**，回源只剩 **1%** |
| **②** | **按钮防重 + 答题** | 点击立刻置灰 + 一次性 token + **滑块验证** | 把「一秒同时发射」的流量**拉平到几秒** |
| **③** | **风控 + 黑名单** | 设备指纹、行为验证、一人一单 | 把**机器流量从真人里剥出来**，真人少排队 |
| **④** | **下单接口极简** | 能漏到这里的请求，**一次 Redis 往返就定生死** | **接口越轻，单机上限越高** |

关于 ②，作者还开了个玩笑，这个比喻要留着：

> 大家是不是都做过这种滑块题？**把图片归到正常的位置，给它补上那个缺口。这也算是一个零成本的削峰。**

关于成本，作者给了一个量化的对比：

> **CDN 边缘拦一次的成本，大约等于数据库里拦一次的 1/10000。** 所以尽量让限流**发生在用户的手机上**。

### 4.5 压测：把纸面数字变成实测数字

**方法：阶梯加压** —— 50 并发起步，**每档跑 3 分钟**，逐步加到 400。

| 并发 | QPS | RT | 判断 |
|---|---|---|---|
| 50 | **920** | 54 ms | 健康 |
| 100 | **1740** | 57 ms | **线性增长，健康** |
| 200 | **2870** | 70 ms | RT 开始上升，**这是信号** |
| 400 | **2910** | **137 ms** | **并发翻倍，QPS 不动 → 拐点** |

> 📌 **补充**：表中 50/100/200 的 RT 是按第 1 章公式 `并发数 = QPS × RT` 反推的（50÷920≈54ms，100÷1740≈57ms，200÷2870≈70ms）；视频只明确报了 400 并发时 RT 为 **137ms**。

解读链条：`50→100` QPS 920→1740 近似翻倍，线性健康；`100→200` QPS 2870 但 RT 开始上升，预警信号；`200→400` QPS 只到 2910、RT 猛涨到 **137ms**——**并发翻倍、QPS 不动，这就是拐点**。

> **系统容量大约就是 2900 左右。过了拐点，加并发只会让 RT 爆炸。所以限流阈值要设在拐点的八成左右。**

**定位瓶颈：按层下钻**

```
① CPU / 线程池  → 活跃线程满了吗？队列在堆吗？
② 连接池        → 拿连接的等待时间在涨吗？
③ 慢 SQL / 锁   → 有慢查询吗？有行锁等待吗？
④ Redis / 网络  → 缓存命中率掉了吗？带宽打满了吗？
```

> **哪一层的队列在堆积，瓶颈就在哪一层。**

**最后一步：对账** —— 第 1 章估算约 **2800 QPS**，第 4 章实测约 **2900 QPS**，**两个数对上了就敢上线**（互相证明）。

📌 **补充**：压测工具有两条路线——**JMeter**（图形化，阶梯加压用 `Ultimate Thread Group` / `Stepping Thread Group` 插件）和 **wrk / Gatling**（脚本化、资源占用低，适合打高并发）。比工具更重要的是**压测数据构造**：用户 ID 要打散、缓存要预热、要压到稳定态而不是刚启动那 10 秒。

## 5. 落地路线：三个阶段，别一口气全上

> **不要把前面这些东西一口气全部搬到项目里，要按顺序升级。**

| 阶段 | 做什么 | 达到什么 | 代价 |
|---|---|---|---|
| **① 止血** | **索引 + 缓存** | 覆盖 **8 成**的并发问题 | 极低（改 SQL、加一层缓存） |
| **② 防身** | **限流 + 熔断 + 异步** | 系统做到「**打不死**」 | 中（引入 Sentinel / MQ） |
| **③ 扩容** | **无状态 + 读写分离 + 归档 + 分库分表** | 容量真的能加上去 | **高**（要动数据模型、要迁移） |

三条纪律：**每一步做完都压测一次**；**第三阶段「压测数据说了算」才能动**；**先用便宜的，再用贵的；先保命，再提量。**

顺序背后的逻辑：**止血解决「RT 太长」**（回到第 1 章公式，RT 降 10 倍，并发压力降 10 倍），**防身解决「流量太猛」**，**扩容解决「单机真的到顶」**。顺序反了会怎样？先分库分表，最后发现瓶颈只是一条没走索引的 SQL——**钱花了，问题还在**。

## 6. 五个坑：每一条都能独立搞出一次事故

| # | 坑 | 后果 | 正确做法 |
|---|---|---|---|
| **1** | **缓存了会变的数据** | 库存/余额缓存 5 分钟 → 很多人以为还有货 → **超卖** | 强一致数据不走缓存读路径 |
| **2** | **无界队列 + 不设超时** | 请求越攒越多 → **OOM** | 队列必须有界；远程调用必须设超时 |
| **3** | **MQ 不做幂等** | **重复订单** | 订单号做唯一键，保证「同一张小票只干一次活」 |
| **4** | **压测环境和生产是两张皮** | 得出错误结论 → **误导生产** | 数据量、机器规格、网络拓扑尽量贴近生产 |
| **5** | **盲目加机器** | 慢 SQL 加机器 = **让烂查询跑在更多机器上** | 先定位瓶颈，再决定加什么 |

第 5 条是全场最狠的一句吐槽，也是开场观点在这里的呼应：

> **慢 SQL 你加机器，它只能让这些烂查询跑在更多的机器上，根本没用。**
> **总原则：先用便宜的再用贵的，先保命再提量。每一步都压测，让数字说话。**

## 8. 速查卡：公式 / 算法 / 配置一页查完

### 8.1 三条公式

| 公式 | 用途 | 例 |
|---|---|---|
| **并发数 ≈ QPS × RT** | 由 QPS 和 RT 推算需要多少线程/连接 | 2000 × 0.05 = 100 |
| **单机 QPS ≈ 线程数 ÷ RT** | 推算单机容量 | 200 ÷ 0.5 = 400 |
| **IO 密集线程数 = 核数 × (1 + 等待/计算)** | 定核心线程数 | 8 × (1 + 4) = 40 |

### 8.2 容量估算四步

`① 日活 × 人均次数 = 日请求量` → `② × 0.8 ÷ 17280 = 日常高峰 QPS` → `③ × 峰值系数（日常 3）= 设计目标` → `④ 应用按 70% 水位分摊，数据库只接缓存没挡住的部分`

### 8.3 关键数字与配置

| 项 | 值 | 出处 |
|---|---|---|
| Tomcat 默认工作线程 | **200** | 第 1 章 |
| MySQL 默认连接数 | **151** | 第 1 章 |
| 缓存命中率目标 | **≥ 90%** | 第 2 章 |
| 雪崩 TTL 抖动 | 1800s → **1800~2400s** | 第 2 章 |
| 延迟双删间隔 | **500 ms** | 第 2 章 |
| 限流阈值 | **压测拐点 × 80%** | 第 3、4 章 |
| 单表分库分表阈值 | **> 1000 万行** | 第 3 章 |
| 上线卡点 | **扫描 > 10 万行必须走索引** | 第 3 章 |
| 线程池队列 | **必须有界** | 第 3 章 |
| 看门狗续期 | **每 10 s**（默认锁 30 s） | 第 3 章 |
| 秒杀压测拐点 | **≈ 2900 QPS / 400 并发 / RT 137ms** | 第 4 章 |

## 10. 面试自测题（含答案）

先自己答，再看答案。

<details>
<summary><b>Q1：QPS 没涨，系统却挂了，为什么？</b></summary>

因为 **RT 涨了**。由 `并发数 ≈ QPS × RT`：QPS 2000、RT 从 50ms 变成 500ms，并发数就从 100 涨到 1000，资源占用翻 10 倍，线程池瞬间拉满。

**所以压垮系统的往往不是「流量变多」，而是「变慢」。** 反过来，优化 RT 就是最直接的扩容手段——这就是缓存和索引优先级最高的原因。
</details>

<details>
<summary><b>Q2：为什么崩的总是数据库，而不是应用服务器？</b></summary>

因为**应用无状态，数据库有状态**。应用可以复制 100 份，数据库只有唯一副本，且有三条硬约束：**连接数有上限**（MySQL 默认 151）、**热点行锁是独木桥**（同一行更新必须串行，100 个连接也没用）、**查询可能碰磁盘**（内存纳秒级 vs 磁盘毫秒级）。所以全课纲领是：**让请求最好别到数据库。**
</details>

<details>
<summary><b>Q3：缓存穿透、击穿、雪崩，一句话区分 + 各自解法？</b></summary>

| | 一句话 | 解法 |
|---|---|---|
| **穿透** | 查的数据**根本不存在**，缓存永远建不起来 | 空值缓存（短 TTL）/ 布隆过滤器 |
| **击穿** | **一个热点 key** 过期瞬间，大量并发查库 | 互斥锁（只放一个回源）/ 逻辑过期 |
| **雪崩** | **一大批 key 同时过期** 或 Redis 宕机 | TTL 随机抖动 / 哨兵高可用 / 熔断限流兜底 |

口诀：**查无此人堵入口，热点过世锁回填，集体殉职摊 TTL。**
</details>

<details>
<summary><b>Q4：为什么写缓存是「删除」而不是「更新」？为什么顺序是「先更库再删缓存」？</b></summary>

**为什么删：** 并发写时两次回写缓存可能乱序到达（B 后写库但先到缓存，A 先写库但后到缓存），缓存长期留旧值；而且很多缓存是**多表聚合算出来的**，根本没法「改」，只能整体重算。

**为什么先更库：** 反过来（先删缓存再更库）中间会有读请求读到旧值并回填，窗口是**分钟级**；先更库再删缓存，窗口只有**几毫秒**。

**删失败怎么办：** 丢 MQ 重试，或订阅 binlog 自动删。要求更高就用**延迟双删**（更库 → 删 → 等 500ms → 再删）。
</details>

<details>
<summary><b>Q5：线程池的核心线程数怎么定？为什么不能用 Executors？</b></summary>

**核心线程数：** CPU 密集 `核数 + 1`；IO 密集 `核数 × (1 + 等待/计算)`，如 8 核、等 400ms 算 100ms → `8 × 5 = 40`。

**为什么禁 Executors：** `newFixedThreadPool` / `newSingleThreadExecutor` 用的是**无界队列**（可能 OOM），`newCachedThreadPool` / `newScheduledThreadPool` 的最大线程数是 `Integer.MAX_VALUE`（可能创建海量线程）。生产要手写 `ThreadPoolExecutor`，**队列给明确容量**，拒绝策略用 **`CallerRunsPolicy`**（谁提交谁干，天然降速）。

上线盯三个指标：**活跃线程数、队列堆积数、拒绝次数**，后两个不为 0 就说明容量到顶了。
</details>

<details>
<summary><b>Q6：漏桶和令牌桶的区别？什么时候用哪个？</b></summary>

| | 漏桶 | 令牌桶 |
|---|---|---|
| 机制 | 请求进桶排队，**恒速流出** | 系统**恒速发令牌**，请求拿令牌放行 |
| 突发 | **不允许**（出口永远匀速） | **允许**（平时攒的令牌可一次用掉） |
| 用途 | 保护**极脆弱**的下游（第三方支付） | **通用业务限流**（首选） |

一句话：**漏桶管「出口必须匀速」，令牌桶管「平均速率 + 允许适度突发」。**
</details>

<details>
<summary><b>Q7：熔断器三个状态是什么？熔断和降级什么关系？</b></summary>

**CLOSED（闭合）** 正常放行 + 统计失败率 → 失败率超阈值 → **OPEN（断开）** 请求不再发出、直接降级 → 静默期后 **HALF_OPEN（半开）** 放几个试探请求，成功恢复、失败继续断开。

**关系：熔断是保护自己，降级是保住用户体验，必须成对出现。** 只熔断不降级 = 用户看到一片空白；只降级不熔断 = 每次都白等超时。

降级三种形态：**返回兜底数据**（推荐挂了给默认精选）、**简化流程**（大促暂停积分）、**写请求排队**（进 MQ）。
</details>

<details>
<summary><b>Q8：为什么 <code>UPDATE ... WHERE stock > 0</code> 能防超卖，先查再改不行？</b></summary>

先查再改是 **check-then-act**：查和改之间有**时间缝隙**（查 0.3s + 扣 0.2s，中间 0.5s），47 个线程都能读到「还剩 1」，全都判断通过、各自减一次 → 超卖 47 台。

写成一条 SQL 后，**判断条件 `stock > 0` 和减法在同一个语句里**，由**行锁**保证同一行串行：第一条 `1→0` 影响 1 行，第二条 `WHERE stock>0` 不成立影响 0 行。**超卖在数学上不可能发生。**

**本质：把「判断」和「执行」合并成一个原子动作。**
</details>

<details>
<summary><b>Q9：压测怎么找拐点？阈值定在哪？为什么说「足够快」比「足够大」更重要？</b></summary>

**阶梯加压**（50 → 100 → 200 → 400，每档 3 分钟），看 QPS 和 RT 的关系：QPS 线性涨、RT 平稳 = 健康；**QPS 不涨、RT 猛涨 = 拐点**。

实测：400 并发时 QPS 只到 2910（200 并发已 2870），RT 从 70ms 猛涨到 **137ms** → **拐点 ≈ 2900**。**阈值设在拐点的 80%**，留两成余量。

「足够快」之所以更重要：回到 `并发数 ≈ QPS × RT`，**RT 翻倍等于并发压力翻倍**。过了拐点再加并发只会让 RT 爆炸，吞吐一点不涨——所以优化 RT 是唯一能同时降压力和提吞吐的手段。
</details>

## 11. 📌 补充：视频没细讲但一定会踩的坑

> 以下为原讲解之外的延伸，按重要性排序。

### 11.1 缓存和「计数器」是两个角色，别混

Redis 既做缓存（第 2 章）又做预扣（第 3 章），但可靠性要求完全不同：

| | 当缓存用 | 当计数器用（预扣） |
|---|---|---|
| 数据能丢吗 | **能**（丢了回源重建） | **不能**（丢了就超卖 / 少卖） |
| 淘汰策略 | `allkeys-lru` | **不能让它被淘汰** |
| 持久化 | 可以只开 RDB | 建议 **AOF everysec** |
| 故障降级 | 直接回源数据库 | **必须拒绝服务**（不能放行） |

**把「库存」当普通缓存配 `allkeys-lru`，是能搞出超卖的事故配置。**

### 11.2 预扣成功但落库失败 = 「少卖」

Redis 预扣了 1 个，消息投递失败 / 消费者异常 / 数据库回滚 → Redis 少了 1 个但数据库没少。**表现是「库存显示 0，实际还有货，用户一直抢不到」。**

解法：预扣时写「预扣流水」，定时任务对账，**超过 N 分钟仍未落库成功的预扣回滚 Redis 库存**。

> 防超卖只做了一半，防少卖是另一半。

### 11.3 分布式 ID 选型

**雪花算法**趋势递增、本地生成，但依赖机器时钟（回拨会出问题）；**Redis INCR** 简单严格递增，但多一次网络往返、成强依赖；**号段模式**（Leaf）批量取号性能好，但要额外的号段服务。**UUID 别当主键**——无序会让 B+ 树频繁页分裂。

### 11.4 限流的「拒」比「等」更重要

```
排队 → 客户端超时 → 客户端重试 → 请求数翻倍 → 队列更长 → 更多超时
```

这是**正反馈**，一旦启动就刹不住。而 429 是**负反馈**：客户端会退避，压力自然下降。**所以限流一定要「快速失败」**——除非你非常确定下游必须匀速（那就是漏桶，且队列必须有界）。

### 11.5 秒杀还有一个「看不见的成本」：对账

`Redis 预扣数` vs `MQ 消息数` vs `数据库实扣数` vs `支付成功数` —— 每个环节都可能不一致，必须有对账任务每天跑。

**秒杀系统的复杂度不在峰值那一刻，而在峰值之后的账要平。**

## 12. 一句话总结

作者最后给了三句话，要求「牢牢记住」。

> **第一句：高并发的本质是分层消化。** 没有哪一个数据库天生扛得住 10 万的 QPS，但是架构可以让到达它的只有 800。以后遇到系统扛不住，**第一反应是画漏斗**——问题在哪一层？那一层为什么没有挡住？

> **第二句：容量先估算，上限先压测。** 估算给出设计目标，压测给出实测容量。**两个数对上了，系统才算设计完成。**

> **第三句：并发控制的最高境界是无锁。** 能用原子操作解决的，就别急着请出锁和分布式锁。**先看看能不能把这些操作合并成原子的**，能合并就一定要合并。

最后一句是全课的方法论收口：

> **组件会过时，但这套方法不会。先定义，再算账；按漏斗找位置，用压测闭环。**
