## 0. 课程地图：一个 3.2 秒的叫车接口

### 0.1 开场事故：飞驰出行的 3.2 秒白屏

假设有一个网约车平台叫**飞驰出行**。乘客打开 APP，点「叫车」，就应该派单给司机来接人。

但现在出了个问题：**乘客点完「叫车」，APP 白转了 3.2 秒，才跳进「正在为你派单」的页面。**

这 3.2 秒不是玄学，深挖下去，它是**五步串出来的**：

| 步骤 | 动作 | 耗时 | 用户当下真的在等吗 |
|---|---|---|---|
| 1 | 校验乘客定位 | **120 ms** | ✅ 在等（不知道你在哪儿就没法派单） |
| 2 | 写行程单 | **180 ms** | ✅ 在等（单子得先存在） |
| 3 | 派单给司机 | **900 ms** | ✅ 在等（这才是「叫车」本身） |
| 4 | 记行程积分 | **800 ms** | ❌ 不关心（晚 10 分钟到账也无所谓） |
| 5 | 更新乘客画像 | **1200 ms** | ❌ 不关心（晚 1 小时更新也没感觉） |
| | **合计** | **3.2 s** | 只有 1.2 s 是必须等的 |

### 0.2 作者特意强调的两点：别把锅甩给运力

**第一，慢的不是「等司机」。**
早晚高峰运力紧张，等一会儿司机，用户能接受，这是没办法的事。但现在慢的是**接口本身**：点了按钮页面没反应，用户根本不知道发生了什么。

**第二，这还只是普通时段。**
晚高峰这五步叠加起来，很可能涨到**十来秒**，甚至直接报错。

```
普通时段：120 + 180 + 900 + 800 + 1200 = 3200ms  → 3.2 秒白屏
晚高峰：  每一步都被放大 → 10 秒以上，甚至超时报错
```

### 0.3 病根在哪：两个细节

**细节一：积分和画像根本不配站在主链路上。**
积分晚 10 分钟到账、画像晚 1 小时更新，对「我现在就要叫到车」这件事，用户毫无感知。但它们却让用户白等了整整 2 秒（800 + 1200）。

**细节二：五步是串联的，任何一步抛异常，整个叫车回滚。**

```
校验定位 ✅ → 写行程单 ✅ → 派单 ✅ → 记积分 💥 超时
                                            ↓
                              整个调用回滚，行程白建，叫车失败
```

晚高峰网络抖一下、某个服务正在发版升级，超时率就飙升；走到哪一步炸，整个叫车就失败。一晚上能收到**几百条投诉**——而且投诉的还不是「积分没记上」，是「**你这个 APP 叫不到车**」。

### 0.4 一句话点破

> **这个接口，把用户在当下「没有在等」的事情，全干完了才返回。**

一个跟「叫车成败」无关的服务挂了，凭什么拖累整个叫车服务？

**要解决它，就要用到今天的主角：消息队列。**

### 0.5 今天要走的四段路

| 段落 | 章节 | 要回答的问题 | 关键词 |
|---|---|---|---|
| 第 1 段 | 第一章 | 消息队列是什么？有哪些角色？ | 生产者、消费者、Broker、Topic、消费者组、位点、重试、死信 |
| 第 2 段 | 第二章 | 怎么给一个真实项目装上它？ | Redis Stream、XADD、XREADGROUP、XACK、幂等、死信清扫、削峰 |
| 第 3 段 | 第三章 | 怎么保证消息不丢、不重、不乱？ | 三道防线、幂等三板斧、单流有序 |
| 第 4 段 | 第四章 | 市面上有哪些产品？什么时候该换？ | Kafka、RocketMQ、RabbitMQ、Redis 的三条边界 |

作者的原话意思：**概念用生活里的比喻讲，代码用真实项目讲，选型用「丢了会不会赔钱」讲。**

## 1. 第一章 认识消息队列：角色、模型、代价

### 1.1 先看事故代码：五步串成一条链

```java
// 改造前：createTrip 从上到下五步，合计 3.2 秒
public CreateTripResp createTrip(CreateTripCmd cmd) {
    checkLocation(cmd);                    // ① 校验定位      120ms
    String tripId = saveTrip(cmd);         // ② 写行程单      180ms
    dispatch(tripId);                      // ③ 派单给司机    900ms

    pointService.add(tripId, cmd);         // ④ 记行程积分    800ms  ← 用户不关心
    profileService.update(tripId, cmd);    // ⑤ 更新乘客画像  1200ms ← 用户不关心

    return new CreateTripResp(tripId, "DISPATCHING");
}
```

前 3 步是用户真在等的：**校验状态和定位、写行程单、给司机派单**。
后 2 步是用户不在等的：**积分、画像**。

这 5 件事的**重要性是有差别的**：有的必须立刻干，有的晚几分钟、甚至几小时都影响不大。

**但现在它们排成一队，同生共死。**

### 1.2 排成一队的三宗罪

#### 第一宗罪：慢 —— 耗时是加法

串行调用下，总耗时就是每一步相加。**最可气的是：没有任何一步慢得离谱，但它们加起来就明显慢了。**

```
3.2s = 0.12 + 0.18 + 0.9 + 0.8 + 1.2
```

#### 第二宗罪：脆 —— 可用性是乘法

这是全课最值得记的一个换算：

| 单步可用性 | 5 步串联后的可用性 |
|---|---|
| 99% | 99% × 99% × 99% × 99% × 99% ≈ **95%** |

**95% 意味着一天里总有那么一段时间，这个服务会慢、甚至会挂。**

更狠的是**连锁反应**：积分服务抖了一下，前面的活儿全白干——行程白建了，叫车也失败了。

> 作者的原话意思：**一不出事，全部陪葬。**

#### 第三宗罪：崩 —— 同步系统没有缓冲

晚高峰每秒来**上万个请求**，你一个不落全怼到数据库上，而数据库只能扛 **2000 QPS**：

| 指标 | 数值 |
|---|---|
| 晚高峰入口流量 | **10,000 QPS** |
| 数据库承受能力 | **2,000 QPS** |
| 每秒多出来的请求 | **8,000 个** 只能排队 |
| 结果 | 压垮连接池、压垮 CPU |

**同步系统里没有「缓冲」这个概念：流量是什么形状，压力就是什么形状。**

```
流量形状（同步直连）：
10k ┤      ██
    │     ████
 2k ┤ ▁▁▁██████▁▁▁▁▁▁▁▁        ← 数据库上限这条线，峰值直接穿过去
    └──────────────────→ 时间
         💥 超时、连接池耗尽、雪崩
```

#### 三宗罪的共同病根

> **所有事情不管多急多慢、不管靠不靠谱，都挤在同一个管道里，必须同一时刻按顺序干完。**

病根**不在于某一步慢，而在于「排队」这个结构本身**。

所以作者下了一句很重的话：

> **结构的问题，改配置是解决不了的。要换的是结构。**

### 1.3 换结构：从「站着等出餐」到「拿号坐下」

作者用食堂点单做比喻：

**旧结构（同步串行）**：你站在收银台前，店员当着你的面收钱 → 喊后厨做饭 → 做完装盘 → 找零打小票 → 全弄完才给你 → 才轮到下一位。你全程站着等，体验极差。

**新结构（消息队列）**：点完单，店员给你一个**取餐号**，你就找桌子坐下。后厨按自己的节奏出餐，好了叫号。

> 点单只花几秒；做饭就算慢了两分钟，你也不介意——刷两个短视频就过去了。

**这个画面的关键不是「快」，而是「你不用站着等了」。**

### 1.4 三个词，落到三个具体动作

把五件事按「紧急程度」重新分堆：**必须现在干的前三步**，**可以晚点干的后两步**。这一分堆，就同时解决了三宗罪：

| 原来的罪 | 分堆后得到的能力 | 一句话解释 |
|---|---|---|
| 慢 | **异步** | 不在等的活儿，不占用户的时间 |
| 脆 | **解耦** | 下游挂了，不连累上游（柜子还在，件儿还在） |
| 崩 | **削峰** | 洪峰先存着，下游按自己的速度慢慢消化 |

> **这三个词你可能早就听过，但今天之后它们不再是名词，而是三个具体的动作、三个具体的目标。**

### 1.5 快递柜：四个画面看懂四个角色

作者说：**从今天开始，你小区的快递柜就是消息队列。**

#### 画面一：快递员放包裹 → 生产者 Producer

快递员把包裹放进格子，**咚**一声关上柜门，就去送下一单了。**不等收件人来，不等他拆开，不等他签收。**

对应到代码：叫车服务**不直接调积分服务**，而是把「行程已创建」写成一封短信塞进柜子，塞完就返回。

> 结果：乘客在**很短的时间内**就能看到「正在派单中」的页面。

**生产者（Producer）= 发出消息的一方。**

#### 画面二：柜子负责暂存 → Broker

柜子是一台**独立的设备**：有自己的电源、有自己的锁，**24 小时都在那儿**。

**Broker = 独立运行、先把消息存下来的中转程序。**

关键在「**独立**」两个字：寄件的快递员和取件人**从不见面**。快递员放下就走，取件人有空来取，**谁也不等谁**。

#### 画面三：有空再来取 → 消费者 Consumer

你下班顺路取件，6 点下班也好，加班到 10 点也好，件儿都在。**快递员早就送完去送别的单了。**

**消费者（Consumer）= 订阅并处理消息的一方。**

在我们的例子里，**积分服务**就是取件人，它按自己的节奏取消息、算积分。

> 如果积分服务抖了、宕机了——柜子里的件儿**原封不动地等着**，对叫车本身**一点影响都没有**。

#### 画面四：坏件有兜底 → 重试与死信

取件人拆开发现商品是坏的，**不是扔了不管**，而是退回去重发一次。

**重试（Retry）= 处理失败后，系统自动再次投递。**

如果重发几次都不行呢？有个**坏件专柜**，放进去等人工处理。

**死信（Dead Letter）= 反复失败的消息单独存放，后续有人跟进。**

#### 一条设计原则

> **消息永远不会凭空消失。**

这就是整个消息队列的底线。后面第三章的三道防线、第二章的死信清扫，全是在守这一条。

### 1.6 定义：一句话说清

> **消息队列是一个独立运行的中转程序：发送方把消息塞进去就返回，接收方按自己的节奏取出来处理。**

### 1.7 柜子的内部结构：核心模型

光有比喻不够，得看柜子里面长什么样。

```
                   ┌──────────────────────────────────────────┐
                   │            Broker（独立进程）             │
 ┌──────────┐      │  ┌────────────┐  ┌────────────┐          │      ┌──────────────┐
 │ Producer │─────▶│  │ trip-created│  │ pay-created │  ...    │─────▶│  Consumer A  │
 │ 叫车服务  │ 写   │  │  Topic 行程 │  │ Topic 支付  │          │ 读   │ 积分服务      │
 └──────────┘      │  └────────────┘  └────────────┘          │      └──────────────┘
                   │        │                                   │      ┌──────────────┐
                   │        ├───────────────────────────────────┼─────▶│  Consumer B  │
                   │        │                                   │      │ 画像服务      │
                   │        └───────────────────────────────────┼─────▶└──────────────┘
                   └──────────────────────────────────────────┘      ┌──────────────┐
                                                                     │  Consumer C  │
                                                                     │ 推荐 / 风控   │
                                                                     └──────────────┘
```

#### Topic：柜子是有分栏的

柜子**不是一整片格子混着放**，它有分栏：**行程事件一栏、支付事件一栏、用户事件一栏，每一栏只放一类消息。**

这个分类栏，行业黑话叫 **Topic（主题）**。

**为什么要分栏？** 积分服务只想收行程事件。混着放，它得把支付消息也收进来，再一条条挑出去扔掉——**白费功夫**。

所以：**一栏一类消息，消费者各守各的栏。**

#### 点对点 vs 发布订阅

| 模式 | 快递柜类比 | 含义 | 典型场景 |
|---|---|---|---|
| **点对点（P2P）** | 一件包裹只能一个人取走 | 一条消息只被一个消费者处理 | 任务分发、工单派发 |
| **发布订阅（Pub/Sub）** | 行程事件这一栏，积分、画像、推荐**各拿一份复印件** | 一次发布，多方各自订阅 | **绝大多数业务消息** |

#### 推模式 vs 拉模式

| 模式 | 类比 | 特点 |
|---|---|---|
| **推（Push）** | 快递员把包裹送到你家里、送到你手上 | 实时性好，但消费者可能被撑死 |
| **拉（Pull）** | 你自己去快递柜取 | **按自己的消化能力取，不会被撑死** |

> **主流是拉模式。** 生产者只负责往柜子里放，消费者自己控制节奏。

#### 消费者组：几台机器一起分活儿

同一栏的件儿，分给**组内的几台机器各处理一部分**，这就是**消费者组（Consumer Group）**。

扩容有两条路：

| 扩容方式 | 做法 | 上限 |
|---|---|---|
| **纵向扩容** | 换一台处理能力更强的机器 | 很快撞到天花板（单机总有极限） |
| **横向扩容** | 多加几台普通机器，一起分着取 | 理论上可以一直加 |

#### 解耦的实感：加一个新下游，一行代码不改

叫车 APP 现在要接**风控服务**，怎么办？

```
改造前：改叫车服务的代码 → 加一行 riskService.check() → 联调 → 发版 → 回归
改造后：风控服务自己去订阅 trip-created 这个 Topic → 叫车服务 0 改动
```

> **这就是消息队列带来的解耦。**

#### 各家产品的叫法不一样，骨架是同一张

Kafka、RocketMQ、Redis 的界面五花八门，**但骨架基本就是上面这张图**。

| 概念 | Kafka | RocketMQ | RabbitMQ | **Redis** |
|---|---|---|---|---|
| 分类栏（主题） | Topic | Topic | Exchange + Queue | **Stream** |
| 生产 | Producer | Producer | Producer | XADD |
| 消费 | Consumer | Consumer | Consumer | XREADGROUP |
| 进度 | Offset | Offset | 手动/自动 ACK | last-delivered-id |
| 消费组 | Consumer Group | Consumer Group | —（靠队列竞争） | Consumer Group |

> 作者原话意思：**在 Redis 里，一条 Stream 就是一个 Topic。**

### 1.8 位点 Offset：柜子怎么记住你取到哪儿了

还剩两个问题：① 柜子怎么记住每个取件人取到哪儿了？② 几台机器一起取，怎么分工？

**答案：给每个取件人发一张「取件进度卡」。**

```
进度卡（Offset）
┌────────────────────────────────┐
│  画像服务   已取到：第 3 件      │  ← 取一件，确认一件，数字往后挪一格
└────────────────────────────────┘
```

- **重启机器、断电恢复**：照着卡片继续取
- **取过的不会重来，没取的不会漏掉**

> 这张「取件进度卡」，术语叫 **位点（Offset）**，它是我们后面「不丢失、不重复」的**第一根支柱**。

### 1.9 消费者组 × 位点：两张卡，互不拖累

假设画像服务一台机器处理不过来：

```
横向扩容：3 台机器一起取 trip-created 这一栏
   ├─ 一条消息只给组内的一台机器处理
   ├─ 3 台就是 3 倍速度
   └─ 坏了一台，也只是停了 1/3 的处理能力

三台机器组成【画像组】，共享同一张进度卡
积分组是另一张卡 —— 画像取完了，积分才取一半，互不拖累
```

**这又回到了发布订阅：一条消息，每个组各拿一份。**

> 看到这张图，以后你再看 Kafka 的 `consumer group` + `offset`，或者 Redis 的消费者组 + `last-delivered-id`，**实现思路是差不多的**。

### 1.10 泼一盆冷水：四个代价

消息队列不是免费引进来的。作者把四个代价摆上台面：

| # | 代价 | 具体表现 | 应对 |
|---|---|---|---|
| 1 | **一致性变慢** | 同步时积分画像当场做完才算叫车成功；异步后叫车先成功，积分晚几分钟才到 | 中间存在**数据暂时不一致的窗口**，业务能容忍才行；不能容忍就留在同步里 |
| 2 | **会重复** | 队列的保命设计是「**宁可重复，不可丢失**」，同一封信息可能推两遍 | 收件方必须认得出「这单我处理过了」→ **幂等** |
| 3 | **会积压** | 消费者慢了或挂了，柜子里的件儿越堆越多 | 必须有人盯**堆积量**，配**告警** |
| 4 | **运维多一摊** | 原来只管数据库，现在要多一套部署、监控、扩容的集群 | 认了，或者选托管服务 |

### 1.11 什么时候**不要**用消息队列

| # | 不要用的场景 | 原因 |
|---|---|---|
| 1 | 用户要**立刻拿到结果**的操作（查余额、支付确认） | 异步了会影响用户判断，钱的事不能「稍后再说」 |
| 2 | **只有一个系统在用** | 没必要自己跟自己解耦 |
| 3 | 流量平稳的小系统（一天几千单） | 没有洪峰，不需要削峰填谷 |

> **总结这笔账**：付出的是**及时性、一致性、简单性**；换回的是**主链路飞快、故障隔离、洪峰缓冲**。
>
> **这笔账在不同系统上算出来的结果不一样。所以用不用消息队列，是一个架构决策，不是每个系统的默认操作。**

### 1.12 一条消息的一生：五站

从生产到处理完，一共 **5 站**。每一站都要问两个问题：**它可能出什么事？保障机制是什么？**

```
 ①发送        ②存储         ③投递         ④处理         ⑤签收
Producer ──▶ Broker ──▶ Consumer ──▶ 业务代码 ──▶ XACK
   │            │            │            │            │
 网络抖动      硬盘坏了     消费者刚拿到    代码抛异常    回执确认
 消息没进柜    柜子宕机     就掉线了       处理到一半    进度卡前移
   │            │            │            │            │
 发送确认      刷盘+备份    没确认就算     自动重投      才算真正落幕
 拿到消息 ID   互为副本     没送出去       重试机制
```

| 站 | 动作 | 风险 | 保障机制 |
|---|---|---|---|
| **① 发送** | 生产者把消息交给柜子 | 网络抖动，消息根本没进柜子 | **发送确认**：柜子回一个消息编号，拿到编号才算真放进去，没拿到就重发 |
| **② 存储** | 消息写到柜子里（落盘） | 硬盘坏了、Broker 宕机 | **刷盘 + 备份**：主柜坏了，备用柜顶上，两个柜子**互为副本** |
| **③ 投递** | 柜子把消息交给消费者 | 消费者刚拿到就掉线，你不知道他收到没 | **没确认就一直算没送出去**，消息还挂在柜子里，回头再投 |
| **④ 处理** | 消费者执行业务代码 | 代码抛异常，处理到一半失败 | **自动重投机制**（见 1.13） |
| **⑤ 签收** | 消费者回一句「这条我处理完了」 | — | **ACK**，进度卡往前挪一格 |

#### 为什么必须「签收」？

> **在签收之前，这条消息都不算处理完。**

为什么这么设计？因为「处理之后、签收之前」这个时间段，如果处理到一半崩了，而队列**以为你做完了**——那这单就**永远丢在半路了**。

> **宁可多走一步去签收，也不能让它丢掉。**

#### 故障排查口诀

| 现象 | 查哪一站 |
|---|---|
| 消息**丢了** | 查 **① 发送** 和 **② 存储** |
| 消息**卡住不动** | 查 **④ 处理** |
| 消息**重复了** | 查 **⑤ 签收** |

### 1.13 重试与死信：坏件去哪儿了

消费者处理失败，队列要走 **4 步**：

```
① 消费失败
   画像服务处理消息时要调推荐引擎 → 推荐引擎超时 → 代码抛异常
   这条没处理完，也没签收
        ↓
② 自动重投
   队列没收到「处理完了」的确认 → 把消息再交出去一次 → 再失败就再试
   全程自动，不需要有人管
        ↓
③ 超过次数 → 进死信
   重试 3 次都失败 → 多半不是暂时故障，而是代码 bug 或脏数据
   → 挪进【死信专区】单独存放，不再反复挡路
   → 配了告警，有人来查，修好后重新投递
        ↓
④ 人工闭环
   运维看死信 → 定位原因
   ├─ 是 bug：修完重投
   └─ 是脏数据：登记结案
```

#### 为什么值得重试？

因为**很多故障是暂时的**：数据库正在重启、网络抖了一下，过 10 秒再试一次就好了。

#### 为什么不能无限重试？

重试 1 万次也没用——**代码有 bug，或者数据本身就是坏的**。所以要有一把尺子。

#### 这把尺子叫「投递计数」

> 队列给每条消息记「被送过几次」。**1 次可能是抖动，3 次失败就可能是真的坏了。**

这个次数，就是**区分「暂时故障」和「真坏件」的分界线**。

### 1.14 埋个雷：重试是有副作用的

这是全课反复回扣的一个坑：

```
第一次投递：积分 +10  ✅ 干完了，但 XACK 没发出去（进程崩了）
第二次投递：积分 +10  ❌ 又加了一遍！用户白赚 10 分
```

> **消息的重试，必然带来重复。** 这就是为什么必须有**幂等**——第二章第 3 段代码专门解决它。

## 2. 第二章 实战：给网约车平台装上队列（重点）

### 2.1 为什么拿 Redis 练手？三个原因

**① 你可能已经有了**——项目里很多都在用 Redis 跑缓存，不用再装一套新东西；**② 命令就几个，一个下午上手**——但它的**概念和理念跟专业 MQ 完全相通**，学会了去哪儿都能快速上手；**③ 中小系统扛得住**——中小系统的消息量，Redis 的消息队列够用。

**术语映射先记住**：前面说的**主题（Topic）**，在 Redis 里叫 **Stream（流）**。**一条流 = 一个主题。**

### 2.2 动手之前先动脑：哪些能搬，哪些不能搬

判断依据只有一条：

> **这一步的结果，用户当下要不要看到？**

| 步骤 | 用户当下要看到吗 | 去向 |
|---|---|---|
| 校验定位 | ✅ 要 | 留主链路 |
| 写行程单 | ✅ 要 | 留主链路 |
| 派单给司机 | ✅ 要 | 留主链路 |
| 记行程积分 | ❌ 不要 | **搬进队列** |
| 更新乘客画像 | ❌ 不要 | **搬进队列** |

```
改造前的链路（3.2s 全在用户眼前）：
用户 ──▶ [校验 120] [写单 180] [派单 900] [积分 800] [画像 1200] ──▶ 返回

改造后的链路（1.2s 就返回）：
用户 ──▶ [校验 120] [写单 180] [派单 900] [XADD 5ms] ──▶ 返回「派单中」
                                                  │
                                                  ▼
                                        ┌──────────────────┐
                                        │  trip-created 流  │
                                        └────────┬─────────┘
                                    ┌────────────┴────────────┐
                                    ▼                         ▼
                              [积分组]                   [画像组]
                            按自己节奏消费             按自己节奏消费
```

### 2.3 代码 1：生产者（XADD）

#### Java（Spring Data Redis）

```java
@Service
public class TripService {

    private final StringRedisTemplate redis;

    public CreateTripResp createTrip(CreateTripCmd cmd) {
        // ① 主链路三步，一步都不能少
        checkLocation(cmd);                    // 120ms
        String tripId = saveTrip(cmd);         // 180ms
        dispatch(tripId);                      // 900ms

        // ② 原来的两段同步调用，注释掉
        // pointService.add(tripId, cmd);      // 800ms
        // profileService.update(tripId, cmd); // 1200ms

        // ③ 换成一行：往流里追加一条消息
        Map<String, String> body = new HashMap<>();
        body.put("tripId", tripId);            // 行程号
        body.put("riderId", cmd.getRiderId()); // 乘客号

        RecordId msgId = redis.opsForStream().add(
                StreamRecords.mapBacked(body).withStreamKey("trip-created"));

        // 合计约 1.2 秒，拿到的 msgId 就是「真的进柜了」的凭证
        return new CreateTripResp(tripId, "DISPATCHING", msgId.getValue());
    }
}
```

#### 底层原生命令

```bash
# X 是 Redis 消息队列这一套命令的统一前缀，ADD 就是追加
XADD trip-created * tripId T20261115001 riderId R8899
# 返回： "1763180000000-0"
```

| 命令 | 含义 |
|---|---|
| `XADD` | 追加一条消息（生产） |
| `XREADGROUP` | 按消费者组读（消费） |
| `XACK` | 确认签收 |
| `XPENDING` | 查待确认列表（挂账单） |
| `XCLAIM` | 领回消息所有权 |
| `XLEN` / `XTRIM` | 查长度 / 裁剪 |

#### XADD 干的三件事

| # | 做的事 | 细节 |
|---|---|---|
| 1 | 把消息**追加到流的末尾** | 只追加，不改旧数据 |
| 2 | **自动生成消息 ID** | 格式 `毫秒时间戳-序号`，同一毫秒内序号自增，**天然按先后排好** |
| 3 | **返回 ID** | 生产者拿到它，才知道消息真的进流了 |

#### 两个参数

| 参数 | 本例取值 | 含义 |
|---|---|---|
| 流名 | `trip-created` | 就是前面说的 Topic/分栏，**行程创建事件全进这条流** |
| 消息体 | `tripId` / `riderId` | 键值对列表，把「哪段行程、哪个乘客」说清楚 |

#### 一个重要的设计取舍：消息里**只放线索，不放全量**

积分要算里程怎么办？画像要算行为明细怎么办？

> **拿着 `tripId` 回查数据库。**

作者的原话意思：

> **消息是一个「事件通知」，不是「数据搬家」。**
> 你要是把数据全塞进消息里，消息体越滚越大——**这个柜子就变成数据库了。**

#### 留一个伏笔

> 如果 `XADD` 失败了怎么办？行程建了，事件却没进流。
> ——第三章的**三道防线**会回应这个问题。

### 2.4 代码 2：消费者（XREADGROUP + XACK）

以画像服务为例。整个方法就是一个死循环，分三步：**读 → 干活 → 划账**。

```java
@PostConstruct
public void start() {
    while (true) {
        // ① 读：按「组」读，对应原生命令 XREADGROUP
        List<MapRecord<String, Object, Object>> records = redis.opsForStream().read(
                Consumer.from("profile-group", "worker-1"),          // 组名 + 组内身份
                StreamReadOptions.empty().count(10).block(Duration.ofSeconds(2)),
                StreamOffset.create("trip-created", ReadOffset.lastConsumed()));

        if (records == null || records.isEmpty()) continue;

        for (MapRecord<String, Object, Object> record : records) {
            String tripId = (String) record.getValue().get("tripId");

            // ② 干活：真正的业务就这一行
            profileService.update(tripId);

            // ③ 划账：精确传消息 ID，Redis 只认编号
            redis.opsForStream().acknowledge("trip-created", "profile-group", record.getId());
        }
    }
}
```

#### 三个关键参数

| 参数 | 取值 | 作用 |
|---|---|---|
| **组名** | `profile-group` | Redis 看到新组名会**自动建组**，并从此记一个自己的位点 |
| **组内身份** | `worker-1` | 一条消息**只会给组内一个 worker**；两个 worker 就是两倍速度 |
| **读取位置** | `last-consumed`（`>`） | 从**这个组上次读到的地方**继续，读过的不再来 |

#### 位点 + 挂账单：两个机制合起来才可靠

```
        ┌─────────────────────────────────────────────┐
        │  trip-created 流（只追加，读完不删）           │
        │  [msg1] [msg2] [msg3] [msg4] [msg5] ...      │
        └─────────────────────────────────────────────┘
                     │                    ▲
        投递给 worker-1│                    │ 位点（last-delivered-id）
                     ▼                    │ 记录「这一组读到第几条」
        ┌────────────────────────┐        │
        │   PEL 待确认列表         │────────┘
        │  （挂账单：领了件没签收）  │
        │  msg4 ← 干了活没 XACK    │  → 重启后还能再领出来处理
        └────────────────────────┘
```

| 机制 | 保证什么 |
|---|---|
| **位点（offset / last-delivered-id）** | 消息**不漏**：没读过，下次还会读到 |
| **挂账单（PEL，Pending Entries List）** | 消息**不丢**：干了活没划账的，都挂在这上面，还能再领出来 |

#### 崩溃场景：这就是「至少一次」

> 进程在「干完活」和「划账」之间崩了怎么办？
> **重启之后，这条会被再次投递。**

但这也引入一个问题：**画像会不会更新两遍？**

> **消息的重试，必然带来重复。** 所以下一步必须做幂等。

### 2.5 代码 3：幂等（SET NX + 过期）

#### 重复是怎么发生的

```
第 1 次投递 → 处理失败
第 2 次投递 → 处理失败
第 3 次投递 → 处理成功 ✅ 但位点还没来得及提交（进程崩了）
第 4 次投递 → 又算了一遍 ❌
```

**消费者必须自己会确认：「这件事我是不是已经干过了？」**

#### 用 `SET IF ABSENT`

```java
for (MapRecord<String, Object, Object> record : records) {
    String tripId = (String) record.getValue().get("tripId");

    // 键 = 业务动作 + 单号，24 小时过期
    String dedupKey = "dedup:trip:profile:" + tripId;
    Boolean first = redis.opsForValue()
            .setIfAbsent(dedupKey, "1", Duration.ofHours(24));

    if (Boolean.TRUE.equals(first)) {
        // 第一次见到：干正事
        profileService.update(tripId);
    }
    // 已经处理过：跳过正事，但【照样要签收】
    // 否则它会永远待在 PEL 里被反复重投

    redis.opsForStream().acknowledge("trip-created", "profile-group", record.getId());
}
```

#### 为什么这一行就够了

| 事实 | 作用 |
|---|---|
| `SET key value NX EX 86400` | 键不存在就写入并返回 `true`；已存在就**什么也不做**，返回 `false` |
| **查询和写入是一步完成的** | 中间没有缝隙，不存在「查了没有，然后两个请求都写进去」 |
| **Redis 单线程执行命令** | 两个请求同时到，必然一前一后 |

#### 键的设计比代码更重要

> **键 = 业务动作 + 单号。**

| 业务 | 键 |
|---|---|
| 加积分 | `dedup:trip:point:{tripId}` |
| 更新画像 | `dedup:trip:profile:{tripId}` |

- 同一个行程的积分和画像**是两个键**，互不干扰
- 不同行程天然是不同键
- **先想清楚「什么算重复」，再动手写代码**

#### 两层防线：Redis 挡 90%，数据库兜底

| 层 | 手段 | 作用 |
|---|---|---|
| 第 1 层 | **Redis `SET NX`** | 挡掉 **90% 以上**的重复；TTL **24 小时**，键不会无限堆积 |
| 第 2 层 | **数据库唯一索引** | Redis 也宕机时兜底（极端情况） |

> **核心业务（钱、积分）两层都上；通知类业务上一层就够。**
>
> 这样就能同时保证两件事：**至少送达一次（at-least-once）+ 只生效一次（幂等）**。

### 2.6 代码 4：死信清扫（每分钟一次，5 步）

会发消息了、会消费了、能防重复了。**还差一件事：那些重试的坏件，最后去哪儿了？**

> 进**坏件专柜**。也就是需要一个**每分钟跑一次的定时任务**，把死信清出来。

```java
@Scheduled(cron = "0 * * * * ?")   // 每分钟一次
public void sweepDeadLetter() {

    // ① 查挂账：这个组在这条流上「领了件但没签收」的消息，一次最多 10 条
    PendingMessages pending = redis.opsForStream()
            .pending("trip-created", "profile-group", Range.unbounded(), 10);

    for (PendingMessage pm : pending) {

        // ② 判断坏没坏：投递计数 ≥ 3 才算真坏
        if (pm.getTotalDeliveryCount() < 3) continue;

        // ③ 领回：把所有权从原 worker 转到清扫人 sweeper
        List<MapRecord<String, Object, Object>> claimed = redis.opsForStream()
                .claim("trip-created", "profile-group", "sweeper",
                        Duration.ofMinutes(5), pm.getId());

        for (MapRecord<String, Object, Object> record : claimed) {
            // ④ 转投死信流 + 原流划账
            redis.opsForStream().add(
                    StreamRecords.mapBacked(record.getValue()).withStreamKey("trip-dead"));
            redis.opsForStream().acknowledge("trip-created", "profile-group", record.getId());
        }

        // ⑤ 告警到值班群
        alertGroup.push("死信告警: " + pm.getId()
                + " 已投递 " + pm.getTotalDeliveryCount() + " 次");
    }
}
```

#### 五步拆开看

| 步 | 动作 | 关键点 |
|---|---|---|
| ① | `XPENDING` 查挂账单 | 查「领了件但没签收」的消息，一次最多 **10 条** |
| ② | 看 `getTotalDeliveryCount()` | **≥ 3 次**才判死；投递计数是 Redis 每次领回时自动累加的 |
| ③ | `XCLAIM` 领回所有权 | 待确认表里的消息**不一定读得出来**，得先让它成为你的，才能转投 |
| ④ | `XADD` 到 `trip-dead` + 原流 `XACK` | 不划账的话 PEL 会**无限堆积** |
| ⑤ | 告警 + 人工闭环 | 看消息体和日志定位：bug 修完重投，脏数据登记结案 |

#### 唯一需要你拍板的策略

> **重试次数定多少？** 这是在「重试的耐心」和「坏件滞留的时间」之间做平衡。本例取 **3 次**。

#### 为什么要有「先领回」这一步

因为 **PEL 里的消息只记录了 ID 和投递信息，不一定能直接读出完整内容**。必须先 `XCLAIM` 把所有权转过来（本例转给 `sweeper`），才能拿到完整消息体去转投。

### 2.7 削峰填谷：晚高峰怎么扛

一句话总结：

> **上游照单全收，下游匀速消化。**

#### 算一笔账

| 指标 | 数值 |
|---|---|
| 晚高峰入口 | **10,000 请求/秒** |
| Redis `XADD` 追加写 | 这个量级**毫无压力**，照单全收 |
| 消费者消化速度 | **2,000 条/秒**（匀速） |
| 积压速度 | 8,000 条/秒 |
| 一次 10 分钟洪峰 | 积压达到**几十万条** |
| 清空积压耗时 | 约 **50 分钟 ~ 1 小时** |
| 积分 / 画像的更新延迟 | 最晚 **半小时 ~ 1 小时** |

**结果**：积分和画像晚一点更新，但**系统不崩**。这就是削峰填谷。

```
改造前：
QPS 10k ┤        ██
        │       ████
   2k   ┤ ▁▁▁▁▁██████▁▁▁▁▁▁      ← 穿破数据库上限 💥
        └──────────────────────▶

改造后：
QPS 10k ┤        ██             ← 上游：全部写进流
        │       ████
        │      ██████
        │     ████████
   2k   ┤▁▁▁▁██████████████▁▁▁▁  ← 下游：恒定 2000/s 匀速消化
        └──────────────────────▶
             洪峰被「掰」成了匀速
```

> **这个柜子，把洪峰掰成了匀速。**

#### 两个必须注意的点

| # | 注意点 | 原因 |
|---|---|---|
| 1 | **上游也要限流** | 网关限制单机 QPS，**别让洪峰先打垮叫车服务本身**；队列只是缓冲，不是免死金牌 |
| 2 | **容量要提前算** | `洪峰量 ÷ 消化速度 = 积压时长`。超过业务容忍度，就提前加消费者（组内加 worker） |

### 2.8 对账：改造前后到底变了什么

| # | 维度 | 改造前 | 改造后 |
|---|---|---|---|
| 1 | **接口耗时** | **3.2 s** | **1.2 s**（砍掉的全是用户不想等的） |
| 2 | **积分服务挂 1 小时** | 叫车事件**全部失败** | 叫车**完全不受影响**，恢复后还能追着消费补齐 |
| 3 | **晚高峰上万 QPS** | 直捅数据库，崩溃 | 排队消化，匀速处理 |
| 4 | **加新下游（风控）** | 改叫车服务代码、发版 | 自己订阅，叫车侧 **0 改动** |
| 5 | **消息可靠性** | 一步失败，全部回滚 | 自动重试 + 死信兜底 |
| 6 | **代价** | 无 | 积分/画像从「当场完成」变成「晚一段时间完成」 |

> 第 6 行是**固有的代价**，不是 bug。而在「用户当下就要叫到车」这个场景里，这点延迟影响不大。

## 3. 第三章 可靠性：不丢失 / 不重复 / 不乱序

> 作者的定位：**「快」只是一个副产品，「挂了也不怕」才是主菜。**

消息队列要闯三关：**不丢失、不重复、不乱序**。

### 3.1 第一关：不丢失（三道防线）

```
 ①发送端              ②存储端 Broker          ③消费端
 XADD 超时            掉电 / 宕机             处理到一半断电
 消息没进柜             ↓                     划账没发出去
    ↓                AOF 持久化 + 主从复制      ↓
 确认回执 + 失败重发    主挂了从库顶上          处理完才 XACK
 拿到 ID 才算数                               没 XACK 留在 PEL，重启再处理
```

#### 防线一：发送端 —— 确认回执 + 失败重发

`XADD` 的返回值就是**消息 ID**：

```java
try {
    RecordId id = redis.opsForStream().add(...);   // 拿到 ID 才算真进流
} catch (Exception e) {
    retryOnce();                                    // 没拿到就重发一次
}
```

> 类比：**寄件人必须看到柜门「正关上」，他才走。**

#### 防线二：存储端 —— AOF 持久化 + 主从复制

Redis 在这里的手段是：

| 手段 | 作用 |
|---|---|
| **AOF 持久化** | 写操作先记到 AOF 日志，**再应答** |
| **主从复制** | 从库再复制一份，**主库挂了从库顶上** |

**代价也要说清楚**：

```conf
appendonly yes
appendfsync everysec     # 每秒刷一次盘
```

> 极端掉电时，**最多丢最后一秒的数据**。

**这正是 Redis 队列和专职 MQ 拉开差距的地方**：

| 产品 | 极端情况下会丢吗 | 代价 |
|---|---|---|
| **Redis Stream** | 可能丢**最后 1 秒** | 简单、够快、不用多维护一套 |
| **Kafka / RocketMQ** | 能做到**一条不丢** | 吞吐和复杂度都要付出代价 |

#### 防线三：消费端 —— 处理完才划账

```java
profileService.update(tripId);        // 先干活
redis.opsForStream().acknowledge(...); // 再 XACK
```

没 XACK 的消息**挂在 PEL 待确认表**里，重启后重新读出来再处理。

> **在划账之前，这条消息都不算处理完。**

#### 三道防线的结论

> 三道防线配齐，Redis 队列在**极端情况下最多丢最后刷盘的那一秒**。
>
> 所以：**资产损失级别的业务，不要用 Redis 队列**，用专职 MQ；**通知、积分这类丢一条也能接受的业务，Redis 刚刚好**。

### 3.2 第二关：不重复（幂等三板斧）

> 不丢的代价，就是**可能会重复**。所以必须用幂等机制兜住。

#### 第一板斧：Redis 查重

就是 2.5 那段 `setIfAbsent` 代码。**能拦住大多数重复**。

#### 第二板斧：数据库唯一索引

给积分流水表的 `trip_id` 加唯一约束：

```sql
CREATE TABLE point_flow (
    id       BIGINT PRIMARY KEY AUTO_INCREMENT,
    trip_id  VARCHAR(32) NOT NULL COMMENT '行程号',
    points   INT         NOT NULL,
    created  DATETIME    DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_trip (trip_id)      -- 同一行程只允许一条积分流水
);
```

第二条重复消息插入时**直接报错**，捕获后跳出即可。**Redis 挂了它也拦得住**——这就是兜底。

#### 第三板斧：状态机（带条件的更新）

不依赖 Redis，也不依赖额外唯一索引，**全靠数据库自带的行锁 + 你的 SQL**。

```sql
-- ❌ 普通写法：重复来两次，就执行两次
UPDATE orders SET status = '已发货' WHERE id = 123;

-- ✅ 状态机写法：加前置条件
UPDATE orders SET status = '已发货' WHERE id = 123 AND status = '已支付';
```

| 第几次 | 数据库里的状态 | `WHERE status='已支付'` | 结果 |
|---|---|---|---|
| 第 1 次 | 已支付 | ✅ 满足 | 更新为已发货，影响行数 1 |
| 第 2 次（重复） | **已发货** | ❌ 不满足 | 什么都不改，**影响行数 0**，天然跳过 |

> **稳定、零成本。**
>
> 适用前提：**业务对象本身就有状态流转**（订单的已支付 → 已发货）。

#### 三板斧怎么配合用

| 业务类型 | 推荐组合 | 理由 |
|---|---|---|
| **有状态流转**（订单、行程） | **第三板斧** | 最低成本、最稳，一行 SQL 解决 |
| **无状态但怕出事**（扣钱、加积分） | **第一 + 第二板斧** | 双重保险 |
| **通知类**（发短信、推消息） | **只上第一板斧** | 用 Redis 轻量挡一下就够了 |

### 3.3 第三关：不乱序

#### 好消息：Redis 单流天然有序

消息 ID 是 `毫秒时间戳-序号`，**先 ADD 的永远排在前面**。

#### 真正的乱序来源：分区并行

专职队列（比如 Kafka）为了吞吐，会把**一个 Topic 拆成很多 Partition 并行处理**——**并行才是乱序的来源**。要保序，就得**按业务 key 分区**（同一订单/同一行程永远进同一个分区）。

> 📌 这部分属于产品范畴，作者说以后讲 Kafka 时再展开。

#### Redis 真正的坑：消费端的多个 worker

```
worker-1 拿到「接单」  ─┐
worker-2 拿到「行程结束」─┴─▶ 谁先干完？不一定
```

**解法：要严格顺序，就一组一个工人。**

```
一个消费者组 = 一个 worker
单线程消费，一条处理完才取下一条
```

> **顺序和吞吐，只能二选一。这是物理规律。**

#### 什么时候才真的需要顺序？

| 场景 | 需要顺序吗 | 原因 |
|---|---|---|
| 行程状态流转（先接单 → 后结束） | ✅ 需要 | 消息之间有**前后依赖** |
| 账户流水（先加后减） | ✅ 需要 | 顺序错了余额就错了 |
| 两条推送通知 | ❌ 不需要 | 谁先到谁后，用户根本不关心 |

> **判据只有一条：消息之间有没有前后依赖。** 没有依赖，就别为了顺序牺牲并行度。

## 4. 第四章 生产与选型：三大 MQ 与 Redis 的边界

### 4.1 三个产品，三个出身

#### Kafka —— 数据管道

> 类比：**别把消息当成一封信，要当成一股水流。**

LinkedIn 当年每天有**上亿条用户行为日志**要搬运，传统消息队列直接趴下。Kafka 的思路是：

- **顺序写磁盘** + **成批搬运**
- 单集群每秒能处理**上万到上百万条**
- 快到飞起来

**代价**：它生来是搬日志的，**不太关心「这一条有没有被处理完」**。业务消息要的回执、重试、死信，**都得你自己在上面搭积木**。

**典型场景**：日志采集、数据管道、流式处理。

#### RocketMQ —— 业务消息专家

阿里「双 11」交易链路孵化的产品。订单、支付、库存要的东西它**全都有**：

| 能力 | 解决的业务问题 |
|---|---|
| **事务消息** | 下单和扣库存，要么都成，要么都不成 |
| **延迟消息** | 30 分钟未支付自动关闭订单 |
| **消息轨迹** | 这条消息谁发的、谁消费的，全程可查 |

- Java 写的，**Java 团队看源码毫无障碍**
- 吞吐**十万级**，不如 Kafka 极致
- 但业务消息要的可靠性，**开箱即用**

#### RabbitMQ —— 灵活路由的老将

- **路由规则最丰富**：一条消息可以按规则**同时投给多个队列**，复杂分发逻辑一行配置
- 管理界面友好，**入门简单**
- 吞吐**上万级**
- 中小系统常见；超大规模场景不合适

### 4.2 四大 MQ 选型对比

> 前三列均为视频原意；**Pulsar 那一行是 📌 补充**（视频未提及，但选型时绕不开）。

| 维度 | **RabbitMQ** | **RocketMQ** | **Kafka** | **Pulsar**（📌 补充） |
|---|---|---|---|---|
| 出身 | Erlang，AMQP 老牌 | 阿里双 11 交易链路 | LinkedIn 日志管道 | Yahoo，云原生时代 |
| 定位 | 灵活路由 | 业务消息专家 | 数据管道 / 流平台 | 存算分离的消息平台 |
| 吞吐（量级） | **万级** | **十万级** | **百万级** | 百万级 |
| 消息模型 | Exchange + Queue | Topic + Queue | Topic + **Partition** | Topic + Partition + Segment |
| 延迟消息 | 插件实现 | **原生支持**（多级延时） | 不支持（需自建） | 原生支持 |
| 事务消息 | 弱（靠 confirm） | **原生支持** | 仅幂等写 + 事务写 | 支持 |
| 死信队列 | **原生 DLX** | 原生 | 无原生（自己建 Topic） | 原生 |
| 顺序消息 | 单队列有序 | **分区有序** | **分区有序** | 分区有序 |
| 消息回溯 | 弱 | 支持按时间回溯 | **强（按 Offset 重放）** | 强 |
| 运维复杂度 | 低 | 中 | 中高 | 高（需 BookKeeper） |
| 典型场景 | 中小系统、复杂路由 | 电商交易、金融 | 日志、埋点、流计算 | 多租户、大规模云原生 |

### 4.3 Redis 队列的三条边界

什么时候该换成专职 MQ？

| # | 边界 | 具体问题 |
|---|---|---|
| 1 | **消息全在内存** | 堆积**几百万条**，内存就紧张；Kafka 这类写硬盘的，堆一年也不怕 |
| 2 | **持久化有秒级窗口** | `appendfsync everysec`，极端掉电**丢最后一秒**；**资产损失级别的业务不能接受** |
| 3 | **高可用要自己搭** | 主从切换要人工或哨兵；专职 MQ **自带集群、自动切换** |

### 4.4 那什么时候 Redis 队列刚刚好？

| 条件 | 说明 |
|---|---|
| 每天**几万到几十万条** | 量级不大 |
| 公司**本来就有 Redis** | 不用新装一套中间件 |
| **丢几条也能接受** | 通知、积分、画像这类 |

> 收益：**省掉一整套中间件的部署和监控值班**。中小系统非常划算。

### 4.5 判断线只有一句话

> **这个消息丢了，会赔钱、会造成很大损失吗？**
>
> **会 → 用专职 MQ；不会 → Redis 够用了。**

```
                 消息丢了会赔钱吗？
                   /            \
                 会              不会
                 │                │
        ┌────────▼───────┐   ┌───▼────────────┐
        │ 专职 MQ         │   │ Redis Stream    │
        │ Kafka/RocketMQ │   │ 通知/积分/画像   │
        │ 事务/延迟/回溯   │   │ 几万~几十万条/天 │
        └────────────────┘   └────────────────┘
```

### 4.6 画等号：概念是通用的，产品只是实现

今天学的**三个角色、消费者组、位点、划账、幂等、死信**，搬到 Kafka / RocketMQ 里，**一个词都不用换**。

只是 API 名字不同：

| 概念 | Redis Stream | Kafka |
|---|---|---|
| 发消息 | `XADD` | `send()` |
| 签收 | `XACK` | `offset commit` |
| 位点 | `last-delivered-id` | `offset` |
| 消费组 | Consumer Group | Consumer Group |
| 死信 | 自己建 `trip-dead` 流 | 自己建 DLQ Topic |

> **先学原理，再学产品。** 原理学会了，产品只是换个 API。

### 6.1 Redis Stream 命令

| 命令 | 作用 | 本课用法 |

## 7. 动手路线：4 段代码 + 3 个实验

四段代码按顺序敲：① `TripService.createTrip` 里的 `opsForStream().add`（验证 3.2s → 1.2s）；② `ProfileConsumer` 的 `read(Consumer.from(...), ReadOffset.lastConsumed())` + `acknowledge`（验证位点前移）；③ 加 `setIfAbsent(key,"1",Duration.ofHours(24))`（验证同一 tripId 只生效一次）；④ `DeadLetterSweeper` 的 `pending` + `claim` + `add("trip-dead")`（验证 3 次失败进死信）。

```bash
# 实验一：停掉消费者，灌 10 万条，看堆积
for i in $(seq 1 100000); do
  redis-cli XADD trip-created * tripId T$i riderId R1 > /dev/null
done
redis-cli XLEN trip-created                      # 看到 10 万
redis-cli XPENDING trip-created profile-group    # 看到挂账

# 实验二：消费一条但不 XACK，重启消费者 → 它会被再次投递（至少一次）
redis-cli XPENDING trip-created profile-group - + 10

# 实验三：造一条必失败的消息，3 个周期后它出现在 trip-dead，同时收到告警
#   if (tripId.startsWith("BAD")) throw new RuntimeException("脏数据");
```

> 📌 上线前还必须补三件事：**流裁剪**（`XTRIM trip-created MAXLEN ~ 1000000`）、**堆积监控**（`XLEN`/`XPENDING`，要看「积压时长」而不只是条数）、**消费者优雅停机**（停机前处理完手上这批再退出）。

## 8. 面试自测题（含答案）

**Q1：消息队列解决什么问题？**
异步、解耦、削峰。**注意：它不解决并发，也不减少总工作量**，它改变的是「谁在什么时候等」。

**Q2：为什么五步同步调用会「又慢又脆」？**
耗时是**加法**，可用性是**乘法**。5 个 99% 串起来就只剩 95%——一天里总有段时间会挂。

**Q3：位点和 PEL 分别保证什么？**
位点（offset）保证**不漏**：没读过下次还会读。PEL（挂账单）保证**不丢**：领了件没签收的还在，能再领出来处理。

**Q4：为什么必须先 XACK 才算处理完？**
因为「处理完但没签收」这段时间如果进程崩了，队列会以为你做完了，**这条消息就永远丢在半路**。宁可多签一次，不能丢。

**Q5：重试为什么必须有上限？**
暂时故障（网络抖动、DB 重启）重试有效；代码 bug / 脏数据重试 1 万次也没用，还会挡住后面的消息。所以要**投递计数 + 死信兜底**。

**Q6：幂等三板斧分别适合什么？**
Redis `SET NX`（轻量、挡多数）、数据库唯一索引（兜底、抗 Redis 宕机）、状态机条件更新（零成本、要求业务有状态流转）。

**Q7：Redis 队列会不会丢消息？**
三道防线配齐后，**最多丢最后刷盘的那 1 秒**（`appendfsync everysec`）。所以资产级业务不要用。

**Q8：Redis 单流有序，那为什么还会乱序？**
坑在消费端：**组内多个 worker 并行消费**，谁先干完不一定。要严格顺序就**一组一个工人**。

**Q9：什么时候从 Redis 换到 Kafka / RocketMQ？**
三条边界：**堆积几百万条（内存）**、**不能容忍丢 1 秒（持久化）**、**要高可用自动切换（运维）**。判断线：**丢了会赔钱吗？**

## 9. 📌 补充：视频没细讲但一定会踩的坑

> 以下均为原讲解之外的延伸，按重要性排序。

### 9.1 视频里那笔削峰的账，口径要看清

按视频给的数字：入口 10,000 QPS，消费 2,000 QPS，积压速度 8,000 条/秒。**如果洪峰真的持续 10 分钟**，积压应该是 `8,000 × 600 ≈ 480 万条`，按 2,000/s 消化需要约 **40 分钟**。

视频里说的是「几十万条、50 分钟到 1 小时」。这更像是**峰值只持续很短时间（比如 1~2 分钟）**、或者按「万级请求里只有一部分是行程事件」估算的口径。

**真正要带走的是公式，不是数字**：`积压量 = (入口 QPS − 消费 QPS) × 洪峰持续秒数`，`清空时长 = 积压量 ÷ 消费 QPS`。上线前拿这三个数算一遍，比记任何结论都有用。

### 9.2 `XPENDING` + `XCLAIM` 的真实语义差异

视频里用的是「先 `XPENDING` 查、再 `XCLAIM` 领」。实际生产中还有更省事的 **`XAUTOCLAIM`**（Redis 6.2+）：**一次调用完成「扫描空闲超时的消息 + 转移所有权」**，不用自己算 ID——`XAUTOCLAIM trip-created profile-group sweeper 60000 0-0 COUNT 10`。

一个补充：`XPENDING` 返回的只是**摘要**（ID、消费者、空闲时长、投递次数），**不含消息体**。要看内容又不想记投递次数，用 `XRANGE` 按 ID 精确读；要正式转投，才用 `XCLAIM`。

### 9.3 幂等键 TTL 设 24 小时的隐含假设

24 小时能挡住重复，前提是「**同一条消息的重复投递不会晚于 24 小时**」。如果业务里有跨天补偿、离线重放、人工重投，**幂等键可能已经过期**，重复就漏过去了。所以：通知类 24 小时够用；**积分、账务必须再加数据库唯一索引做最终判据**，Redis 只当第一层加速。

### 9.4 死信不是垃圾桶

死信队列最常见的死法：**只进不出**。三个月后 `trip-dead` 里躺着几十万条，没人敢动，也不敢删。最低要求：**要有监控告警**（数量突增就是事故信号）、**要有 TTL 或归档策略**、**要有重投工具**（别靠人肉 `XADD` 复制，字段容易搞错）。

### 9.5 消费端别用 `while(true)`

视频里的死循环是为了讲清「读 → 干活 → 划账」三步。生产写法是 Spring Data Redis 的 `StreamMessageListenerContainer`：`container.receive(Consumer.from("profile-group","worker-1"), StreamOffset.create("trip-created", ReadOffset.lastConsumed()), this::handle)`，在回调里做业务 + XACK。

`@PostConstruct` 里的 `while(true)` 会**占死一个启动线程**，而且**没法优雅停机**——停机时手上那批消息没签收，全部变重投。

### 9.6 一个容易忽略的坑：消费组不能「重读历史」

`XREADGROUP` 用 `>` 时只读**新消息**。如果建组时想从头消费（比如新上线一个下游要补历史数据），必须显式指定起始 ID：

```bash
# 建组时把位点设到 0，才能消费到已有的全部历史
XGROUP CREATE trip-created risk-group 0 MKSTREAM
```

**上线新风控服务时最容易踩这个坑：订阅了，但一条历史消息都收不到。**

### 9.7 顺序消息的边界：一组一工人 ≠ 全局有序

「一组一个工人」只能保证**这一组内的处理顺序**。如果上游是多实例并发 `XADD`，**消息进入流的顺序本身就是不确定的**——流有序，不代表业务事件的发生顺序有序。

要真正确保「先接单后结束」，得让**同一个业务实体的事件由同一个生产者顺序发出**（或者用「实体 ID 作为分区键」的思路）。

### 10.2 📌 补充：11 集其实是一条「从扛住到扛久」的路

把合集摊开看，这 11 集并不是 11 个孤立的技术名词，而是一条越来越难的线：

| 集 | 主题 | 回答的问题 | 与消息队列的关系 |
|---|---|---|---|
| EP01 | Redis | 缓存怎么扛住读流量 | **本集实战就用 Redis Stream**，位点/PEL 是 Kafka 的简化版 |

| EP06 | 高并发架构 | 流量怎么分层拦截 | MQ 是「最后一层缓冲」 |
| EP07 | 高可用架构 | 单点怎么消除 | MQ 的副本、主从、自动切换就是高可用的样本 |
| EP08 | 高性能架构 | 怎么把延迟压下去 | **异步是降延迟最便宜的手段**（本集 3.2s → 1.2s） |

| EP10 | 区块链架构 | 多方不互信怎么达成一致 | 与 MQ 相反：一个求「最终一致」，一个求「共识一致」 |
| **EP11** | **消息队列** | **必须现在做的事，怎么变成之后再做** | **收口的一集：前面所有「解耦 / 削峰 / 异步」的落地工具** |

一条主线可以这么记：

```
扛住流量（EP01/02/06/08）
   → 拆开系统（EP03/04）
   → 拆开之后要能解耦、能异步（EP11）
   → 系统要能扛久、能自治（EP07/09/10）
```

**消息队列恰好是这条线上「承上启下」的那一环**：往上，它承接高并发与微服务的拆分；往下，它把「可靠性」这件事推到了台前——**不丢、不重、不乱，三条都是硬功夫**。

### 10.3 四句话复盘整堂课

| 问题 | 答案 |
|---|---|
| 它是什么 | 一个独立运行的中转程序：发送方塞进去就返回，接收方按自己节奏取 |
| 它解决什么 | 异步（慢）、解耦（脆）、削峰（崩）——**治的是「排队」这个结构** |
| 它的代价 | 一致性窗口、可能重复、可能积压、多一套运维 |
| 什么时候别用 | 要立刻拿到结果、只有一个系统、流量本来就平稳 |

## 11. 一句话总结

> **消息队列不解决并发。它只是把「必须现在做完的事情」，变成「可以之后慢慢去做好的事情」。**
>
> **它换掉的不是一个组件，而是一个结构：从「所有事挤在一个管道里同生共死」，换成「各走各的道，各按各的节奏」。**
>
> **而它换来的三样东西——主链路飞快、故障隔离、洪峰缓冲——代价是及时性、一致性和简单性。**
>
> **这笔账在每个系统上算出来都不一样。所以用不用它，是一个架构决策，不是默认操作。**
