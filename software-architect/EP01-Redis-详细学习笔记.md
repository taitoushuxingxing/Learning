## 0. 课程地图：Redis 不是一个数据库，是一个工具箱

### 0.1 一句话定位

> **Redis 不是一个数据库，它是一个工具箱。**

数据库的职责是「保证数据正确」，Redis 的职责是「替数据库扛住它不该扛的事」。这个认知贯穿全课，也是最后一页总结的核心。

### 0.2 六层抽屉

课程用「打开工具箱的 6 层抽屉」来组织，每一层都遵循同一个讲解套路：

> **先问「如果不用 Redis 会出什么事故」→ 看事故现场 → 再给解法**

这样记住的不是「Redis 有哪些名词」，而是「Redis 到底解决了什么问题」。

| 抽屉 | 章节 | 核心问题 | 关键词 |
|---|---|---|---|
| 第 1 层 | 第一章 | Redis 是什么？能干什么？ | 内存、单线程、五大数据类型 |
| 第 2 层 | 第二章 | 数据怎么自动过期？缓存翻车了怎么办？ | 过期策略、淘汰策略、穿透/击穿/雪崩 |
| 第 3 层 | 第三章 | 几十台机器抢一个库存，怎么保证只有一个成功？ | **分布式锁**（本课重点） |
| 第 4 层 | 第四章 | 怎么让多条命令变成一个不可打断的动作？ | **Lua 脚本**、原子性 |
| 第 5 层 | 第五章 | 一秒涌进 10 万个请求，数据库怎么活下来？ | **消息队列**、削峰填谷 |
| 第 6 层 | 第六章 | Redis 自己挂了怎么办？ | 持久化、主从、哨兵、Cluster |

### 0.3 全课的知识闭环

```
问题复杂度递进：
单机缓存（第1-2章） → 单条数据的并发正确性（第3-4章） → 系统级流量（第5章） → 基础设施自身可靠性（第6章）
```

这四步恰好是一个后端工程师从「会写业务代码」到「能设计系统」的成长路径。

## 1. 第一章 内存数据库：它是什么、为什么快、能装什么

### 1.1 开场事故：一个 3 秒的订单列表页

假设你毕业后进公司，第一个需求是给后台做**订单列表页**。产品经理说「再加两个筛选条件」，你改完上线，测试跑过来说：**这页面打开要 3 秒。**

你去查，索引加了，SQL 也优化了，为什么还是 3 秒？把每段耗时打出来：

| 环节 | 耗时 | 说明 |
|---|---|---|
| 重复查询数据库 | **2.4 s** | 页面每刷新一次，就把同样的 200 条数据重查一遍 |
| 语句解析 | 0.4 s | 每次都要重新解析、优化、执行 |
| 网络返回 | 0.2 s | 数据传输 |
| **合计** | **3.0 s** | |

**问题不在 SQL 写得对不对，而在于同一个结果被反复算了几百遍。**

再追问一句：这些数据里是不是有一半以上根本不会变？商品名字会变吗？三个月前的订单金额会变吗？——基本不会。**既然算一次就够了，为什么要算 100 次？**

答案就出来了：**把算好的结果放到一个地方存起来。** 那个地方就是 Redis。

### 1.2 加了 Redis 之后，链路变成什么样

```
不加缓存：
用户 → 应用服务器 → MySQL
                     ↑ 每次都打过来，100ms 起

加了缓存：
用户 → 应用服务器 → 先问 Redis
                    ├─ 命中（1ms）→ 直接返回，MySQL 完全没人打扰
                    └─ 未命中 → 问 MySQL（100ms）→ 顺手写回 Redis → 返回
```

这就是那 3 秒的来源：**1ms 和 100ms，差 100 倍。**

### 1.3 名字就是线索：REmote DIctionary Server

把 Redis 的全称拆开，三个词全是线索，每一个都直接对应后面的一章：

| 词 | 含义 | 对你的实际影响 |
|---|---|---|
| **Remote**（远程） | 它是一个独立的软件，跑在另一台机器上，**不是你程序里的一个 jar 包、一个库** | 你要装它、连它，**它会挂**，也要运维它 → 对应第 6 章高可用 |
| **DIctionary**（字典） | 存东西的方式极简：给一个 key，还你一个 value。**没有表结构，没有 SQL，不用建库建表** | 心智模型和 MySQL 完全不同 |
| **Server**（服务器） | 它是一个长期运行的进程，**会满、也会崩** | 会满 → 第 2 章淘汰策略；会崩 → 第 6 章持久化 |

### 1.4 为什么快：三层原因，不是一句「因为在内存里」

很多人只答得出第一层，面试就到此为止了。完整答案是三层：

#### 第一层：内存 vs 磁盘（数量级差距）

作者用图书馆打比方：

- **内存 = 你正在用的那张书桌**：笔、书、草稿纸都摊在桌上，抬手就能拿到。但桌面有限，放不下全部东西；**而且闭馆你人一走，桌上的东西就被清掉了**（这就是「断电即失」）。
- **磁盘 = 堆满资料的书柜**：东西全都在，但你要走过去、拉开柜门、翻目录、抽出来、再翻到想要的那一页——慢，但容量大，**而且你走了它还在**。

正确做法：**常用的那一份放桌面，书柜留全部资料。这就是缓存的思想。**

三个数字，感受量级（不用背）：

| 介质 | 一次随机读取耗时 |
|---|---|
| 内存 | 100 ns |
| SSD | 100 µs |
| 机械磁盘 | 10 ms |

**最慢比最快慢约 10 万倍。** 注意这是**数量级**的差距，不是「快一点点」。

#### 第二层：SQL 查询要走的流程太多

一条 SQL 的完整生命周期：建立网络连接 → 语法解析 → 优化器挑执行计划 → 加锁 → 事务处理 → 从磁盘页读数据。

而 Redis：**一次网络往返 + 一次哈希查表**，就两步。

#### 第三层：单线程（反直觉，但恰恰是它快的原因）

所有命令排队，一个接一个执行。**没有线程切换开销，也没有锁竞争。**

> 常见疑问：单线程不是应该更慢吗？
> **单线程 ≠ 慢。** 在纯内存操作下，省掉上下文切换和锁竞争，反而更快，而且**行为完全可预测**。

**但它有真实代价**：单个命令不能执行太久。这正好解释了后面两件事：
- 为什么 Lua 脚本必须写短（第 4 章）
- 为什么不能在生产上敲 `KEYS *`（会阻塞全站）

### 1.5 五大数据类型：五个比喻 + 一句口诀

这一页作者说「希望大家闭上眼睛都能想起来」。

| 类型 | 比喻 | 结构 | 典型场景 |
|---|---|---|---|
| **string** | 一个变量（像 `int a = 5`） | 1 key → 1 value | 验证码、token、计数器，**最常用** |
| **hash** | 一个对象（像 `new User()`，有 name/age/city） | 1 key → 多个 field:value | 商品详情、用户信息、购物车 |
| **list** | 一根管道 | 两头都能进出，天然有序 | 可当栈，也可当队列；最新消息列表 |
| **set** | 一个不能重复的集合 | 塞 100 遍「张三」，里面只有 1 个张三 | 去重、交集（共同好友） |
| **zset** | 一个排行榜 | 每个元素带一个分数，**按分数自动排序** | 热搜榜、Top 10、**延迟队列** |

**口诀（作者原文）：**

> 单个值用 **string**，对象用 **hash**，排队用 **list**，去重用 **set**，排名用 **zset**。

**随堂思考题**：微信朋友圈的**点赞列表**用哪个？
答案是 **set**——你不能重复点两次赞，但也不需要排序。

### 1.6 命令 × 场景对照表（建议截图）

> 横着看是命令，竖着看是场景。作者说「这张表大家也可以把它拍下来」。

| 类型 | 核心命令 | 典型场景 | 为什么选它 |
|---|---|---|---|
| **string** | `SET` `GET` `INCR` `DECR` | 短信验证码、登录 token、接口限流计数 | 写入时可顺手带过期时间；自增天生不重复 |
| **hash** | `HSET` `HGET` `HINCRBY` | 商品详情、用户信息、购物车 | 可以只改单个字段，不用整体读写 |
| **list** | `LPUSH` `RPOP` `BRPOP` | 最新消息列表、简单任务队列 | 天然有序，两头进出 |
| **set** | `SADD` `SISMEMBER` `SINTER` | 点赞去重、抽奖池、共同好友 | 天然去重，集合运算一行搞定 |
| **zset** | `ZADD` `ZRANGE` `ZRANGEBYSCORE` `ZINCRBY` | 排行榜、**订单超时取消** | 带分数自动排序，可按分数区间查询 |

#### 重点追问：为什么商品详情用 hash，不用 string 存一整坨 JSON？

假设商品有 50 个字段，你只想改「库存」这一个：

**用 string 存 JSON（错）**：
```
1. 读出整个 JSON（50 个字段全拉过来）
2. 反序列化解析
3. 改一个值
4. 序列化
5. 整个写回去
```
5 步，而且有并发覆盖风险。

**用 hash（对）**：一条命令搞定。
```bash
HSET product:1001 stock 99
```

#### 重点追问：zset 怎么做「订单超时取消」？

这是全课最巧妙的一个设计，作者说「很真实，用得非常常见」：

```
元素 = 订单号
分数 = 到期时间戳
后台任务每秒扫一遍：ZRANGEBYSCORE orders:timeout 0 <now> → 取出来的全部取消掉
```

这叫**延迟队列**——凡是「按时间排序」的需求，用 zset 天然就能解决。
底层是**跳表**，按分数取前 N 名非常快。

### 1.7 三段真正能跑的代码

#### ① 手机验证码（5 分钟有效）

**传统做法**：建表存验证码 + 发送时间，写定时任务每分钟扫一遍删过期的。麻烦，而且扫表本身还占用数据库资源。

**Redis 做法**：一条命令。
```bash
# key = 手机号，value = 验证码，300 秒后自动消失
SET code:13800138000 8674 EX 300
```

> 过期这件事 Redis 自己管，**你一行清理代码都不用写**。

**延伸：一分钟只能发一次**
```bash
SET code:13800138000 8674 NX EX 60
```
`NX` = 不存在才设置。第一次发成功，60 秒内再发直接失败。**一条命令搞定防刷。**

#### ② 阅读量（原子自增）

**MySQL 做法**：
```sql
UPDATE article SET views = views + 1 WHERE id = 1001;
```
一篇文章爆了，一秒 1 万人看，这一行数据被反复加锁，所有写请求排队等。

**Redis 做法**：
```bash
INCR article:view:1001
```
`INCR` 是**原子**的，1 万个并发请求同时加，最终结果**不多不少**。这就是 Redis 在计数场景最重要的价值。

#### ③ 全局唯一单号（发号器）——注意这里有坑

```bash
INCR order:sequence
```

`INCR` 天生自增、天生不重复，看起来完美。**但作者特意标了一个提醒：**

> ⚠️ **Redis 重启可能丢号。** 如果没开持久化，重启后计数从头开始，产生的订单号会**重复**。

生产上一般用 **时间戳 + Redis 步长**，或者干脆用**雪花算法（Snowflake）**。

> 这里不是让你记方案，而是记一个思维习惯：**用任何工具之前，先想清楚它在什么情况下会出错**——尤其是重启、宕机这种情况。

### 1.8 三个「小题大做」的结构（了解即可）

这三个结构面试可能问到，共同思路是：**用极小的空间，解决一个特定的统计问题。**

| 结构 | 原理 | 省多少空间 | 场景 |
|---|---|---|---|
| **Bitmap**（位图） | 1 个 bit 存一个人的状态。8 号签到 → 第 8 位置 1；`BITCOUNT` 数有几个 1 | 100 万用户只占 **125 KB** | 签到、活跃用户统计 |
| **HyperLogLog** | 不存元素，只**估算**有多少个不同的 | 固定 **12 KB**，误差约 **0.81%** | UV 统计（一亿用户也才 12KB） |
| **GEO** | 底层还是 zset，把经纬度编码成分数 | 省掉自建空间索引 | 附近的人、附近门店、外卖骑手距离 |

> HyperLogLog 的哲学：**用一点点精度损失，换巨大的空间节省，非常划算。**

## 2. 第二章 过期与缓存：会自己清理，还要不翻车

本章两件事，**注意它们是两件不同的事**：
1. **给单个 key 设过期**（微观）
2. **内存整体满了怎么办**（宏观）

### 2.1 单个 key 的过期

```bash
SET code:xxx 1234 EX 300     # 写入时直接带过期（推荐）
EXPIRE key 300               # 事后补设
TTL key                      # 查还剩几秒
```

`TTL` 的两个特殊返回值，面试常考：

| 返回值 | 含义 |
|---|---|
| `-1` | key 存在，但**没有设过期时间**（永不过期） |
| `-2` | **key 已经不存在**了 |

### 2.2 过期 key 是怎么被删掉的？两种策略配合

| 策略 | 做法 | 特点 |
|---|---|---|
| **惰性删除** | 你访问到这个 key 时，顺手检查是不是过期了，过期就删 | 不浪费 CPU，但**没人访问就一直占内存** |
| **定期删除** | 后台每秒**随机抽查**一部分设了过期时间的 key | 为什么随机？精确扫全部 key 代价太高 |

**所以要记住一个重要事实：**

> ⚠️ **过期的 key 不一定是立刻消失的。** 它可能还占着内存，直到被访问或被抽查到。

### 2.3 🔥 实战技巧：批量设过期一定要加随机值

```bash
# 不要这样（36000 秒 = 10 小时，全都一样）
EXPIRE key 36000

# 要这样
EXPIRE key $((36000 + RANDOM % 300))     # 10 小时 + 0~300 秒随机
```

**为什么？** 同一批一起写入的数据，如果过期时间完全一样，它们会在**同一秒集体消失**。那一刻数据库就会被瞬间打爆。

这个坑的名字，就叫**缓存雪崩**（见 2.5）。

### 2.4 内存满了怎么办：maxmemory + 淘汰策略

`maxmemory` 限定最多能用多少内存，超了就要按策略删掉一部分 key。

| 策略 | 含义 | 适用 |
|---|---|---|
| **noeviction**（默认） | **不删，直接对写入命令报错（OOM）** | ⚠️ 缓存场景下非常危险 |
| **allkeys-lru** | 在所有 key 里淘汰**最久没用过**的（Least Recently Used） | ✅ **纯缓存首选，最省心** |
| **allkeys-lfu** | 淘汰**访问次数最少**的（Redis 4.0 新增） | 有热点数据倾斜时更准 |
| **volatile-lru / volatile-lfu / volatile-ttl / volatile-random** | **只在设了过期时间的 key 里**淘汰 | ✅ 有不能丢的数据时必须用 |

#### 两个必须记住的点

**① 默认策略是 noeviction，不是帮你淘汰，而是报错。**
内存满了，写命令直接返回 OOM。缓存场景下这等于**缓存完全失效**，非常危险。生产上必须显式改。

**② 怎么选？**
- **纯做缓存** → `allkeys-lru`，最省心。
- **Redis 里存了不能丢的数据**（比如把 list 当队列用，消息在排队）→ **必须用 `volatile-lru`**，否则队列里的消息会被当成缓存淘汰掉。

> 作者原话：「这个坑很真实，应该是有不少人踩过的。」

⚠️ 而且注意：`volatile-*` 只作用于**设了过期时间**的 key。如果你把队列 key 设了过期时间，它照样会被淘汰——**队列 key 不要设过期时间，并用 volatile 策略淘汰其他缓存**。这是很多人忽略的细节。

### 2.5 缓存三大经典事故：穿透 / 击穿 / 雪崩

三个词长得像，尤其「穿透」和「击穿」，但**完全是三件事**。用一句话区分：

| 事故 | 一句话定义 | 关键词 |
|---|---|---|
| **穿透** | 数据**根本不存在**，每次请求都穿过缓存打到数据库 | **不存在** |
| **击穿** | **单个热点 key** 刚好失效，大量请求同时打到数据库 | **一个热点 key** |
| **雪崩** | **一大批 key** 同时失效，或整个 Redis 挂了 | **一大批** |

#### 逐个拆解 + 解法

**① 缓存穿透：查一个根本不存在的东西**

场景：数据库里 ID 只从 1 到 100，有人拿 `ID=0`、`ID=-1` 疯狂请求。缓存里没有（本来就不该有），数据库里也没有，于是**每次请求都穿过缓存直插数据库**。

> 比喻：有人拿一把假钥匙，一次一次插你的门锁。门根本打不开，但锁被磨坏了。

| 解法 | 做法 | 成本 |
|---|---|---|
| **缓存空值** | 数据库查不到也往缓存写一个 `null`，设短过期（如 60 秒） | 低，最常用 |
| **布隆过滤器** | 在缓存前面先挡掉「一定不存在」的 key（作者叫它「不存在判断器」） | 中，有误判率、不支持删除 |
| **参数校验**（最朴素） | `ID=-1` 这类请求在入口直接拦掉 | 极低，**很多事故用这一步就能避免** |

**② 缓存击穿：一个热点 key 刚好到期**

场景：某个爆款商品的缓存**刚好在这一秒过期**，1000 个请求同时来，全部发现缓存是空的，全部跑去查数据库。

| 解法 | 做法 | 代价 |
|---|---|---|
| **互斥锁** | 只让一个线程去查库回填，其他线程等一下再读缓存 | 有短暂等待，但保护了数据库 |
| **逻辑永不过期** | 热点 key **不设过期时间**，后台定时任务异步刷新 | 实现稍复杂，可能读到极短时间旧值 |

**③ 缓存雪崩：一片 key 同时消失**

场景：一大批 key 同时失效，或整个 Redis 挂掉 → 数据库被彻底压垮。

| 解法 | 说明 |
|---|---|
| **过期时间加随机值** | 错开失效时刻（第二章开头讲的那个技巧） |
| **多级缓存** | 本地缓存（Caffeine）+ Redis，Redis 挂了还有一层 |
| **Redis 高可用** | 主从 + 哨兵 + Cluster（第 6 章） |
| **数据库侧兜底** | 限流 + 降级，宁可拒绝一部分请求，也不能让数据库死 |

#### 一条架构原则

> **任何架构设计都要假设下面那一层会挂。** 缓存挂了，不能让数据库跟着一起死。所以总要有兜底策略——限流和降级。

#### 课堂小测验（面试高频）

> **问**：双 11 零点，所有商品缓存都在 0 点整写入，一小时后过期，会发生什么？

**答**：0 点整写入、1 小时后过期 → **1 点钟集体失效 → 雪崩**。
解法：过期时间加随机值。

### 2.6 缓存与数据库的一致性：Cache Aside 旁路缓存

前面讲的是「缓存怎么不翻车」，这一节讲「缓存和数据库的数据怎么对得上」。

最常用的套路是 **Cache Aside（旁路缓存）**。名字很高级，本质很简单：

> **缓存不是必经之路，你自己在代码里决定什么时候读缓存、什么时候清缓存。**

#### 读写规则

**读**：
```
1. 先查缓存 → 命中直接返回
2. 未命中 → 查数据库
3. 把结果写回缓存（回填，带随机过期时间）
```

**写**：
```
1. 先更新数据库
2. 再删除缓存     ← 注意：是删除，不是更新
```

#### 🔥 面试必问：为什么是「删除缓存」而不是「更新缓存」？

因为**并发下写缓存会留下脏数据**：

```
时刻  请求 A              请求 B
 t1   更新数据库 = 100
 t2                      更新数据库 = 200
 t3                      写缓存 = 200
 t4   写缓存 = 100        ← A 后写，缓存留下旧值 100
```

结果：数据库是 200，缓存是 100，而且**这个脏值会一直留到下次过期**。谁最后写缓存，谁决定缓存内容——但这跟「谁最后在数据库生效」不一定一致。

**删除缓存为什么就安全？**
删掉之后，下一次读自然会回源查数据库，拿到新值再回填。代价只是**那一次多查了一次数据库**，用很小的成本换掉了「长时间存在脏数据」的风险。

#### 回填时必须带随机过期时间

```java
// 伪代码
Object value = redis.get(key);
if (value == null) {
    value = db.query(key);
    // 注意：过期时间要加随机值，呼应 2.3 的雪崩
    int ttl = 3600 + ThreadLocalRandom.current().nextInt(300);
    redis.setex(key, ttl, value);
}
return value;
```

#### 进阶：删除缓存失败了怎么办？

生产做法：
- 把删除操作放进**消息队列重试**
- 或**订阅 MySQL 的 binlog**，异步补偿删除

这套机制有个名字：**最终一致性**。

#### 一个观念（作者重点强调）

> **缓存和数据库不需要时刻一致，只需要最终一致。**
> 追求强一致就要上分布式事务，成本高得多——**大部分业务根本不值得**。

## 3. 第三章 分布式锁：20 台机器抢一个库存（重点）

> 作者明说这是全课重点，也是分布式锁这个概念的「题眼」所在。

### 3.1 从一个熟悉的场景说起：synchronized 为什么失效了

写 Java 的人都知道 `synchronized`，Python 里有 `Lock`。它们保证**同一时刻只有一个线程能进那段代码**。单机下你觉得理所当然。

**但它在分布式环境下会失效。不是因为它写错了，而是因为它「管不着」。**

```
【只有 1 台服务器】
所有线程在同一个 JVM 里 → 抢的是同一把锁对象 → 互斥成立 ✅

【部署 20 台】
机器 A：synchronized 锁住了自己的 100 个线程
机器 B：synchronized 锁住了自己的 100 个线程
A 的锁和 B 的锁，互相完全不认识 → 各管各的 → 等于没锁 ❌
```

### 3.2 题眼：锁的作用域，不再匹配你的业务范围

> **程序里的锁，作用域是「一个进程」。**
> **我们需要一把作用域是「整个集群」的锁。**

那把锁要放在哪？**必须放在一个 20 台机器都能看到的地方。**

Redis 正好是这样的独立外部服务——20 台机器都能访问同一个 key。于是这把锁自然而然地放进了 Redis。

> **所以：分布式锁不是什么新发明的技术，它只是把锁挪到了一个所有人都能看得见的地方。**

#### 面试题（作者亲历被问过）

> **问**：库存服务部署了 20 台机器，其中一台的代码里写了 `synchronized`，能防止超卖吗？

**答**：**不能。** 其他 19 台看不见这把锁，作用域不匹配业务范围。

### 3.3 Redis 分布式锁的实现：SET key value NX EX

思路极简：**在 Redis 里放一个 key 代表「锁被占了」，谁能写进去谁就拿到锁，写不进去就等着或直接失败。**

但需要两个关键参数：

```bash
SET lock:stock:1001 <uuid> NX EX 10
```

| 参数 | 全称 | 作用 |
|---|---|---|
| **NX** | Not eXists | 只有 key 不存在才设置 → **天然实现互斥**。第一个人写进去，第二个人写不进去 |
| **EX** | EXpire | 设置过期时间 → **防止死锁** |

**为什么必须有 EX？**
如果程序拿到锁之后突然崩了、或者服务器断电了，这把锁就**永远不释放**，别人也永远拿不到——这就是死锁。加过期时间，等于给锁上了一道保险：程序崩了，锁几秒后自动消失，系统还能继续运转。

### 3.4 三个坑（这一节是面试的分水岭）

#### 坑 ①：先 SET 再 EXPIRE —— 两条命令之间会崩

```bash
SET lock:1001 uuid      # 第 1 条执行成功
# ↓ 就在这个瞬间，程序崩了 / 断电了
EXPIRE lock:1001 10     # 这条永远没执行
```

结果：**锁永远在，没有过期时间 → 死锁。**

✅ **正确做法：写成一条命令**，Redis 保证单条命令是原子的，中间没有任何间隙：
```bash
SET lock:1001 uuid NX EX 10
```

#### 坑 ②：直接 DEL 解锁 —— 可能删掉别人的锁（最隐蔽）

时间线：
```
t=0s   A 拿到锁，锁过期时间 30s
       A 的业务卡住了（GC、慢查询、网络抖动…）
t=30s  锁自动过期，B 拿到了新锁
t=40s  A 的业务终于跑完，执行 DEL lock:1001
       ↑ A 删掉的是 B 的锁！
t=40s+ B 以为自己还持有锁，实际上锁已经没了
       → 这时 C 也能拿到锁 → 互斥机制彻底失效
```

✅ **正确做法**：加锁时 `value` 放一个**自己生成的唯一标识**（UUID），解锁前先比对「这把锁是不是我的」。

但新的问题来了：`GET` 比对 + `DEL` 删除，**又是两条命令，中间还有空隙，还是可能被打断**。

✅ **终极解法：用 Lua 脚本把这两步合成一步**（第 4 章详讲）。

#### 坑 ③：业务执行时间 > 锁的过期时间

锁提前释放了，后面的互斥就全乱了。**这个问题光靠客户端代码解决不了**，需要**自动续期**机制 → 这就是 Redisson 的看门狗（3.6）。

### 3.5 一次抢购请求里，这把锁的「一生」

```
① 请求 A 加锁 → 成功
② 请求 B 同时来 → 发现 key 已存在 → 加锁失败
   → 可以重试，也可以直接告诉用户「稍后再试」
③ A 执行真正的业务（扣库存、生成订单）
④ A 解锁 —— ⚠️ 必须写在 finally 里！
   否则业务抛异常，锁就漏掉了
⑤ B 下一轮重试 → 成功拿到锁
```

**为什么解锁一定要用 Lua？** 再看一遍坑 ②：
```
GET（比对身份）→ 空隙 → DEL（删除）
```
这个空隙就是漏洞。Lua 脚本让整段在 Redis 里**不可打断**地执行完，空隙消失。

### 3.6 生产上不会自己手写：Redisson 的四大特性

手写锁有个绕不过去的问题：**业务超时**。先看这个矛盾：

> **问**：你怎么知道你的业务需要执行多久？
> - 设 10 秒？万一这次赶上数据库慢，业务跑了 12 秒，锁提前释放。
> - 设 60 秒？万一程序崩了，别人要干等 60 秒才能拿到锁，这一分钟所有其他请求全失败。
>
> **设长设短都可能是错的。**

#### 特性 ① 看门狗（Watchdog）—— 解决这个矛盾

- 不指定过期时间时，**默认 30 秒**
- 后台起一个线程，**每 10 秒自动续期一次**，把有效期重新拉回 30 秒
- **只要程序还活着，锁就一直有效**
- 程序真挂了 → 续期自然停止 → **锁 30 秒后自动释放**

完美解决了「业务超时」和「死锁」的矛盾。

#### 特性 ② 可重入

```java
void A() {
    lock.lock();
    B();          // B 里又去加同一把锁
    lock.unlock();
}
void B() {
    lock.lock();  // 不可重入的锁：这里死锁了，自己把自己锁住
    ...
}
```

Redisson 的锁**可重入**，内部用**计数器**记录重入了几次。底层数据结构是 **hash**：

```
key   = 锁的名字
field = 线程 ID
value = 重入次数
```

#### 特性 ③ 一整套同步器

除了普通互斥锁，还有：**读写锁、信号量（Semaphore）、倒计时门闩（CountDownLatch）**。

> 如果你用过 JDK 的 JUC 工具包，会发现 Redisson 和它**几乎一模一样**——只是从「单机版」变成了「分布式版」。会用 JUC，基本就能很快掌握 Redisson。

#### 特性 ④ 红锁（RedLock）—— 了解即可，一般别用

担心主从切换时锁丢失，于是提出：**在 5 个独立节点分别加锁，多数成功才算成功。**

听起来严谨，但**安全性至今有争议**：依赖各节点的时钟、依赖 GC 停顿时间……

> **作者建议：一般业务别用，知道有这么回事就行。**

### 3.7 Redisson 标准写法（可直接抄）

```java
RLock lock = redissonClient.getLock("lock:stock:1001");
try {
    // 只传等待时间，不传 leaseTime → 等于告诉 Redisson「用看门狗帮我续期」
    boolean ok = lock.tryLock(3, TimeUnit.SECONDS);
    if (!ok) {
        // 没抢到锁，直接返回失败，不要死等
        return Result.fail("系统繁忙，请稍后再试");
    }
    doBusiness();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} finally {
    // 判断锁是否还被当前线程持有 → 防止误删别人的锁
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

**两个关键点**：
1. `tryLock` 只传等待时间，不传 `leaseTime` → 启用看门狗
2. `finally` 里用 `isHeldByCurrentThread()` 判断 → 防误删

## 4. 第四章 Lua 脚本：把多步合成一步

前面两处都用到 Lua（解锁、扣库存），所以单独开一章。

### 4.1 反例：看起来完全正确的扣库存代码

```java
int stock = Integer.parseInt(redis.get("stock:1001"));  // ① 读
if (stock > 0) {                                        // ② 判断
    redis.decr("stock:1001");                           // ③ 扣减
}
```

逻辑看起来无懈可击，**但并发下会出错**：

```
库存 = 1
时刻   请求 A              请求 B
 t1    读到 1
 t2                        读到 1        ← 就在这一个瞬间
 t3    判断 1 > 0 ✅
 t4                        判断 1 > 0 ✅
 t5    DECR → 0
 t6                        DECR → -1
结果：库存 -1，卖出 2 件 ❌
```

#### 根源不是代码写错了

> **而是「读」和「写」之间有一个空隙。只要有空隙，高并发下就一定会有人插进来。**

### 4.2 解法：让这两步之间没有空隙

把那一段逻辑**写成脚本发给 Redis**。Redis 是单线程的，会**一口气把整个脚本跑完，中间不处理任何其他命令**。

于是判断和扣减之间**没有空隙**了。这就是**脚本的原子性**——原子性 = **不可分割**。

```lua
-- stock.lua
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then
    return -1                      -- 商品不存在
end
if stock <= 0 then
    return 0                       -- 已售罄
end
redis.call('DECR', KEYS[1])
return 1                           -- 扣减成功
```

```java
// Java 调用
DefaultRedisScript<Long> script = new DefaultRedisScript<>(luaText, Long.class);
Long r = redisTemplate.execute(script, Collections.singletonList("stock:1001"));
if (r == 1L) { /* 成功 */ }
else if (r == 0L) { /* 提示已售罄 */ }
else { /* 商品不存在 */ }
```

### 4.3 为什么用 KEYS[1] / ARGV[1] 而不是拼字符串？

作者特意强调的两个原因：

| 原因 | 说明 |
|---|---|
| **① 避免注入** | 拼字符串等于把用户输入直接塞进脚本，有注入风险 |
| **② Cluster 兼容** | 用了 Redis Cluster 后，Redis 需要**根据 key 判断这个脚本落在哪个槽**。拼进字符串它就无法识别 |

> 作者原话：「这是要养成的一个习惯。」

### 4.4 返回码约定：给程序看的结果

脚本最后返回 `1` / `0` / `-1` 三个码，这是**特意做的设计**：

| 返回码 | 含义 | 程序动作 | 给用户的提示 |
|---|---|---|---|
| `1` | 成功 | 走成功流程 | —— |
| `0` | 已售罄 | 走失败流程 | 「商品已售罄」 |
| `-1` | 异常/不存在 | 走异常流程 | 「商品不存在」 |

> **脚本的执行结果，是给程序判断用的。** 把不同失败原因用不同返回码区分开，前端才能给用户**精确的提示**——「您已经购买过了」和「商品已售罄」是完全不同的两句话，用户体验也完全不同。

### 4.5 三条纪律

| # | 纪律 | 原因 |
|---|---|---|
| 1 | 用 `KEYS` / `ARGV` 取参，不要拼字符串 | 避免注入 + Cluster 槽位识别 |
| 2 | **脚本必须短** | 脚本执行期间 Redis 阻塞，全站都在等它。写个死循环 → **整个 Redis 卡死** |
| 3 | 生产用 `EVALSHA` / `SCRIPT LOAD` | 避免每次传输整个脚本内容，也不用把脚本硬编码在代码里 |

### 4.6 ⚠️ 最重要的澄清：Lua 不是事务，它不会回滚

很多人把「原子性」理解成「要么全部成功，要么全部失败回滚」——**这是错的**。

> **Lua 脚本保证的是「不被打断」，不是「出错自动撤销」。**

所以写脚本必须遵守一个原则：**先判断，后执行**。把可能出错的部分放在前面，确保走到写操作时不会再出问题。

| | 事务（如 MySQL） | Redis Lua |
|---|---|---|
| 是否原子（不可分割） | 是 | **是** |
| 出错是否回滚 | 是 | **否（不回滚）** |
| 执行中途是否被打断 | 否 | 否 |

### 4.7 两个生产必备脚本

#### ① 一人一单（所有抢购类业务的基本要求）

```lua
-- KEYS[1] = 库存key, KEYS[2] = 已购用户集合key, ARGV[1] = userId
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2                              -- 已经买过了
end
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock <= 0 then
    return 0                               -- 已售罄
end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])       -- 记入已购集合
return 1
```

**为什么必须用脚本？**
「判断这个人买过没有」和「扣库存」必须是**一个动作**。如果在 Java 里分两步写，同一个人在并发下可能**通过两次检查，抢到两单**。

**为什么用 set 存已购用户？** 天然去重，不需要额外判断。可以给这个集合设 24 小时过期，第二天活动重新开始。

#### ② 限流（每用户 60 秒最多 5 次）

```lua
-- KEYS[1] = 限流key, ARGV[1] = 上限, ARGV[2] = 窗口秒数
local c = redis.call('INCR', KEYS[1])
if c == 1 then
    redis.call('EXPIRE', KEYS[1], tonumber(ARGV[2]))   -- 窗口第一次，设过期
end
if c > tonumber(ARGV[1]) then
    return 0                                            -- 超限，拒绝
end
return 1
```

**为什么这里必须用脚本？**
`INCR` 和 `EXPIRE` 又是两步。如果 `INCR` 之后程序崩了、没来得及设 `EXPIRE`，**这个计数器永远不会归零，用户就被永久封禁了**。

**进阶：滑动窗口**
用 zset 存每次请求的时间戳，统计「最近 60 秒内有多少个时间戳」，更精确。思路完全一样，都是「计数 + 判断」，只是窗口计算方式不同。

## 5. 第五章 消息队列：一秒 10 万请求怎么让数据库活下来

### 5.1 场景：秒杀的峰值有多恐怖

| 指标 | 数值 |
|---|---|
| 秒杀峰值 | **10 万 QPS** |
| 普通 MySQL 实例能扛 | 约 **4000 QPS** |
| 差距 | **25 倍** |
| 平时流量 | 约 5000 QPS |
| 峰值 / 平时 | **20 倍** |
| 峰值持续时间 | **仅 2 秒** |

**核心矛盾**：为了这 2 秒的峰值，去买一台超强数据库？

- 不划算：峰值一过，机器全部回归空闲
- 但普通数据库又确实扛不住这 2 秒

### 5.2 解法：把「立刻下单」改成「立刻登记，稍后处理」

```
原来的链路：
10 万请求/秒 → 数据库（只能扛 4000）→ 💥 数据库被打爆

改后的链路：
10 万请求/秒 → 写队列（内存操作，毫秒级登记完成）
                        ↓
              后端按数据库能扛的节奏（每秒 4000）
              匀速从队列里取出来处理
                        ↓
              数据库看到的永远是平缓的流量 ✅
```

**这就是削峰填谷**：把尖峰削下来，填到后面的低谷里去。

> **生活比喻**：食堂打饭。12 点下课，所有人同时涌向餐厅。如果用消息队列的思路——**先排队取号，再按号叫人**。

### 5.3 Redis 做队列：两个老办法 + 一个新办法

#### 老办法 ①：list 当队列

```bash
LPUSH queue:order order123      # 生产者：从左侧塞入
BRPOP queue:order               # 消费者：从右侧取出
```

`BRPOP` 里的 **B = Block**：队列空着时就**阻塞等着**，不用你自己写循环不停问「有没有新消息」。

> ❌ **致命短板**：`BRPOP` 弹出消息后，**这条消息就从队列里消失了**。如果消费者拿到它之后崩了，**这条任务就永久丢失了**——没有任何人知道它丢过，也没有任何重试机制。

#### 老办法 ②：发布订阅（pub/sub）

```bash
PUBLISH channel:config "new config"
SUBSCRIBE channel:config
```

像广播电台：一个频道，所有订阅者同时收到。**适合做配置刷新这类通知**。

> ❌ **致命短板**：**消息完全不落地**。没人在线，消息就直接丢掉；客户端断线期间的消息也收不到。
> **绝对不能当任务队列用，一个字都不能改。**
> 作者提醒：项目里经常看到有人用 pub/sub 当队列，线上就会莫名其妙丢任务，影响非常严重。

#### 新办法 ③：Stream（Redis 5.0+，专业级消息队列）

**定位：Redis 专门为消息队列做的数据结构。**

记忆方式：**像一条只会往后追加的日志。**

| 特性 | 说明 |
|---|---|
| 消息 ID | 每条消息有自增 ID，格式是 `毫秒时间戳-序号` |
| **读完不删** | 写进去就一直在，直到你主动删除 |
| 记录进度 | **记着谁读到了哪儿** → 可以**重放**，也能**重试** |

> 与 list 最大的区别：**list 读完就删，stream 读完不删。** 这就是它「可靠」的地方。

**核心命令**：

| 命令 | 作用 |
|---|---|
| `XADD stream:* field value` | 写消息，`*` 让 Redis 自动生成 ID |
| `XRANGE stream - +` | 从头读一遍历史消息，**且不删除** |
| `XTRIM stream MAXLEN ~ 1000` | ⚠️ **必须做**，只保留最近 1000 条，否则消息一直堆着**内存会涨爆** |

### 5.4 消费者组：多实例消费不重复

**问题**：订单处理服务部署了 3 个实例，都从同一个 stream 取任务，**怎么保证同一条订单不会被处理两次？**

**答案**：消费者组（Consumer Group）。把 3 个实例组成一组，**组内成员不会重复拿到同一条消息**。

**五步机制**：

```
① 新消息分配给组里的某个成员
② 消息不立即删除，而是进入该成员的「待确认列表」（pending）
③ 业务真的处理成功 → 发 XACK → 从 pending 移除
④ 如果成员处理中崩溃、没发 XACK → 消息留在 pending 里，不会消失
⑤ XAUTOCLAIM 把「空闲超过 60 秒还没被确认」的消息
   转移给其他成员重新做一遍
```

> 这五步合起来，叫做 **「至少一次投递」（at-least-once）**。

⚠️ **由此引出一条硬性要求**：既然可能投递两次，**你的业务必须做成幂等**——同一条消息处理两次，结果必须一样。否则就会重复扣款、重复发货。

### 5.5 什么时候该换成 Kafka / RocketMQ？

作者点明了这层关系：

> **Stream 这套「投递 → 确认 → 超时转移」的机制，就是 Kafka / RocketMQ 里 ACK 和 Rebalance 的简化版。**
> 今天理解了 stream，以后学专业 MQ 会非常快，核心思想是一样的。

| 场景 | 选型 |
|---|---|
| 中小规模、不想多维护一个中间件 | **Redis Stream** ✅ |
| 百万级消息量 | Kafka / RocketMQ |
| 需要落盘削峰 | Kafka / RocketMQ |
| 需要严格顺序 | Kafka / RocketMQ |
| 需要事务消息 | RocketMQ |

## 6. 第六章 持久化与高可用：Redis 自己挂了怎么办

前五章都在讲「Redis 怎么用」，最后一章面对更沉重的问题：**Redis 自己挂了怎么办？**

### 6.1 先纠正一个观念

> ⚠️ **持久化不是给数据库做备份用的，而是为了「重启后快速恢复」用的。**
> **你的真数据永远在 MySQL 里。**

Redis 丢了，可以从 MySQL 重建。但如果每次重启都要从 MySQL **全量重建缓存**，可能需要几十分钟——**这期间数据库很可能被打爆**。

所以持久化的真实目的：**让重启后的恢复足够快。**

### 6.2 三种落盘方式

#### ① RDB 快照

每隔一段时间，把内存里**全部数据**写成一份二进制文件 `dump.rdb`。

| 优点 | 说明 |
|---|---|
| 文件小 | 二进制压缩 |
| **恢复极快** | 直接把文件读进内存，比重新执行 1000 万条命令快得多 |
| **不阻塞主进程** | `fork` 一个子进程去写，主进程照常服务 |

| 代价 | 说明 |
|---|---|
| **会丢数据** | 两次快照之间宕机，这段数据全丢。5 分钟一次 → 最坏丢 5 分钟 |
| 适用性 | 做缓存可以接受；**存队列消息就不可接受了** |

#### ② AOF 日志

把**每一条写命令**按顺序追加到日志文件，重启时从头重放一遍。

| 优点 | 说明 |
|---|---|
| **丢得最少** | `appendfsync everysec` → 最坏只丢 **1 秒** |
| **可读可审计** | 文本文件，能看懂、能审计、能手动修改 |

| 代价 | 说明 |
|---|---|
| 文件大得多 | 存的是一堆命令，不是数据快照 |
| **恢复慢** | 要重放全部命令 → 需要定期**重写（rewrite）**压缩 |

#### ③ 混合持久化（Redis 4.0+）—— ✅ 生产推荐

AOF 重写时，**先用 RDB 格式写一份快照当开头，后面再追加增量命令**。

重启时：先快速加载 RDB 快照 → 再重放后面少量的增量命令。

> **既快，又丢得少。这是现在生产环境的推荐配置。**

### 6.3 三种方式对比

| | RDB | AOF | 混合 |
|---|---|---|---|
| 文件大小 | 小 | 大 | 中 |
| 恢复速度 | 快 | 慢 | **快** |
| 数据丢失 | 分钟级 | **秒级** | **秒级** |
| 推荐度 | 单独用不推荐 | 可单独用 | ✅ **生产首选** |

### 6.4 持久化解决不了的问题 → 主从复制

> ⚠️ **持久化解决的是「重启后数据还在」，但它解决不了「硬盘坏了」「机器炸了」。**

要解决这个，需要让**数据同时存在多台机器上**：**主从复制**。

```
        主节点（Master）—— 唯一可以写
         /      |      \
    从1(只读) 从2(只读) 从3(只读)

主节点每收到一条写命令 → 异步转发给所有从节点 → 从节点跟上
```

**两个好处**：

| 好处 | 说明 |
|---|---|
| **读写分离** | 读请求分给从节点，主节点专心扛写，整体吞吐翻几倍。1 万个人读，3 个从节点分摊，每个只扛 3000 多 |
| **数据副本** | 主节点磁盘坏了，从节点还有一份完整数据 |

**两个必须注意的点**：

#### 注意 ①：主从延迟（关键词是「异步」）

主节点写完**不等从节点确认**就返回。所以从节点会慢半拍，**刚写入就读，可能读不到**。

> 对一致性敏感的场景——比如**用户下单后立刻查订单**——**必须强制读主节点**。

#### 注意 ②：主节点挂了，没人自动接班

从节点只会**傻等**，它不知道自己该不该上位。这段时间里，**整个系统没有可以写的 Redis**。

怎么办？需要有人来挑一个新主节点 → **哨兵**。

### 6.5 哨兵（Sentinel）：只干三件事

名字取得很形象：**站在旁边盯着你的那个人**。它自己也是一个独立进程，用三个动词概括：

| 动词 | 做什么 | 细节 |
|---|---|---|
| **① 盯着** | 每秒向主节点发 `PING`：「你还在吗？」 | 探活 |
| **② 选新主** | 主节点不回话 → 判断故障 → 从从节点里挑**数据最新的**升级为主 | 见下方「主观/客观下线」 |
| **③ 通知** | 把新主节点的地址**推送给客户端**，程序自动连过去 | **不用改配置、不用重启应用** |

#### 关键概念：主观下线 vs 客观下线

```
单个哨兵认为主挂了          → 主观下线（带主观情绪，不算数）
超过半数哨兵都确认主挂了     → 客观下线 ✅ 才能动手
```

> 这就是为什么**哨兵至少要部署 3 个，而且必须是奇数**。

#### 为什么不能只部署 1 个哨兵？

自己网络抖了一下，就以为主节点挂了，**自己把从节点扶上位** → 可能出现**两个主节点 → 数据就乱了**。

> 需要多个哨兵互相印证。

#### 客户端怎么知道新主是谁？

**你代码里配的是「哨兵地址」，不是主节点地址。** 哨兵告诉你现在该连谁。这是哨兵最容易被忽略但最有价值的特性——**故障切换对业务代码完全透明**。

### 6.6 Cluster 集群：容量不够了怎么办

哨兵解决了「挂一个不慌」，但解决不了一个问题：**数据越来越多，一台机器的内存装不下。**

> 一台机器最多 64G 内存就是 64G，数据涨到 100G 怎么办？

**Cluster 的思路很直接：分片（Sharding）。**

```
把整个 key 空间切成 16384 个槽（slot），分给多台机器各管一段：

节点 A：0    ~ 5460
节点 B：5460 ~ 10922
节点 C：10922 ~ 16383
```

**容量直接变 3 倍。**

#### 为什么是 16384 这个数？

**权衡了「槽位信息的传输量」和「集群规模」两个点**，最终选了这个数。

> 你只需要记住这个数字，面试时能说出「是权衡传输量和集群规模的结果」就够了。

#### 数据怎么找到？

```
① 客户端对 key 做哈希 → 对 16384 取模 → 算出属于哪个槽
② 直接发到管这个槽的节点
③ 客户端缓存「槽 → 节点」的映射表，第二次就不用再算
④ 映射表变了（比如扩容加了新节点）→ 节点返回 MOVED 重定向
   告诉客户端「你找错了，去那边」
⑤ 客户端刷新缓存 —— 整个过程中对业务透明
```

#### ⚠️ Cluster 的限制

> **用了 Cluster，就不要再写「跨节点的多 key 事务」和「跨节点的 Lua 脚本」。**

因为这些 key 可能落在不同的机器上。除非你用 **hash tag**（`{user:1}:name`、`{user:1}:age` 这样把 key 强行分到同一个槽）。

### 6.7 三种部署方式怎么选（经验法则）

| 条件 | 选型 |
|---|---|
| 数据量**装得下**，只要高可用 | **哨兵（一主二从三哨兵）** ✅ |
| 数据量会**一直涨**，超过单机内存 | **Cluster** |

> **不要一上来就用 Cluster。** 它的限制更多（跨槽事务/脚本失效）、运维更复杂。
> 很多项目几十个 G 的数据，**一主二从三哨兵跑得非常好**。

## 10. 面试自测题（含答案）

先自己答，再看答案。

<details>
<summary><b>Q1：库存服务部署 20 台机器，其中一台代码里写了 synchronized，能防超卖吗？</b></summary>

**不能。** `synchronized` 的作用域是**一个 JVM 进程**，另外 19 台机器看不见这把锁，各管各的，等于没锁。
分布式场景需要的是**作用域覆盖整个集群**的锁——这就是分布式锁存在的理由。
</details>

<details>
<summary><b>Q2：加锁为什么必须用 <code>SET k v NX EX 10</code>，而不是 <code>SET</code> 之后再 <code>EXPIRE</code>？</b></summary>

`SET` 和 `EXPIRE` 是两条命令，**中间有空隙**。如果程序在两条命令之间崩溃/断电，锁就**永远没有过期时间 → 死锁**。
`SET ... NX EX` 是单条命令，Redis 保证原子执行，中间没有间隙。
</details>

<details>
<summary><b>Q3：解锁为什么一定要用 Lua 脚本？</b></summary>

因为解锁需要「先比对身份，再删除」两步。如果分两条命令：
- 只 `DEL` 不比对 → 可能删掉别人的锁（A 业务超时，锁已过期被 B 拿到，A 回来删了 B 的锁）
- `GET` 比对 + `DEL` → 两步之间仍有空隙，还是可能被打断

Lua 脚本让「比对 + 删除」在 Redis 里**不可打断**地执行完，空隙消失。
</details>

<details>
<summary><b>Q4：Lua 脚本是事务吗？出错会回滚吗？</b></summary>

**不是事务，不会回滚。**
Lua 保证的是**「不被打断」**（原子性 = 不可分割），**不保证「出错自动撤销」**。
所以脚本必须写成「**先判断，后执行**」，把可能出错的部分放在前面。
</details>

<details>
<summary><b>Q5：缓存穿透、击穿、雪崩的区别？</b></summary>

| | 关键点 | 数据状态 |
|---|---|---|
| 穿透 | **数据根本不存在** | 缓存和库都没有，每次都穿过去 |
| 击穿 | **单个热点 key 失效** | 数据是存在的，只是一个 key 过期瞬间大量并发 |
| 雪崩 | **一大批 key 同时失效 / Redis 挂了** | 大范围失效 |

解法也完全不同：穿透 → 缓存空值/布隆过滤器/参数校验；击穿 → 互斥锁/逻辑永不过期；雪崩 → 过期时间加随机值/多级缓存/高可用/限流降级。
</details>

<details>
<summary><b>Q6：为什么写缓存时是「删除缓存」而不是「更新缓存」？</b></summary>

并发两个请求同时写：A 先更新库、B 后更新库，但写缓存时 B 先写、A 后写 → 缓存留下 A 的旧值，而与数据库的最终生效顺序不一致 → **缓存长期是脏的，直到下次过期**。
删除缓存则安全：下次读自然回源拿新值回填。代价只是**多一次查库**，用很小成本换掉长期脏数据风险。
</details>

<details>
<summary><b>Q7：maxmemory-policy 默认是什么？生产上缓存场景该用什么？</b></summary>

默认是 **`noeviction`**——**不淘汰，直接对写命令报 OOM 错误**。缓存场景下这等于缓存彻底失效，非常危险。
纯缓存场景用 **`allkeys-lru`** 最省心；如果 Redis 里存了不能丢的数据（如 list 当队列），**必须用 `volatile-lru`**，否则队列消息会被当缓存淘汰。
</details>

<details>
<summary><b>Q8：为什么哨兵至少要 3 个且必须是奇数？</b></summary>

因为「主节点到底挂没挂」要靠**多数投票**决定（客观下线需要过半哨兵确认）。
只部署 1 个：它自己网络抖一下就会把从节点扶上位 → **可能出现双主，数据错乱**。
</details>

<details>
<summary><b>Q9：Cluster 为什么是 16384 个槽？</b></summary>

权衡了**槽位信息的传输量**和**集群规模**两个因素后选定的值。
（记住这个数字和「权衡」这个理由即可。）
</details>

<details>
<summary><b>Q10：双 11 零点所有商品缓存 0 点写入、1 小时后过期，会发生什么？</b></summary>

**1 点钟集体失效 → 缓存雪崩 → 数据库被打爆。**
解法：过期时间加随机值（如 3600 + 0~300 随机），把失效时刻错开。
</details>

<details>
<summary><b>Q11：Redis Stream 和 list 做队列，本质区别是什么？</b></summary>

**list：消息读完就从队列消失**，消费者拿到后崩溃 → 任务永久丢失，无重试、无人知晓。
**Stream：消息读完不删**，会进入消费者的 pending 列表，业务 `XACK` 后才移除；成员崩溃时消息还在 pending，可用 `XAUTOCLAIM` 转移给其他成员重做。
代价是 Stream 是**至少一次投递**，业务必须**幂等**。
</details>

## 11. 📌 补充：视频没细讲但一定会踩的坑

> 以下为原讲解之外的延伸，按重要性排序。

### 11.1 「单线程」的准确含义

视频里说的单线程，准确来说是：**命令执行是单线程的**。
- 网络 I/O 在 **Redis 6.0 之后是多线程的**（只处理读写 socket，不处理命令）
- 持久化（RDB fork、AOF fsync）是**子进程/后台线程**做的

面试如果被追问「Redis 6.0 不是多线程了吗」，答这一句就够了。

### 11.2 大 key 与热 key

| 问题 | 危害 | 排查 | 处理 |
|---|---|---|---|
| **bigkey**（单个 key 几 MB～几百 MB） | 删除/读取时阻塞、网络拥塞、集群数据倾斜 | `redis-cli --bigkeys`、`MEMORY USAGE` | 拆分（hash 分片）、压缩 |
| **hotkey**（单个 key 每秒几十万 QPS） | 单节点 CPU 打满 | `redis-cli --hotkeys`、`MONITOR`（慎用） | 本地缓存兜底、key 加随机后缀分散到多节点 |

### 11.3 布隆过滤器的两个限制

- **有误判率**：说「不存在」一定不存在；说「存在」可能不存在
- **不支持删除**（标准布隆）：要删除得用 Counting Bloom Filter 或定期重建

### 11.4 `KEYS *` 是生产事故的常见源头

`KEYS` 要遍历全部 key，**单线程下会阻塞整个 Redis**。生产用 `SCAN` 游标分批遍历。

### 11.5 缓存预热

上线 / 重启后缓存是空的，第一波流量会全部打到数据库（本质是一次「人为制造的雪崩」）。
做法：发布前用脚本把热点数据预先加载进 Redis。

### 11.6 分布式锁不是万能解：三种并发控制手段的取舍

| 方案 | 适用 | 代价 |
|---|---|---|
| **数据库唯一索引** | 防重复插入（一人一单） | 简单可靠，但有写库开销 |
| **乐观锁（version 字段）** | 冲突少的更新场景 | 冲突多时重试成本高 |
| **Redis 分布式锁** | 跨服务、跨资源的互斥 | 多一次网络往返，需要处理锁超时 |

> 秒杀扣库存更常见的做法其实是 **`DECR` + Lua 直接在 Redis 里完成扣减**（不回源数据库判断），**根本不用锁**。锁是用在「必须串行走一段复杂业务」的场景。

### 11.7 关于 `EXPIRE` 的精度

Redis 的过期是**秒级精度**（`PEXPIRE` 是毫秒），而且如视频所说，过期 key 是**惰性 + 定期**删除的，**不保证到点立刻消失**。所以不要用 TTL 做精确的业务定时。

## 12. 一句话总结

> **今天我们讲了 6 个东西：缓存、锁、计数、队列、限流、发号。它们看起来是 6 个不同的技术，但本质上都是同一件事。**
>
> **Redis 的价值不在于它有多快，而在于它替你扛住了那些不该由数据库去扛的事儿。**
>
> **因为数据库是用来保证数据正确的，它不是用来扛流量的。**
>
> **把这两件事分开，是一个系统从「能跑」走向「能扛」的分水岭。**
