## 1. 第一章 凌晨 1:40 的三行代码：一场 27 步的上线事故

**事故现场**：某年某月某日凌晨 **1:40 左右**，某公司要上一个改动。改了多少行代码？——**三行**。但上线方式是纯手工的：

```
上线流程（约 27 步，全靠人逐步执行）
 1.打包 → 2.上传 → 3.停服务 → 4.备份 → 5.替换文件 → 6.改配置 → 7.重启 → 8.验证 → ... → 23. ...
24. ← 出事了：两台生产服务器，有一台配置文件漏改了
25. 做不下去了 → 26. 全部回滚 → 27. 从头再来
```

**结果**：三个人，耗掉一整个后半夜，只为换三行代码。扎心之处在于：**没有人偷懒，全是熟练工**；**27 步 × 2 台机器 = 54 个动作，漏一个就全盘重来**；**错在第 24 步的「一台机器」，没有任何机制能发现它**。

**为什么**：

> 作者原话：**「问题不是出在人身上，是出在把软件当成了手工艺品。」**

```
手工艺品模式：每一次上线 = 靠人手工雕一遍 → 可能出错 → 重新开始雕 → 事故重复
工业品模式：  模具统一（镜像）｜ 流程固定（流水线）｜ 每件产品一模一样（不可变）
              错误率从「人的注意力」变成「机器的确定性」
```

这句话是全集的引子。后面讲的所有技术——镜像、流水线、声明式、HPA——都在回答同一个问题：**究竟要换成什么样，才能让「三行代码」不再消耗三个人一整个后半夜？**

三个追问铺出全课路线：

| 追问 | 后面在哪回答 |
|---|---|
| 为什么每一步都要人做？能不能让机器做？ | 自动化原则（4.5）+ 五步流水线（5.6） |
| 为什么改三行代码要全量回归、要等所有人？ | 服务化原则（4.1）+ 怎么拆（6.2） |
| 为什么一台机器漏改配置，另一台不知道？ | 不可变镜像 + 面向终态（4.5、7.1） |

## 2. 第二章 云是什么：本质是把机房交给别人管

**「云」听着玄，其实很朴素：把机房交给别人来管。**

| 维度 | 自建机房（打井） | 租云（自来水） |
|---|---|---|
| 服务器 | 提前买，一买得够用三四年 | 网页点几下，几分钟到手 |
| 扩容 | 走采购流程，**以周为单位** | 改一个数字，**以分钟为单位** |
| 付费 | 先掏一大笔钱，不忙时机器空转 | **用多少付多少** |
| 电力 / 空调 / 网络 | 全自己操心 | 云厂商全包 |
| 生活比喻 | **要喝水，自己打一口井** | **要喝水，拧开水龙头就有** |

比喻虽土但准确：**打井的钱花在「有没有水」，而不是「喝多少水」。** 自建机房的钱，大部分花在了「保证随时有水」这件事上。

### 2.1 第一个必须掰开的误解：上云 ≠ 云原生

> 「你把原来那套程序**原封不动**搬到云服务器上，那它只是**换了一个地方住**，这个叫**上云**。」

```
上云（只是搬家）                        云原生（生下来为云而生）
 老程序（单体、手工部署、本地配置）         从设计第一天起就奔着云环境去造
        │ 搬                                ├─ 容器化 ├─ 声明式
        ▼                                   ├─ 自动化 └─ 可观测
 云服务器（还是单体、还是手工部署）
        └─ 27 步上线一步没少
```

区别非常具体：**搬家之后，那 27 步一步都不会少。** 只是换了一台更贵的机器，继续手工雕。

### 2.2 云上能租什么：三层楼

云厂商把服务器、数据库、中间件全做成「点一下就有的商品」，按**你租到的深度**分三层——像一幢楼，租得越高，精装程度越高。

| 层 | 全称 | 租给你什么 | 你还要管什么 | 比喻 |
|---|---|---|---|---|
| **IaaS** | Infrastructure as a Service 基础设施即服务 | 云服务器（ECS）、云盘、网络、负载均衡 | **操作系统、中间件、程序**全自己装 | **毛坯房** |
| **PaaS** | Platform as a Service 平台即服务 | Redis、消息队列、K8s、RDS、对象存储 | **只管业务代码和数据** | **精装房**（家具家电齐了） |
| **SaaS** | Software as a Service 软件即服务 | 企业邮箱、在线文档、在线会议 | **只负责怎么用**，一行代码不写 | **住酒店** |

> 一句话：**租得越高，自己管的越少，可定制的余地也越小。**

| 你想干什么 | 该租哪层 |
|---|---|
| 完全自主、装特殊驱动、改内核参数 | IaaS（毛坯房） |
| 日常开发，Redis / MQ / K8s 拿来就用 | **PaaS（精装房）——开发天天打交道的就是这层** |
| 只想用、不想维护 | SaaS（酒店） |

作者顺带点了一句：**招聘要求里那些 ECS、RDS、OSS，说的就是这一层的商品名。**

### 2.3 三层之后的关键一句

> **云服务只解决了「资源随取随用」；至于资源怎么用、程序怎么打包、怎么部署——那是云原生要管的内容。**

```
资源有了（IaaS / PaaS）
        │ 还差三件事
        ├─ ① 程序怎么打包，才能到哪儿都跑得一样？   → 镜像 / 容器
        ├─ ② 打包好的一堆东西，谁决定跑在哪台机器？ → 编排 / K8s
        └─ ③ 发布、回滚、扩容、排障，谁来做？       → 流水线 / 可观测
```

## 3. 第三章 云原生是什么：为云而生，只管四件事

**native 是「土生土长」**：不是「搬到云上住」，而是「**生下来就是为云而生的**」。

**屏幕上那段 CNCF（云原生计算基金会）定义**，作者说「简单看有个印象就行」，重点是后面四格：

> 云原生技术让组织能在公有云、私有云、混合云这类**现代动态环境**中构建和运行**可伸缩的应用**。
> **容器、服务网格、微服务、不可变基础设施、声明式 API** 是这种方法的典型代表。

📌 补充：这段定义里最值得记的不是「容器」，而是 **`不可变基础设施`** 和 **`声明式 API`**——它们是「自动化原则」的理论依据，也是面试里最能区分「用过 K8s」和「懂 K8s」的两个词。

### 3.1 云原生只管四件事

| 格子 | 一句话 | 关键词 | 章节 |
|---|---|---|---|
| **怎么装** | 把应用和它要的**一切环境**打包成一个集装箱，搬到哪儿都能原样跑 | **容器化** | 3.3 |
| **怎么拆** | 把臃肿的大系统拆成一堆小服务，各自独立开发部署 | **微服务化** | 4.1 / 6 |
| **怎么发** | 用**自动化流水线**代替手工上传 | **持续交付 CI/CD** | 4.5 / 5.6 |
| **怎么看** | 日志、指标、链路全留痕，顺着数据找根因而不是猜 | **可观测性** | 4.3 / 8.2 |

```
              ┌──────── 云原生 = 四件事 ────────┐
        ┌─────┴────┬──────────┬──────────┬─────┴─────┐
        ▼          ▼          ▼          ▼
     怎么装      怎么拆      怎么发      怎么看
     容器化     微服务化    持续交付    可观测性
    (Docker)   (Microsvc)  (CI/CD)  (Log/Metric/Trace)
        └──────────┴────┬─────┴──────────┘
                        ▼
              解决开场那场 27 步事故
```

**注意「怎么发」那一格**，作者特意回扣开场：**「凌晨手工上传要走多少步、耗费多少时间？怎么优化，其实就是靠云原生的自动化流水线。」**

### 3.2 传统 vs 云原生：六行对照表

| 维度 | 传统方式 | 云原生方式 |
|---|---|---|
| **交付单位** | 一个几十兆的 **war 包** | **自带环境的容器镜像** |
| **运行环境** | 人工一台台配 JDK、改配置，**错一台就出事** | 镜像里全带着，**到哪儿跑的都一模一样** |
| **部署方式** | 手工走很多步骤（那 27 步） | **流水线自动做，业务不中断** |
| **扩容方式** | 采购、买机器，**以周 / 月计量** | **自动扩缩容，以秒计量** |
| **故障处理** | 人工登机器看日志，凭经验猜 | **监控告警 + 自动重启** |
| **发布节奏** | 一月一次，每次**如临大敌** | **一天多次，小步快跑，随时可回滚** |
| **系统结构** | 单体，**牵一发而动全身** | 若干微服务，**各管各的** |

> 归结成两件事：**效率**（交付单位、部署方式、扩容方式、发布节奏）和**可靠**（运行环境、故障处理、系统结构）。

### 3.3 镜像、容器、编排：集装箱的故事

> 以前货物是**散装**上船的，形状千奇百怪，装卸全靠人，**换一条船就得把货重新码一遍**。
> 后来有了**标准集装箱**，靠吊车一把抓，**什么船、什么码头都能接**。软件行业，其实就是模仿了这个思路。

| 词 | 是什么 | 集装箱类比 | 关键属性 |
|---|---|---|---|
| **镜像 Image** | 打包好的**软件模板**，**只读、不可更改**；装着代码、运行环境、依赖库、配置 | **出厂封装好的那只箱子**，货已按标准码整齐 | **一次构建，到处运行**：开发机跑得通，生产一定跑得通 |
| **容器 Container** | **镜像跑起来就是容器**，即「正在运行的那一份」 | 箱子被吊上船、占了位置、正在用 | 轻、快，**几秒启动** |
| **编排 K8s** | **码头调度系统**，指挥成千上万的箱子 | 哪个箱子放哪条船、船满了换一条、破了补一只 | 调度、**自愈**、扩缩容、滚动升级、服务发现 |

**镜像 vs 虚拟机**（最容易混的一组）：

| 维度 | 虚拟机 (VM) | 容器 (Container) |
|---|---|---|
| 装什么 | **一整套操作系统** | 只装**应用 + 依赖** |
| 内核 | 每个 VM 一个内核 | **共用宿主机内核** |
| 重量 / 启动 | GB 级 / **几分钟** | MB 级 / **几秒** |

> **这三个词记住，后面的内容你就大概能理解了。**
>
> 📌 补充：容器「轻」的代价是隔离性弱于 VM——它和宿主机共用内核，所以「容器里别跑 root」不是说着玩的。

### 3.4 五层技术地图：说技术要有章法

这张图解决一个很实际的问题：**写方案、写简历、写文档时，「采用了什么技术」怎么写才显得有章法。**

```
┌────────────────────────────────────────────────────────────┐
│ ① 业务应用层  订单 / 库存 / 支付 / 用户 服务                 │
│               （普通用户真正接触到的那些功能）                │
├────────────────────────────────────────────────────────────┤
│ ② 服务治理层  注册中心 / 服务发现 / API 网关 / 配置中心       │
│               / 熔断限流（拆开之后，怎么找到彼此、怎么被管住）  │
├────────────────────────────────────────────────────────────┤
│ ③ 容器编排层  Kubernetes（K8s）★★★ 整个体系的中枢 ★★★       │
│               决定每个容器跑在哪台机器、挂了怎么重启、         │
│               流量大了怎么多开几个                           │
├────────────────────────────────────────────────────────────┤
│ ④ 容器层      Docker：把程序、依赖、配置封装成标准箱子        │
├────────────────────────────────────────────────────────────┤
│ ⑤ 基础设施层  云服务器 / 网络 / 存储 / 负载均衡（IaaS 那层）   │
└────────────────────────────────────────────────────────────┘
```

| 层 | 这一层回答什么问题 |
|---|---|
| 业务应用层 | 业务功能**拆成了哪几个服务** |
| 服务治理层 | 服务之间**怎么找到彼此、怎么被保护** |
| **容器编排层（核心，标红）** | 容器**跑在哪、挂了谁补、忙了扩几个** |
| 容器层 | 程序**怎么打包成标准件** |
| 基础设施层 | **算力从哪来** |

> 作者的实用技巧：按层写，就显得特别有章法。比如「在**容器编排层**，我们采用了 **Kubernetes** 完成调度；在**服务治理层**，我们通过 **API 网关**统一接入」——**「这听起来就像你是做过事情的人。」**

📌 补充：这个技巧有效的真正原因是——它回答的是**架构师的提问方式**。评审时别人不问「你用了什么框架」，而问「**这一层你打算怎么解决**」。先分层再填技术，逻辑自动闭环。

### 3.5 后端架构五代演进：每代都在收拾上一代的烂摊子

> 三十年换了五代。**每一代，其实都是在收拾上一代留下来的烂摊子。**

| 代 | 架构 | 怎么组织 | 留下的烂摊子 |
|---|---|---|---|
| **一** | 单体 | 所有功能打成一个包 | **改一行代码，全量回归一遍** |
| **二** | 垂直拆分 | 按「谁用」切：门户 / 后台 / 接口各一套 | 公共逻辑（如日志）**复制好几份**，越改越乱 |
| **三** | SOA | 公共能力抽成服务，统一走**企业服务总线 ESB** | **总线变瓶颈**，改一处要协调全公司 |
| **四** | 微服务 | 按**业务域**拆，独立开发 / 部署 / 扩容 | 服务一多，**治理和部署全靠人扛** |
| **五** | **云原生** | 容器打包 + 编排调度 + 网格治理 | 问题从「代码怎么组织」变成「**一堆服务怎么管**」 |

第五代最大的变化：**运维能力也被做成了标准件**。弹性、自愈、可观测不再是「你要额外去建的能力」，而是**平台默认给你的**——所以问题从「代码怎么组织」变成了「一堆服务怎么管」。

## 4. 第四章 五大设计原则：拆、伸缩、看清、扛住、少人

> 这五条原则，就是那五代**踩出来的经验**。每条都配了一个动作：**拆、伸缩、看清、扛住、少人**。

### 4.1 原则一：服务化（拆）

> **当代码规模超出了小团队的协作范围，就应该进行服务化拆分。**

**先纠正一个用词：服务化 ≠ 微服务。** 微服务是一种**具体形态**；服务化是一个**动作**——把耦合的东西按边界切开。**拆多大、拆多小都不重要，重要的是「拆开」这个动作**，而这个动作有三个关键问题：

| 关键问题 | 判断标准 |
|---|---|
| **① 什么时候拆？** | 看信号：**十几个人改同一个工程** / **一次上线要等所有人测完** / **一次回归要跑几个小时**。不是想拆就拆 |
| **② 按什么边界拆？** | 业务边界 **+ 生命周期** |
| **③ 拆完怎么管？** | 面向接口 / 高内聚 / 公共模块复用 |

**② 的「生命周期」最容易被忽略，作者用了一个特别具体的例子：**

| 模块 | 变更频率 |
|---|---|
| **促销规则** | **天天在改** |
| **用户认证** | **几年不动** |

```
绑在一个工程里：
  促销改一次 ──▶ 认证陪着你跑一遍全量回归 ──▶ 认证也要重新上线
                  ↑ 迭代快的，被迭代慢的给拖累了
```

> **拆开的理由不一定是「业务不相关」，而是「节奏不一样」。** 变更频率差一个数量级的东西，必须分开。

**③ 拆完怎么管的三件事**：**面向接口编程**（调用方只认契约不认实现）、**功能高内聚**（自己的一亩三分地自己管）、**公共模块复用**（鉴权 / 日志 / 短信抽出来共用，别每人写一遍）。

```
拆之前：一个大功能，订单 + 库存 + 支付 + 用户缠在一块
┌────────────────────────────────────────────────┐
│  订单   库存   支付   用户 （同一份代码库）      │
│  改一行 → 跑全量回归 → 等所有人 → 一起上线       │
└────────────────────────────────────────────────┘

拆之后：四个服务，各自独立
┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐
│ 订单服务│  │ 库存服务│  │ 支付服务│  │ 用户服务│
│ 独立开发│  │ 独立开发│  │ 独立开发│  │ 独立开发│
│ 独立部署│  │ 独立部署│  │ 独立部署│  │ 独立部署│
│ 独立扩容│  │ 独立扩容│  │ 独立扩容│  │ 独立扩容│
└────────┘  └────────┘  └────────┘  └────────┘
            公共能力：鉴权 / 日志 / 短信
```

**⚠️ 坑**：拆开之后**流量怎么扛？** 单体时一台扛不动就加机器；拆成四个服务后，是哪个服务扛不住？加哪个？加几个？——引出第二条原则。

### 4.2 原则二：弹性（伸缩）

> **容量跟着业务走，不再靠提前猜。**

```
容量
 ▲
 │                    ╱╲  ← 大促波峰
 │                   ╱  ╲
 │      ╱╲          ╱    ╲
 │     ╱  ╲        ╱      ╲
 │────╱────╲──────╱────────╲───────────  ← 实际业务需求
 │═══════════════════════════════════════  ← 按峰值预留的固定容量
 │        ↑ 次高峰
 └──────────────────────────────────────▶ 时间
          ↑ 平时这些全是浪费的算力
```

| 情况 | 后果 |
|---|---|
| **猜高了** | 大部分时间灰线在红线最高处之上 → 低谷期**一直在烧钱** |
| **猜低了** | 大促那一下红线**冲破灰线** → **当天就可能崩溃** |
| **想临时加机器** | 又要走采购流程 → **来不及** |

> 这是一个死局：**猜高烧钱，猜低崩盘，临时加来不及。**

**云原生怎么做：定一条规则，交给 K8s。** 比如「**CPU 平时超过 70%，就加实例**」——码头调度系统发现船装不下了，自己多调一条船；货卸完了，把多调的船撤走。结果三个词：**资源利用率提升、成本下降、秒级应变**。

**⚠️ 坑**：系统会自己伸缩了，但**真出事时你怎么知道？** 弹性解决「扛得住」，没解决「看得见」。

### 4.3 原则三：可观测（看清）

> **让系统的内部状态能够被外部看到，而不是靠猜。**

| 支柱 | 回答什么问题 | 手段 | 常见工具 | 类比 |
|---|---|---|---|---|
| **日志 Log** | **刚才到底发生了什么** | 每笔请求、每次异常都留文字记录，集中收集、统一检索 | **ELK** | 现场的**笔录** |
| **指标 Metric** | **系统现在健不健康** | CPU / 内存 / QPS / 响应时间 / 错误率，**按秒采集画曲线**，设阈值超红线自动告警 | Prometheus + Grafana | 仪表的**指针** |
| **链路 Trace** | **这笔慢请求慢在哪一环** | 把整条调用链耗时画成**瀑布图**，能下钻到具体 SQL、某个三方接口 | **SkyWalking** | 行程的**时间线** |

> 日志为什么要「集中」：以前排查要**登录 20 台机器挨个 grep**；现在**一个搜索框**就搞定。
> 指标为什么比投诉早：它按秒采集、画曲线、设阈值，用户还没感觉就已经越线，**比投诉更早知道出事**。

```
下单请求（总耗时 1.9s）
├─ 网关            12 ms  ▏
├─ 订单服务        40 ms  ▎
├─ 库存服务      1830 ms  ████████████████████████████  ← 瓶颈
├─ 支付服务        30 ms  ▏
└─ 通知服务         8 ms  ▏
                            ↑ 一眼可见卡在库存，还能继续下钻到那条 SQL
```

> **金句：指标告诉你「哪里不对」，日志告诉你「错在哪一行」，链路告诉你「卡在哪一环」。**

### 4.4 原则四：韧性（扛住）

> **依赖的东西一定会坏，关键是坏了之后你的系统还能不能继续服务。**

**先纠正最常见的误解**：**韧性不是要求系统永不出故障**——这在物理上做不到（硬盘会坏、网络会抖、机房会断电）。**真正的要求是**：某个组件坏了，**整个系统仍然能对外提供服务，并且恢复得很快**。

**MTBF = Mean Time Between Failures**（平均无故障时间，两次故障之间的平均间隔）：

```
正常运行 ──────────────✗ 故障 ── 恢复 ──────────────✗ 故障 ── 恢复 ──▶
         ←──── MTBF ────→      ←──── MTBF ────→
         ↑ 韧性做的所有事情，都是在把这一段拉长
```

**要抵御的不是一种异常，是五类：**

| # | 类型 | 例子 |
|---|---|---|
| 1 | **硬件故障** | 宕机、磁盘损坏、网络抖动 |
| 2 | **资源瓶颈** | CPU / 内存 / 数据库连接数打满 |
| 3 | **流量超出设计能力** | 大促洪峰、恶意刷单、爬虫 |
| 4 | **故障与灾难** | 机房断电、可用区网络中断 |
| 5 | **软件缺陷与外部攻击** | 代码 bug、内存泄漏、DDoS |

> 注意 2 和 3 的区别：**资源瓶颈是「自己不够用」，流量超出是「外面来太多」。** 一个靠扩容 / 优化，一个靠限流 / 拒绝。具体六招见 8.3。

### 4.5 原则五：自动化（少人）

> **先标准化，再自动化。这个顺序不能颠倒。**

```
❌ 先自动化（必然失败）：27 个手工步骤直接写成脚本 → 脚本里藏着 27 种差异 → 换环境就崩
✅ 先标准化，再自动化：
   ① 标准化：统一代码规范 + 统一构建方式 + 统一环境定义
   ② 自动化：提交代码 → 自动构建 → 自动测试 → 自动打镜像 → 自动部署 → 失败自动回滚
```

**为什么顺序不能反**：「如果每台机器配置方式都不一样、每个人打包命令都不一样，**你就没有可以自动化的对象了**。」

**回扣开场事故**：那二三十个步骤之所以必须手工做，是因为**从来没有人把它标准化下来**。20 多个步骤里每一步都有细微差异，**机器学不会，就只能人来做**。——这就是整场事故的最终解释：**不是人不行，是没有标准件。**

**两个必须理解的概念：**

| | 命令式（老办法） | 声明式（云原生） |
|---|---|---|
| 你怎么说 | 一步步指挥：装 JDK → 解压 → 改配置 → 启动 | **只说你想要什么**：3 个实例，每个 2 核 4G |
| 少一步会怎样 | **就出错了** | 剩下的交给工具 |
| 谁负责过程 | 你 | 平台 |

**面向终态**：工具**持续对比「现状」与「你描述的终态」，发现差距就自动补齐**。

```
你声明：我要 3 个实例
  现状 3 个 → 一致，什么都不做 ｜ 现状 2 个 → 立刻再起 1 个 ｜ 现状 4 个 → 干掉 1 个
```

> 运行中的容器挂了一个，它会立刻再起一个——因为你描述的终态是 3 个。**运维从此可以不用天天守着屏幕手工救火了。**

### 4.6 五条原则一张表 + 15 个字

| 原则 | 防的什么事故 | 抓手（技术） |
|---|---|---|
| **服务化（拆）** | 改一处要全量回归、团队互相等待 | 微服务拆分、领域驱动设计、API 网关、注册发现 |
| **弹性（伸缩）** | 大促撑不住，平时机器空转 | **Kubernetes**、HPA、负载均衡 |
| **可观测（看清）** | 出事只能靠猜，排查一小时甚至一天 | **ELK**、Prometheus 指标、**SkyWalking** 链路 |
| **韧性（扛住）** | 依赖一抖，全线崩 | **熔断、限流、降级**、多可用区容灾 |
| **自动化（少人）** | 手工发布易错，上线熬通宵 | **CI/CD 流水线**、蓝绿、灰度 |

```
┌──────────────────────────────────────────────────┐
│   拆得开  ·  伸得缩  ·  看得见  ·  扛得住  ·  少动手  │
└──────────────────────────────────────────────────┘
```

> **这 15 个字是云原生的钥匙，请你一定要记住。** 拆得开＝按边界切；伸得缩＝容量跟着业务；看得见＝日志指标链路；扛得住＝依赖坏了还活着；少动手＝先标准后自动。

## 5. 第五章 真实项目落地：订单履约中台的五个实践

### 5.1 项目背景与四个痛点

| 项 | 内容 |
|---|---|
| 项目 | 某大型**连锁零售企业**的**订单履约中台**云原生改造 |
| 目标 | 支撑**三年内业务量涨 4 倍**；**大促不用人工扩容**；全年可用性 **≥ 99.99%** |
| 周期 / 团队 | **16 个月** / **18 人**（后端、前端、测试、运维） |
| 你的角色 | **系统架构师**：总体架构、技术选型、关键方案评审 |
| 技术栈 | **Spring Cloud**、**Docker**、**Kubernetes**、**Prometheus**、**SkyWalking**、**Jenkins** |

> 作者说：「你可以把这个想象成是**你自己**，你怎么去解决这些问题。」**后面每一个数字，都是「你」要拿去汇报的东西。**

| 改造前痛点 | 数字 |
|---|---|
| 核心单体太大 | **80 万行代码**，**12 个模块**挤在一个工程里 |
| 回归太慢 | 任何改动都要跑 **3 小时**全量回归 |
| 发布互相等 | **4 个业务小组共用一条流水线**，谁发版都要等其余三组确认 |
| 需求太慢 | 平均一个需求**走 4 周** |

### 5.2 实践一：服务化 —— 按业务领域切成 4 个服务

```
  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
  │ 订单服务  │   │ 库存服务  │   │ 支付服务  │   │ 会员服务  │
  │ 独立仓库  │   │ 独立仓库  │   │ 独立仓库  │   │ 独立仓库  │
  │ 独立流水线│   │ 独立流水线│   │ 独立流水线│   │ 独立流水线│
  │ 独立扩容  │   │ 独立扩容  │   │ 独立扩容  │   │ 独立扩容  │
  └──────────┘   └──────────┘   └──────────┘   └──────────┘
        └──────────────┴──────────────┴──────────────┘
                  公共组件：鉴权 / 日志 / 短信
```

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 需求交付周期 | **4 周** | **1 周** |
| 故障隔离 | 库存异常，全链路陪葬 | **库存异常不拖垮整个交易链路**，影响面可控 |
| 新服务接入 | **5 天** | **1 天**（鉴权、日志、短信抽成公共组件） |

### 5.3 实践二：弹性 —— 从「按峰值预留」到「HPA 自动扩」

**问题**：订单流量**峰谷比 12:1**；过去按峰值预留，平时**七成算力空转**、**一年白花几百万**；大促当天还要运维**从凌晨开始手工加机器**，漏一台就可能影响成交。

```
① 平时：4 个实例就够，CPU 平均 35%
        ▼
② 大促流量上来：CPU 超过 85% 阈值
        ▼
③ HPA 自动触发（不需要任何人介入），30 秒内拉起 20 个实例
        ▼
④ 扛住峰值 1.2 万 TPS；流量退去自动收回，只按实际用量付费
```

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: order-service-hpa }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: order-service }
  minReplicas: 4                     # 平时 4 个，CPU 约 35%
  maxReplicas: 24
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 85 }   # 超 85% 触发
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0                              # 扩容要快
      policies: [{ type: Percent, value: 100, periodSeconds: 15 }]
    scaleDown:
      stabilizationWindowSeconds: 300                            # 缩容要慢
```

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 大促扩容 | 提前申请机器、凌晨人工加 | **零人工干预** |
| 服务器月账单 | **42 万** | **26 万** |
| 峰值承载能力 | 基准 | **翻 4 倍** |

> **作者在这里卖了个关子**：「30 秒扩容听起来很不错，但真到洪峰那个瞬间，**这 30 秒够不够用？** 后面专门分析。」→ 第 8.1 节揭晓。

### 5.4 实践三：可观测 —— 把黑盒变成透明的

**问题**：一笔下单**跨 8 个服务**，用户只反馈「下单很慢」；排查要**登 8 台机器 grep 日志**、人工拼时间线，平均定位一次故障 **2 小时以上**。

| 支柱 | 落地做法 |
|---|---|
| **日志** | 统一格式、**打上链路 ID（traceId）**、全部收进 **ELK**；按 traceId **一个搜索框拉出全部相关日志** |
| **指标** | JVM、接口耗时、错误率全采集进**仪表盘**，越线**自动推送到值班群**（比用户投诉早一步） |
| **链路** | **无侵入式探针**自动记录跨服务调用，画成**瀑布图**；一眼看到卡在库存 1.8 秒，**还能下钻到具体那条 SQL** |

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 平均故障定位时间 | **2 小时** | **8 分钟** |
| 异常提前发现率 | — | 约 **70%** 的异常在**用户感知之前**被抓到 |

### 5.5 实践四：韧性 —— 一个短信接口引发的雪崩

```
① 第三方短信接口响应：50 ms ──▶ 5 s（慢了 100 倍）
        ▼
② 调用它的线程全部被占住（等响应）
        ▼
③ 线程池耗尽 ──▶ 下单接口的线程也拿不到
        ▼
④ 整个下单接口不可用 ──▶ 用户下不了单
```

> 一个**边缘的、非核心的**依赖抖了一下，**全链路陪葬**。

| 招式 | 做法 | 比喻 |
|---|---|---|
| **① 熔断** | 下游**连续失败超阈值**就直接断开，不再傻等 | **保险丝**：短路了先跳闸 |
| **② 限流** | 按接口或用户限速，超了直接拒绝 | **宁可挡住一部分，也别全体卡死** |
| **③ 降级** | 非核心功能出问题就返回兜底内容 | 推荐位拉不到就展示**默认商品**，但**下单主链路必须走完** |
| **④ 多可用区容灾** | 核心服务**同时部署在两个可用区**，一个机房异常，流量自动切另一个 | **双活**，业务无感 |

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 短信超时 | 短信发不出 + **下单跟着挂** | 短信发不出去，**下单照常完成** |
| 全年可用性 | 99.9% | **99.99%** |
| 故障影响范围 | 可能全站不可用 | **收敛在单个服务内** |

> 作者把韧性的定义又念了一遍：**「依赖坏了，系统还活着。」**

### 5.6 实践五：自动化 —— 五步流水线，替掉那 27 步

> 你还记得开场那个凌晨发布的事故吗？**解决它的方案，就在这一页。**

```
① 提交代码    推到指定分支，即刻触发流水线（不需要人工发起）
        ▼
② 编译构建    统一构建脚本，保证任何人在任何机器上产物一致
        ▼
③ 自动化测试  单元测试 + 接口测试自动跑，不过就卡住不许往下走
        ▼
④ 构建镜像    打成容器镜像推到仓库，版本号与代码提交一一对应
        ▼
⑤ 部署发布    灰度 5% 流量 → 观察指标 → 正常则全量 / 异常则自动回滚
```

```groovy
pipeline {
    agent any
    environment { IMAGE = "registry.example.com/order-service:${env.GIT_COMMIT.take(8)}" }
    stages {
        stage('① 提交触发')   { steps { echo "分支 push 自动触发，无需人工发起" } }
        stage('② 编译构建')   { steps { sh './mvnw -B clean package -DskipTests' } }
        stage('③ 自动化测试') { steps { sh './mvnw -B test; ./mvnw -B verify -Pit' } }   // 不过就中断
        stage('④ 构建镜像')   { steps { sh "docker build -t ${IMAGE} .; docker push ${IMAGE}" } }
        stage('⑤ 灰度 5%')    { steps {
            sh "kubectl set image deploy/order-service order-service=${IMAGE}"
            sh "kubectl rollout status deploy/order-service --timeout=120s" } }
    }
    post { failure { sh "kubectl rollout undo deploy/order-service" } }   // 失败自动回滚
}
```

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 一次发布耗时 | **40 分钟**（手工） | **6 分钟**（全自动） |
| 发布频率 | **月均 1 次** | **日均 3 次**，白天也敢发版 |
| 由发布引入的故障占比 | **35%** | **8%** |

> 「**开场那三个人的后半夜，以后就可以不用再熬了。**」

## 6. 第六章 架构深浅（一）：微服务全景、怎么拆、怎么通信

> 从这章起「往技术细节里钻」：**靠什么技术实现，坑在哪儿**。每一页解决一个真实问题。

### 6.1 微服务系统由哪几块拼起来：五层全景

```
┌───────────────────────────────────────────────────────────┐
│ ① 入口层  浏览器 / APP / 小程序 / 开放 API                  │
│           4 种客户端只认一个域名，不关心后面有几个服务        │
├───────────────────────────────────────────────────────────┤
│ ② 网关层  所有请求的唯一入口                                │
│           路由转发 / 统一鉴权 / 限流熔断 / 灰度分流          │
│           （鉴权、日志这些「每个服务都要做」的事，这做一次）   │
├───────────────────────────────────────────────────────────┤
│ ③ 业务层  订单 / 库存 / 支付 / 用户…… 各管一摊              │
│           每个服务有自己的代码库、发布节奏、副本数            │
├───────────────────────────────────────────────────────────┤
│ ④ 支撑层  注册发现 / 配置中心 / 链路追踪                     │
│           实例会变 → 让「谁在哪」随时可查；改配置不用重启     │
├───────────────────────────────────────────────────────────┤
│ ⑤ 数据层  MySQL（分库分表）/ Redis / Kafka / 对象存储         │
│           ★ 原则：一个服务只管自己的库，不直接连别人的表 ★    │
└───────────────────────────────────────────────────────────┘
```

| 层 | 关键约束 |
|---|---|
| 入口层 | 客户端**只认域名** |
| 网关层 | **横切能力只做一次**，服务里不重复写 |
| 业务层 | 独立代码库 / 发布节奏 / 副本数 |
| 支撑层 | 「谁在哪」随时可查，**改配置不重启** |
| 数据层 | **不跨库直连** |

> **「不直接连别人的表」是「微服务能不能拆干净的一个分水岭」。** 理由很硬：一旦 A 直接读 B 的表，B 改表结构就等于要改 A——**拆了等于没拆**。

### 6.2 服务怎么拆：先记住一句反话

> **拆分不是越细越好。拆错了，比不拆还要惨。** 那种状态叫 **「分布式单体」**：**看着拆开了，但改一下还是得全体协调。**

```
分布式单体长什么样：
  订单服务 ──直连──▶ 库存服务的表      支付服务 ──直连──▶ 订单服务的表
  表面：4 个服务、4 个仓库
  实际：改一张表，4 个团队一起改、一起上线 → 还不如不拆（至少不拆时还少一层网络调用）
```

| 依据 | 自检问题 | 合格的样子 |
|---|---|---|
| **① 按业务能力拆** | **你能不能用一句话说清它负责什么？** | 订单 / 库存 / 支付 / 会员，各是一件完整的事 |
| **② 按变化频率拆** | 快节奏模块**有没有被慢节奏模块拖住发布？** | 营销规则一周改 3 次、账单逻辑一年不动 → **别绑在一块** |
| **③ 按团队边界拆** | 两个团队共管一个服务，**改代码要不要互相等？** | 一个服务由一个团队**从开发到上线完整负责** |

> 第一条自检特别狠：**「如果你说不清你拆出来这个到底是干什么的，那你就是拆错了。」**

📌 补充：第 ③ 条其实是**康威定律的正向应用**——系统结构会不可避免地与组织结构同构。与其对抗它，不如顺着它拆：**先看团队怎么坐，再定服务怎么切**，往往比先画架构图更落地。

### 6.3 拆完怎么通信：打电话 vs 发微信

| | **同步调用**（RPC / HTTP） | **异步消息**（MQ） |
|---|---|---|
| 比喻 | **打电话**：我打过去，等你说完才继续 | **发微信**：发出去就不管，你什么时候看都行 |
| 适合 | **下一步动作依赖这个结果** | **必须做，但不着急做** |
| 例子 | 下单要先**验库存** | **扣积分、发券、写日志** |
| 风险 | 对方慢了，**我的线程一直被占着**，一个慢服务拖垮整条链路 | 消息会**重复投递、会丢、会乱序** |
| 配套 | 超时 + 熔断 + 线程隔离 | **幂等 + 重试 + 死信队列** |

```
同步：下单 ──▶ 库存（等 1.8s）──▶ 继续 ──▶ 返回
             ↑ 这 1.8 秒里，这个线程什么也干不了

异步：下单 ──▶ 发一条消息到 MQ ──▶ 立刻返回
                             ├─▶ 积分服务（慢慢消费）
                             ├─▶ 券服务（慢慢消费）
                             └─▶ 日志服务（慢慢消费）
```

```yaml
# Spring Cloud OpenFeign：超时一定要配，且要比上游更短
feign:
  client:
    config:
      inventory-service: { connectTimeout: 500, readTimeout: 800 }   # 上游给的是 1s
  circuitbreaker: { enabled: true }
resilience4j:
  circuitbreaker:
    instances:
      inventory-service:
        slidingWindowSize: 20
        failureRateThreshold: 50        # 失败率超 50% 就打开
        waitDurationInOpenState: 10s    # 10 秒后进入半开试探
```

## 7. 第七章 架构深浅（二）：K8s 七个对象、服务网格、数据一致性

### 7.1 容器编排的核心思想

> **在 K8s 里，你不要指挥它「怎么干活」，你只要告诉它「你想要什么结果」。** 这就是**声明式**，剩下的脏活累活它自己搞定。

```bash
# 命令式（老办法）：一步步指挥，少一步就错
docker run -d --name order-1 order-service:v1
docker run -d --name order-2 order-service:v1
# 挂了一个？你自己 docker ps 看看，再手动补一个

# 声明式（云原生）：只说要什么
kubectl apply -f order-service.yaml     # 我要 3 个副本，挂了它自己补，升级它自己滚
```

### 7.2 K8s 最该记住的七个对象

| # | 对象 | 比喻 | 管什么 | 一句话 |
|---|---|---|---|---|
| 1 | **Pod** | **合租屋** | K8s 里**最小的家** | 一个屋里可住好几个容器，**共享同一张网络、同一块存储** |
| 2 | **Deployment** | **无状态管家** | 没「身份证」的服务（Web 前端等） | 你说要 3 份，少一份它自己补；升级时按策略一个个换 |
| 3 | **StatefulSet** | **有身份的服务管家** | MySQL、Kafka 这类 | 每个实例有**固定名字**（db-0、db-1）和**独立存储**，重启后**还是原来的配方，数据不丢** |
| 4 | **Service** | **固定电话 / 座机** | 给一群会跑的 Pod 一个**永不变的地址** | Pod 的 IP 一直在变，Service 的电话不变，打过去**自动转接到活着的那个 Pod** |
| 5 | **Ingress** | **公司前台** | 集群对外的大门 | 看**域名和路径**，把外部请求引导到内部对应的 Service |
| 6 | **ConfigMap** | **小本本** | 配置（数据库地址、环境变量） | 把配置从代码和镜像里**抽出来**；改配置**不用重新打包** |
| 7 | **HPA** | **智能空调** | 水平自动扩缩容 | 盯 CPU / 内存 / QPS，**忙了多开几个 Pod，闲了关掉几个**，省电也省钱 |

**四个容易混的对象，一句话分清**：Pod **会死、IP 会变** → 调用方通过 **Service**（固定电话）找它 → 外面的人通过 **Ingress**（前台看域名）进来 → **Deployment / StatefulSet** 保证「一直是 3 个」→ **HPA** 决定「什么时候变 5 个」。

```yaml
# ① ConfigMap：配置抽成「小本本」，改配置不用重打镜像
apiVersion: v1
kind: ConfigMap
metadata: { name: order-config }
data: { DB_HOST: "mysql.order.svc.cluster.local", LOG_LEVEL: "INFO" }
---
# ② Deployment：无状态管家，3 副本，滚动发布不中断
apiVersion: apps/v1
kind: Deployment
metadata: { name: order-service }
spec:
  replicas: 3
  selector: { matchLabels: { app: order-service } }
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # 期间不允许 Pod 不可用
  template:
    metadata: { labels: { app: order-service } }
    spec:
      containers:
        - name: order-service
          image: registry.example.com/order-service:v1.2.3   # 带版本号，绝不用 latest
          ports: [{ containerPort: 8080 }]
          envFrom: [{ configMapRef: { name: order-config } }]
          resources:
            requests: { cpu: "500m", memory: "1Gi" }   # 调度依据
            limits:   { cpu: "2",    memory: "2Gi" }   # 上限，防噪音邻居
          readinessProbe:            # 就绪探针：不通过就不接流量
            httpGet: { path: /actuator/health/readiness, port: 8080 }
            initialDelaySeconds: 20
          livenessProbe:             # 存活探针：不通过就重启容器
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            initialDelaySeconds: 40
---
# ③ Service：给会跑的 Pod 配一个永不变的座机号
apiVersion: v1
kind: Service
metadata: { name: order-service }
spec:
  selector: { app: order-service }
  ports: [{ port: 80, targetPort: 8080 }]
  type: ClusterIP
---
# ④ Ingress：公司前台，按域名 / 路径分流
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata: { name: shop-ingress }
spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - { path: /order, pathType: Prefix,
              backend: { service: { name: order-service, port: { number: 80 } } } }
```

```bash
kubectl apply -f order-service.yaml          # 声明式提交（幂等，可反复执行）
kubectl get hpa                              # 看扩容状态（TARGETS 那一列）
kubectl rollout undo deploy/order-service    # 回滚（一条命令，这就是「留好后路」）
kubectl describe pod <pod>                   # 排障第一命令：看 Events
```

> ⚠️ 本章反复埋的坑：`image: ...:latest` 是禁忌。**镜像必须带明确版本号，且与代码提交一一对应**——否则「回滚」时你根本不知道该回哪个版本，「留好后路」就是空话。

### 7.3 服务网格：把治理能力从代码里搬出来

**旧做法：每个服务都塞一套治理 SDK，有三宗罪——**

| 坏处 | 具体表现 |
|---|---|
| **语言被绑死** | Java 服务用 Java 的 SDK；换 Go 要**重写一遍** |
| **升级要全量重发** | SDK 升级 → **所有服务重新打包、重新发布** |
| **业务代码被污染** | 一大堆和业务无关的治理代码，**影响可读性也影响修改** |

**新做法：每个服务旁边挂一个贴身代理 Sidecar**（常见的是 **Envoy**），**进出的流量全经过它**。

```
        ┌─────────────────────── Pod ───────────────────────┐
        │  ┌──────────────┐        ┌──────────────────────┐  │
请求 ──▶│  │   Envoy      │──────▶ │  业务容器             │  │
        │  │  (Sidecar)   │◀────── │  一行治理代码不用写    │  │
        │  └──────────────┘        └──────────────────────┘  │
        └────────┬──────────────────────────────────────────┘
                 ▼  治理在这里做：超时 / 重试 / 熔断 / 限流 / mTLS / 埋点
```

| ✅ 好处 | ⚠️ 代价 |
|---|---|
| 业务代码里**一行治理代码都不用写** | **多一层网络开销**（每请求多两跳） |
| 调策略、改配置**业务无感，不用重新发布** | **多一层要自己运维的东西** |

**网格接管的事**：流量管理、超时重试、熔断限流、服务间加密（mTLS）、可观测数据。

**什么时候才该上网格——技术选型永远看规模：**

| 你的情况 | 建议 |
|---|---|
| 服务数**超过二三十个**，且**技术栈不止一种语言** | 上网格**划算** |
| 有**专门的平台团队** | 上网格**划算**（有人运维那层） |
| 只有 **五六个服务** | **老老实实用 SDK**，更省事 |

> **「没有先进的技术，只有这个规模下划算的技术。」** 这句话值得抄下来贴墙上。

### 7.4 跨服务的账怎么算平：数据一致性

```
一次下单，动了 3 个库：
  订单库 ── 写订单 ｜ 库存库 ── 扣库存 ｜ 用户库 ── 加积分
  订单写完了，库存还没扣，服务挂了 ──▶ 数据不一致
```

> 单体时**一个数据库事务就能解决**，拆开之后**反而变成了一个难题**。

| 解法 | 怎么做 | 一致性 | 性能 | 适用 |
|---|---|---|---|---|
| **① 2PC 两阶段提交** | 全程**锁着资源**，准备 → 提交 | **强一致** | **差** | 银行内部转账这类**必须同时成功**的；互联网业务基本不用 |
| **② 可靠消息（最终一致）** | 把「写库」和「记一条要发的消息」**绑在同一个本地事务**；投递失败就重试，直到对方确认消费 | **最终一致**（有短暂不一致） | **好，最常用** | 绝大多数互联网业务 |
| **③ 补偿事务 Saga** | 哪一步失败，就**反向补偿**已完成的步骤 | 最终一致 | 较好（不如②） | 长流程，如**订机票 + 酒店 + 租车** |

```
② 可靠消息：
  本地事务 ┌────────────────────────────┐
          │ ① 写订单库                  │
          │ ② 同时写一条「待发消息」      │ ← 同一本地事务，要么都成，要么都不成
          └────────────┬───────────────┘
                       ▼
                投递到 MQ（失败就重试）──▶ 库存服务消费（幂等）──▶ 确认消费

③ 补偿事务：
  ① 订机票 ✅ ──▶ ② 订酒店 ✅ ──▶ ③ 租车 ❌ ──▶ 反向补偿：取消酒店 ⟲ ──▶ 取消机票 ⟲
```

**两条铁律，少一条都不行：**

| 铁律 | 为什么 |
|---|---|
| **① 幂等** | **同一请求来两次，结果必须一样。** 消息会重复投递——订单不幂等就**重复扣款 / 重复转账** |
| **② 对账** | **每天定时把两边数据对比一遍，不一样就补回去。** 再好的设计也有漏网之鱼，这是**兜底** |

```sql
-- 幂等的最后一道防线：唯一索引（重复投递时插入失败，捕获后返回上一次结果）
CREATE UNIQUE INDEX uk_order_biz ON t_order (biz_no);
```

📌 补充：幂等有三种层次，工程上通常**三层都做**——① **业务唯一键**（唯一索引）是不会骗人的最后一层；② **状态机校验**（只允许 `待支付 → 已支付`）；③ **去重表 / Redis SETNX**（短窗口拦截）。只靠 ③ 不够：Redis 可能丢数据。

## 8. 第八章 架构深浅（三）：弹性的延迟、可观测的协作、韧性的顺序、发布的安全

### 8.1 弹性伸缩：30 秒到底够不够（揭晓关子）

> **自动扩容不是一键变快，它是有延迟的。**

```
CPU 超过阈值
     ├─① 指标要「连续超阈值一段时间」才能动   ← 防抖动，故意等的
     ├─② 调度器找机器、拉镜像                 ← 十几秒 ~ 几分钟
     ├─③ 启动应用（JVM 预热、连接池建立）     ← 往往比拉镜像更久
     └─④ 健康检查通过，才挂到负载均衡         ← 在此之前流量全打给老副本
                    ▼
              新实例才真正开始扛流量
```

| 阶段 | 为什么慢 |
|---|---|
| ① 指标窗口 | **防止来回抖动**（否则一次毛刺就扩一次） |
| ② 调度 + 拉镜像 | 镜像大、节点没缓存时**十几秒到几分钟** |
| ③ 启动应用 | JVM 预热、连接池、缓存加载，**往往比拉镜像更久** |
| ④ 健康检查 | 探针通过才进 LB，这段**全靠老副本硬扛** |

> **答案：不一定够。如果洪峰来得太猛，新实例还在路上，老实例可能已经倒了。**

**所以真实项目里，弹性是三件事一起做：**

| 做法 | 具体 |
|---|---|
| **① 提前扩** | 大促前**按日历定时扩**，别等洪峰来了再说 |
| **② 留缓冲** | 日常水位控制在 **50% 左右**，不要等 85% 才动手 |
| **③ 缩容要慢** | **缩要比涨得慢**，不然流量一抖就来回伸缩 |

```yaml
# 用 CronJob 在大促前定时预热扩容（比 HPA 更早动手）
apiVersion: batch/v1
kind: CronJob
metadata: { name: pre-scale-for-promotion }
spec:
  schedule: "0 20 * * 5"          # 每周五 20:00，大促前
  jobTemplate:
    spec:
      template:
        spec:
          containers:
            - { name: scaler, image: bitnami/kubectl,
                command: ["sh","-c","kubectl scale deploy/order-service --replicas=12"] }
          restartPolicy: OnFailure
```

> **扩容是预案，不是急救。** HPA 兜住的是「慢慢涨上来的流量」，不是「瞬间的洪峰」。

### 8.2 可观测：一条链路的数据怎么串起来

```
① 请求进网关 ──▶ 生成全局唯一的 traceId
                        ▼
② traceId 跟着每次调用往下传（HTTP Header / MQ Header），每个服务记录自己那一段耗时
                        ▼
③ 异步、批量上报（不影响业务性能）──▶ ④ 按 traceId 拼成一张瀑布图

排查顺序：指标「整体不对了」→ 链路「慢在库存那一跳」→ 日志「哪条 SQL 超时」
```

> **这三样数据，缺一不可。** 只有指标 → 知道不对但不知哪不对；只有链路 → 知道哪一跳但不知哪一行；只有日志 → 8 台机器 grep 到天亮。

**最后分清两个词：**

| | 监控 Monitoring | 可观测 Observability |
|---|---|---|
| 面向 | **已知的毛病** | **没见过的问题** |
| 做法 | 给已知指标**设阈值**，超了报警 | 能**一步步追问下去**（任意维度切片、下钻） |
| 边界 | 没设过的阈值就不报警 | 没预想过的问题也能查出来 |
| 一句话 | **我猜到会这样坏，所以我盯着** | **我不知道会怎么坏，但坏了我也能查出来** |

### 8.3 韧性六手段：各管一段，顺序不能乱

> 这是**一套组合拳**。别人家的服务**一定会挂、一定会慢**，我们能控制的**只有自己怎么反应**。

| # | 手段 | 解决什么 | 关键细节 | 坑 |
|---|---|---|---|---|
| 1 | **超时** | 不让请求**无限等待**，尽快把线程和连接还回去 | **必须设，且比上游更短**，逐层递减 | 不设 = 线程池被慢依赖吃干 |
| 2 | **重试** | 偶发网络抖动、瞬时错误 | **只重试幂等操作**；必须配**退避间隔 + 次数上限** | **重试本身就是流量洪峰**（3 次 = 4 倍流量） |
| 3 | **熔断** | 下游**持续失败**时直接切断，不再白等耗资源 | **三态**：关闭 / 打开 / 半开 | 打开后不试探，就永远恢复不了 |
| 4 | **限流** | 保护自己**不被超过处理能力的流量打垮** | **令牌桶 / 漏桶**；**按接口、按用户分别设** | 只设一个总闸 → 一个热点拖垮全站 |
| 5 | **降级** | 保住核心，关掉非核心 | **必须提前准备兜底数据** | 临时甩错误页给用户 = 体验灾难 |
| 6 | **隔离** | 一个慢依赖**拖不死整个服务** | 线程池隔离、机房隔离、连接池隔离 | **前 5 个手段的前提**，少了它全白搭 |

```
                失败率超阈值
   ┌────────┐ ──────────────▶ ┌────────┐
   │  关闭   │                 │  打开   │
   │ CLOSED │ ◀────────────── │  OPEN  │
   └────────┘   半开试探成功    └────────┘
        ▲                          │ 等待一段时间
        └──── 半开 HALF-OPEN ◀──────┘   拿少量请求试探：活 → 关闭；死 → 打开
```

```
顺序不能乱：
入口先【限流】→ 调用时设【超时】→ 失败了【有限度地重试】
   → 还不行就【熔断】→ 真出问题就【按业务意愿降级】
   而【隔离】，要从第一天就开始做
```

> 为什么是这个顺序？因为这是**请求的生命周期**：**拦在门外 → 别等太久 → 给它机会 → 别再试了 → 退回兜底**。而**隔离是容器**——它不属于流程里的某一步，是**装这五步的那个盒子**，所以必须一开始就有。

### 8.4 发布与安全：最后一公里的底线

> 云原生让发布从**一月一次**变成**一天几次**，代价是**出错的机会也变多了**。

| 打法 | 怎么做 | 优点 | 代价 |
|---|---|---|---|
| **滚动发布 Rolling** | 一批一批地换 | **最省资源** | 新老版本**会同时跑一段时间** |
| **蓝绿发布 Blue-Green** | 两套环境，**一切换就完事** | **回滚最快** | **资源翻倍** |
| **灰度 / 金丝雀 Canary** | 先给 **1%~5%** 用户，看指标再放量 | 风险最小、指标驱动 | 需要流量切分能力 |

```
滚动：  [v1 v1 v1] ──▶ [v2 v1 v1] ──▶ [v2 v2 v1] ──▶ [v2 v2 v2]
蓝绿：  蓝 v1（全量）｜ 绿 v2（就绪）── 一键切 ──▶ 出问题一键切回
金丝雀：[v1 v1 v1 ... v1] 99% ｜ [v2] 1%  ← 只看 1%~5%
```

**共同的前提：数据库变更必须向后兼容。**

```
✅ 正确顺序（三次发布）
  发布 1：加新字段（旧代码不认识它，但不受影响）
  发布 2：新代码同时写新旧字段、读新字段（新老共存期都能跑）
  发布 3：确认无旧版本在跑 → 删旧字段

❌ 错误顺序（一次发布）
  直接改名 / 删字段 → 滚动期间老版本还在跑 → 老代码读不到字段 → 全站报错
```

> 这是**滚动和蓝绿都会踩的坑**：只要「新老共存」存在一秒钟，数据库就必须同时兼容两种代码。

**安全底线（六条）**：镜像用**可信源 + 扫漏洞**；容器**尽量别用 root**；口令走 **Secret 注入**（**绝不写进代码仓库**）；网络**默认拒绝、按需开通**（白名单）；三方包**锁版本**；留**审计记录**。

```yaml
apiVersion: v1
kind: Secret
metadata: { name: order-db-secret }
type: Opaque
stringData: { password: "******" }        # 实际由 Vault / KMS 注入，不进 Git
```

**上线五步清单（逐条核对，不是「知道就行」）：**

| # | 检查项 | 说明 |
|---|---|---|
| 1 | **数据库先动** | 表结构变更先上，且向后兼容 |
| 2 | **留好后路** | 回滚**一条命令完成**（`kubectl rollout undo`） |
| 3 | **指标看得见** | 关键指标、仪表盘、告警都就位 |
| 4 | **放量有标准** | 灰度放量的判断标准写清楚（错误率 < x%、P99 < y ms） |
| 5 | **责任到人** | 谁发布、谁观察、谁决策回滚 |

## 11. 动手路线：5 步把云原生从名词变成手感

> 这套课的规矩：**听懂了不算，能跑过才算。**

| 步骤 | 做什么 | 巩固了什么 |
|---|---|---|
| **1** | 装 **Docker**，写 5 行 `Dockerfile`，把任意小程序打成镜像跑起来 | 镜像 vs 容器（3.3） |
| **2** | 装 **minikube** / **k3d**，`kubectl apply` 一个 3 副本 Deployment，再**手动 `kubectl delete pod`**，看它 10 秒内自己补回来 | 面向终态（4.5、7.1） |
| **3** | 给上一步配 **Service + Ingress**，从浏览器按域名访问到你的服务 | Service / Ingress（7.2） |
| **4** ⭐ | 装 **metrics-server**，配 **HPA**（CPU 50%），用 `kubectl run -it --rm load-generator --image=busybox -- sh -c "while true; do wget -q -O- http://your-svc; done"` 压上去，`kubectl get hpa -w` **看着副本从 1 涨到 5** | 弹性（8.1） |
| **5** ⭐ | 用 Docker Compose 起 **Prometheus + Grafana**，给服务加 `/metrics`，画 QPS 曲线和 P99 曲线 | 可观测（4.3、8.2） |

> **第 2 步和第 4 步是这套课的灵魂。** 第 2 步让你亲眼看见「声明式」：**你没让它重建，它自己重建了。** 第 4 步让你亲眼看见「弹性」：**你没动它，副本自己涨了。** 这两次「它自己动了」，比读十篇文章都管用。

**课后作业**：打开手上任何一个真实项目，用 9.3 节的**五把尺子**量一遍，把「不合格」的地方列成清单。**那份清单，就是你下一个季度的技术规划。**

## 12. 面试自测题（含答案）

先自己答，再看答案。

<details>
<summary><b>Q1：上云和云原生，区别到底是什么？</b></summary>

**上云是搬家，云原生是重新造。**

- **上云**：把原单体程序**原封不动**搬到云服务器。表面在云上，但 **27 步手工上线一步没少**，弹性、自愈、灰度一个都没用上。
- **云原生**：软件**从设计第一天起**就奔着云环境造——容器化、微服务化、持续交付、可观测。

判断标准：**如果「机器挂了自动重启」「流量涨了自动扩容」都不成立，那就只是上云。**
</details>

<details>
<summary><b>Q2：IaaS / PaaS / SaaS 怎么分？开发日常打交道的是哪层？</b></summary>

IaaS = **毛坯房**（OS、中间件、程序自己装）；PaaS = **精装房**（只管业务代码和数据，Redis / MQ / K8s / RDS 拿来就用）；SaaS = **住酒店**（只管怎么用，一行代码不写）。

**开发天天打交道的是 PaaS。** 一句话：**租得越高，自己管的越少，可定制的余地也越小。**
</details>

<details>
<summary><b>Q3：镜像和容器、容器和虚拟机，分别差在哪？</b></summary>

- **镜像 vs 容器**：镜像是**只读模板**（出厂封装的箱子）；容器是**镜像跑起来的那一份**（箱子吊上船正在用）。一个镜像可以跑出 N 个容器。
- **容器 vs 虚拟机**：VM 要装**一整套 OS**（GB 级、启动几分钟）；容器**共用宿主机内核**，只带应用和依赖（MB 级、几秒）。

代价也要说清：**共享内核意味着隔离性弱于 VM**——容器进程和宿主机同一个内核，所以「容器里别用 root」不是说着玩的。
</details>

<details>
<summary><b>Q4：Pod、Deployment、Service、Ingress 各自解决什么？</b></summary>

**Pod** 是最小调度单元（共享网络和存储的合租屋）；**Deployment** 保证副本数与滚动升级（无状态）；**Service** 给一直变 IP 的 Pod 一个**永不变的座机号**；**Ingress** 是集群对外的**前台**，按域名/路径分给不同 Service。

一条链：**外部 → Ingress（看域名）→ Service（固定地址）→ Pod（真实干活，随时会换）**。
</details>

<details>
<summary><b>Q5：为什么「声明式」比「命令式」适合云环境？</b></summary>

命令式是**一步步指挥**（装 JDK → 解压 → 改配置 → 启动），**少一步就错**，中途失败后状态是「半截的」，没人知道该从哪继续。声明式是**只描述终态**（3 个副本、2 核 4G），由控制器**持续对比现状与终态，发现差距自动补齐**——所以它天然**自愈**，也天然**幂等**（`kubectl apply` 执行 1 次和 100 次结果一样）。这也是 CNCF 定义里「不可变基础设施 + 声明式 API」的由来。
</details>

<details>
<summary><b>Q6：HPA 扩容只要 30 秒，为什么洪峰来了还是可能扛不住？</b></summary>

扩容**不是瞬时的**，中间有四段等待：① 指标要**连续超阈值**才触发（防抖动）；② 调度找机器、拉镜像，**十几秒到几分钟**；③ 启动应用（JVM 预热、连接池建立），**往往比拉镜像更久**；④ 健康检查通过才挂 LB，这段**全靠老副本硬扛**。

所以真实项目是**三件事一起做**：**提前扩（按日历）+ 留缓冲（日常水位 50%）+ 缩容要慢**。**扩容是预案，不是急救。**
</details>

<details>
<summary><b>Q7：熔断和限流都在「拒绝请求」，区别是什么？</b></summary>

| | 限流 | 熔断 |
|---|---|---|
| 拒绝的理由 | **我自己扛不住了**（进来的太多） | **对面已经坏了**（出去的全失败） |
| 保护对象 | **自己** | **自己不被下游拖死** |
| 触发依据 | QPS / 并发数 | **失败率 / 慢调用比例** |
| 恢复方式 | 流量降下来就恢复 | **半开状态试探**，成功才关闭 |

一句话：**限流是「门太窄，排队」；熔断是「桥断了，别过」。**
</details>

<details>
<summary><b>Q8：熔断的三个状态？为什么必须要有「半开」？</b></summary>

**关闭（Closed）→ 打开（Open）→ 半开（Half-Open）**。关闭时正常放行并统计失败率；超阈值后**打开**，直接拒绝、不再耗资源等一个注定失败的响应；等待一段时间后进入**半开**，放**少量请求**试探。

**为什么必须半开**：没有它，熔断一旦打开就**永远恢复不了**——要么一直拒绝，要么只能人工重启。半开是「**自动探测对方是否活过来**」的唯一机制：成功 → 关闭；失败 → 打开。
</details>

<details>
<summary><b>Q9：重试为什么会变成事故？正确姿势是什么？</b></summary>

**重试本身就是一个流量放大器**：3 次重试 = **4 倍流量**。下游已经过载时，重试会把它彻底打死；而且**重试是同步放大的**——上游超时如果不够长，重试还没结束上游就先超时，等于白重试还多打了流量。

正确姿势：① **只重试幂等操作**；② **指数退避 + 抖动**，不能固定间隔猛打；③ **次数上限**（通常 2~3 次）；④ **和熔断配合**，熔断打开后不再重试。
</details>

<details>
<summary><b>Q10：拆了微服务之后，一个跨 3 个库的下单怎么保证数据一致？</b></summary>

单体时代一个本地事务搞定，拆开后**没有跨库事务**了。三种解法：**2PC**（强一致、性能差，银行内部转账那种「必须同时成功」）、**可靠消息**（最终一致、性能好、**最常用**）、**补偿事务 Saga**（最终一致、适合长流程如机票+酒店+租车）。

**但真正保命的是两条铁律**：**幂等**（消息会重复投递，不幂等就重复扣款）、**对账**（每天比对，再好的设计也有漏网之鱼）。

**「最终一致」不是「不管了」，而是「不一致的窗口有上限，且有兜底」。**
</details>

<details>
<summary><b>Q11：服务网格解决了什么问题？什么规模才该上？</b></summary>

**解决「治理逻辑和业务代码耦合」的三宗罪**：语言被绑死（换语言重写 SDK）、SDK 升级要全量重发、业务代码被治理代码污染。做法：把治理搬到 **Sidecar**（如 Envoy），**进出流量全经过它**，业务代码一行不写，改策略业务无感。**代价**是多一层网络开销（每请求多两跳）、多一层要运维的组件。
**什么时候上**：服务数**超过二三十个** ✓、技术栈**不止一种语言** ✓、有**专门的平台团队** ✓；只有五六个服务 → **用 SDK 更省事** ✗。**技术选型永远看规模。**
</details>

<details>
<summary><b>Q12：蓝绿、灰度、滚动，三种发布怎么选？</b></summary>

| 打法 | 优点 | 代价 | 什么时候用 |
|---|---|---|---|
| **滚动** | 最省资源 | 新老版本**同时跑一段时间** | 默认选择，绝大多数服务 |
| **蓝绿** | **回滚最快**（切回去） | **资源翻倍** | 核心交易、要秒级回滚 |
| **灰度/金丝雀** | 风险最小、指标驱动 | 需要流量切分能力 | 大版本、影响面不确定时 |

**三者共同的死穴**：**数据库变更必须向后兼容**——只要「新老共存」存在一秒钟，DB 就必须同时兼容两种代码。正确顺序：**先加字段 → 再改代码用 → 最后删旧字段**。
</details>

## 13. 📌 补充：视频没细讲但一定会踩的坑

> 以下为原讲解之外的延伸，按重要性排序。

### 13.1 `requests` 和 `limits` 不是一回事

| | requests | limits |
|---|---|---|
| 作用 | **调度依据**：按它决定 Pod 能放哪台机器 | **运行时上限** |
| CPU 超了 | — | **被限流（throttle）**，变慢但不被杀 |
| 内存超了 | — | **OOMKilled，容器被杀** |

**经典事故**：`limits.cpu` 设太低（如 `500m`），HPA 显示 CPU 永远 100%，其实是被限流了——**你以为流量问题，其实 CPU 配额问题**。排障先看 `kubectl describe pod` 里的 Throttling。

### 13.2 探针配错的两种死法

**livenessProbe 太激进**：应用只是**慢启动**（JVM 预热 40 秒），探针 20 秒就判死 → **反复重启，永远起不来**。**readinessProbe 缺失**：还没连上数据库就被挂进 LB → **流量打进来全是 500**。

正确做法：`liveness` 的 `initialDelaySeconds` **大于最慢启动时间**；`readiness` 要**真检查依赖**而不是只回 200；优雅停机配 `terminationGracePeriodSeconds` + `preStop`，否则滚动发布时**正在处理的请求被硬切**。

### 13.3 HPA 的三个前提（少一个就扩不起来）

① **必须装 metrics-server**（否则 TARGETS 显示 `<unknown>`）；② **Pod 必须配 `resources.requests`**（否则算不出使用率百分比，HPA 直接不工作）；③ **扩容上限受节点资源限制**——集群 CPU 满了，HPA 想扩也扩不出来，Pod 卡在 `Pending`，这就是为什么还需要 cluster-autoscaler。

另外 HPA / VPA / KEDA 分工不同：**HPA 加副本（横向）、VPA 调单 Pod 资源（纵向）、KEDA 按事件源扩（MQ 堆积、Cron）**；HPA 和 VPA **不要同时对同一个指标使用**。

### 13.4 SLO / SLI / 错误预算：把「99.99%」变成可执行的东西

| 可用性 | 一年不可用 | 一天不可用 |
|---|---|---|
| 99% | 3.65 天 | 14.4 分钟 |
| 99.9% | 8.76 小时 | 1.44 分钟 |
| **99.99%** | **52.6 分钟** | **8.6 秒** |

**SLI** 是实测值（如「P99 < 200ms 的比例」），**SLO** 是承诺目标（99.99%），**错误预算** = 1 − SLO。**99.99% 意味着一年只允许 52 分钟不可用**——预算花完，就必须停止发布新功能，全力做稳定性。

> 这是 SRE 的核心机制：**它把「稳定性」和「迭代速度」的冲突，变成了一个可计算的预算问题。**

### 13.5 可观测的下一代：OpenTelemetry

| | 经典组合（视频里的） | OpenTelemetry |
|---|---|---|
| 采集 | 三套 SDK / Agent 各干各的 | **一套 SDK 同时产出 logs / metrics / traces** |
| 绑定 | 绑厂商（SkyWalking 探针） | **厂商中立**，后端可换 |
| 关联 | 手工把 traceId 塞进日志 | **traceId 天然贯穿三者** |

📌 新项目建议直接用 OTel；老项目不用急着换，**先把 traceId 打通，收益更大**。

### 13.6 成本陷阱：K8s 不是免费的

视频里月账单 42 万 → 26 万很美好，但真实项目还有几笔账：**平台团队人力**（集群维护、升级、etcd 问题）、**资源碎片**（DaemonSet 与预留余量让实际利用率常只有 40%~60%）、**跨 AZ 流量与云盘 IOPS**（账单里的隐形大头）、**学习成本**（从会写代码到会调 K8s 是几个月）。

> 所以「要不要上 K8s」的标准不是「它先不先进」，而是：**你的服务数量、发布频率、团队规模，撑不撑得起它。**
> 顺带两个常被忽略的小坑：容器默认时区是 **UTC**（日志时间差 8 小时，镜像里 `ENV TZ=Asia/Shanghai` 固定）；容器 + HPA **最少留 1 个副本**，想「缩到 0、按调用付费」得上 **Serverless / FaaS**（代价是冷启动、状态难存、厂商锁定）。

## 14. 一句话总结

> **云原生不是一个技术栈，是五把尺子。**
>
> **拆得开**——服务化，让迭代不再互相拖累；**伸得缩**——弹性，让容量跟着业务走；
> **看得见**——可观测，让内部状态能被看到；**扛得住**——韧性，让依赖坏了系统还活着；
> **少动手**——自动化，让机器替人做那 27 步。
>
> **而这五条尺子量到底，其实只在量同一件事：别再把人当成流水线，把软件当成手工艺品。**
>
> **开场那个凌晨 1:40，三个人熬一整个后半夜，只为换三行代码。**
> **那不是人的问题，是「没有标准件」的问题。**
> **云原生做的所有事情，归根到底就是把「手艺」变成「标准件」。**
