## 0. 开场：这篇文章到底在解决什么问题

### 0.1 作者的背景，决定了这篇文章的视角

开场作者先自我介绍：**大概 7 年工作经历**，路径是 **单体服务 → 集群服务 → 微服务 → 现在是 AI Agent**，一步步走过来。

这个履历很关键，因为它解释了后面所有的类比：他讲 Agent 的时候，用的全是传统后端的那套词汇——流程编排、灰度、CI/CD、可观测、线程通信、熵增。**他不是把 Agent 当成一个新东西讲，而是当成「又一个需要工程化的系统」讲。**

另外他提到自己**看过 Pi 和 Claude Code 的源码**，想把里面的设计整合进来讲。所以本文里凡是提到 Pi / Claude Code 的地方，都不是随口举例，而是当作「工业级参考实现」在用。

### 0.2 这篇文章是什么：一篇「总纲」，不是一本手册

原著规模是 **9 篇、20 章**，覆盖范围从「什么是 Agent」到「Agent 怎么自我进化」。而这一篇的角色是**总纲**：把所有点串成一条线、一张图。

作者原话的意思是：这一篇不会对某个点「大谈特谈」，只会做一个简单的概括，说清楚**大概有哪些东西**；复杂主题（如 RAG 实战）**单独起文章**。

> 这句话其实给了读者一个很重要的预期管理：**综述篇的价值不在细节，而在于「知道有这一块，以及它该放在哪」。** 你现在读的这篇笔记，也是同一个定位。

### 0.3 它想解决的最大问题：把散点串成图

> **「普通视频只讲一个单点，而我希望把它串成一条线、或者说一张图，综合地去回答整个 Agent 相关的问题。」**

这是全篇的立意。市面上讲 Agent 的内容大多是「ReAct 是什么」「MCP 是什么」「怎么写 Prompt」——每个点单独看都懂，但拼不起来。**拼不起来就会导致一个典型症状：不知道该在什么时候用哪个。**

所以这篇的骨架是一条**有顺序的链**：内核 → 工具 → 记忆 → 安全 → 协作 → 工程 → 进化。顺序本身就是信息。

### 0.4 适合谁读

- **管理者 / 负责 AI 产品的工程师**：需要一套**可评估、可落地、可迭代**的框架 → 这里给全景图 + 每层的代价与坑。
- **面试者**（尤其是秋招）：需要查漏补缺，知道**每一步为什么这样设计、代价是什么、坑在哪** → 这里给设计动机与取舍，而不是名词解释。
- **想从 Pi / Claude Code 里取经的人**：需要迁移思路 → 这里有工具三形态、原语、Harness 的拆解。

注意第二条里那个「为什么这样设计、代价是什么、坑在哪」——**这是本篇的隐藏主线**，后面每讲一个模块，都会跟着讲它的代价。

### 0.5 全篇的一句话立论

> **Agent 的演化，不是我们去换一个更强的模型，而是在模型固定（或更换）的情况下，通过模型之外的能力去达到一个很好的效果。**

这句话是整篇 9 篇 20 章的地基，也是后面所有模块存在的理由。**如果换模型就能解决，那这篇 20 章就没有必要存在了。**

## 1. 主线：从「会答题的模型」到「能干活的 Agent」

### 1.1 一条链：每加一层，解决一个「不够用」

作者把整本书的结构画成一条链，每一环都是因为上一环不够用才出现的：

```
① 基础模型        会回答问题，但不会干活
      ↓ 输出不稳、不守格式
② 极小内核        Prompt / Workflow / ReAct / Plan，让模型"按套路思考"
      ↓ 只会想，不会动手
③ 工具            Function Calling / MCP / CLI，让模型能改变外部世界
      ↓ 每次都从零开始，不记得历史
④ 记忆 + 上下文 + RAG   知道"之前发生过什么""我们公司有什么"
      ↓ 能做事，但不能稳定地做事
⑤ 稳定性 + 权限/沙箱/安全   给能力装上边界
      ↓ 单 Agent 顶不住复杂任务
⑥ Multi-Agent     把复杂任务拆给多个角色
      ↓ 出了问题不知道出在哪
⑦ 可观测 / 可评估 / 可上线   让系统可被度量、可被信任
      ↓ 只解决"这一次"发布，下次还得重来
⑧ Loop Engineering   让系统自己对抗熵增
```

这条链有三个特征，值得单独记下来：

| 特征 | 含义 | 对设计的启示 |
|---|---|---|
| **单向依赖** | 后面每一层都建立在前一层之上 | 不要跳级。内核没稳固就上 Multi-Agent，一定翻车 |
| **代价递增** | 越往后，工程复杂度、成本、组织成本越高 | 能用第 ② 层解决的，绝不要上第 ⑥ 层 |
| **问题转移** | 每解决一个问题，就暴露下一个问题 | 「不够用」是常态，不是设计失败 |

链条的顺序其实也回答了「该先学什么」这个问题。很多人学 Agent 的顺序是反的：先学 Function Calling、先接 MCP、先搭 RAG，最后才回头想「我这个 Agent 到底该怎么思考」。作者的顺序相反——**先解决「怎么想」，再解决「怎么做」，最后解决「怎么做好」**。

📌 **补充**：这个顺序在生产上有个很实际的体现——你在做 POC 时接一堆工具很容易显得「很 Agent」，但真正上线后，大部分 bad case 出在**内核**（该走固定流程的用了 ReAct、该循环的写成了一次性 Prompt），而不是工具不够多。

### 1.2 Harness：模型之外的一切

链条讲完，作者给了一个统括性的概念——**Harness**（转写里被听成「哈尼斯」）。

> **Harness 就是「模型之外的一切」。**

它包含两部分：

| 部分 | 内容 | 来自哪里 |
|---|---|---|
| **控制 / 流程 / 编排** | 内核模式、循环控制、工具调度、状态管理 | 传统工程里的「流程编排」 |
| **CI/CD / 可观测** | Trace、Eval、灰度发布、回滚、监控 | 传统工程里的「研发基础设施」 |

两者共同构成整个 **Harness 工程**。所以后面第 11 章作者会说：**Agent = LLM + Harness**。

📌 **补充**：Harness 这个词来自「马具」——它的作用不是让马跑得更快，而是**把马的力量导向正确的方向**。这个隐喻非常准确：模型的能力是既定的，Harness 决定这股力量是去拉车，还是去撞墙。「Scaffold（脚手架）」是近义词，但 Scaffold 更强调「支撑结构」，Harness 更强调「约束与传导」。

## 2. 极小内核：四种设计模式

这是全篇信息密度最高的一段。作者把「一个极简 Agent 的内核」归纳成 **4 种模式**，并明确说：**极小内核是这 4 种模式的混合。**

### 2.1 模式一：Prompt Engineering（单体 Prompt）

最原始形态：**一个普通的 Prompt + 一些思维链（CoT）+ 温度 / 系数之类的参数调整。** 典型写法就是一段 System Prompt（「你是一个客服助手，请先识别诉求类型，再判断是否可处理，最后按模板回答」）+ 用户输入，一次性拿到结果。

> **适用**：单点任务（分类 / 改写 / 抽取 / 简单问答）｜**代价**：模型只能「说」不能「做」，复杂任务会漏步骤、格式不稳。

这是「内核」的原子，不是被淘汰的旧东西——Pi / Claude Code 这类系统的 System Prompt，依然是最重要的资产之一。

### 2.2 模式二：Workflow（固定流程 / SOP）

当你做的是**复杂但流程相对固定的 SOP 型任务**时，就该写 Workflow——**把多个步骤编排在一起**。

```python
# 伪代码：一个典型的固定流程
def handle_ticket(user_input):
    intent   = llm.classify(user_input)              # 步骤 1：分类
    if intent == "refund":
        order = db.query_order(user_input)           # 步骤 2：查库（固定动作）
        ok    = llm.judge_refundable(order)          # 步骤 3：判断
        reply = llm.draft_reply(order, ok)           # 步骤 4：生成
    elif intent == "logistics":
        reply = llm.answer_logistics(user_input)
    else:
        reply = llm.fallback(user_input)
    return reply
```

> **适用**：流程稳定、SOP 明确、分支可枚举｜**代价**：出了预设分支就废，需求一变就要改代码。

作者的核心观点很明确：**SOP 型任务不要上 ReAct，用 Workflow 更稳更便宜。** 很多人第一反应会做错——觉得 ReAct「更 AI」，实际是在给自己制造不确定性。

### 2.3 模式三：ReAct（Reasoning + Acting 循环）

当你面对的是**开放性问题**——不知道要几步、不知道下一步该干嘛——就需要 ReAct：**通过不断的 loop 迭代，一步步完善，最终回答一个开放性问题。**

```python
# 伪代码：ReAct 循环
while not done and step < MAX_STEPS:
    thought = llm.reason(history)          # Reasoning：我现在该干什么
    action  = llm.choose_action(thought)   # Acting：选一个工具
    obs     = tools.run(action)            # 执行，拿到观察结果
    history.append((thought, action, obs)) # 观察回填上下文
    done    = llm.is_answer_ready(history)
```

关键点：**循环的每一步，上下文都在变长**——这是它能力强的来源，也是它成本和失控的来源。

> **适用**：开放问题、路径不可预知｜**代价**：可能无限循环、token 随轮数增长、路径难测。

作者在讲第 3 篇时专门点出：**「ReAct loop 它可能会进行无限循环，那你怎么控制你的循环？」**——这是 ReAct 落地的第一号问题（见 2.7 与第 7 章）。

### 2.4 模式四：Plan-and-Execute（先规划，再执行）

如果是**长任务**，就要结合 Plan：**先去规划，然后再分步执行。**

```python
# 伪代码：Plan-and-Execute
plan = llm.make_plan(task)          # ① 一次性产出结构化计划
for step in plan:                   # ② 逐步执行
    result = execute(step)          #    单步内部可以是 Workflow 或 ReAct
    if need_replan(result):         # ③ 偏离预期则重规划
        plan = llm.replan(task, plan, result)
```

> **适用**：长任务、多步骤、目标明确但路径复杂｜**代价**：计划错了整条链都错，且计划本身也吃 token。

### 2.5 四种模式横向对比

| 维度 | ① Prompt | ② Workflow | ③ ReAct | ④ Plan |
|---|---|---|---|---|
| 任务形态 | 单点 | SOP / 固定流程 | 开放问题 | 长任务 |
| 流程确定性 | 无流程 | **最高** | **最低** | 中（骨架固定、路径可变） |
| 谁决定下一步 | 模型（一次性） | 工程师 | 模型（每轮） | 模型（计划阶段） |
| 调用次数 | 1 次 | N 次（固定） | 不定（**可能很多**） | 1 + N 次 |
| 成本可预测性 | 高 | 高 | **低** | 中 |
| 可测试性 | 高 | 高 | **低**（路径不固定） | 中 |
| 主要风险 | 幻觉、不行动 | 框不住真实业务 | 死循环、发散、烧钱 | 计划质量决定上限 |
| 典型场景 | 分类 / 改写 / 抽取 | 工单、审核、报表 | 深度检索、调试、排障 | 长报告、多文件改造 |

### 2.6 关键结论：不是四选一，是「混合」

作者的原话是：**「极小内核，我认为是 4 种模式的一个混合。」**

具体怎么混，他给了两条非常实用的判断规则：

```text
规则一：任务偏「封闭型」（流程可枚举）
    → 主体用 Workflow
    → 中间那些"可变的节点"，用 ReAct 去执行
    → 例：Workflow[ 固定步骤 → ReAct 节点 → 固定步骤 ]

规则二：任务偏「开放型」（流程不可枚举）
    → 主体用 ReAct
    → 里面结合 Plan（先定骨架）或 Workflow（固化子流程）
    → 单点环节退回 Prompt
```

用图表示就是**嵌套**，而不是并列：

```
封闭型任务                          开放型任务
┌──────────────────────┐          ┌──────────────────────┐
│ Workflow（骨架固定）   │          │ ReAct（主循环）        │
│  ├─ Step 1  (固定)    │          │  ├─ Plan（先出计划）    │
│  ├─ Step 2  ┌────────┐│          │  ├─ Workflow（子流程）  │
│  │           │ ReAct  ││          │  ├─ Prompt（单点判断）  │
│  │           │ loop   ││          │  └─ Tool（行动）       │
│  │           └────────┘│          └──────────────────────┘
│  └─ Step 3  (固定)    │
└──────────────────────┘
```

> **一句话记住：封闭型用 Workflow 兜底，把不确定性关进 ReAct 那个小盒子里；开放型用 ReAct 探路，用 Plan 和 Workflow 收住它。**

### 2.7 这一层留下的三个难题（第 3 篇要解决的）

作者很坦白：这 4 种模式一用起来，立刻会遇到三个问题，这三个问题就是原著第 3 篇的主题。

| 难题 | 具体表现 | 需要回答的问题 |
|---|---|---|
| **SOP 怎么固化** | 业务口头描述的流程，怎么变成稳定的 Workflow | 边界怎么划、异常分支怎么收 |
| **循环怎么控制** | ReAct 可能无限循环 | 步数上限？token 预算？收敛判据？ |
| **计划怎么拆** | Plan 的粒度太难拿 | 拆太细浪费、拆太粗失控；何时重规划 |

📌 **补充**：这三个问题的通用解法思路是「**外置判据**」——不要指望模型自己知道该停，而是由 Harness 提供硬约束：最大步数、最大 token、最大时长、连续 N 轮无新增信息即终止。**能让代码判断的，不要交给模型判断。**

## 3. 工具：Agent 唯一能「动手」的地方

> **「当你有了这个极小内核，你需要真正去行动、去做一些事的时候，那就需要用一些工具。」**

作者把工具演进分成 **3 个体系 / 3 个形态**。这一段是全篇最有「工业感」的部分，因为它讲的是**权力如何从工程师手里转移到模型手里**。

### 3.1 三形态总览

| 形态 | 名称 | 谁定义工具 | 核心变化 | 关键词 |
|---|---|---|---|---|
| 第一形态 | **Function Calling** | 工程师（预先定义） | 让模型能「调函数」 | 契约、Schema |
| 第二形态 | **MCP** | 工程师 / 平台（标准化） | 能力可以**跨部门、跨公司共享** | 通用化、复用 |
| 第三形态 | **CLI / 原语** | **模型自己**（现场组合） | 只给原语，让模型自己写代码 | Read / Write / Bash、代码即行动 |

### 3.2 第一形态：Function Calling —— 本质是「契约」

第一形态就是 Function Calling。作者强调的重点不是「怎么调」，而是**你要定义什么**：

| 要定义的东西 | 作用 | 写不好会怎样 |
|---|---|---|
| **函数名** | 模型靠它理解「这是干什么的」 | 命名含糊 → 选错工具 |
| **输入 / 输出** | 参数结构、类型、必填项 | 类型不清 → 参数瞎编 |
| **目标** | 这个工具要达成什么 | 目标含糊 → 用错场景 |
| **描述** | 什么时候该用、什么时候不该用 | 描述缺失 → 该用时不用、不该用时乱用 |

```json
{
  "name": "query_order",
  "description": "根据订单号查询订单详情。仅在用户提供了订单号、且需核实订单状态时调用。不要用它查询用户信息。",
  "parameters": {
    "type": "object",
    "properties": { "order_id": { "type": "string", "description": "订单号，形如 SO-2026-xxxx" } },
    "required": ["order_id"]
  }
}
```

> 作者用了一个词：**契约**。工具的输入输出就是模型和系统之间的合同——**合同写得越清楚，越不会扯皮。**

📌 **补充**：description 里那句「不要用它查询用户信息」是刻意写的**负向约束**。实践中工具选错的头号原因不是模型笨，而是有多个工具的 description 语义重叠，模型无法区分。**同一类工具的描述要互斥，最好在描述里明确写出「不适用场景」。**

### 3.3 第二形态：MCP —— 把能力沉淀成「共享基础设施」

MCP 的定位，作者讲得很清楚：它其实是**沉淀了通用化的能力**，是**能够跨部门、甚至跨公司一起使用的一项能力**。

| 对比项 | Function Calling | MCP |
|---|---|---|
| 复用范围 | 单个应用内 | **跨应用 / 跨部门 / 跨公司** |
| 集成方式 | 每个应用自己写一遍 | 接一次 Server，多处复用 |
| 谁维护 | 业务方 | 能力提供方 |
| 主要价值 | 能用 | **不用重复造** |

所以 MCP 解决的不是「能不能用工具」，而是「**工具要不要每家都重写一遍**」。这是典型的工程化问题，不是 AI 问题。

📌 **补充**：MCP 协议侧提供的不止「工具」一种原语，通常还包括 Resources（可读资源，类似文件/数据）和 Prompts（预置提示模板）。三者对应「能动手」「能看」「能复用套路」，做选型时不要只盯着 tools。

### 3.4 第三形态：CLI / 原语 —— 把定义权交给模型

这是三种形态里最反直觉的一种，也是 Pi / Claude Code 的核心思想。

作者的描述是：**工具由大模型自己去定义如何执行，而不是你预先定义好工具。** 在 ReAct 的循环过程中，模型知道「我需要怎么执行」，然后通过 CLI 的**动态组合**，构造出完整的一次行动。

换句话说：工程师不再想「要做一个查询订单的工具」，而是只给 read / write / bash 这几个原语，**模型自己判断「我要读这个文件、用 grep 过滤、再写回去」，现场拼出一条命令链**，完成原本需要一个专用工具才能做的事。

| 项 | Function Calling | CLI / 原语 |
|---|---|---|
| 给模型的东西 | 一个**成品工具** | 几个**基础动作** |
| 谁做组合 | 工程师 | **模型** |
| 能覆盖的场景 | 预先想到的 | **没想到的也能覆盖** |
| 失控风险 | 低 | **高** |

作者点出了这背后的根本原因：**这个演进过程，是因为模型越来越智能，所以我们更相信模型底层的泛化能力。**

> 这句话是整个第 3 章的核心：**工具形态的演进，本质是「信任的转移」。** 你越相信模型的泛化能力，就越愿意只给它原语；你越不信，就越要把每个动作都定义死。

### 3.5 灵活性与不可控性，是一条此消彼长的曲线

> **「当然，在带来灵活性的同时，你就带来了不可控性，所以控制与失控也是这里面的一个要点。」**

```text
能力覆盖
   ↑
   │                          ╭──── CLI / 原语（几乎无上限）
   │                    ╭─────╯
   │              ╭─────╯  MCP（生态内共享）
   │        ╭─────╯
   │  ╭─────╯  Function Calling（预先定义的范围）
   │──┴──────────────────────────────────────→ 不可控性
   低                                        高
```

**没有「更好」的形态，只有「匹配」的形态：**

| 你的诉求 | 该选 |
|---|---|
| 场景固定、要稳、要审计 | Function Calling |
| 能力要给多个团队复用 | MCP |
| 场景开放、要给模型最大发挥空间 | CLI / 原语 + 沙箱 |
| 又要开放又要安全 | CLI / 原语 + **强沙箱**（见第 7 章） |

📌 **补充**：第三形态不是「Function Calling 的替代品」，而是「兜底手段」。成熟系统里三者是共存的：**高频稳定动作做成 Function Calling，跨团队能力走 MCP，长尾/未知场景用 CLI 兜底**。只留 CLI 会导致成本和延迟失控（每次都要生成代码），只留 FC 会导致遇到新场景就死。

## 4. 记忆：让 Agent 知道「之前发生过什么」

> **「光有工具还不够，那你还需要结合一些历史。」**

作者在这里给的是一张**分层记忆图**，而不是「短期 / 长期」两分了事。这是这一章最有价值的部分。

### 4.1 记忆的分层结构

```text
Memory
├── 静态记忆（一次加载内基本固定）
│   ├── ① 核心记忆：角色 / 能力（抽象能力）/ 约束
│   ├── ② 能力记忆：Skill / Tool 的描述
│   └── ③ 项目记忆：State / Workspace，例如 CLAUDE.md
└── 动态记忆（按需检索、按需加载）
    ├── ④ RAG 检索结果（ES / 向量检索）
    ├── ⑤ 图结构 / 多级摘要
    └── ⑥ 数据驱动记忆（画像 / 行为）
```

### 4.2 五层逐一说明

| 层 | 内容 | 类比 | 加载时机 |
|---|---|---|---|
| **核心记忆** | 角色是什么、能干什么、抽象能力是什么、约束是什么 | 员工手册 + 岗位说明书 | 每次必带（前缀） |
| **能力记忆** | 你提供的 Skill / Tool 的描述 | 工具箱清单 | 每次必带（前缀） |
| **项目记忆（State / Workspace）** | 当前项目的状态，长期项目要沉淀的东西 | 项目交接文档 | 进项目时加载 |
| **RAG 记忆** | 动态检索出来的知识 | 临时查资料 | 用到时检索 |
| **数据驱动记忆** | 从数据分析总结出的画像、行为、体系信息 | 用户档案 | 按需注入 |

作者特意点明了一个例子：**「比如说像 Claude 的 CLAUDE.md，都是沉淀的一些项目级记忆。」** —— 这类文件的价值在于，它把「这个项目的约定」从每次对话里的重复交代，变成了一个**可版本管理的文件**。

### 4.3 关键切分：静态 vs 动态（这一段直接决定了成本）

> **「核心记忆、Skill、Tools 在一次加载中其实是偏固定的，它们组成了静态记忆；而 State / Workspace、RAG，其实是动态记忆。」**

为什么要这么切？因为 **Token 越来越贵**，而这里有一个非常具体的省钱手段：

> **「你如果能尽量让模型的 Prompt 进行一种前缀匹配，那你就能尽量利用到 Prompt Caching，这样就会节省很大的 Token 消耗。所以如何设计你的 Prompt，也是未来的一个课题。」**

用图表示 Prompt 的排布原则：

```text
┌────────────────────────────────┐
│ ① System Prompt（角色 / 约束）  │ ┐
│ ② Skill / Tool 描述             │ ├ 静态前缀 ← 命中缓存
│ ③ 项目记忆（CLAUDE.md 等）      │ ┘
├────────────────────────────────┤
│ ④ 检索结果（RAG）               │ ← 每次都变
│ ⑤ 对话历史                      │
│ ⑥ 本轮用户输入                  │ ← 变化最频繁
└────────────────────────────────┘
        越靠前越稳定，越靠后越易变
```

**排布铁律：稳定的放前面，易变的放后面。** 一旦把易变内容插到前面，后面所有 token 的缓存全部失效。

📌 **补充**：前缀缓存（Prompt Caching）的命中条件是**从第一个 token 开始连续相同**。所以哪怕你只是在 System Prompt 中间插了一个当前时间戳，整段缓存也会作废。常见做法是把时间、用户名、会话 ID 这类变量**全部下沉到用户消息里**，System Prompt 保持字节级不变。

### 4.4 另一条分类轴：短期 / 长期 / 数据驱动

除了「静态 / 动态」，作者还给了第二条分类轴，这两条轴是交叉的，不要混：

| 类型 | 是什么 | 典型内容 | 存哪里 |
|---|---|---|---|
| **短期记忆** | 当前上下文里的东西 | 本轮对话、刚拿到的工具结果 | Context Window |
| **长期记忆** | 跨会话沉淀的东西 | 历史报错、角色偏好、项目流程规划 | 外部存储 / 文件 |
| **数据驱动记忆** | 通过数据分析总结出来的 | 用户画像、用户行为、体系信息 | 数仓 / 特征库 |

作者对长期记忆举的例子非常具体：**多次跟 Agent 交互时出现的报错、你的角色偏好、项目流程的规划**——这些写进长期记忆，下次就不用再说一遍。

而数据驱动记忆是**另一种模式驱动的**：它不是对话里产生的，而是**分析出来的**。

### 4.5 记忆不是「只加不减」

> **「那记忆里面，你就要根据不同类型进行加载、整合，甚至是遗忘一些功能，包括隐私的保护。」**

| 动作 | 做什么 | 为什么必须有 |
|---|---|---|
| **加载** | 按类型、按场景决定这次带哪些记忆 | 全带上会爆上下文 |
| **整合** | 多条记忆合并、去重、摘要 | 记忆会互相矛盾 |
| **遗忘** | 主动删除过期 / 错误 / 敏感记忆 | 错误记忆会**持续污染**后续所有决策 |
| **隐私保护** | 敏感信息脱敏、分级、隔离 | 记忆是最容易泄露的地方 |

> ⚠️ 作者把「遗忘」和「隐私」和「加载」并列讲，说明这不是可选项。**一个只会写入、不会遗忘的记忆系统，时间一长必然变成负资产。**

📌 **补充**：长期记忆的常见失败模式是「**写入无审核**」——模型自己判断「这个值得记」，结果把一次性的错误结论写成了永久事实。生产做法是给写入加一道闸：**要么人工确认，要么延迟写入（同一条信息被多次验证才落库），要么带 TTL 和置信度。**

## 5. 上下文管理与 Token 优化：记忆装不下了怎么办

这一节在原著里是独立一章，作者在视频里给了两个动机：**模型的注意力缺陷**，和**成本**。

### 5.1 动机一：Lost in the Middle

> **「我们做上下文管理，主要是应对模型……它会引发一个 Lost in the Middle：它对开头的记忆和末尾的记忆其实更关注，而中间的记忆其实是模糊的，这取决于模型的训练方法。」**

```
模型注意力（示意）：
高 │█                              █
   │ ██                          ██
低 │   ██████████████████████████
   └──────────────────────────────→ 位置
     开头        中间被忽略        末尾
```

**这意味着：即使你把所有信息都塞进去了，中间那段也约等于没塞。**

作者还补了一句关键的：**即使现在模型已经到 1M（百万级）上下文，还是会引发「长上下文下它不知道用户在描述什么」的问题。**

> 这句话很重要，它直接否掉了「等上下文够大就不用做管理了」这个幻想。**上下文变大，不等于注意力变好。**

所以结论是：**上下文管理在目前仍然不可或缺。**

### 5.2 三种通用手段

- **压缩（Compress）**：把长历史总结成摘要。代价是有信息损失，且摘要本身要花一次调用。
- **裁剪（Trim）**：直接丢弃旧轮次 / 低价值内容。代价是可能丢掉关键约束。
- **动态加载（Dynamic Load）**：不预加载，用到时再取（工具化检索）。代价是多一次往返，延迟上升。

📌 **补充**：三者不是互斥的，生产上通常是「**分层组合**」：System Prompt 与最近 N 轮永不全量压缩 → 中期历史做滚动摘要 → 远期历史只留索引，需要时用检索工具捞回来。另外「裁剪」要特别小心**约束类信息**（如「不要退款超过 500 元」），这类内容一旦被裁掉，Agent 就会违规。

### 5.3 动机二：Token 就是钱，ROI 是硬指标

> **「现在 Agent 也逐步成熟了，一家公司在关注 Agent 上面，不仅关注它的效果，也关注它的损耗，因为要算 ROI 了。」**

所以两件事变成必做项：

| 事项 | 为什么 |
|---|---|
| **模型选型** | 不是所有节点都需要最强模型。分类用小模型、生成用大模型是常规做法 |
| **成本监控** | 没有监控就没有优化。要能看到「哪个环节在烧钱」 |

作者还点了一个很容易被忽略的因果：**「包括我们上面讲的 ReAct loop，其实不断地循环、不断地循环，消耗的都是成本。」**

原因很简单：**每一轮都要把「全部历史」重新送进模型**，单轮成本随轮数上升，累计成本近似平方级。所以「循环控制」既是稳定性问题，也是成本问题——**同一个开关，管两件事。**

## 6. RAG：知识工程，不是「接个向量库」

作者把 RAG 单独拎出来称为「知识工程」，并且明确分成**离线**和**在线**两个阶段。这个两分法很重要——**大部分 RAG 效果差，问题都出在离线阶段，但所有人都在调在线阶段。**

### 6.1 两阶段全景

```text
【离线】把原始数据变成"可检索的知识"
  原始数据 ──① ETL──→ 知识沉淀 ──② Chunk──→ 可检索知识（索引）
              ├─ 数据清洗（去噪 / 去重 / 统一格式）
              ├─ 数据挖掘（抽取结构化信息）
              └─ 数据整合（多源合并 / 对齐）

【在线】把"检索结果"变成"准确的答案"
  用户问题 ──③ Query 改写/扩写──→ ④ 多路检索（向量/关键词/图）
           ──→ ⑤ Rerank ──→ ⑥ 指标判定 + 生成 ──→ 准确答案
```

### 6.2 离线阶段：三步 ETL + 一次分块

作者的原话是「如何做 ETL，就是我们通常讲的数据清洗、数据挖掘，然后做数据整合，大概这三步」。

| 步骤 | 做什么 | 做不好的后果 |
|---|---|---|
| **数据清洗** | 去噪、去重、统一格式 | 检索出来的全是垃圾片段 |
| **数据挖掘** | 从非结构化内容里抽出结构化信息 | 关键字段检不到 |
| **数据整合** | 多源数据合并、对齐、消歧 | 同一实体有多个版本，答案自相矛盾 |
| **分块（Chunk）** | 把长文档切成可检索单元 | 切太大 → 噪声多；切太小 → 语义断裂 |

> 注意顺序：**先 ETL，再 Chunk。** 很多人是先切块再想清洗，结果脏数据被切得更碎，永久留在索引里。

### 6.3 在线阶段：五个动作，一个都不能省

| 动作 | 作用 | 省掉的后果 |
|---|---|---|
| **Query 改写 / 扩写** | 把口语化问题变成可检索的查询；补全指代 | 用户说「这个怎么退」，检索不到任何东西 |
| **多路检索** | 向量 + 关键词 + 图，互补召回 | 单路召回率上不去 |
| **Rerank** | 对候选集重新排序，把真正相关的顶上来 | 前几条是「看起来像」而不是「真的对」 |
| **指标判定** | 判断检索质量够不够、要不要兜底 | 检不到也硬答 → 幻觉 |
| **生成** | 基于证据作答，而不是凭记忆作答 | 答案不可溯源 |

### 6.4 一张「症状 → 病根」对照表

| 症状 | 大概率病根 | 先改哪里 |
|---|---|---|
| 检索不到明明存在的内容 | Chunk 切分 / 清洗 | **离线** |
| 检索到了但排序很靠后 | 缺 Rerank / 单路召回 | 在线 |
| 答案和文档对不上 | 生成没用证据约束 | 在线（Prompt） |
| 同一问题两个答案 | 数据整合没做消歧 | **离线** |
| 口语提问检索为空 | 缺 Query 改写 | 在线 |

📌 **补充**：RAG 的评估必须**分阶段**做（召回率、排序质量、答案忠实度分开测），否则你永远不知道是检索错了还是生成错了。这也是本目录第 4 篇《用 Langfuse 搭建评测闭环》要解决的问题——**不上 Trace，RAG 调优就是盲调。**

## 7. 稳定性与安全：让 Agent 别把库删了

> **「有了这些东西，其实 Agent 能够做事了，但是它不能稳定地做事。所以需要添加一些稳定性或者说权限的东西。」**

这一章作者分成两半：**稳定性**（出错怎么办）和**安全**（不让它乱来）。

### 7.1 稳定性：先把错误分类，再谈解决

> **「 Agent 在整个过程中可能会有各种各样的错误，比如说你要把你的错误进行一个分类——这类错误可能需要有一个解决方案，那类错误有另外一个解决方案。」**

| 错误类型 | 表现 | 处理策略 |
|---|---|---|
| **格式错误** | 输出不是合法 JSON / 缺字段 | Schema 校验 + 重试（带错误信息） |
| **工具错误** | 参数不对、工具报错、超时 | 把错误当观察结果回填，让模型重试 |
| **逻辑错误** | 步骤跳了、判断错了 | 检查点 / 自检 / Reflection |
| **循环错误** | 反复调同一个工具，原地打转 | 步数上限 + 重复检测 + 强制终止 |
| **环境错误** | 网络、权限、依赖不可用 | 降级 / 兜底话术 / 转人工 |

关键设计原则：**错误不能中断流程，要变成「上下文的一部分」。** 把 `tool_error: xxx` 塞回 history，模型下一轮就知道该怎么绕——这就是作者说的「**让 Agent 在出错的情况下也能够自愈**」。

### 7.2 三个具体机制

| 机制 | 解决什么 | 怎么做 |
|---|---|---|
| **死循环控制** | ReAct 无限循环 | 最大步数 / 最大 token / 最大时长；连续 N 轮无新增信息即停 |
| **Schema 校验** | 输出不可用 | 用结构化约束（JSON Schema / 严格模式），校验失败带原因重试 |
| **自愈** | 一次失败就整条链崩 | 错误回填 + 有限次重试 + 降级路径 |

### 7.3 安全：四道墙

作者的引子非常生动：

> **「 Agent 如果不给它加任何权限，它删库跑路怎么办？人和人删库跑路你还可以管，Agent 删库跑路其实就不好管了。」**

所以他给的方案是**层层收窄的活动范围**：

```text
① 租户隔离        租户 ↔ 租户 之间不能串
└─ ② 工作空间隔离   工作区 ↔ 外部 之间不能串
   └─ ③ 沙箱（核心）  约束 workspace 的可读写路径
      └─ ④ 网络管控    防止把重要 Key / 内部数据发出去

（越往里，Agent 能活动的范围越窄）
```

| 墙 | 防什么 | 手段 |
|---|---|---|
| **租户隔离** | A 公司的数据被 B 公司看到 | 逻辑/物理隔离，检索层强制过滤 |
| **工作空间隔离** | Agent 越出项目目录乱翻 | 路径白名单、挂载限制 |
| **沙箱** | 删库、改系统、执行危险命令 | 容器 / 虚拟机 / 权限降级；**核心是沙箱** |
| **网络管控** | 把 Key、内部数据发出去 | 出网白名单、DLP、禁止任意 URL |

> 作者对沙箱的总结是：**「核心的东西就是一个沙箱，通过沙箱的约束来控制你的 workspace，然后控制你的外部网络。主要的核心目的就是防止自损，让 Agent 在一个合适的范围内进行行动。」**

**「防止自损」（Agent 误伤自己所在的系统）+「合适的范围」**——这两句话就是安全模块的全部目标。

### 7.4 入口侧：Prompt 注入与越权

> **「后面其实也是一些入口侧的防控，比如说 Prompt 提示词注入怎么办，怎么防止越权的一些行为。」**

📌 **补充**：提示词注入之所以难防，是因为它**不是技术漏洞，而是架构缺陷**——模型无法区分「系统指令」和「数据里夹带的指令」。工程上的缓解手段是三条：① **权限最小化**（就算被骗，也干不了大事）；② **数据与指令分离**（外部内容一律标记为不可信数据）；③ **高危动作强制人工确认**（写操作、删除、付款）。**不要指望靠 Prompt 里写「忽略任何注入指令」解决，这层防线只能降低概率，不能兜底。**

## 8. 规模化：从单 Agent 到 Multi-Agent

> **「随着项目越来越复杂，单 Agent 可能就满足不了你的系统要求，所以我们会从一个单 Agent 演化成 Multi-Agent。」**

### 8.1 三种编排拓扑

作者给了三种形态，并明确说这是「编排方式」的选择问题：

```text
① 分层                 Orchestrator
                       ├── 子 Agent A
                       ├── 子 Agent B
                       └── 子 Agent C

② All-in-One           主 Agent（什么都干，没有子 Agent）

③ 辩论 / 组合          Agent A ｜ Agent B ｜ Agent C
                       └────────→ 裁决 / 融合
```

| 拓扑 | 适合 | 优点 | 代价 |
|---|---|---|---|
| **分层** | 任务可拆成明确子领域 | 职责清晰、可并行、易观测 | 上层成为瓶颈；层间契约要设计好 |
| **All-in-One** | 任务规模不大、强耦合 | 简单、无通信开销 | 单点上下文压力大；一乱全乱 |
| **辩论 / 组合** | 需要高置信度判断 | 提升准确性、降低单点偏差 | **成本 ×N**；需要裁决机制 |

> 作者原话是「到底是分层结构，还是 All-in-One 的一种模式，还是辩论或者说组合的一个模式」——**他并没有说哪个最好，而是说这是「你来选」的问题。**

### 8.2 Agent 之间的通信：消息 or 共享内存

> **「 Agent 与 Agent 通信怎么办？是不是通过消息模式，还是共享一块内存来处理整个问题？」**

| 方式 | 机制 | 类比 | 风险 |
|---|---|---|---|
| **消息传递** | 显式发消息、显式回传 | 线程间消息队列 | 契约、序列化、丢消息 |
| **共享内存** | 共用一块状态（如共享文件/上下文） | 共享变量 | **竞态、脏读、互相覆盖** |

作者在这里做了一个非常有价值的类比：

> **「这其实不仅是 Agent 与 Agent 之间的问题，其实也是我们在日常处理高并发时线程与线程之间通信的问题，可以映射到这个点里面。」**

📌 **补充**：这个映射很实用。线程通信的经典结论可以直接搬过来：**共享可变状态是万恶之源**。所以多 Agent 系统里，优先「消息传递 + 单一写入者」，避免多个 Agent 同时改同一份状态。真需要共享，就像数据库那样加锁或版本号。

### 8.3 什么时候才该上 Multi-Agent

| 信号 | 说明 |
|---|---|
| ✅ 任务能**自然拆成独立子领域** | 拆分成本低于协调成本 |
| ✅ 子任务**可并行**，且各自上下文很重 | 单 Agent 上下文塞不下 |
| ✅ 需要**不同角色视角**（评审、对手） | 辩论模式有收益 |
| ❌ 只是「觉得 Multi-Agent 更高级」 | 协调成本会吃掉全部收益 |
| ❌ 单 Agent 的 Prompt 还没调好 | **先修内核，再拆架构** |

## 9. 工程落地：可观测 / 可评估 / 可上线

> **「随着你的 Agent 任务越来越复杂，你需要知道哪边出了问题，或者说我到底是在哪个节点是有问题的。所以你需要可观测、可评估。」**

作者把这块拆成两件事，然后加上第三件「上线」。

### 9.1 三个「可」的关系

```text
① 可观测（Trace）──提供数据──→ ② 可评估（Eval）──提供判据──→ ③ 可上线（灰度 / 回放 / AB）
   发生了什么                    这样算不算好                    敢不敢放量
```

**顺序不能颠倒**：没有 Trace，Eval 就没有输入；没有 Eval，灰度就没有判据（只能靠感觉放量）。

### 9.2 可观测：全链路 Trace

> **「全链路的 Trace 怎么做。」**

一个 Agent 请求的 Trace 不是一条日志，而是一棵树：

```text
trace: session-xxx / turn-3
├── llm.call          (system + user → assistant，含 thought)
├── tool.read_file    (path=... → 内容摘要)
├── llm.call
├── tool.bash         (cmd=... → stdout / stderr)
├── llm.call          ← 这一步决定"要不要停"
└── answer            (tokens: prompt/completion ｜ latency: 各 span 耗时)
```

必须能回答的四个问题：**走了几步、每步花了多少 token、哪一步慢、哪一步开始跑偏。**

### 9.3 可评估：四件套

| 组成 | 内容 |
|---|---|
| **目标** | 这个 Agent 到底要达成什么（可判定的目标） |
| **测试集** | 覆盖典型场景 + 边界 + 历史 bad case |
| **指标** | 正确率 / 完成率 / 工具调用准确率 / 成本 / 延迟 |
| **漏斗拆解** | 把端到端指标拆到每一层，定位是哪一层掉的 |

作者特别提到 **「能力边界相关的东西」**——即你要测的不只是「它能不能做对」，还要测「**它在什么情况下会做错，以及做错时会不会承认**」。

### 9.4 可上线：四种手段

| 手段 | 作用 |
|---|---|
| **版本回滚** | 出问题能立刻退回上一个版本 |
| **流量回放** | 用真实历史请求重跑新版本，对比差异 |
| **A/B 实验** | 小流量对比，用数据决定 |
| **快照** | 固定输入集 + 固定输出，做回归基线 |

> 作者的原则：**「你需要去有的放矢地去放量，然后去进行一些灰度。」** —— **Agent 的好坏其实取决于 A/B**，不能靠 demo 拍脑袋。

📌 **补充**：Agent 的 A/B 比传统服务难，因为**输出不是确定性的**。可行做法是：① 用固定评测集做离线回归（可重复）；② 线上用「任务完成率 + 人工抽检」这类**结果指标**，而不是逐字比对；③ 对同一输入采样多次，看稳定性而不只看单次。

## 10. Loop Engineering：让 Agent 自己变好

> **「上面这些问题只是解决你单次 Agent 发布的问题。而你需要让你的 Agent 持续变好，或者说让它自动化变好。」**

### 10.1 闭环长什么样

```text
① 收集 Bad case（线上真实失败）
     ↓
② 分类归因（缺知识？缺流程？缺工具？）
     ↓
③ 形成机制：更新 SOP / 沉淀 Skill / 补知识库
     ↓
④ 回归验证（跑评测集，确认没退化）
     ↓
⑤ 灰度发布
     │
     └──────────→ 回到 ①，持续循环
```

作者举的例子正好是 RAG：**「比如说像 RAG，我们通过分析 Bad case 能够自动补全里面的一些信息。」**

### 10.2 为什么叫「对抗熵增」

> **「因为我们系统的知识其实是业务知识，其实是持续增加的，本质上也是对抗熵增，让 Agent 能够自我进化。」**

这个说法很精准：**业务在变，知识在膨胀，昨天对的答案今天就是错的。** 一个不更新的 Agent 不是「保持不变」，而是「持续变差」——因为它面对的世界在漂移。

| 不进化 | 会进化 |
|---|---|
| 每次 bad case 靠人肉修 | bad case 自动变成资产 |
| 知识库逐渐过期 | 知识库持续校准 |
| Prompt 越改越乱 | 有回归保护，改动可验证 |

### 10.3 最后一公里：人机协作与产品化

> **「 Agent 产品中肯定也会涉及到一些交互、信任，或者中断管理……怎么把 Agent 产品化，让人和 Agent 之间能够和谐共处，是这章需要讲的一个重点。」**

| 概念 | 含义 |
|---|---|
| **信任** | 用户要知道它什么时候可能错、错到什么程度 |
| **中断管理** | 长任务要能暂停、干预、接管、恢复 |
| **人机协作** | 不是「全自动」或「全手动」，而是分级授权 |

📌 **补充**：「中断管理」在生产上是刚需但最容易被漏掉的一环。具体要实现三件事：**可暂停**（长任务有检查点）、**可接管**（人能改中间状态）、**可恢复**（从检查点继续而不是重跑）。这三件事没做，Agent 就只能做「几秒钟内能完成」的任务，永远上不了长流程。

| 不知道要几步才能解决 | **ReAct** | 让模型现场探索 |
| 长任务、步骤多 | **Plan-and-Execute** | 先有全局骨架 |
| 流程固定但中间某步不确定 | **Workflow + ReAct 节点** | 把不确定性关进小盒子 |
| 工具要给多个团队用 | **MCP** | 一次建设，多处复用 |
| 场景开放、工具想不到 | **CLI / 原语 + 沙箱** | 靠模型泛化兜底 |
| 要记住项目约定 | **项目记忆（CLAUDE.md 类）** | 可版本管理 |
| 要回答公司内部知识 | **RAG** | 证据驱动，可溯源 |
| 单 Agent 上下文顶不住 | **Multi-Agent 分层** | 拆上下文，不是拆时髦 |

本篇是整个 agent 专题的**第 1 篇（总览篇）**，职责是把架构地图立起来。另外三篇是在这张图上往下钻：

## 15. ✅ 落地检查清单

拿去评审一个 Agent 设计，逐条打勾。

### 定位与内核

- [ ] **1. 这个任务的形态说清楚了吗？** 是封闭型（流程可枚举）还是开放型（流程不可枚举）？——决定用 Workflow 还是 ReAct。
- [ ] **2. 有没有「模式混用」的设计？** 封闭型任务里，可变节点是否用 ReAct 单独包起来，而不是整条链都交给模型？
- [ ] **3. 内核的边界写下来了吗？** 哪几步是写死的、哪几步是模型决定的，能在图上指出来吗？

### 行动与工具

- [ ] **4. 每个工具的「契约」完整吗？** 名字 / 输入输出 / 目标 / 描述四件套齐全，且描述里写了**不适用场景**。
- [ ] **5. 有没有该走 MCP 却被重复实现的能力？** 跨团队复用的工具是否已经沉淀。
- [ ] **6. 用了 CLI / 原语的话，沙箱配了吗？** 没有沙箱的 CLI 等于把生产环境交给模型。

### 记忆与上下文

- [ ] **7. 记忆分层了吗？** 核心记忆 / 能力记忆 / 项目记忆 / RAG / 数据驱动，各自存在哪、什么时候加载。
- [ ] **8. Prompt 的排布是「稳定在前、易变在后」吗？** 有没有变量（时间戳、用户名）插在静态前缀中间，导致缓存全废。
- [ ] **9. 有「遗忘」机制吗？** 过期、纠错、敏感信息删除的路径是否存在。
- [ ] **10. 上下文超限时的降级策略定了吗？** 压缩什么、裁剪什么、绝不裁什么（约束类信息）。

### 边界与协作

- [ ] **11. 错误分类表有了吗？** 每一类错误对应的处理策略（重试 / 回填 / 降级 / 转人工）。
- [ ] **12. 死循环的三道闸设了吗？** 最大步数、最大 token、最大时长，以及「连续 N 轮无新增信息即停」。
- [ ] **13. 最坏情况推演过吗？** 「如果模型被注入、被误导，它能造成的最大破坏是什么」——租户隔离、工作空间隔离、沙箱、出网白名单是否覆盖。
- [ ] **14. 上 Multi-Agent 的理由写下来了吗？** 是因为任务真的可拆，还是因为「听起来更高级」；Agent 间是消息传递还是共享状态。

### 工程与进化

- [ ] **15. 三个「可」闭环了吗？** Trace 能看到每一步 → Eval 有测试集和指标 → 灰度有回放和回滚；以及 bad case 有没有一条路径回流成 SOP / Skill / 知识。

## 16. 一句话总结

> **这篇综述讲了一件事：Agent 不是「一个更聪明的模型」，而是「一个围绕模型建起来的系统」。**
>
> **从内核的四种模式，到工具的三种形态，到记忆的分层、上下文的取舍、边界的设定、协作的拓扑、工程的三件套，最后到自我进化的闭环——每一层都在回答同一个问题：模型不会的那部分，你打算怎么补。**
>
> **所以「从零到一设计 Agent」，本质上不是「从零到一写 Prompt」，而是「从零到一设计一个操作系统」。**
>
> **模型决定上限，Harness 决定你能不能摸到那个上限。**
