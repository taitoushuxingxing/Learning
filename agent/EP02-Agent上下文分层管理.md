## 0. 坐标系：这是 8 层总图里的 L4

《从零到一设计 Agent》给过一张 8 层总图：

```
┌──────────────────────────────────────────────────────────┐
│  L8  进化     Loop Engineering：让 Agent 自己变好          │
│  L7  工程     可观测 / 可评估 / 可上线（Trace、评测集）      │
│  L6  协作     单 Agent → Multi-Agent，分工与回传           │
│  L5  边界     稳定性与安全：权限、沙箱、Human-in-the-loop   │
├──────────────────────────────────────────────────────────┤
│  L4  上下文 ★本文★  分层 / 加载 / 压缩 / 保护 / 隔离        │
│              决定「模型这一刻看到什么」                     │
├──────────────────────────────────────────────────────────┤
│  L3  记忆     存什么、怎么取（短期 / 长期 / 数据记忆）       │
│  L2  行动     工具与 Tool Result：Agent 唯一能动手的地方     │
│  L1  内核     极小内核 + 四种设计模式                       │
│  L0  模型底座 无状态计算引擎、窗口、KV Cache、计价           │
└──────────────────────────────────────────────────────────┘
```

**为什么 L4 值得单独抽一集？** 因为 L0~L3 的产出最后都要经过 L4 才起作用：

| 层 | 它产出的东西 | 到 L4 变成了什么 |
|---|---|---|
| L0 模型底座 | 窗口大小、KV Cache、按 token 计价 | 硬约束：**装不下就是装不下，装多了就是更贵** |
| L1 内核 | 任务拆解、循环 | 每一轮都会**重新组装一次上下文** |
| L2 行动 | 工具调用与 Tool Result | 上下文增长最快的来源（一次 `cat` 就是几千 token） |
| L3 记忆 | 长期记忆、知识 | 需要被**按需搬进**上下文，不能常驻 |

作者把这篇定位成「综述」——上一期讲「从 0 到 1 把 Agent 搭起来」，这一期把其中**上下文工程**那一块抽出来讲透。

## 1. 定义：上下文到底是什么

### 1.1 第一基石：大模型是「无状态的计算引擎」

> **大模型的本质是一个无状态的计算引擎。**

「无状态」的意思是：它不记得你上一轮说过什么。所谓「多轮对话」，是**你在客户端把之前的对话又拼了一遍发过去**，模型看到的永远是一次性的完整输入。

作者补了一句关键限定：

> 网上说模型内部有 KV Cache、各家厂商也做了缓存，你可以说它「有缓存」；但**对我们做大模型应用的人来说，基本上可以先把它当成无状态来理解**——因为你每次其实都要把 prompt 重新给它。

| 认知 | 后果 |
|---|---|
| 「模型会记住」 | 你会以为上下文是模型的属性，于是不去设计它 |
| 「模型每次都从零读一遍我发的东西」 | 你会意识到**上下文是一份你可以设计的输入**，是产品的一部分 |

📌 补充：这还意味着「多轮对话」本质上是一个压缩问题——能不能在保持效果的前提下少发一点，直接决定成本与延迟。

### 1.2 上下文 = 某一次请求里放进模型的全部内容

> **所谓上下文，就是在某一次请求里面你放进模型里的全部内容。**

它不是一个单一概念，而是**一个组装出来的概念**。作者在幻灯片里拆成 9 块：系统提示词、工具清单、项目规划、Memory、当前任务、历史对话、Tool Result、文本内容、当前运行状态。

按「谁写的」和「变化频率」归类，这一步直接决定了能不能吃到 Prompt Cache：

| # | 组成 | 谁写的 | 变化频率 | 能否前缀缓存 |
|---|---|---|---|---|
| ① | System Prompt | 你（开发者） | 几乎不变 | ✅ 最该缓存 |
| ② | 工具清单（tool / skill schema） | 你 | 低（加工具时才变） | ✅ |
| ③ | 项目规划 / CLAUDE.md | 你 + 用户 | 低（改文件时才变） | ✅ |
| ④ | Memory | 系统（写入）+ 检索（读出） | 中 | ⚠️ 半缓存 |
| ⑤ | 当前任务 | 用户 | 每任务一次 | ⚠️ |
| ⑥ | 历史对话 | 模型 + 用户 | **每轮都变** | ❌ |
| ⑦ | Tool Result | 工具 | **每轮都可能爆量** | ❌ |
| ⑧ | 文本内容 | 工具 / 用户 | 高 | ❌ |
| ⑨ | 当前运行状态（Task State） | 框架 | 高 | ❌ |

**这张表是全文的地基**：前 3 行稳定、后 6 行动荡。第 3 章的「分层」就是要把这条分界线变成架构。

### 1.3 上下文 vs 记忆：工作台与档案库

这两个词在企业里被混用得最厉害。作者用了一个很好记的类比：

| | 上下文（Context） | 记忆（Memory） |
|---|---|---|
| 类比 | **工作台 / 办公桌** | **档案室 / 图书馆** |
| 容量 | 桌上最多摆几样工具，**窗口有限** | 人脑能放很多本书，**档案近乎无限** |
| 怎么取用 | 已摆在桌上，**抬手就能用** | 需要**触发机制去唤起**（检索） |
| 追求 | 有限窗口里**装得下、用得上** | 持续存储里**存得对、找得到** |
| 设计机制 | 组装、排序、压缩 | 写入、索引、检索、遗忘 |
| 出问题的样子 | 溢出、被噪声淹没、中间内容丢失 | 检索不到、检索到错的、越存越脏 |

> 作者的总结句：**窗口是有限的，但是档案是无限的。**

由此推出上下文管理的第一条基本原则——**按需存取**：

> 你必须在你工作台上摆放**你正在工作中的、合适的图纸和工具**。

不是把所有资料都摊在桌上（放不下，也找不到重点），也不是全塞进档案室（用的时候调不出来）。

**记忆本身也是分层的**，因为记忆和上下文有交集：

| 记忆类型 | 内容 | 和上下文的关系 |
|---|---|---|
| **短期记忆** | 当前任务的来龙去脉（刚才干了什么、为什么这么干） | **基本常驻在上下文里** |
| **长期记忆** | 跨会话的用户偏好、历史决策、长期事实 | **按需加载**，用时才在 |
| **数据记忆** | 文档、产品资料、数据库 | **叠加态**：有时用得到，有时用不到 |

> 「叠加态」是作者原话，很准确：数据记忆在被检索命中之前，既在又不在。

**为什么记忆不是越多越好**：随着 Agent 干活越来越多，记忆越来越杂，会出现两个退化——① **恶化**：旧信息和新信息冲突，模型开始前后矛盾；② **Lost in the Middle**：上下文太长时模型对**开头和结尾**更敏感，**中间部分会「迷失」**。所以「记忆越多越好」是错的，上下文管理的职责就是在记忆膨胀过程中保住信噪比。

### 1.4 四个概念：Context / Memory / Knowledge / State

```
Context（这一次请求真正发出去的东西）
 └─ Memory     用户偏好 / 历史决策 / 长期事实      → 检索后注入
 └─ Knowledge  文档 / 产品资料 / 数据库            → RAG 后注入
 └─ State      当前步骤 / 变量 / 任务状态          → 每轮动态组装
```

> 原话：**Context 里面都会聚合 Memory、Knowledge 和 State。**

| 概念 | 里面装什么 | 存放位置 | 进入上下文的方式 |
|---|---|---|---|
| **Context** | 上面全部 | 只在这一次请求里存在 | 每轮重新组装 |
| **Memory** | 用户偏好、历史决策、长期事实 | 持久存储（文件/DB/向量库） | 检索后注入 |
| **Knowledge** | 文档、产品资料、数据库 | 外部知识源 | RAG 检索后注入 |
| **State** | 当前步骤、变量、任务状态 | 会话存储 / 文件 | **每轮动态组装** |

📌 补充：这层嵌套有个实用推论——**Memory 和 Knowledge 是「源」，Context 是「快照」，State 是「游标」**。线上出问题时，如果只有 Trace 没有 State 快照，就没法复现「模型当时为什么那么判断」。

### 1.5 上下文管理只管三件事

| 问题 | 管什么 | 对应章节 |
|---|---|---|
| **装什么** | 当前窗口里能看到的所有东西，帮助模型做**长期决策** | 第 1 章 |
| **怎么装** | 装的顺序、分层、按需加载的时机 | 3.1 / 3.2 |
| **满了怎么办** | 上下文溢出：**压缩、遗忘、外置** | 3.3 / 3.4 / 3.5 |

> 「满了怎么办」作者给了三个词：**压缩（Compaction）、遗忘（Forget）、外置（Offload）**——这三个词就是第 3 章后半段的骨架。

## 2. 四层原因：为什么非管不可

视频把「为什么」归成四条，且**由浅到深、由显性到隐性**：第一层是物理约束，第四层是很多人完全没意识到的隐性成本。

### 2.1 四层原因的分层图

```
╔══════════════════════════════════════════════════════════════════╗
║ ④ 隐性成本层：Prompt Cache 的脆弱性                              ║
║   「前缀改一个 token，整段缓存全失效 → 省下的 token 又还回去了」    ║
║   症状：账单没降、首 token 延迟没降   → 解法：分层 + 前缀稳定        ║
╠══════════════════════════════════════════════════════════════════╣
║ ③ 经济层：性能与成本                                             ║
║   「上下文越大 → 回答越慢 + 按 token 计费越贵」                    ║
║   症状：用户等得烦、财务算不过账      → 解法：按需加载 + 压缩        ║
╠══════════════════════════════════════════════════════════════════╣
║ ② 认知层：放得进去 ≠ 用得上                                      ║
║   「噪声污染判断 + Lost in the Middle：中间的内容模型看不见」       ║
║   症状：答非所问、忘掉中间给过的约束   → 解法：分层 + 就近 + 保护     ║
╠══════════════════════════════════════════════════════════════════╣
║ ① 物理层：窗口不是无限的                                         ║
║   「Claude 4.6 做到 100 万 token，读几千行源码跑二三十轮就没了」    ║
║   症状：任务跑到一半爆窗口、被迫中断   → 解法：压缩 + 外置 + 隔离     ║
╚══════════════════════════════════════════════════════════════════╝
      ↑ 越往上越隐蔽、越容易被忽略，也越吃工程能力
```

### 2.2 四层原因一张表

| 层 | 是什么 | 为什么需要管 | 触发条件（什么时候暴露） | 典型做法 |
|---|---|---|---|---|
| **① 物理层** | 窗口有硬上限，每轮都要全量重装 | 爆掉只是时间问题，不是概率问题 | 长任务 + 大文件阅读；二三十轮之后 | 压缩、外置到文件、子 Agent 隔离 |
| **② 认知层** | 放进去的内容会互相干扰，中间位置会被忽略 | 能放进去不代表应该放进去，噪声会污染判断 | 塞了大量「可能有用」的资料、检索结果 | 分层、就近优先、核心区放头尾 |
| **③ 经济层** | 上下文长度直接换算成延迟和钱 | 成本高于人工，方案就没有价值 | ToB / ToC 真实用户、高频调用 | 按需加载、差异化压缩、摘要 |
| **④ 缓存层** | Prompt Cache 是**前缀匹配**，极其脆弱 | 前缀一变缓存全失效，成本与延迟双升 | System Prompt 里有时间戳 / 随机 ID | 前缀字节级稳定、动态内容下沉 |

### 2.3 ① 物理层：窗口不是无限的，所以每轮都要重装

最容易被「百万上下文」的宣传麻痹的一层。

> 作者原话大意：窗口看似比较大，比如 **Claude 4.6 已经把窗口做到 100 万 token**，听起来很大；但你在读**几千行源码**做长任务的时候，**二三十轮这上百万 token 就没了**。

拆一下这笔账（📌 补充的估算，帮助理解）：

| 消耗项 | 单次体量（估） | 30 轮累计 |
|---|---|---|
| System Prompt + 工具清单 | 3k ~ 8k | 3k ~ 8k（不变，但每轮都发） |
| 读进来的源码 | 20k ~ 60k | 20k ~ 60k（常驻） |
| 每轮 Tool Result（grep / cat / 命令输出） | 3k ~ 10k | **90k ~ 300k** |
| 累加的历史对话 | 每轮 +2k ~ 5k | **60k ~ 150k** |
| 合计 | — | **轻松越过 200k ~ 500k** |

关键洞察不是「100 万够不够」，而是：**因为模型无状态，上下文不是「攒起来」的，是「每轮重建」的。** 你第 30 轮付的钱，是前 29 轮所有内容的总和再加一遍。所以爆掉不是平滑逼近，而是**某一轮突然就爆了**。

### 2.4 ② 认知层：能放进去，不代表应该放进去

全篇最容易被低估的一句。论证分两段：

**第一段：噪声会污染判断。**

> 虽然上下文窗口有这么多，它好像都能放；但是还隐藏着一个机制——**如果你的上下文都是噪声，那模型的判断就会被这些噪声影响**。

后果不是「答得慢」，而是「**答错，而且错得很有道理**」——模型会拿无关信息去构建推理链。

**第二段：注意力机制（Lost in the Middle）。**

> 模型只会对**开头的和结尾的**更加关注，对**中间的**会进行一个「迷失」。

合起来推出：**怎么利用上下文，其实比怎么把更多东西塞进去更加重要。** 工程推论很直接：

> 上下文管理就是——把**最重要的放在开头或者结尾**，中间的**该删的删、该压缩的压缩**。

📌 补充：这解释了为什么「把所有相关文档都塞进去让它自己找」在小 demo 上有效、一上生产就崩；也解释了 RAG 为什么必须先**重排（rerank）**再注入——不是「检索到就放」，而是「放进去的必须排对位置」。

### 2.5 ③ 经济层：性能与成本

做 ToB / ToC 的 Agent 时会最先撞上这一层，因为对面是真人。

| 维度 | 机制 | 用户/老板的感受 |
|---|---|---|
| **性能（延迟）** | 上下文越大，模型回答速度越慢 | 「怎么转半天才出字」——需要及时响应的场景体验很差 |
| **成本（账单）** | 输入 token 与输出 token 分开计价，越长越贵 | 「这个月 API 账单怎么这么高」 |

作者把它提到商业判断的高度：

> 企业级搭建 Agent 的核心诉求其实就是**降本增效**。**如果你的 Agent 的调用成本比人工还高，你整个方案可能就没什么价值。**

📌 补充：这话有个常被忽略的反面——不是所有场景都该压到最省。**低频、高价值、正确率优先**的场景（如一次合同审阅），多花 3 倍 token 换 5% 准确率是划算的。上下文管理的第一件事是**知道自己站在「省钱」和「别错」之间的哪一边**。

### 2.6 ④ 缓存层：隐藏成本——Prompt Cache

作者认为「很多 AI 应用开发工程师不会注意」的一层，也是第 5 章六大坑的头号坑。

**机制：服务器做的是前缀匹配的缓存。**

> 因为服务器其实会做**前缀匹配**的缓存：前缀不变就基本可以复用。但要注意——**前缀如果你改动一个 token，那整段缓存都会失效。**

```
✅ 命中
 [System Prompt 一致][工具清单 一致][历史前 N 轮 一致][新一轮]
 └──────────── 整段复用，按缓存价计费 ────────────┘

❌ 未命中（System Prompt 里加了时间戳）
 [System Prompt: "...当前时间 2026-09-14 21:03:07..."][工具清单]...
                  ↑ 就这一个 token 变了
 └──── 从这里开始全部失效，整段按原价重算 ────┘
```

**这条机制直接决定两件事**：① 上下文怎么排布是「有钱的味道」的——稳定的放前面，易变的放后面；② 缓存的脆弱性就是设计上下文的第一约束——不是「尽量少 token」，而是「**尽量保证前缀能完全匹配**」。

作者点名了两家走这条路的产品：

> **Claude Code 和 Codex 走的是这条路**：基本上都是**把底稿压实好、把底稿保留好**，做的是一个**尽量命中缓存**的策略。

> 「压实底稿」很传神：**底稿 = 那些永远不变的前缀（身份、规则、工具、项目约定）**。底稿压得越干净越稳定，后面每一轮就越便宜。

## 3. 六条落地策略（重点）

视频把「怎么做」抽象成 6 条，并明确了主次：

> **这 6 条策略的第一要义就是分层，这是 6 条策略里面一切的基础**，也是应对 Prompt Cache 的核心要义。

| # | 策略 | 一句话 | 治什么病 | 企业必备? |
|---|---|---|---|---|
| 1 | **分层** | 按属性把上下文切层，稳定在前、易变在后 | 信息太**杂** | ✅ 地基 |
| 2 | **按需加载（渐进式披露）** | 先给目录，命中再给正文 | 信息太**多** | ✅ |
| 3 | **差异化压缩** | 先无损后有损，按场景选手段 | 历史越来越**长** | ✅ |
| 4 | **核心保护 + 可回溯** | 划一块永不压缩的区域，压掉的能取回 | 压缩**丢信息** | ✅ |
| 5 | **任务隔离** | 脏活派给子 Agent，只回传结论 | 多任务**串位** | ✅ |
| 6 | **自主化管理** | 把上下文当虚拟内存，交模型自己管 | 规则**难兼容** | ⚠️ 前沿 |

> 作者收口时说：**大多数企业级 Agent 至少会涉及前面 5 项**，第 6 项各家做得深浅不一。

### 3.1 策略一：分层（一切的基础）

**为什么要分层**：

> 分层，就是按属性把当前的内容分成几层，**这样才能做细粒度管控**，通过优先级判断**避开 Lost in the Middle 的坑**。

收益是三重：**缓存收益**（稳定层在前 → 前缀匹配 → 吃满 Prompt Cache）、**注意力收益**（重要的放头尾 → 避开中间迷失）、**管控收益**（每层可用不同的压缩策略与生命周期）。

**三层结构（视频的核心分层法）**：常驻层 / 任务（项目）层 / 多变层。

```
┌───────────────────────────────────────────────────────────┐
│ ① 常驻层（System 级）                            几乎不动   │
│    身份 · 能力边界 · 技能（tools / skills）                 │
├═════════════════════ 缓存分界线（前缀到此为止）══════════════┤
│ ② 任务 / 项目层                                  相对稳定   │
│    CLAUDE.md · 约束规约 · 当前任务说明                      │
├───────────────────────────────────────────────────────────┤
│ ③ 多变层                                      高频按需加载 │
│    历史对话 · Task State · 长期记忆 · RAG 检索结果           │
└───────────────────────────────────────────────────────────┘
     ↑ 上面基本不动、下面让它动起来 → 用 Prompt Cache 省钱
```

| 层 | 是什么 | 为什么需要（作用） | 触发条件（什么时候变） | 典型做法 |
|---|---|---|---|---|
| **① 常驻层** | 系统级：身份、能力边界、可用工具与 skill 清单 | 定义「你是谁、能干什么、不能干什么」，是所有判断的前提 | 几乎不变，只有发版 / 加工具时变 | 写进 System Prompt；工具 schema 精简；**绝不放时间戳/随机数** |
| **② 任务 / 项目层** | CLAUDE.md、约束规约、当前任务描述 | 提供项目级事实与规则，避免每轮重复解释 | 换任务、改 md 文件时变 | 只放「必须每轮都在」的约定；长文档引用路径而非全文；排在缓存分界线之前 |
| **③ 多变层** | 历史对话、State、长期记忆、RAG 结果 | 提供当下这一次决策需要的新鲜信息 | 每轮都变 | 按需加载、压缩、外置、只保留摘要与引用 |

> 一句话记住：**上面不动、下面动；不动的那部分越干净，动的这部分就越便宜。**

**Claude Code 是怎么做的**：

> Claude Code 也是按照这种设计，大致分成 **System Prompt / Project Context / Conversation** 三部分，也是用**前缀匹配**去做。

```
System Prompt   ← 全局身份 + 工具定义 + 行为规则     ┐
Project Context ← CLAUDE.md 等，项目级约定，相对稳定   ├ 缓存命中区
Conversation    ← 用户消息 + 工具结果 + 模型输出      ┘ 缓存失效区（每轮增长）
```

📌 补充：这三段和「常驻 / 任务 / 多变」**一一对应**。不是巧合——所有认真做成本优化的 harness 最后都会收敛到这个形状，因为它被 Prompt Cache 的物理机制逼成了唯一解。

**「就近优先」：文件型系统的分层方式**

> 还有一块就是**就近优先**，也出现在各家的 harness 之间。上面是**通用型的分层**，下面是**文件型的分层**：我们把作用域加载在**就近的**——文件、代码、跟在原数据旁边——这样可以为后面的按需加载提供一个可靠的保障。

```
通用型分层（按稳定性）        文件型分层（按作用域）
 System                       repo/AGENTS.md            ← 全局约定
 Project                      repo/src/AGENTS.md        ← 本目录约定
 Conversation                 repo/src/agent/AGENTS.md  ← 更近的约定
```

**为什么「就近」重要**：它把「什么时候该加载什么」变成**不需要判断的机械规则**——模型动到哪个文件，就把那个目录附近的约定带上。这才让按需加载变得可靠，否则你永远在猜「现在该不该把这份规约塞进去」。

📌 补充：`CLAUDE.md` 是 Claude Code 的项目记忆文件，`AGENTS.md` 是跨工具通用的同类约定（Codex 等在用）。要点一致：**越靠近代码的约定，越应该在模型碰到那段代码时才加载**，而不是全量塞进 System Prompt。

**Pi 的做法：把分层做成可编程**

> Pi 的话，因为它核心是一种**基建的设计模式**，它会设置一些**可编程的事件**让你去做扩展。

| 产品 | 分层的表达方式 | 扩展方式 | 谁做决策 |
|---|---|---|---|
| **Claude Code** | 固定三段：System / Project / Conversation | 靠文件（CLAUDE.md）+ 配置 | 产品帮你分层 |
| **Pi** | 分层是**基建能力**，「什么时候加载什么」暴露成事件 | **事件钩子 + 扩展代码** | 分层策略你自己写 |
| **Codex** | 走「压实底稿、保住底稿、尽量命中缓存」 | 📌 同属前缀稳定路线 | 产品帮你分层 |

### 3.2 策略二：按需加载 / 渐进式披露

> 前面的**分层**是讲**信息放在哪边**；**按需加载**讲的是**什么时候把信息加载进来**。

**机制：先给目录，再给正文**

> 像我们通常理解的 **Skill 和 MCP 都是先加载目录**，然后等你需要的时候再把相关内容加载进来。

```
❌ 全量加载：50 个工具 × 400 token 全部常驻 → 20,000 token 每轮都付
✅ 渐进披露：50 条 name+description 常驻（2,000 token）
              命中某一个时，运行时再注入它的完整 schema（400 token）
```

**Pi 的 Skill 机制**：

> Pi 的话就更详细了：**Skill 其实是它能力的一个合集，只有在触发的时候才会进行加载。**

| | Tool | Skill |
|---|---|---|
| 是什么 | 一次原子调用 | **能力的合集**（说明、步骤、脚本、模板） |
| 体量 | 小（schema 几十到几百 token） | 大（上千行文档 + 多个文件） |
| 加载方式 | 清单常驻，schema 可懒加载 | **目录常驻，正文触发时才加载** |

📌 补充：Skill 之所以必须按需，是因为它的正文往往是**说明书**而不是**能力本身**。模型在不需要时读说明书纯属浪费上下文，还会稀释对当前任务的注意力。

**Cursor 的例子：检索也是一种披露**

> 加载策略各家不同。举 Cursor 的例子：它把整个代码库建 **embedding 以及符号图**，然后通过两种方式——**grep** 和**语义检索**——帮助模型更好地检索相关内容。

```
符号图（Symbol Graph）  → 函数/类/引用关系 → 支持精确定位
向量索引（Embedding）   → 语义相似        → 支持模糊描述召回
        ↓ 两个检索入口
    grep（精确、便宜、可解释） + 语义检索（模糊、贵、能召回同义）
        ↓
   只把命中的片段注入上下文
```

| 检索方式 | 优点 | 缺点 | 什么时候用 |
|---|---|---|---|
| **grep** | 精确、零成本、结果可解释 | 只能字面匹配，找不到同义表达 | 知道确切标识符 / 字符串时 |
| **语义检索** | 能召回同义、跨语言、模糊描述 | 要建索引、有成本、可能召回错的 | 描述性需求（「哪里处理鉴权」） |

> 作者定调：这也是**渐进式披露的一个特点**——**检索本身就是一种披露机制**。

### 3.3 策略三：差异化压缩

> 压缩这一块是**分场景、分差异化**的，主要分成两类。

```
A. 无成本压缩（无损 / 不花 LLM 钱）         B. 付费压缩（有损 / 要调 LLM）
   ① 直接截断：无效内容直接去掉                ③ 分层摘要：按各阶段分别摘要，只留关键
   ② 磁盘映射：大文件落盘，只留预览              ④ 整体摘要：整体压成「目标+计划」骨架
```

**A 类：无成本压缩（Claude Code 用的两种）**

> 第一类是无成本的压缩：像**直接截断无效内容**就直接去掉；第二种是对**大文件内容做磁盘映射**，上下文只保留**预览**。这也是 **Claude Code 里面会用的两种策略**。

| 手段 | 做什么 | 举例 | 风险 |
|---|---|---|---|
| **直接截断** | 把确认无用的内容整段删掉 | 删掉已处理完的 Tool Result、失败的尝试、重复的报错 | 判断错「无用」就永久丢失（靠策略四兜底） |
| **磁盘映射** | 大文件不读进上下文，只留路径 + 预览 | 读 5000 行日志 → 只留「前 20 行 + 总行数 + 路径」 | 模型不知道里面有什么，得自己去 grep |

```text
# 磁盘映射的典型形态（按视频口径整理，非逐字原文）
[Tool Result: read_file]
path: /repo/logs/build-2026-09-14.log
size: 12,847 lines / 2.3 MB
preview (first 20 lines):
  [12:01:03] INFO  starting build...
  [12:01:04] INFO  resolving dependencies...
hint: 文件过大未全文载入。需要细节请用 grep -n "<keyword>" <path> 精确检索。
```

> 这一招的精髓：**把「内容」换成「获取内容的方法」**。上下文省下 12,000 行，代价只是多一次 grep。

**B 类：付费压缩（两种摘要）**

> 付费的话就是**渐进式摘要**：比如上面不是做了分层嘛，那就**根据分层的特性，对各阶段的任务进行分层摘要**，只保留关键信息。
> 然后就是**整体摘要**：因为分层其实已经解决不了你的问题了，你要把整体内容**整体压缩**，只保留**关键目标、执行计划这种骨架**，剔除不需要的细节。

| 手段 | 压缩粒度 | 什么时候用 | 保留什么 | 丢什么 |
|---|---|---|---|---|
| **分层摘要** | 按层 / 按阶段分别压 | 分层还有效，只是某几层太长 | 每层的关键结论 | 层内的过程细节 |
| **整体摘要** | 全局一把压 | **分层已经救不了**（总量超限） | 目标 + 执行计划 + 已知结论（骨架） | 全部细节、试错过程 |

> 分界线很清晰：分层摘要是**在结构内做减法**，整体摘要是**把结构本身压扁**。后者是「最后的办法」，因为一定会丢东西——所以必须配策略四。

**Claude Code 的压缩阶梯：哪些不花钱，哪些要花钱**

> Claude Code 的话——基本上会分为上面几个，就是**你不需要付钱的**；下面几个，**要通过 LLM 去进行压缩**。

```
不花钱：截断无效内容 → 大文件磁盘映射（只留预览）
要花钱：分层/阶段性摘要 → 整体摘要（压到目标 + 计划骨架）
        ↑ 永远先走上面，走不通才走下面
```

**Pi 的路线：把压缩策略交给你写**

> Pi 走的是另外一条，就是**可编程**：把**触发条件的策略交给扩展去定制**，把相关扩展交给我们去做决策。

**四条通用原则（两家都适用）**：

| # | 原则 | 含义 | 违反的后果 |
|---|---|---|---|
| 1 | **先便宜后贵** | 能截断就别摘要；能映射就别读全文 | 无谓的 LLM 调用成本 |
| 2 | **先无损后有损** | 无损手段用尽，再动摘要 | 过早丢信息，后面要重读 |
| 3 | **底稿要全** | 核心内容（目标、计划、关键结论）必须完整保留 | 压缩后行为漂移、重复劳动 |
| 4 | **压缩要看有没有动缓存** | 不只看省了多少 token，还要看是否打乱前缀 | **省下的 token 又还给缓存** |

> 第 4 条最容易被忽略：一次压缩如果重排了前缀，你省了 20k 输入 token，却让后面每一轮都失去缓存。**这笔账必须一起算。**

### 3.4 策略四：核心保护区 + 可回溯

> 因为你为了省钱做了压缩，其实会带来**行为漂移、任务重复**，然后**缓存引用也会丢失**，所以需要建立起一层保护。

| 失效模式 | 表现 | 本质 |
|---|---|---|
| **行为漂移** | 压缩后 Agent 的判断标准变了，跟前面不一致 | 丢掉了「为什么这么做」的约束 |
| **任务重复** | 又去做已做过的事、又踩已踩过的坑 | 丢掉了「已经做过什么」的事实 |
| **缓存引用丢失** | 压缩块重排后，之前引用的片段对不上了 | 丢掉了「东西在哪」的指针 |

**① 开辟一个永不压缩的核心保护区**

> 你要开辟一个**永不压缩的核心保护区**。里面主要放：你的 **plan**、**当前做到哪一步了**、以及**下一步要做什么**——大概就是一个**核心任务概览**，守住底层逻辑。

```md
<!-- ============ CORE（永不压缩，每轮原样保留） ============ -->
## 核心任务
目标：把 payments 模块从 callback 风格迁移到 async/await，不改变外部行为

## 进度
- [x] 盘点全部 callback 调用点（37 处，清单见 .agent/survey.md）
- [x] 迁移 order/ 与 refund/（测试通过）
- [ ] 迁移 subscribe/（当前）
- [ ] 全量回归 + 灰度

## 下一步
1. 处理 subscribe/renew.py 中的嵌套 callback
2. 注意：retry 逻辑依赖 callback 调用次数，改写时必须保持语义

## 已知约束（不可违反）
- 不引入新的三方依赖
- 所有公开方法签名保持不变
<!-- ============ /CORE ============ -->
```

> 一个反直觉但重要的点：核心保护区应当放**「状态 + 约束」**，不是**「过程」**。过程可以压，状态不能压。作者说的「守住底层逻辑」就是守住这个「为什么」和「到哪了」。

**② 压缩片段必须可回溯**

> 另外一个就是，你在压缩的时候要注意**这些片段都是可回溯的**，帮助 Agent 能在需要的时候**恢复这些历史的记忆**。

```
原文 12,000 token → 压成 800 token 摘要 + 一条引用
                      └─ ref: .agent/history/turn-18.md  ← 需要时可 read_file 取回

关键：摘要负责「让模型知道有这回事」，指针负责「让模型能拿回细节」
```

| 做法 | 保留了什么 | 代价 |
|---|---|---|
| 直接删除 | 什么都不留 | 0（但不可恢复）❌ |
| **摘要 + 指针** | 「有这回事」+ 取回路径 | 摘要的 token + 一次落盘 |
| 全量落盘 | 完整信息 | 磁盘（几乎免费）✅ |

**Manus 与 Devin 的两种兜底思路**

> **Manus 是做状态外置：把一切都当做文件系统，把中间状态都存在文件里面。** 也是一个哲学——你要保留的话尽量去保留，你可以做压缩，但你也需要保留你的核心内容。
> **Devin 就是做一套我们所说的验收机制**：Agent 可能会做压缩，但我需要干完活再检测一遍。所以用**单独的验证环节去兜住整个流程**，我觉得也是一个关键的设计点。

| 框架 | 兜底哲学 | 具体做法 | 治的是 |
|---|---|---|---|
| **Manus** | **状态外置**：「一切皆文件系统」 | 中间状态、中间产物全落盘，上下文只留引用 | 信息丢失 |
| **Devin** | **验收兜底**：单独验证环节 | 干完活另起一个环节检测结果对不对 | 行为漂移 / 压缩致错 |
| **Claude Code / Pi** | 核心保护 + 可回溯 | 见上 | 三者都治 |

> Devin 这一招的洞察是：**压缩一定会出错，所以不要追求压缩完美，而是让错误可被发现。** 独立验证把「压缩导致的质量损失」和「模型本身的能力上限」解耦——这样你调压缩策略时才敢下狠手。

📌 补充：三种兜底可以叠加。实践中较稳的组合是 **状态外置（Manus 式）+ 核心保护区 + 独立验收（Devin 式）**：文件系统保证不丢，核心区保证方向不偏，验收保证错了能发现。

### 3.5 策略五：任务隔离（Sub-agent）

> 因为我们知道上下文毕竟是有限的，你需要保留你的关键内容。那这个时候你需要**通过子 Agent 去防止上下文过度膨胀**。

> 一个 Agent 干不了的活，你得派给你的子 Agent。**如果子 Agent 干完了，就不需要带着你的历史上下文完整回来，只要带着有效的信息回来就行。**

```
不用 Sub-agent：主线被脏活污染
  任务 + grep 结果×40 + 读了 30 个文件 ← 全是噪声，结论只有 12 行
  有用 : 噪声 ≈ 1 : 500

用 Sub-agent：主线只收结论
  主线（任务 → 结论表） ⇄ 子 Agent（自己 grep、自己读文件，用完即弃）
  有用 : 噪声 ≈ 1 : 0
```

> Claude Code 也是做 sub agent：**Agent 独立干活，最终只汇成摘要**，这样就比较清晰。

**子 Agent 拆分判据**（📌 按视频口径归纳）：

| 判据 | 该拆（派给 Sub-agent） | 不该拆（主线自己做） |
|---|---|---|
| **信息量** | 要读的东西远超结论体量（读 30 个文件只为 1 张表） | 结论和过程差不多大 |
| **可丢弃性** | 过程用完即弃（搜索、扫描、遍历） | 过程本身要复用（边做边定的推理） |
| **耦合度** | 任务边界清晰，输入输出可定义 | 需要频繁跟主线来回确认 |
| **并行性** | 可多路并行（多目录、多维度） | 严格串行、后一步依赖前一步 |
| **失败代价** | 失败可整体重试 | 失败会污染已完成的成果 |
| **权限** | 需要收窄权限（只读、限定目录） | 需要全量权限 |

> **一句话判据：过程比结论贵得多的时候，就该拆。**

📌 补充：拆 Sub-agent 有个隐藏成本——**上下文翻译损耗**。子 Agent 不知道主线已试过什么、排除了什么，容易重复劳动。所以实践中通常要给子 Agent 一段「最小必要背景」（任务目标 + 已排除项）。这也是「只回传有效信息」的另一面：**下行也要给有效信息**。

### 3.6 策略六：自主化的上下文管理（反模式 / 前沿）

> 第六种，我们会讲到一种**自主化的上下文管理**。上面 5 种可能是一个「正向」的模式，这种其实是一个**反模式**。

注意「反模式」不是「错误」，而是**把控制权反过来**：前 5 条是「我们帮 Agent 管上下文」，第 6 条是「Agent 自己管」。

> 这种通常理解来说就是把**上下文类比成操作系统的虚拟内存**，交给 Agent 自己去管理，有点类似于 Spring 的**控制反转（IoC）**。上面都是讲我们怎么帮 Agent 管理上下文，这里讲的是**由 Agent 自己去判断信息的归档、存储、删除和加载规则**。

```
传统：开发者当「操作系统」    开发者/框架 ──规则──→ 上下文
自主化：模型当「操作系统」    模型（归档/删除/加载规则）⇄ 分层存储（内存/文件/DB）
```

> 依托的其实就是我们去设计 **LRU 缓存、文件系统、RAG、SQLite** 这种底层能力，然后**模型自己去进行管控**。

| 底层能力 | 在自主化里的角色 | 类比 OS |
|---|---|---|
| **LRU 缓存** | 决定「哪些热数据留在窗口里」 | 页表 / 页面置换 |
| **文件系统** | 决定「冷数据落到哪、怎么取回」 | 磁盘 / swap |
| **RAG** | 决定「怎么按语义找回」 | 缺页中断时的查找 |
| **SQLite / DB** | 决定「结构化状态怎么存」 | 元数据 / 索引 |

> 关键在于：**这些能力不是给开发者用的 API，而是给模型用的「系统调用」**——模型自己决定什么时候 swap、什么时候 page in。

**学术出处：MemGPT**

> 这个思想在 **MemGPT** 里面的一篇论文可以重点看一下：它**把记忆进行分层**，然后**模型通过函数直接进行改写**，让模型去承担了一切。

📌 补充：MemGPT 的核心设计是把 LLM 当「有中断的进程」，主上下文 = 内存，外部存储 = 磁盘，模型通过 function call 主动执行 `archival_memory_insert` / `archival_memory_search` 实现自我换页。它和本节讲的是同一件事的学术版本。

**现状判断**：

> 当然目前这条路**还不是特别成熟**，但是随着大模型越来越强，也是一个可以深挖的点。

| 维度 | 判断 |
|---|---|
| 成熟度 | ⚠️ 不成熟，生产上慎用为主路径 |
| 前提条件 | 模型的**判断力**要够（知道自己缺什么） |
| 代价 | 需要一整套底层检索 / 存储能力支撑（原话：「要做好后面的一系列底层检索能力」） |
| 适用时机 | **规则难兼容的时候**——「你还不如直接交给模型一了百了」 |
| 趋势 | 模型越强越值得深挖 |

> 取舍标准很务实：**当你发现前 5 条的规则互相冲突、怎么配都不对时，与其继续加规则，不如把决策权交给模型。** 这不是偷懒，是承认「规则的复杂度已经超过它能带来的确定性」。

### 3.7 六条策略总表：各治什么病

视频结尾有一段很漂亮的收口，把六条策略和六种病一一对上：

| 策略 | 治的病 | 作者原话口径 |
|---|---|---|
| **分层管理** | 信息太**杂** | 解决信息太杂的问题 |
| **按需加载** | 信息太**多** | 解决信息太多的问题 |
| **差异化压缩** | 历史越来越**长** | 解决历史越来越长的问题 |
| **核心保护 + 分片恢复** | 压缩**丢信息** | 解决压缩丢信息的问题 |
| **任务隔离** | 多任务**串位** | 解决多任务串位的问题 |
| **自主化管理** | 规则**难兼容** | 规则很难兼容时，不如交给模型 |

```
信息太杂 ──→ 分层          压缩丢信息 ─→ 核心保护 + 可回溯
信息太多 ──→ 按需加载       多任务串位 ─→ 任务隔离
历史太长 ──→ 差异化压缩     规则难兼容 ─→ 自主化管理（最后一招）
```

> **注意这个顺序不是随意的**：先治结构（杂）→ 再治体量（多）→ 再治时间（长）→ 再治副作用（丢）→ 再治并发（串）→ 最后放弃规则（自主）。前一条不稳，后一条就是在沙子上盖楼。

| 维度 | **Claude Code** | **Pi** | **Cursor** | **Manus** | **Devin** |

📌 补充：共同点是——**没有一家只靠一种手段**。生产级 harness 都是「分层 + 按需 + 压缩 + 保护 + 隔离」五件套的组合，差别只在权重。所以别指望选一个「最好的方案」，而要**按自己的瓶颈配权重**：账单疼就学 Cursor / Claude Code，质量飘就学 Devin，状态丢就学 Manus。

## 5. 六大高频坑

> **说明**：视频正片因时间关系（原话：「由于时间问题，我们在常见问题和解决方案里面，重点去关注一个点」），**只完整展开了第 1 个坑**。其余 5 个在视频里作为「失败模式」散落在各条策略中（行为漂移、任务重复、缓存引用丢失、多任务串位、上下文膨胀），这里按视频口径归纳，并逐条标注来源。

### 5.1 坑 1（视频唯一完整展开）：前缀里塞了时间戳

作者点名「企业里常见、但很多人不注意」的头号坑。

> 我在看企业级 Agent 的时候，大家可能会忽略一个点：虽然有些人是 AI 应用开发工程师，但他们其实**不会注意前缀或者 Prompt Cache 这个点**。所以我经常看到有些 prompt 里面**被加了一些时间戳，导致整个前缀都失效**，导致你的缓存不命中。

| 项 | 内容 |
|---|---|
| **症状** | 账单没降、首 token 延迟高；缓存命中率长期接近 0 |
| **根因** | System Prompt 里写了 `当前时间：2026-09-14 21:03:07` 这类每次都变的字段，而缓存是**前缀匹配**的 |
| **后果 1（成本）** | 缓存失效 → 每轮按原价重算 → **成本增加** |
| **后果 2（延迟）** | 缓存失效 → 重新计算 → **整个延迟也会增大** |
| **隐蔽性** | 单看代码完全合理（「模型需要知道今天几号」），只在账单和 P99 上看得出来 |

> 作者定调：**从成本和延迟两个角度，你都需要关注这个点，尽量让它命中前缀匹配。**

```text
❌ 错：动态字段混进 System Prompt（前缀每轮都变）
  你是一个代码助手。
  当前时间：2026-09-14 21:03:07    ← 💥 一个 token 变了
  当前用户：u_88213                ← 💥
  会话ID：sess_a91f                ← 💥
  ...（后面 8000 token 的规则全部作废，重新计费）→ 命中率 = 0

✅ 对：稳定前缀 + 动态内容下沉到多变层
  【稳定区｜可缓存】System Prompt（身份+规则+工具，字节级不变）
                   Project Context（CLAUDE.md / 约定，改文件才变）
  【动态区｜不参与前缀匹配】第一条 user 消息开头：
                   <env>now=2026-09-14T21:03+08:00 user=u_88213</env>
```

```bash
# 自检：把两轮实际请求体 dump 下来，对稳定区做字节级 diff
$ diff <(head -c 20000 turn_1.request.json) <(head -c 20000 turn_2.request.json)
# 期望输出：（空）   如果有输出 → 你的前缀在漏，钱在漏
```

📌 补充：常见的「隐性前缀破坏者」——时间戳、UUID / request_id、随机排序的工具列表（dict 遍历顺序不稳定）、JSON 序列化 key 顺序变化、多语言切换、把绝对路径 `cwd` 写进 System Prompt、每次启动重新生成的规则摘要。这些都比时间戳更隐蔽。

### 5.2 坑 2~6：一张表看完

| # | 坑 | 症状 | 根因 | 后果 | 对应策略 | 视频依据 |
|---|---|---|---|---|---|---|
| 2 | **把窗口当仓库** | 答非所问、忽略明确给过的约束、答得「有道理但不对」 | 「能放进去 ≠ 应该放进去」，噪声污染 + Lost in the Middle | 准确率下降且难归因 | 分层 + 就近优先，关键约束放头尾 | 第 2 层原因 |
| 3 | **压缩只算 token 不算信息** | 压缩后风格/判断变了，重复做已完成的事 | 把压缩当「文本变短」而非「信息保真」 | **行为漂移 + 任务重复** | 「底稿要全」+ 核心保护区 | 3.3 / 3.4 |
| 4 | **压缩动了前缀** | 做了压缩，账单没降甚至上升，延迟反变差 | 压缩重排/改写了缓存区 | 「省 20k 输入，赔掉后面 20 轮缓存」 | 压缩只发生在缓存分界线之后 | 3.3 原则 4 |

| 6 | **Sub-agent 全量回传** | 拆了子 Agent，主上下文还是爆 | 隔离只在「出去」时做了，没在「回来」时做 | 白拆，甚至更贵 | 回传只带有效信息 + 固定 schema | 3.5 |

**修法要点**（按坑号）：

```text
# 坑 2：进上下文前问三个问题
① 这条信息能改变模型这次的决策吗？  ── 不能 → 不放
② 它必须现在放，还是可以留个指针？   ── 能留指针 → 只放指针
③ 它该放在头/尾，还是中间？         ── 重要 → 挪到头或尾

# 坑 3：压缩前先标注「哪些不可压」
绝不压：目标/验收标准 · 当前进度/下一步 · 已知硬约束
可以压：试错过程（压成结论）· 工具原始输出（截断/落盘）· 中间推理（压成一句）

# 坑 4：压缩只允许在缓存分界线以下发生
常驻层（缓存区）禁止压缩/重排/插入 ｜ 任务层（缓存区）只允许追加
━━━━━━━ 分界线 ━━━━━━━  多变层：随便压、随便删、随便重排

# 坑 6：给子 Agent 的回传定 schema，而不是自由发挥
## 结论  <一句话直接回答主线下发的问题>
## 证据  - file.py:123 <关键行摘要>
## 存疑  - <需要主线决策的点>
## 详细过程  见 .agent/sub/report-<id>.md   ← 只给指针，不贴正文
```

📌 补充：坑 5 最典型的形态是「**约束残留**」——上个任务说「不要动数据库 schema」，这个任务明明该改，模型却不敢改。症状看着像「模型变笨了」，实际是上下文里有一条过期硬约束。

## 6. 什么时候该开新 Session

这是「任务隔离」在工程上最具体的落点，也是坑 5 的解药。视频没给完整判据表，这里按六条策略反推 📌 归纳：

| 判据 | 该开新 Session | 可以继续用 | 理由 |
|---|---|---|---|
| **目标变了** | 换了一个交付物（修 bug → 写文档） | 同一目标的不同步骤 | 目标是最不可压的 core |
| **代码域变了** | 从 `payments/` 换到 `billing/` | 同一模块内 | 就近优先的作用域失效了 |
| **连续失败** | 同一问题连续 2~3 次没解决 | 第一次尝试 | 失败尝试变成强噪声，越陷越深 |
| **上下文利用率** | 超过窗口 60%~70%（📌 经验值） | 低于 50% | 要留空间给后续 Tool Result |
| **话题漂移** | 开始聊「顺便问一下…」 | 严格同一主线 | 漂移内容会污染后续判断 |
| **约束变更** | 用户改了硬性要求（不能用某库） | 补充说明 | 旧约束会和新约束打架 |
| **已压缩 2 次以上** | 建议新开 + 带上 core 区 | 只压过 1 次 | 多次压缩的累积损失不可逆 |
| **跨天 / 跨人接手** | 新开 + core + 交接摘要 | 同一人连续作业 | 状态在文件里比在对话里可靠 |

**「换 session 的交接包」长什么样**（📌 补充的落地形态）：

```md
<!-- handoff.md —— 开新 session 时作为第一条消息注入 -->

## 上一个 session 完成了什么
- 已迁移 order/、refund/，测试全绿
- 结论：retry 逻辑依赖 callback 调用次数（见 .agent/notes/retry.md）

## 未完成
- subscribe/ 还剩 3 个文件

## 已排除的方案（不要重试）
- 用装饰器包装：破坏签名兼容性
- 用 asyncio.to_thread：性能不达标

## 需要遵守的约束
- 不引入新依赖；公开签名不变
```

> 关键洞察：**开新 session 不是「丢掉上下文」，而是「把上下文做一次人工压缩」**。压缩的产物就是这份交接包——它恰好只包含 core 区该有的东西（状态 + 约束 + 已排除项）。

### 7.2 压缩手段取舍表

| 手段 | 类型 | 成本 | 信息损失 | 动缓存？ | 什么时候用 |
|---|---|---|---|---|---|
| **直接截断** | 无损 | 0 | 低（只删确认无用） | 否 | 首选，随时可用 |
| **磁盘映射（只留预览）** | 无损 | 几乎 0 | 中（要知道怎么取回） | 否 | 大文件、日志、长文档 |
| **滑动窗口** | 有损 | 0 | 高（丢久远信息） | **是**（前缀变了） | 📌 短对话型场景，长任务慎用 |
| **分层摘要** | 有损 | 中（LLM） | 中 | 是 | 某一层过长，结构还清晰 |
| **整体摘要** | 有损 | 高（LLM） | 高 | 是 | 分层已救不了，最后手段 |
| **外置到文件系统** | 无损 | 0（磁盘） | 0 | 否 | Manus 式：状态全落盘 |
| **Sub-agent 隔离** | 无损（对主线） | 一次额外调用 | 0（主线） | 否 | 过程远大于结论 |

> 选择顺序：**截断 → 映射 → 外置 → 分层摘要 → 整体摘要**。前面能用就别往后走。

### 7.3 六条策略速记

```
分层 → 按需 → 压缩 → 保护 → 隔离 → 自主
 │      │      │       │      │       │
杂     多     长      丢     串      乱
```

## 8. 📌 补充：视频没展开但一定会踩的部分

> 以下均为原讲解之外的延伸，不是视频原意。

### 8.1 上下文管理的效果怎么量化

视频讲了「怎么做」，没讲「怎么证明做对了」。最小可用的四个指标：

| 指标 | 怎么算 | 健康信号 |
|---|---|---|
| **缓存命中率** | 命中 token / 总输入 token | 稳定任务 > 70% |
| **每任务 token 成本** | 总 token × 单价 / 完成任务数 | 随优化下降，且准确率不降 |
| **压缩频次** | 每任务触发 Compaction 次数 | ≤ 1 次为佳，> 2 次说明分层没做好 |
| **信噪比（人工估）** | 真正被引用的内容 / 上下文总内容 | 越低说明塞得越脏 |

> **这四个指标必须和准确率一起看。** 只盯成本，你一定会压到模型变傻——这也是「评测闭环」要解决的事。

### 8.2 渐进式披露的两个反效果

| 反效果 | 现象 | 缓解 |
|---|---|---|
| **披露不足** | 目录写得太抽象，模型不知道该去取什么 | 目录条目要写「什么时候用我」，不只写「我是什么」 |
| **披露抖动** | 每轮加载的东西不一样，前缀一直变 | 把「已加载集合」记在 State 里，只增不减 |

### 8.3 分层与「就近优先」冲突时怎么办

两者会打架：**按稳定性分层要求「稳定在前」**，**按作用域分层要求「就近才加载」**。解法是把它们放在不同维度上：

```
上下文 = 〔稳定前缀（按稳定性分层）〕 + 〔按需注入段（按作用域就近）〕

稳定前缀：System → Project →（缓存分界线）
按需注入：在「当前这一轮」的 user / tool 位置插入就近的约定
```

> 也就是说：**分层决定「常驻什么」，就近决定「临时插什么」**，两者不在同一层竞争。

### 8.4 一个常被忽略的层级：Tool Result 的治理

视频把 Tool Result 列为上下文组成之一，但没单独展开。实践中它往往是**上下文增长的第一大来源**：

```text
Tool Result 进上下文前的三道闸（📌 补充）
闸 1 体积闸：> 8k token 不直接进 → 落盘 + 只给路径与 20 行预览
闸 2 去重闸：digest 已出现过 → 只留一句「重复内容，见 turn N」
闸 3 结构闸：原始噪声 → 转成结构化摘要（上限 ~1.5k token）
```

## 10. ✅ 落地检查清单

> 用法：拿这 14 条去评审任何一个 Agent 的上下文管理设计。**打不了勾的，就是下一次线上事故的位置。**

**A. 分层与前缀（对应策略一，坑 1、4）**

- [ ] **1.** 上下文被显式切成「常驻层 / 任务层 / 多变层」三段，且代码里有明确的数据结构（不是一个巨大的字符串拼接）。
- [ ] **2.** 两轮真实请求的**稳定区做字节级 diff 为空**（时间戳、request_id、cwd、随机序都已下沉到多变层）。
- [ ] **3.** 工具清单的序列化顺序是**确定的**（不是 dict 遍历顺序），加工具时才变。
- [ ] **4.** 压缩与重排**只发生在缓存分界线之后**，稳定区只允许追加、不允许改写。

**B. 加载（对应策略二，坑 2）**

- [ ] **5.** 工具 / Skill 走「先目录后正文」，目录条目写清了「什么时候用我」，而不只是「我是什么」。
- [ ] **6.** 有明确规则回答「这条内容凭什么进上下文」（能改变决策吗 / 能否只留指针 / 该放头尾吗）。

**C. 压缩与保护（对应策略三、四，坑 3）**

- [ ] **7.** 压缩有**阶梯**：截断 → 磁盘映射 → 外置 → 分层摘要 → 整体摘要，且先无损后有损。
- [ ] **8.** 存在一块**永不压缩的 core 区**，至少包含：目标、当前进度、下一步、硬约束。
- [ ] **9.** 每次压缩都**落盘 + 留指针**，模型可按需取回原文（可回溯）。
- [ ] **10.** 压缩决策时**同时算 token 账和缓存账**（不是只看省了多少 token）。

**D. 隔离与生命周期（对应策略五，坑 5、6）**

- [ ] **11.** 有「什么时候开新 Session」的**书面判据**（目标变 / 域变 / 连续失败 / 利用率阈值 / 压过 2 次）。
- [ ] **12.** Sub-agent 的**回传有固定 schema**（结论 + 证据 + 存疑 + 指针），回传体量不超过结论体量的合理倍数。

**E. 可观测与验证（对应第 8 章）**

- [ ] **13.** 四个指标可查：**缓存命中率 / 每任务 token 成本 / 压缩频次 / 信噪比**，并且和准确率一起看。
- [ ] **14.** 改动上下文策略后，**有评测集能证明「没变傻」**（哪怕 20 条人工 case），否则不许上线。

## 11. 一句话总结

> **大模型是无状态的，上下文是每轮重建的输入；所以上下文管理的本质不是「塞更多」，而是「分层让它便宜、按需让它干净、压缩让它可持续、保护让它不失真、隔离让它不串味」——而这一切的第一块砖，是稳定不动的那个前缀。**

如果只记一句话，记作者那句：

> **怎么利用上下文，比怎么把更多东西塞进去更重要。**
