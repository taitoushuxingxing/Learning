## 0. 课程地图：这一集在讲什么

> **上一集解决「一个组件内部怎么写」，这一集解决「组件之间怎么说话」。**

四集分工：第 1 集核心语法（JSX、函数组件、useState）→ **第 2 集组件进阶（通信、插槽、Context）** → 第 3 集其他 Hooks → 第 4 集（合集未完）。

这一集是「通信难度递增」的阶梯，**不要打乱顺序**：

```
① DOM 组件的 props（className / style / 展开）
      ↓
② React 组件的 props（父 → 子）→ 数据分层 → 层层透传
      ↓
③ 「插槽」= children + JSX 作为 prop（父 → 子传 UI）
      ↓
④ props 只读 → 子 → 父（回调/自定义事件）→ 兄弟（父组件中转）
      ↓
⑤ 层级太深 → Context + Provider + useContext
```

顺序里藏着设计意图：**先把「props 能传什么」推到极限**（字符串 → 布尔 → 一整棵 JSX 树），**再告诉你「它不能往回传」**，于是引出回调；等一级级传累了，才引出 Context。每一步都是被上一步的痛点逼出来的。

📌 **补充：为什么作者把所有组件写在一个文件里**——他的原话是「为了演示更加清晰，不按开发方式分割文件，否则要来回跳」。跟敲时按单文件来，**敲完再自己拆一次**，拆的过程正好检验你是否清楚每个 props 从哪来。（目录组织见已有笔记 §12。）

## 1. 第一章 两种组件：DOM 组件与 React 组件

> 「React 中的组件分为两种类型，一种是 **DOM 组件**，一种是 **React 组件**。DOM 组件指的是 React 支持的所有的 HTML 和 SVG 的标签。」

| 类型 | 开头 | 例子 | 谁定义的 |
|---|---|---|---|
| **DOM 组件**（内置/宿主组件） | 小写 | `<div>` `<img>` `<svg>` | React 内置，对应真实 DOM 节点 |
| **React 组件**（自定义组件） | **大写** | `<Article />` `<List />` | 你自己写的函数 |

大小写不是风格，是**语法规则**：小写 → 字符串标签名（`createElement('div')`）；大写 → 变量（`createElement(Article)`）。本集正好两个都用：`<article>`（HTML 标签）装文章，`<Article>`（自定义组件）是那一层封装——**不是笔误**。

### 1.1 HTML 属性在 React 里叫 props

> 「我们在图片中可以给图片设置属性，例如 `src`、`alt`。而这些像 HTML 属性的功能在 React 中称为叫 **props**。」

```jsx
import logo from './logo.svg';
<img src={logo} alt="React logo" />;
```

`src` 用 `{logo}`（`import` 进来的是变量，不是字符串路径）；`alt` **必须写**——「如果你没设置 alt，它会给你一个警告」。📌 装饰性图片写 `alt=""`（空串）是合法的，语义是「对读屏软件无意义」，不等于「忘了写」。

### 1.2 第一个真正的差异：`class` → `className`

> 「由于我们现在使用的是 JSX 语法，所以它可能会牵扯到跟 JavaScript 的关键字 `class` 重复的情况。所以在 React 中，如果希望给 DOM 组件设置类名，需要更改为另外一个名字叫做 `className`。」

写错的现场（视频真演示了一遍）：`Warning: Invalid DOM property 'class'. Did you mean 'className'?`

注意措辞是 **Invalid DOM property**——React 不是「不认识」，而是明确告诉你「这个 prop 名对 DOM 元素不合法」，甚至给出正确写法。📌 这类警告只在开发环境出现，生产构建会剥掉，**别指望上线后被发现**。

| HTML | JSX | 原因 |
|---|---|---|
| `class` / `for` | `className` / `htmlFor` | 撞 JS 关键字 |
| `tabindex` / `onclick` / `readonly` | `tabIndex` / `onClick` / `readOnly` | 统一驼峰 |
| `style="color:red"` | `style={{ color: 'red' }}` | 见 1.3 |

记忆法：**HTML 里全小写的多词属性 → JSX 基本变驼峰；撞 JS 关键字的 → 换名字。**

### 1.3 `style` 为什么是两个大括号

> 「`style` 是一种键值的结构，所以 JSX 允许你通过键值对，说白了就是**对象**的形式来设置。现在这个大括号代表的是 JSX 的标记，那我在内部如果希望写一个对象的字面量，我可以这样来写。」

```jsx
// 外层大括号 = 「这里要插一个 JS 表达式」；内层大括号 = 「这个表达式是对象字面量」
<img src={logo} alt="logo" style={{ width: 200, height: 200 }} />
```

作者还演示了编辑器怎么帮你区分：「注意看编辑器可以很好的帮我们做一个区分，**颜色是不同的**。」

| 规则 | 写法 | 说明 |
|---|---|---|
| 数字自动补 `px` | `width: 100` → `100px` | 「我写一个 100，它默认单位是 px」 |
| 带单位写字符串 | `width: '100vh'` | 否则被当成错误值 |
| 连字符转驼峰 | `backgroundColor` | 「带横线的属性，不出意外地需要写成驼峰」 |

**工程建议**（很多教程不讲）：「如果你有在 DOM 组件中设置样式的需求，我建议你**直接书写一个变量，再把变量放到 JSX 大括号中**，要远比大括号套对象字面量更清晰。」`const imgStyleObject = { width: 200, height: 200, backgroundColor: 'gray' };` 然后 `style={imgStyleObject}`。

📌 **补充：哪些属性不补 `px`**——`opacity`、`zIndex`、`flex`、`flexGrow`、`order`、`lineHeight`（多数情况）都是纯数字。`lineHeight: 1.5` 是「1.5 倍行高」，`'24px'` 是固定行高，语义不同，这是 CSS 规则，React 只是不插手。

## 2. 第二章 展开语法：JSX 独有的属性打包

属性一多，一行写不下；更麻烦的是**属性来自接口**——字段名刚好就是属性名。

```jsx
const imgData = { src: logo, alt: 'React logo', className: 'small', style: { width: 200, height: 200 } };

function App() {
  return <img {...imgData} />;
}
```

> 「我在 JSX 中它支持展开语法，就是通过点点点的方式直接写一个 `imgData`。这样保存，你会发现功能是完全没有问题的。」

### 2.1 它不是 ES6 的展开运算符（面试点）

作者专门去控制台演示，是本集少有的「主动讲原理」段落：

```js
const obj = { a: 1, b: 2 };
{ ...obj }   // ✅ 对象字面量里展开，得到新对象
...obj       // ❌ 报错：没有容器，不能单独使用
```

> 「有同学说这个写法不就是 ES6 的展开运算符吗？**但其实并不是**。它的功能是将当前对象的键值直接放到这个位置上，它**不能在没有容器的地方单独使用**……之所以能支持，是 **JSX 单独的功能支持**，说白了就是**在编译的时候做了一些额外的操作**。」

| | ES6 对象展开 | JSX 属性展开 |
|---|---|---|
| 写在哪 | 对象字面量、数组、函数实参 | **只能在 JSX 标签的属性位置** |
| 运行时 | 真的拷贝属性，生成新对象 | **编译期把 props 对象整个传给创建函数** |
| 编译产物 | 原样保留 | `_jsx("img", { ...imgData })` 或 `React.createElement("img", imgData)` |
| 本质 | 运算符 | **语法糖 / 编译期行为** |

作者补了一句关键的：「这块不也有一个大括号吗？但注意这个**大括号只是 JSX 的语法标记**，就算把它解开，也不可能直接放在 img 标签之中。」有人误以为「有 `{}` 就是 ES6 展开」——这正是要纠正的。

📌 **补充：三个真实用途**：① **属性透传**（第 3 章马上用到），中间层不需要知道有哪些属性；② **覆盖顺序后面赢**——`<Button {...defaults} className="special" />` 最终是 `"special"`；③ **`key` 会被单独拎出来**，`<Item key={id} {...rest} />` 里子组件 `props.key` 永远是 `undefined`（第 14 章）。

## 3. 第三章 父传子：props 与数据分层

### 3.1 从「写死的 Article」到「可配置」

```jsx
function Article() {
  return (<article><h2>标题</h2><p>内容</p></article>);
}
```

> 「这样你使用多少次 `Article` 它都是固定的……但是我们在进行组件复用的时候，通常只是**结构、样式、逻辑**复用，**内容是不可能也复用的**。」

**复用的是「壳」，不是「瓤」。** 真实场景是：「在父组件 `App` 中请求服务端给到我们一个数据列表，包含 5 篇文章的标题和内容，然后创建多个 `Article`，把不同内容传进去。」

```
后端接口 → 父组件 App（持有数据）→ 循环创建子组件 → 每个子组件拿到自己那份 props → 渲染
```

### 3.2 传与收：跟写 HTML 属性一模一样，收到后解构

```jsx
// 传：字符串字面量 / 表达式
<Article title="标题1" content="内容1" />
<Article title={article.title} content={article.content} />

// 收：props.xxx（啰嗦）→ 解构（推荐）
function Article(props) { return (<article><h2>{props.title}</h2><p>{props.content}</p></article>); }
function Article({ title, content }) { return (<article><h2>{title}</h2><p>{content}</p></article>); }
```

> 「我们书写的方式，跟我们之前写标签属性是完全一样的。你可以写成固定值，也可以通过 JSX 来书写其他值。」「这种写法可能比较复杂，因为你每次都要 `props.a.b.c`。所以一般在使用的时候，会采用**解构**的方式。」

作者特意防止你把解构算成 React 的功劳：「**这功能是 ES6 提供的，并不是 React 独有的**。」还解释了它不只是「少打字」：「你可以想用哪个属性就取哪个属性，因为有的时候，这些属性并不一定都要在当前组件内使用，也有可能要**传递到组件的内部的内部**。」——这是 3.4 的伏笔。

📌 `title="标题1"` 传字符串，`title={1}` 传数字；写 `title="{article.title}"` 会得到**字面量字符串**，页面直接把这串符号显示出来（`EP01` 的「引号陷阱」）。

### 3.3 布尔属性：不写值就是 `true`

```jsx
function Article({ title, content, active = false }) {
  return (<article>
    <h2>{title}</h2><p>{content}</p>
    <span>{active ? '显示中' : '已隐藏'}</span>
  </article>);
}

<Article title="标题1" content="内容1" active />   {/* 不写值 = true */}
```

> 「这种属性非常类似 DOM 中的 `selected` 或者 `autoplay`。它其实**不需要给值**……如果你写了，默认值就是 `true`；没写自然就是 `false`。」「如果你选中设置的话，它是一个 `true`，那这时我们就选一个『显示中』；如果你没有去设置，那我们写一个『已隐藏』。」

📌 **补充①**：`active` 与 `active={true}` 等价，但 **`active="false"` 是 `true`**——非空字符串 truthy。布尔值一定要用 `{}`。

📌 **补充②**：`active = false` 是视频没写但我建议加的默认值，可读性更好、也方便 TS。这就是已有笔记 §6.3② 的「解构默认参数」，等同 Python 的 `def f(active=False)`。

### 3.4 数据分层：让接口结构决定 props 结构

需求升级：标题区可能有用户信息、时间，内容区可能有图片、各种模块。「这时我们可能还会将标题跟内容区域也进行一个**组件的封装**。」于是拆出 `Detail`。

一个个列 `<Detail content={content} active={active} author={author} />` 太啰嗦，作者给了更聪明的做法——**让数据自己分层**：

> 「我在早期肯定也知道这个属性设定的情况……我们在提前的这个区域就对它进行一个**打包设置**。」「我的 `content` 跟 `active` 可能都属于 `detail` 的信息，那我写成 `detailData` 来做一个包裹……这就是靠**接口设计**那边的一个操作了。」

```jsx
const articleData = {
  title: '标题1',
  detailData: { content: '内容1', active: true },   // ← 属于 Detail 的，打包成子对象
};

function Detail({ content, active }) {
  return (<div className="detail"><p>{content}</p><span>{active ? '显示中' : '已隐藏'}</span></div>);
}

function Article({ title, detailData }) {
  return (<article><h2>{title}</h2><Detail {...detailData} /></article>);
}

export default function App() {
  return <Article {...articleData} />;
}
```

> 「现在我发现这个 `detailData` 在我当前这里边**根本就不用**，所以我就把它**原封不动地传递给 `Detail`**……前面加一个点点点，那这时所有属性就都被传到了 `Detail` 内部。」

这四行其实演示了**两次展开**：

| 位置 | 摊开了什么 | 谁受益 |
|---|---|---|
| `<Article {...articleData} />` | `title`、`detailData` | `Article` 只挑 `title`，把 `detailData` 转发 |
| `<Detail {...detailData} />` | `content`、`active` | `Detail` 拿到自己那两个 |

📌 **补充：这就是「透传（pass-through）」的雏形**，真实项目天天用。价值是**解耦**（`Detail` 加字段，`Article` 一行不改），代价是**可读性下降**（看 `Article` 不知道 `Detail` 收到什么）。经验法则：**属性少于 3 个就老实列出来，超过 3 个或本来就是一整包配置才用展开。**

📌 **补充：按 `type` 选组件**。作者顺口提了一句「再加一个 `type`，判断内容状态……是 `type1` 就用 `type1` 组件」。最直白是三元，但类型一多会嵌套成意大利面，用组件映射表更干净：

```jsx
const DETAIL_MAP = { text: TextDetail, image: ImageDetail, video: VideoDetail };

const Comp = DETAIL_MAP[detailData.type] ?? TextDetail;   // 兜底
return (<article><h2>{title}</h2><Comp {...detailData} /></article>);
```

`Comp` **必须大写开头**——第 1 章那条规则的直接应用，小写会被当成 HTML 标签字符串。

### 3.5 小结

| 要传的东西 | 写法 | 子组件怎么收 |
|---|---|---|
| 字符串 / 数字 / 布尔 | `title="x"` / `count={3}` / `active` | `{ title }` `{ count }` `{ active }` |
| 对象 / 函数 | `user={user}` / `onClick={handleClick}` | `{ user }` / `{ onClick }` |
| 一整包属性 | `{...data}` | 解构 / `...rest` |
| **一整棵 JSX** | `footer={<Footer />}` | `{ footer }` |
| **标签之间的内容** | `<Card>xxx</Card>` | `{ children }` |

**最后两行就是「插槽」**——下一章的全部内容。

## 4. 第四章 「插槽」这个词：Vue 有，React 没有

> 本文的核心增量。视频只用了约 6 分钟，且用的是 Vue 的措辞；我把它摊开讲，因为这里概念最容易打架。

### 4.1 视频怎么引入的（原文照录）

> 「父组件除了可以传递一些普通的值，它还可以**传递一些 JSX**。那这就不得不提到，在 **Vue 学习中我们会有一个叫做插槽的概念**。」
>
> 「就这样，就利用 JSX 语法实现了所谓的一个叫做**插槽**的概念。所以**在 React 中你几乎看不到关于插槽这两个字**，因为它就是使用了一个 JSX 语法。所以在 React 中，叫做**将 JSX 作为 prop 传递给子组件**。它跟普通的 prop 的区别在于，它是被**预定义了一个值叫做 `children`**。」
>

作者的表述**其实是准确的**，他自己就点破了关键。但标题沿用了「插槽」，因为这是中文教程的搜索习惯——搜「React 插槽」，出来的全是讲 `children` 的文章。正确理解是：

> **「React 插槽」是一个俗称，指 `props.children` 和「把 JSX 作为 prop 传递」这套做法。它不是 API，不是语法，不是官方术语。**

### 4.2 三个必须先建立的事实

**① JSX 元素就是普通对象。** `const el = <li>列表项1</li>` 约等于 `{ type: 'li', props: { children: '列表项1' } }`。既然是对象，就能赋给变量、放进数组、当函数参数、当对象属性——**天然可以当 prop 传**。Vue 的模板做不到（编译产物是渲染函数，不是值），所以才需要 `slot` 这种「占位符 + 编译期填充」机制。

**② `children` 只是名字固定的一个 prop。** `<Card>你好</Card>` 等价于 `<Card children="你好" />`。React 编译时把「开始/结束标签之间的所有内容」塞进去，**没有魔法，没有占位符**。

**③ 子组件决定 `children` 出现在哪、出现几次。** `{children}` 写在哪就渲染在哪，写两次就渲染两次。

### 4.3 默认插槽 → `props.children`

```jsx
function List({ children }) {
  return <ul>{children}</ul>;
}

export default function App() {
  return (
    <List>
      <li>列表项1</li>
      <li>列表项2</li>
    </List>
  );
}
```

> 「React 得益于它直接可以使用 JSX，也就是可以将 HTML 语法跟 JS 语法**混合书写**，所以它**并不需要一些特殊的语法**，一切都是水到渠成的。」
>
> 「这个属性叫做 `children`，指的就是**内部的子元素**。你只需要按照 JSX 语法把 `children` 放在这儿，它就自动会接收开始跟结束标记之间的**所有内容**。」

**这就是「默认插槽」——一个 prop 搞定，零新语法。**

📌 **补充：`children` 可以是什么？**

| 传入 | 子组件收到的 `children` |
|---|---|
| `<Card>文字</Card>` | 字符串 `"文字"` |
| `<Card>{1 + 1}</Card>` | 数字 `2` |
| `<Card><A /><B /></Card>` | 数组 `[<A/>, <B/>]` |
| `<Card />` 或 `<Card></Card>` | `undefined` |
| `<Card>{null}</Card>` | `null`（不渲染） |
| `<Card>{(x) => <i>{x}</i>}</Card>` | **函数**（见 4.5） |

### 4.4 具名插槽 → 传多个 props

需求升级：列表还要有**标题**和**底部**（「有的文章底部是评论，有的是广告，可能**完全需要自定义**」）。

> 「如果你希望以更多的方式传递内部结构，那就还是通过 **props** 来处理，因为你不要忘记，这个写法无非就是一个更简单的 props 设置而已。它变成了一个 `children`，那如果你有 8 个位置，自然就没有预定义的方式可用，你就**可以自己再定义**。」

```jsx
function List({ title, children, footer = <div>默认底部</div> }) {
  return (<div>{title && <h2>{title}</h2>}<ul>{children}</ul>{footer}</div>);
}

export default function App() {
  return (<>
    <List title="列表1" footer={<p>底部内容1</p>}><li>列表项1</li><li>列表项2</li></List>
    {/* 没传 footer，走默认值 */}
    <List title="列表2"><li>X</li><li>Y</li><li>Z</li></List>
  </>);
}
```

视频里有个**很关键的提醒**：

> 「你这个 `footer` 包括 `title` 也一样，**如果可选的话，你需要给它一个默认值**，如果你没有默认值，呈现的时候就会有问题。」

准确说：`{footer}` 里塞 `undefined` 不会「语法错误」，而是**什么都不渲染**；但访问 `footer.xxx` 就会 `Cannot read properties of undefined`。结论：**可选 JSX prop 一定兜底**——`footer = <默认/>`（连 props 都变默认值）或 `{footer ?? <默认/>}`（只在渲染时替换，保留「用户传没传」的判断能力）。

**对照一眼就明白：**

```vue
<!-- Vue：需要 template + # 语法，因为要在模板里标出「哪段填哪个洞」 -->
<List><template #footer><p>底部内容1</p></template></List>
```

```jsx
// React：就是普通 prop，JSX 本身就是值，直接当属性值丢过去
<List footer={<p>底部内容1</p>}>...</List>
```

### 4.5 作用域插槽 → 函数作为 children（render props）

视频**没讲**、但 Vue 用户一定会问的一块。Vue 的作用域插槽能让**子组件把数据反向提供给插槽内容**：

```vue
<!-- Vue 子组件 --> <li v-for="item in items"><slot :item="item" /></li>
<!-- Vue 父组件 --> <template #default="{ item }"><strong>{{ item.name }}</strong></template>
```

React 里没有「作用域」概念，因为 **JSX 表达式在父组件的作用域里求值**，子组件无法往里「注入」变量。唯一办法：**让 `children` 是函数，由子组件带着数据去调用。**

```jsx
function List({ items, children }) {          // children 是函数
  return (<ul>
    {items.map((item, index) => (
      <li key={item.id ?? index}>{children(item)}</li>   // ← 变成函数调用
    ))}
  </ul>);
}

export default function App() {
  const items = [{ id: 1, name: '苹果' }, { id: 2, name: '香蕉' }];
  return (<List items={items}>
    {(item) => <strong>{item.name}</strong>}   {/* 传函数，不是 JSX */}
  </List>);
}
```

区别只有一处：`{children}` → `{children(item)}`，父组件传的不是 JSX 而是**返回 JSX 的函数**。这套模式叫 **render props**，通用形态是「某个 prop 的值是函数」：`<Mouse render={(pos) => <p>{pos.x}</p>} />`。

📌 **补充**：`children` 是函数时，`{children}` 直接渲染会报 `Functions are not valid as a React child`，必须 `{children(...)}`。而且同一 prop 不能既是函数又是字符串，所以实战里通常用独立 prop 名（`render`、`renderItem`），避免与「默认插槽」互斥。

### 4.6 逐项对照表（Vue slot ↔ React）

| # | 需求 | Vue 写法 | React 写法 | 等价度 |
|---|---|---|---|---|
| 1 | 默认插槽 | `<slot />` + 标签内内容 | `{children}` + 标签内内容 | ⭐⭐⭐⭐⭐ |
| 2 | 具名插槽 | `<slot name="footer" />` + `<template #footer>` | `footer={<X />}` + `{footer}` | ⭐⭐⭐⭐⭐ |
| 3 | 多个具名插槽 | 多个 `<template #name>` | 多个 JSX prop | ⭐⭐⭐⭐⭐ |
| 4 | 插槽默认内容 | `<slot>默认</slot>` | `children = 默认` 或 `{children ?? 默认}` | ⭐⭐⭐⭐ 需手写兜底 |
| 5 | 作用域插槽 | `<slot :item="item" />` + `#default="{ item }"` | `{children(item)}` + `{(item) => ...}` | ⭐⭐⭐⭐ 机制不同，效果相近 |
| 6 | 判断插槽是否存在 | `v-if="$slots.footer"` | `footer ? ... : null` | ⭐⭐⭐⭐⭐ |
| 7 | 动态插槽名 | `#[slotName]` | `props[slotName]` / `{[name]: jsx}` | ⭐⭐⭐ 少见，写法绕 |
| 8 | 插槽内容访问子组件数据 | slot props | 函数参数 / Context | ⭐⭐⭐ 需换思路 |
| 9 | 同一插槽渲染多次 | 可以 | 可以（`{children}` 写两次） | ⭐⭐⭐⭐⭐ |
| 10 | 插槽内容的编译作用域 | 父组件作用域（能拿 slot props） | **纯父组件作用域** | ⭐⭐ 关键差异 |

第 10 行是最本质的差异：

| | Vue slot | React children |
|---|---|---|
| 内容在哪求值 | 父组件的渲染上下文 | 父组件的 JS 作用域 |
| 能否用子组件的变量 | ❌ 除非通过 slot props 显式传 | ❌ 除非子组件调用函数时传参 |
| 子组件能否改内容 | ❌ | ❌（props 只读） |
| 「反向传数据」的通道 | slot props（模板语法） | 函数参数（JS 语法） |

### 4.7 能力边界

**React 做不到的**：① 「子组件往插槽内容里塞变量」——除非用函数（`{item.name}` 里的 `item` 父组件拿不到）；② 「插槽内容的 DOM 由子组件控制」——父子之间只有值，没有 DOM 引用，真要操作 DOM 得用 `ref`（第 14 章）。**Vue slot 做不到、React 能做的**：① 把 JSX 存进 state、放进数组、条件判断后再传（它就是普通值）；② 同一个 JSX 变量传给两个不同组件（Vue 模板片段不能这么复用）；③ 用 `{...props}` 把「一堆插槽」整体转发（Vue 里要 `v-bind="$slots"`，很别扭）。

### 4.8 为什么 React 圈不叫「插槽」

| # | 原因 | 说明 |
|---|---|---|
| 1 | **JSX 是表达式，不需要占位符** | slot 的本质是「模板里挖个洞，编译期填内容」。JSX 里 `{children}` 就是普通表达式，编译器不需要知道「这里是个洞」 |
| 2 | **术语归属** | slot 是 Vue / Web Components 的官方 API 名（`<slot>` 是真实 HTML 元素）。React 没这个 API，硬套会让人去找不存在的文档 |
| 3 | **官方术语是另一套** | **passing JSX as props**、**containment**、**composition**、**render props**，搜这些才查得到官方答案 |
| 4 | **它只是「组合」的一招** | children 只是组合里最常见的一种；组合还包括「传组件类型」「传 render 函数」「HOC」 |

面试标准答法（可直接背）：

> 「React 没有插槽这个概念。Vue 的 slot 对应到 React 是 `props.children`——默认插槽就是标签之间的内容，React 自动收集成 `children` 这个 prop；具名插槽就是传多个值为 JSX 的 props；作用域插槽对应 render props，把 children 写成函数，由子组件带着数据调用。之所以不叫插槽，是因为 JSX 本身就是表达式、JSX 元素是普通对象，直接当 prop 传就行，不需要占位符和编译期替换这套机制。」

### 4.9 📌 补充：`children` 的 TS 类型，以及 render props / HOC 的分工

```tsx
import type { ReactNode } from 'react';

interface CardProps {
  title: string;
  children: ReactNode;    // ✅ 最宽：字符串/数字/JSX/数组/null 都行
  footer?: ReactNode;     // 可选插槽
}
```

| 类型 | 包含什么 | 什么时候用 |
|---|---|---|
| `ReactNode` | 字符串、数字、JSX、数组、`null`、`undefined` | **绝大多数情况** |
| `ReactElement` | 只能是 JSX 元素 | 明确只接受「一个组件」 |
| `ReactNode \| ((item: T) => ReactNode)` | 加上函数 | **render props 场景** |

📌 React 18 的 `@types/react` 里 **`React.FC` 不再自动带 `children?: ReactNode`**，必须显式写，否则报「Property 'children' does not exist」。

| 方案 | 长什么样 | 解决什么 | 现在还用吗 |
|---|---|---|---|
| **children / JSX prop** | `<Card>内容</Card>` | 布局复用、内容可定制 | ✅ **首选** |
| **render props** | `<Mouse render={pos => ...} />` | 逻辑复用 + 把内部状态暴露给外部 | ⚠️ 仍在用（TanStack Table、Formik），多数被 Hook 取代 |
| **HOC** | `const Enhanced = withAuth(Page)` | 横切关注点注入 props | ⚠️ 老项目常见（`connect()`、`withRouter`） |
| **自定义 Hook** | `const pos = useMouse()` | 只复用逻辑 | ✅ 主流 |

一句话：**复用 UI 结构 → children/JSX prop；复用「逻辑 + 让调用方决定 UI」→ render props；只复用逻辑 → 自定义 Hook。**

📌 关于「React 19 才有官方说法」这个流传说法，需要说准：**「把 JSX 作为 prop 传」从 React 一开始就成立**，`children` 是内置 prop 十几年没变。变化的是**文档措辞**——React 19 版文档把「Passing JSX as props」写成正式章节，并在 `ReactNode` 说明里明确了这点，同时 `ref` 变成普通 prop。准确说法：**能力一直有，是官方终于给了它正式名字和位置**。

## 5. 第五章 单向数据流：props 是只读的

> 「我们的**所有的 props 都是单向的**。对于子组件来说，**父组件传递的数据都是只读的，都是只读的，所以你不要尝试做修改**。那如果子组件也希望向父组件传数据，那就要使用新的方式。」

```jsx
function Article({ title }) {
  title = '我改一下';       // ❌ 能跑，但没意义：下次渲染又变回去
}

function Article({ user }) {
  user.name = '张三';       // ❌ 更危险：改的是父组件的对象
}
```

第二种才是真坑：**你改的不是 props，而是 props 指向的那个对象**——父组件的 state 被子组件偷偷改了，界面可能不更新（没走 setState），但数据已经脏了。

📌 **补充：为什么这么设计**——**可预测**（组件看到的数据永远等于父组件这次给的值）、**好调试**（界面不对就往上找）、**React 才能优化**（`memo` 靠「props 引用是否变化」判断重渲染，子组件乱改会让判断失效）、**状态可追溯**（这也是与 Vue 的核心哲学差异，`v-model` 是双向语法糖）。想「基于 props 派生可改的值」：派生就用局部变量 `const trimmed = value.trim()`；要本地可编辑就 `const [draft, setDraft] = useState(value)`——注意它**只在首次挂载**用 `value`（`EP01` 第 14 章讲过）。

## 6. 第六章 子传父：回调函数就是自定义事件

作者用购物车铺垫：「我提交购物车里面有多少个商品、每个商品买了多少个，是不是会有不同的子组件？这时候如何让父组件得知？我就需要**往回传**。」原理一句话：「**父组件给子组件设置一个自定义事件**，再通过**事件触发后向父组件传递参数**来实现。」

```jsx
import { useState } from 'react';

function Detail({ onActive }) {              // 子组件：自己管状态，状态变了就通知父组件
  const [status, setStatus] = useState(true);
  const handleClick = () => {
    const next = !status;
    setStatus(next);
    onActive(next);                          // ② 调用父组件传进来的回调
  };
  return (<div>
    <button onClick={handleClick}>切换显示</button>
    <p style={{ display: status ? 'block' : 'none' }}>Detail 的内容</p>
  </div>);
}

export default function App() {
  const [childStatus, setChildStatus] = useState(true);
  const handleActive = (status) => setChildStatus(status);   // ① 父组件准备处理函数
  return (<div>
    <p>父组件看到的状态：{childStatus ? '显示中' : '已隐藏'}</p>
    <Detail onActive={handleActive} />
  </div>);
}
```

> 「这个函数什么时候用呢？我们希望告知父组件的是内部状态……那什么时候变更了？就是在 `handleClick` 点的时候。那这里调了 `setStatus`，所以**同时我们就去进行 `onActive` 的调用**，把参数传过去。」

作者用 `display` 而非条件渲染：📌 `display: null` 在 React 里等于「不设置」，元素回到默认 `block`，**不会隐藏**——正确写法是 `'none'`（转写稿把 `none` 记成了 `null`，此处按正确代码）。另外**「隐藏但占位」用 `display: none`，「彻底不渲染」用条件渲染**，两者对 `useEffect`、表单值保留的行为完全不同。

### 6.1 两个名字的区别（新手最容易混）

> 「你给我设置那个 `onActive`，它是一个 **props**……注意这个名称叫做 `onActive`，你那个 `handleActive` 只是在我们 `App` 里面的一个**处理程序的名字**；而对于 `Detail` 来说，它的属性叫做 `onActive`，是一个**函数**。」

| 名字 | 位置 | 身份 | 谁起的 |
|---|---|---|---|
| `onActive` | 子组件的 props 上 | **prop 名**（`on` 前缀 = 「我会在某个时刻调用你」） | 父子约定 |
| `handleActive` | 父组件内部 | **函数名**（`handle` 前缀 = 「我来处理」） | 父组件自己 |

两者**可以完全不同**：`onActive={handleActive}` 只是把后者挂到前者上，也可以写 `onActive={(s) => console.log(s)}`。

### 6.2 `onActive` 不是 DOM 事件

> 「你可以理解为一个事件，但是它**并不像 DOM 事件**——DOM 事件是通过用户的鼠标、键盘操作；而这个呢，是**需要我们通过代码在某个时机决定触发**的。」

📌 **补充：为什么不能直接把 `setStatus` 传给子组件**（`<Detail setStatus={setStatus} />`）？能跑，但**把父组件内部实现泄露出去了**：子组件从此知道父组件用 `useState`、setter 叫什么。用 `onActive` 这种**语义化命名**，父组件以后换成 `useReducer`、换成请求接口，子组件一行都不用改。这叫「**回调代替 setter**」。

### 6.3 命名约定（团队协作必备）

| 场景 | prop 名 | 父组件函数名 |
|---|---|---|
| 点击 / 确认 | `onClick` / `onConfirm` | `handleClick` / `handleConfirm` |
| 值变化 | `onChange` / `onActive` | `handleChange` / `handleActive` |
| 提交 / 关闭 / 删除 | `onSubmit` / `onClose` / `onDelete` | `handleSubmit` / `handleClose` / `handleDelete` |

规则：**prop 用 `on` + 事件名（接口），处理函数用 `handle` + 事件名（实现）**。和 DOM 一致，所以自定义组件用起来跟原生标签一样自然。反例 `callback={fn}`：三个月后没人知道它什么时候被调用、参数是什么。**命名就是文档。**

### 6.4 📌 补充：`setStatus(!status)` 的隐患

```jsx
setStatus(!status);       // ⚠️ 读的是「本次渲染时」闭包里的 status
setCount(count + 1);      // 连写两次：期望 +2，实际 +1
setCount(count + 1);
```

`status` 是本次渲染捕获的值，同一事件里连调两次、或 React 批处理多次更新时会拿到同一个旧值。**正确写法永远是函数式更新** `setStatus(prev => !prev)`。那「通知父组件」的新值从哪来？两种方案：

```jsx
const next = !status; setStatus(next); onActive(next);   // A：先算新值（视频做法）
onActive(!status);                                       // B：状态提升，交给父组件
```

方案 A 在「单次点击、单次更新」下完全正确，所以列为补充而非错误；但做「点一次加 1、连点 5 次加 5」这类计数器时，必须用 `prev =>`。

📌 **子传父的三种粒度**：`onClose()`（只通知，不带数据）、`onChange(value)`（带一个值，最常见）、`onSubmit({ name, age })`（一整个对象，表单提交）。

## 7. 第七章 兄弟组件：让父组件当中转站

> 「除了父子组件，我们还可以在**同级组件**中传值。同级组件传值，我们**最常用的方式就是借助父组件来进行中转**。」

```
ChildA（产生数据）──onSend──▶ App（持有 state）──props──▶ ChildB（消费数据）
```

```jsx
function ChildA({ onSend }) { return <button onClick={() => onSend('来自 A 的消息')}>发送</button>; }
function ChildB({ message }) { return <p>收到：{message || '（还没有消息）'}</p>; }

export default function App() {
  const [message, setMessage] = useState('');
  return (<div><ChildA onSend={setMessage} /><ChildB message={message} /></div>);
}
```

这个动作有专门的名字：**状态提升（lifting state up）**。

> **判断标准：两个组件都要用同一份数据 → 这份数据就不该属于它们任何一个，往上提到最近的公共父组件。**

### 7.1 三种通信方式对比

| 通信方向 | 核心手段 | 一句话写法 | 数据流向 | 复杂度 |
|---|---|---|---|---|
| **父 → 子** | props | `<Child data={data} />` | 单向向下 | ⭐ |
| **父 → 子（传 UI）** | props 传 JSX / children | `<Child footer={<F/>}>xxx</Child>` | 单向向下 | ⭐⭐ |
| **子 → 父** | 回调函数 | `<Child onXxx={handleXxx} />` + 子组件里 `onXxx(v)` | 向上（函数调用） | ⭐⭐ |
| **兄弟 ↔ 兄弟** | 状态提升到父组件中转 | A 调 `onSend` → 父 setState → B 收 props | 绕一圈向上再向下 | ⭐⭐⭐ |
| **跨多层（3+ 层）** | Context | `createContext` + `Provider` + `useContext` | 跳过中间层 | ⭐⭐⭐⭐ |
| **任意组件（全局）** | 状态库（Zustand/Redux） | 见已有笔记 §13 | 全局 | ⭐⭐⭐⭐⭐ |

📌 **补充：选型口诀**——**能 props 就 props → 兄弟就提到父 → 超过三层才 Context → 全局且频繁变才上状态库。** 反过来也成立：只有一两个组件用的数据别塞 Context，它的代价是「value 一变，所有消费者都重渲染」，滥用比 prop drilling 更痛。

## 8. 第八章 跨层级：Context 与 Provider

> 「如果组件层级比较多，进行数据传递肯定会经历一级一级 props 向下传，然后再一层一层往回传。这种情况下使用 props 比较麻烦，那这时我们就可以利用 React 中的一个钩子 **Context** 来进行操作。」

```
App（有 level）→ Section → Section → Section → Heading
                                  ↑ 只有它要用 level，中间三层都得接一遍
```

中间的 `Section` 只是「容器」，却被迫认识自己不用的东西——和已有笔记 §10.1 的 **prop drilling** 是同一个病。

### 8.1 视频的例子：官网的 Heading

作者说「我直接借助了官网提供的一个例子」：`Section`（区块，可放标题和子区块）、`Heading`（标题，按嵌套深度渲染 `h1`~`h6`）、`App`（组装）。

**需求**：`Heading` 要知道自己是第几级，但它离根组件隔了 N 层 `Section`。笨办法是手动传 `level`：「每次用 `Heading` 都要写这个 `level`……假如你要是有很多级一直嵌下去写，其实比较麻烦。」`<Heading level={2}>` 改结构就全错。

原生思路（理解全例的钥匙）：

> 「我们只需要在根组件声明一个顶级的数据，它是 1 级。然后**每次你只要新套了一层 `Section`，我就加 1 级**——说白了就是记录一下这个结构的一个深度。」

**所以 Context 里存的不是「固定值」，而是「一个随嵌套自动 +1 的计数器」。**

### 8.2 第一步：`createContext` 与默认值

```jsx
const LevelContext = createContext(1);
```

> 「通过 `createContext`，你需要先**创建**这么一个 Context，然后才能去 use。创建的时候需要给它一个**默认值**。」「`LevelContext` 采用**帕斯卡命名法**，每个部分首字母都大写。」

| 规矩 | 说明 |
|---|---|
| **放在组件外面** | `createContext` 只该执行一次。写在组件函数体里，每次渲染都新建 Context，消费者全部重挂载 |
| **大驼峰命名** | `LevelContext`、`ThemeContext`——它「像一个类型」，不是普通变量 |

📌 **补充：默认值到底什么时候生效？** 这是最容易误解的点：

> **只有「往上找不到任何 Provider」时，才用默认值。**

| 情况 | `useContext` 拿到 |
|---|---|
| 外层有 `<LevelContext.Provider value={5}>` | `5` |
| 外层有 Provider，但 `value={undefined}` | **`undefined`**（不是默认值！） |
| 外层完全没有 Provider | `1`（`createContext(1)` 的参数） |

第三行正是本集的关键：**最外层 `Section` 往上找不到 Provider，所以拿到 1**（后来改成 0）。

### 8.3 第二步：`useContext` 取值

> 「这个值不能像变量一样直接去用，因为它可以通过一个叫 `useContext` 的函数来使用。」

```jsx
function Heading({ children }) {
  const level = useContext(LevelContext);   // 往上找最近的 Provider
}
```

作者演示了不设 Provider 时：「它取的就是**默认值 1**……你发现这个标题都是 H 几啊？是不是 H1，所有结构都是 H1？」因为所有 `Heading` 都拿到同一个 `1`——**证明取值成功，只是值都一样**。然后他玩了个调试手法：「把默认值改成 2，你发现全变成 H2 了吧？说明 `useContext` 可以找到 `createContext` 的值。」📌 这个「先让它错，才知道它在干什么」很值得学。

### 8.4 第三步：`Provider` 提供值，并自动 +1

> 「通过 `createContext` 创建的那个值是个对象，它可以提供一个 **`Provider`**，用来给 Context **提供值**。你需要把它**包裹住**要使用 `useContext` 的部分……你现在内部是不是有一个 `children`？这个 `children` 里边就是所有的 `Heading`。」

注意 `Section` 的**双重身份**：既是 `children` 的「插槽使用者」（第 4 章），又是 Context 的「提供者」。这正是这个例子能成立的原因——`Section` 什么内容都不写死，全靠 `children`。

让 `value` 自动 +1 的关键：「如果采用的方式是给每一个 `Section` 加一个级，那可以通过 props 获取。但实际我们需要很多级别，所以这里采用的方式是：**我在 `Section` 里面也通过 `useContext` 来获取**。」

```jsx
function Section({ children }) {
  const level = useContext(LevelContext);        // 我拿到的 = 父级提供的
  return (
    <section>
      <LevelContext.Provider value={level + 1}>{children}</LevelContext.Provider>
    </section>
  );
}
```

> 「走到最外层的时候，`Section` 往外层找，外层其实没有其他的 Provider，它**取的就是默认值 1**。二级 `Section` 再往上找，找的是它呀。这时这个 Provider 提供的值是 1，那我 1 再加 1 就 OK 了。所以意味着我每一次需要用我找到的**上级的 level + 1**。」

```
<Provider value={0+1=1}>        ← 最外层读到默认值 0，提供 1
   <Heading>  ← 读到 1 → <h1>
   <Provider value={1+1=2}>     ← 第二层读到 1，提供 2
      <Heading>  ← 读到 2 → <h2>
      <Provider value={2+1=3}>  ← 第三层读到 2，提供 3
```

关键认知：**Provider 可以嵌套，`useContext` 拿的是「离自己最近的那一层」。** 每层 Section 都在「覆盖」上一层的值，而覆盖的依据是读到的旧值——这就是 Context 版的「递归传参」。

### 8.5 第四步：默认值为什么最后要改成 `0`

> 「你发现最上面一级变成了 H2，所以需要把默认值**改成 0**。因为第一级 `Section` 就会把它加 1，这样就变成第一个 H1，第二级 H2，以此类推。」

| 层级 | 读到的值 | 提供的值 | 渲染 |
|---|---|---|---|
| 最外层 Section | 0（默认） | 1 | —— |
| 第 1 个 Heading | 1 | —— | `<h1>` |
| 第 2 层 Section | 1 | 2 | —— |
| 第 2 个 Heading | 2 | —— | `<h2>` |
| 第 3 个 Heading | 3 | —— | `<h3>` |

📌 **补充：为什么是 0 不是 1？因为「默认值代表『根的父级』」**。`Section` 的语义是「进入下一层」，它读到的永远是「父级深度」，提供的是「自己的深度」；根组件没有父级，深度记 0。这个「**offset 差一**」思维在写递归组件、树形结构、面包屑、缩进层级时到处都用得上。

### 8.6 完整可运行代码

```jsx
import { createContext, useContext } from 'react';

const LevelContext = createContext(0);   // ① 默认值 0 = 根组件的「父级深度」

function Section({ children }) {         // ② 既读又写
  const level = useContext(LevelContext);
  return (<section style={{ marginLeft: 16 }}>
    <LevelContext.Provider value={level + 1}>{children}</LevelContext.Provider>
  </section>);
}

function Heading({ children }) {         // ③ 只读
  const level = useContext(LevelContext);
  const Tag = `h${Math.min(level, 6)}`;  // 超过 6 级兜底成 h6
  return <Tag>{children}</Tag>;
}

export default function App() {
  return (<Section>
    <Heading>一级标题</Heading>
    <Section><Heading>二级标题 A</Heading>
      <Section><Heading>三级标题</Heading></Section>
    </Section>
  </Section>);
}
```

📌 注意 `Tag` 是**小写开头的字符串变量**（值是 `'h1'`），所以 `<Tag>` 渲染成 `<h1>`。写成 `const tag = 'h1'` 再 `<tag>` 就变成渲染未知 HTML 标签了——第 1 章大小写规则的又一个变体。

### 8.7 📌 补充：视频里那个 HTML 面试点（section 嵌 h1 为什么显示不一样大）

作者发现「全是 h1」后，观察到标题**大小居然不一样**：「为什么 H1 在展示的时候会出现从大到小的状态，仿佛在写 H1 到 H6？这是 **`section` 跟 `h1` 嵌套时自然会出现的一个状态**。所以我们经常说 **HTML 是用来做结构呈现的，CSS 才来做样式处理**。」

原理：HTML 规范里 `<section>` 有「隐式标题层级」——每嵌套一层，里面的 `h1` 在**默认样式**上会被降一级显示（devtools 里看还是 `h1`，只是样式被降了），这是 HTML5 早期「大纲算法」的遗留。

作者的收尾建议很对：「无论 H1 到 H6 能呈现什么样的文字大小，我们都**应该自己根据网页设计来设置**，哪怕默认像素跟你要的一样。」📌 实践结论：**别依赖 `h1`~`h6` 的默认字号**，全局重置一下。这也是为什么「全是 h1 但看起来有层级」——**别被默认样式骗了，用 devtools 看标签名才是真相**。

### 8.8 Context 的三个坑（视频没讲）

| 坑 | 现象 | 解法 |
|---|---|---|
| Provider 写在组件内部 | 每次渲染新建 Context，消费者重挂载、状态丢失 | `createContext` 放模块顶层 |
| `value` 传新对象 | `<Provider value={{ theme, setTheme }}>` 每次都是新对象 → 所有消费者重渲染 | `useMemo(() => ({ theme, setTheme }), [theme])` |
| 用在不该用的地方 | 只有两层也上 Context | 能 props 就 props，**超过三层**再考虑 |

📌 还有一条：**Context 不是状态管理**。它只负责「传」，不负责「存」——状态还得靠 `useState`（放在 Provider 的组件里）。第 13 章会和已有笔记的定位做对比。

## 9. 全局复盘：一张图 + 三句口诀

```
App（持有数据）──props 向下──▶ Article ──{...detailData}──▶ Detail
     ▲                                                      │
     └──────────────── onXxx 回调（子 → 父）◀────────────────┘

跨层级（3 层以上）：App ──Provider value──▶ Section ──▶ Heading（useContext 直接拿，跳过中间层）
```

三个判断口诀：① **数据往下走，事件往上走**——`<Child data={data} onSave={handleSave} />` 长这样，设计基本就对；② **谁的数据谁持有，两个组件共用就往上提**；③ **层级超过三层，才请 Context 出场**。

## 10. 速查卡

| HTML | JSX | 备注 |
|---|---|---|
| `class="a"` | `className="a"` | 报 `Invalid DOM property` |
| `for="x"` | `htmlFor="x"` | label 用 |
| `style="width:100px"` | `style={{ width: 100 }}` | 双大括号；数字补 px |
| `background-color` / `onclick` / `tabindex` | `backgroundColor` / `onClick` / `tabIndex` | 统一驼峰 |
| `<img>` 无 alt | 必须有 `alt` | 否则报警告 |

```jsx
<Child title="标题" active count={3} user={user} />     // 1. 父 → 子（数据）
<Child footer={<Foot />}>默认内容</Child>                // 2. 父 → 子（UI / 插槽）
<Child onActive={handleActive} />                        // 3. 子 → 父（子组件里调 onActive(v)）
const v = useContext(Ctx);                               // 4. 跨层级
```

| 报错 / 警告 | 原因 | 修法 |
|---|---|---|
| `Invalid DOM property 'class'. Did you mean 'className'?` | 用了 HTML 的 class | 改 `className` |
| `Each child in a list should have a unique "key"` | 循环没给 key | `key={item.id}` |
| `img elements must have an alt prop` | img 缺 alt | 加 `alt=""` 或描述 |
| `Objects are not valid as a React child` | 把对象直接塞进 `{}` | 取具体字段 `{user.name}` |
| `Functions are not valid as a React child` | children 是函数却没调用 | `{children(item)}` |
| `Cannot read properties of undefined`（渲染处） | 可选 JSX prop 没兜底 | `footer ?? <默认 />` |
| `useContext` 拿到 `undefined` | 没有 Provider 且 `createContext()` 无参 | 给默认值，或确保包了 Provider |

| 10 | **`section` 嵌套 `h1` 的默认样式坑** | 不涉及 | HTML 面试小题 + 解释「看起来有层级其实全是 h1」 |
| 11 | **Vue slot ↔ React 全套对照（10 项）** | 完全没提 Vue | **本文最有价值的部分** |
| 12 | **render props / HOC / 自定义 Hook 的分工**，以及 `ReactNode` vs `ReactElement`、`React.FC` 不再带 `children` | 已有笔记只有自定义 Hook，且沿用旧类型知识 | 看懂老项目（`connect`、`withRouter`）；升级 `@types/react` 后报错的常见原因 |

### 13.3 说法冲突：两套资料讲法不一致的地方

> **不是谁错，而是角度不同，照抄会翻车。**

**冲突 ①：「组件组合」指什么？**

| | 已有笔记 §6.3③ | 本集（视频） |
|---|---|---|
| 例子 | `function Card() { return <div><Header/><Body/><Button/></div> }` | `<List footer={<F/>}>{items}</List>` |
| 组合发生在 | **组件内部**，自己把子组件拼起来 | **组件外部**，父组件把 UI 塞进去 |
| 你学到的是 | 「大组件拆成小组件」（这是**拆分**） | 「组件留口子，调用方决定内容」（这才是 composition / containment） |

**结论**：已有笔记那段叫「拆分」更准确，它没讲「从外部注入 UI」。只按已有笔记理解，你会以为 **props 只能传数据**，看到 `<Child footer={<Foo/>}>` 会懵。两者都要会：拆分管「结构清晰」，注入管「内容可变」。React 官方文档里 composition 主要指后者。

**冲突 ②：`createContext` 的默认值该给什么？**

| | 已有笔记 §10.2 | 本集（视频） |
|---|---|---|
| 写法 | `createContext(undefined)` | `createContext(0)` |
| 配套 | 自定义 `useTheme()` 里 `if (!context) throw` | 靠默认值让**最外层**正常工作 |
| 目的 | **防御**：忘包 Provider 时立刻报错 | **计算**：默认值是递归的起点 |

**结论**：两种都对，但**不能混用**。若照已有笔记写 `createContext(undefined)`，再抄视频的 `value={level + 1}`，会得到 `undefined + 1 = NaN`，整页标题全空。

> **默认值要「有意义」→ 给真实初值（视频）；要「必须显式提供」→ `undefined` + 自定义 hook 抛错（已有笔记）。**

**冲突 ③：更新状态用 `setStatus(!status)` 还是 `setStatus(prev => !prev)`？**

| | 已有笔记 §4.4 | 本集（视频） |
|---|---|---|
| 写法 | 强调「新值依赖旧值一律用函数式」 | 全程 `setStatus(!status)` |
| 理由 | 批处理时 `status` 可能是旧值 | 演示场景是单次点击 |

**结论**：**已有笔记更严格，视频更省事**。一次事件只更新一次 → 都行；一次事件多次更新、或在异步/定时器里更新 → **必须** `prev =>`。视频写法本身不算错，但**别当成通用范式**。

**冲突 ④：Context 是「全局状态」还是「传参工具」？**

| | 已有笔记 §10（标题就叫「Context API —— 全局状态」） | 本集（视频） |
|---|---|---|
| 定位 | 全局状态共享（主题、登录用户） | **跨层级传参**（甚至算「第几级标题」） |
| 状态存在哪 | `ThemeProvider` 内部 `useState` | `Section` 里没有 state，只有计算 |

**结论**：**Context 本身不存状态，它只是「传输管道」。** 已有笔记的标题容易让人以为 Context = 状态管理，于是把业务状态都往里塞。准确说法：**Context 解决「传」，`useState`/`useReducer` 解决「存」**。视频这个例子恰好证明了这点——里面根本没有 state。

**冲突 ⑤：`children` 只是「文字」吗？**

已有笔记 §6.3① 的例子是 `<Button>点我</Button>`，容易让人以为 `children` 是「一段文本」。本集的例子是 `<List><li>1</li><li>2</li></List>`，此时 `children` 是**一个 JSX 数组**。结论：`children` 的类型是 `ReactNode`——**能渲染的一切**。

## 14. 📌 补充：视频没讲但会踩的坑

**① `key` 不会出现在 props 里**：`<Item key={id} {...rest} />` 里子组件 `props.key === undefined`。要拿 id，换个 prop 名（`itemId={id}`）。

**② `{...props}` 会把 `children` 一起传下去**：

```jsx
function Wrapper({ children, ...rest }) {          // ✅ 先剥掉 children
  return <div className="wrap"><Inner {...rest} />{children}</div>;
}
```

**③ 函数作为 children 时别写成 `{children}`**：`{children}` 报 `Functions are not valid as a React child`，必须 `{children(item)}`。

**④ 高频变化的值别放 Context**：`<MouseContext.Provider value={{ x, y }}>` 会让鼠标每动一次就整棵树重渲染。这类值用局部 state 或 `useSyncExternalStore`。

**⑤ 「父组件调用子组件的方法」用 `ref` + `useImperativeHandle`**：

```jsx
const Modal = forwardRef(function Modal({ children }, ref) {
  const [open, setOpen] = useState(false);
  useImperativeHandle(ref, () => ({ open: () => setOpen(true), close: () => setOpen(false) }));
  return open ? <div className="modal">{children}</div> : null;
});

// 父组件：
const modalRef = useRef(null);
<button onClick={() => modalRef.current.open()}>打开</button>
<Modal ref={modalRef}>我是弹窗内容</Modal>
```

要点：`forwardRef` 让函数组件接收 `ref`；`useImperativeHandle` **限制**暴露面（别把整个 DOM 扔出去）。这是「父调子」的**唯一**正规通道，但**能不用就不用**——多数需求改成「状态提升 + props 控制」更 React。📌 React 19 里 `ref` 已是普通 prop，不需要 `forwardRef`。

**⑥ `defaultProps` / `propTypes` 已过时**：`Button.defaultProps = {...}` 在 React 19 已移除对函数组件的支持，改用解构默认值 `variant = 'primary'`；`propTypes` 用 TS 接口代替。

## 15. 一句话总结

> **React 的组件通信只有一条主干：数据靠 props 往下流，事件靠回调往上走；props 能传的不只是值，还能传一整棵 JSX（这就是所谓的「插槽」，即 `children` 与 JSX prop）；当层级深到 props 变成搬运工时，用 Context 在中间架一条直达管道——而它只负责「传」，不负责「存」。**
